# 1. Welcome to the Lab

Linux automation is useful because it can perform repetitive operational tasks consistently.

However, automation also introduces risk.

A shell script can run hundreds of commands without human intervention. If it encounters an unexpected condition and handles that condition incorrectly, it may continue operating with incomplete information.

Consider a backup script that:

1. Checks whether a source directory exists.
2. Creates a backup archive.
3. Calculates a checksum.
4. Writes a completion report.
5. Prints `Backup completed successfully`.

What happens if the archive creation fails?

What happens if the backup destination is unavailable?

What happens if the source directory disappears after the initial check?

What happens if the script receives a termination signal halfway through execution?

And what happens if the script prints an error message but still exits with status `0`?

These are not theoretical questions. They represent common operational failure patterns.

In this lab, you will learn how to design Bash scripts that recognize errors, communicate them accurately, stop when appropriate, recover when safe, and clean up temporary resources.

You will first experiment with small scripts. Then you will build a complete application backup utility, deliberately introduce failures, investigate a simulated production incident, and create an automated test suite.

**Every command in this lab is intended to be followed in order.** The lab uses a disposable workspace and synthetic application data. You will not modify real production backups, system configuration files, or live services.

# 4. Understanding Error Handling

Error handling is the process of detecting unsuccessful operations and deciding what the program should do next.

A useful Bash error-handling design answers five questions.

**What failed?**

For example:

```text
Unable to create backup archive.
```

**Why did it fail?**

For example:

```text
Destination directory does not exist.
```

**Can execution continue safely?**

A missing optional log file may be recoverable.

An inability to create the required backup archive is not.

**What should be cleaned up?**

A failed backup may leave a partially written archive or temporary directory.

**What should the caller be told?**

The script must return a status that accurately reflects the outcome.

## 4.1 Three classes of outcomes

| Outcome | Example | Typical response |
|---|---|---|
| Success | Archive created and verified | Exit successfully |
| Expected negative result | Optional file not present | Handle according to policy |
| Operational failure | Required archive cannot be written | Stop, clean up, return nonzero |

A robust script does not blindly terminate on every nonzero status.

It interprets each command according to the operation being performed.

# 9. Exercise 2 — The Status-Masking Problem

Run:

```bash
false

printf 'Operation finished.\n'

printf 'Reported status: %d\n' "$?"
```

Expected:

```text
Operation finished.
Reported status: 0
```

The final status belongs to the preceding `printf`, not to `false`.

Correct the pattern:

```bash
false

printf 'Operation finished.\n'
printf 'Actual status: %d\n' "$operation_status"
```

Expected:

```text
Operation finished.
Actual status: 1
```

**Engineering rule:** Capture a status before executing another command.

# Part 3 — Building Diagnostic Functions

# 13. Why Standardized Error Messages Matter

In operational scripts, diagnostics should answer:

- What operation failed?
- Which resource was involved?
- What should you investigate?
- Did the script continue or stop?

Use standard error for diagnostics so they can be separated from ordinary output.

A simple pattern is:

```bash
log_error() {
    printf '[ERROR] %s\n' "$*" >&2
}
```

# Part 4 — Defensive Input Validation

# 16. Why Validate Before Executing?

A script that receives invalid paths or missing arguments should fail before creating artifacts.

Consider:

```bash
backup_source="$1"
```

If no argument is provided, the script may behave unpredictably unless it checks for missing input.

A safer approach is:

```bash
if (( $# != 1 )); then
    printf 'Usage: %s SOURCE_DIRECTORY\n' "$0" >&2
    exit 2
fi
```

# Part 5 — Understanding Bash Strict Modes

# 19. `set -e`: Exit on Certain Failures

`set -e`, or `errexit`, instructs Bash to exit in many circumstances when a command fails.

Create:

```bash
cat > scripts/08-errexit.sh <<'EOF'
#!/usr/bin/env bash

set -e

printf 'Before failure.\n'

false

printf 'After failure.\n'
EOF
```

Run:

```bash
bash scripts/08-errexit.sh

status=$?

printf 'Status: %d\n' "$status"
```

Expected:

```text
Before failure.
Status: 1
```

The final message does not execute.

## 19.1 Important limitations

`set -e` has exceptions.

For example, commands used as conditions in `if`, `while`, and `until` are handled differently.

Commands within `&&` and `||` lists can also behave differently depending on their position.

A function's behavior can change when the function itself is invoked in a context where `errexit` is ignored.

**Do not treat `set -e` as a universal exception-handling system.**

# 26. Exercise 14 — Preserve the Original Error

A common mistake is:

```bash
if ! some_command; then
    status=$?
fi
```

Inside the `then` branch, `$?` is the status of the negated command.

It will usually be `0`, not the original failure status.

Use this pattern when you need the exact original status:

```bash
some_command
status=$?

if (( status != 0 )); then
    printf 'Command failed with status %d\n' "$status" >&2
fi
```

Or use an `else` branch:

```bash
if some_command; then
    printf 'Command succeeded.\n'
else
    status=$?
    printf 'Command failed with status %d\n' "$status" >&2
fi
```

## Follow-along test

Run:

```bash

    printf 'Unexpected success.\n'
else
    status=$?
    printf 'Captured original status: %d\n' "$status"
fi
```

Expected:

```text
Captured original status: 1
```

# Part 7 — Cleanup and Traps

# 27. Why Cleanup Matters

Scripts often create temporary files.

A successful script may remove them at the end.

But what happens if the script exits early?

Without cleanup, temporary artifacts may remain.

This can cause:

- Wasted disk space.
- Confusing later runs.
- Accidental reuse of incomplete files.
- Exposure of sensitive intermediate data.
- Incorrect operational reporting.

Bash traps provide a mechanism for running cleanup code when certain events occur.

---

# 28. Exercise 15 — The `EXIT` Trap

Create:

```bash
cat > scripts/14-exit-trap.sh <<'EOF'
#!/usr/bin/env bash

temporary_file="$(mktemp)" || exit 3

cleanup() {
    rm -f -- "$temporary_file"
    printf 'Cleanup completed.\n' >&2
}

trap cleanup EXIT

printf 'Temporary file: %s\n' "$temporary_file"
printf 'Temporary data\n' > "$temporary_file"

printf 'Work completed.\n'
EOF
```

Run:

```bash
bash scripts/14-exit-trap.sh
```

Expected: the script prints a temporary path, reports completed work, and then prints the cleanup message.

The `EXIT` trap runs when the shell exits normally or through an ordinary `exit`.

It does not run after every possible termination event, such as `SIGKILL`.

---

# 29. Exercise 16 — Cleanup After Failure

Create:

```bash
cat > scripts/15-failure-cleanup.sh <<'EOF'
#!/usr/bin/env bash

temporary_dir="$(mktemp -d)" || exit 3

cleanup() {
    local original_status=$?

    rm -rf -- "$temporary_dir"

    printf 'Cleanup ran after status %d.\n' \
        "$original_status" >&2
}

trap cleanup EXIT

printf 'Temporary directory: %s\n' "$temporary_dir"

printf 'Simulating failure.\n' >&2

exit 4
EOF
```

Run:

```bash
bash scripts/15-failure-cleanup.sh

status=$?

printf 'Script status: %d\n' "$status"
```

Expected:

```text
Simulating failure.
Cleanup ran after status 4.
Script status: 4
```

The temporary directory is removed.

The original exit status is preserved.

### Safety note

Only remove temporary paths created by the current script.

Never use a broad cleanup command such as:

```bash
rm -rf "$some_unvalidated_path"
```

when the variable could be empty, unexpected, or controlled by an untrusted source.

# 30. Exercise 17 — `INT` and `TERM` Traps

A script may receive an interruption or termination request.

Create:

```bash
cat > scripts/16-signal-handler.sh <<'EOF'
#!/usr/bin/env bash

cleanup() {
    printf 'Cleanup handler executed.\n' >&2
}

on_interrupt() {
    printf 'Interrupted.\n' >&2
    exit 130
}

on_terminate() {
    printf 'Termination requested.\n' >&2
    exit 143
}

trap cleanup EXIT
trap on_interrupt INT
trap on_terminate TERM

printf 'Waiting for a signal.\n'

sleep 30
EOF
```

Start it in the background:

```bash
bash scripts/16-signal-handler.sh &
lab_pid=$!
```

Terminate the script:

```bash
kill -TERM "$lab_pid"
```

Wait for it:

```bash
wait "$lab_pid"
status=$?

printf 'Signal test status: %d\n' "$status"
```

# Part 8 — Building a Safe Backup Workflow

# 32. Backup Design Principles

Your final utility will follow this workflow:

```text
Start
  |
  v
Parse arguments
  |
  v
Validate source and destination
  |
  v
Create private temporary workspace
  |
  v
Build temporary archive
  |
  v
Verify archive readability
  |
  v
Calculate checksum
  |
  v
Publish completed archive
  |
  v
Write completion report
  |
  v
Clean temporary workspace
  |
  v
Return final status
```

If any critical step fails, the tool must stop and report failure.

## 32.1 Why use temporary artifacts?

Writing directly to the final archive name creates a risk.

If archive creation fails halfway through, the final path may contain an incomplete file.

A safer pattern is:

1. Create the archive under a temporary name.
2. Verify it.
3. Publish it only after verification succeeds.

The final project will implement this pattern in a lab-scoped destination.

---

# 33. Final Project Exit-Code Contract

Your backup utility will use:

| Code | Meaning |
|---|---|
| `0` | Backup completed and verified |
| `2` | Invalid command-line usage |
| `3` | Input or output operational failure |
| `4` | Backup archive creation failed |
| `5` | Backup verification failed |
| `6` | Backup publication or reporting failed |
| `130` | Interrupted by SIGINT |
| `143` | Terminated by SIGTERM |

These are application-level choices for this lab.

Other programs may use the same numbers differently.

# Part 9 — Build the Backup Utility

# 34. Create `safe-backup.sh`

Create the complete script:

```bash
cat > scripts/safe-backup.sh <<'BASH'
#!/usr/bin/env bash

# VERIQTA Linux World
# JUN-065 — Basic Bash Error Handling
# Fault-aware application backup utility.

set -u
set -o pipefail

readonly EXIT_SUCCESS=0
readonly EXIT_USAGE=2
readonly EXIT_IO=3
readonly EXIT_ARCHIVE=4
readonly EXIT_VERIFY=5
readonly EXIT_PUBLISH=6

SOURCE_DIR=""
DEST_DIR=""
BACKUP_NAME=""
REPORT_FILE=""

TEMP_DIR=""
TEMP_ARCHIVE=""
FINAL_ARCHIVE=""
FINAL_CHECKSUM=""

PUBLISHED_ARCHIVE=0
PUBLISHED_CHECKSUM=0

log_info() {
    printf '[INFO] %s\n' "$*" >&2
}

log_error() {
    printf '[ERROR] %s\n' "$*" >&2
}

usage() {
    cat <<'EOF'
Usage:
  safe-backup.sh \
    --source DIRECTORY \
    --destination DIRECTORY \
    --name BACKUP_NAME \
    --report FILE

Exit codes:
  0    Backup completed and verified
  2    Invalid usage
  3    Input/output failure
  4    Archive creation failure
  5    Archive verification failure
  6    Publication/reporting failure
  130  Interrupted
  143  Terminated
EOF
}

cleanup() {
    local original_status=$?

    trap - EXIT

    if [[ -n "$TEMP_DIR" && -d "$TEMP_DIR" ]]; then
        if ! rm -rf -- "$TEMP_DIR"; then
            log_error "Unable to remove temporary workspace: $TEMP_DIR"

            if (( original_status == 0 )); then
                original_status="$EXIT_IO"
            fi
        fi
    fi

    if (( original_status != 0 )); then
        if (( PUBLISHED_CHECKSUM == 1 )); then
            rm -f -- "$FINAL_CHECKSUM" ||
                log_error "Unable to remove published checksum"
        fi

        if (( PUBLISHED_ARCHIVE == 1 )); then
            rm -f -- "$FINAL_ARCHIVE" ||
                log_error "Unable to remove published archive"
        fi
    fi

    exit "$original_status"
}

on_interrupt() {
    log_error "Backup interrupted"
    exit 130
}

on_terminate() {
    log_error "Backup terminated"
    exit 143
}

trap cleanup EXIT
trap on_interrupt INT
trap on_terminate TERM

parse_arguments() {
    local seen_source=0
    local seen_destination=0
    local seen_name=0
    local seen_report=0

    while (( $# > 0 )); do
        case "$1" in
            --source)
                (( $# >= 2 && seen_source == 0 )) || return 2
                [[ -n "$2" && "$2" != --* ]] || return 2

                SOURCE_DIR="$2"
                seen_source=1
                shift 2
                ;;

            --destination)
                (( $# >= 2 && seen_destination == 0 )) || return 2
                [[ -n "$2" && "$2" != --* ]] || return 2

                DEST_DIR="$2"
                seen_destination=1
                shift 2
                ;;

            --name)
                (( $# >= 2 && seen_name == 0 )) || return 2
                [[ -n "$2" && "$2" != --* ]] || return 2

                BACKUP_NAME="$2"
                seen_name=1
                shift 2
                ;;

            --report)
                (( $# >= 2 && seen_report == 0 )) || return 2
                [[ -n "$2" && "$2" != --* ]] || return 2

                REPORT_FILE="$2"
                seen_report=1
                shift 2
                ;;

            *)
                return 2
                ;;
        esac
    done

    (( seen_source == 1 )) || return 2
    (( seen_destination == 1 )) || return 2
    (( seen_name == 1 )) || return 2
    (( seen_report == 1 )) || return 2

    [[ "$BACKUP_NAME" =~ ^[a-zA-Z0-9][a-zA-Z0-9_-]*$ ]] ||
        return 2

    return 0
}

validate_paths() {
    local report_parent=""

    if [[ ! -d "$SOURCE_DIR" || ! -r "$SOURCE_DIR" || ! -x "$SOURCE_DIR" ]]; then
        log_error "Source directory is unavailable"
        return "$EXIT_IO"
    fi

    if [[ ! -d "$DEST_DIR" || ! -w "$DEST_DIR" || ! -x "$DEST_DIR" ]]; then
        log_error "Destination directory is unavailable"
        return "$EXIT_IO"
    fi

    report_parent="${REPORT_FILE%/*}"

    if [[ "$report_parent" == "$REPORT_FILE" ]]; then
        report_parent="."
    elif [[ -z "$report_parent" ]]; then
        report_parent="/"
    fi

    if [[ ! -d "$report_parent" || ! -w "$report_parent" || ! -x "$report_parent" ]]; then
        log_error "Report directory is unavailable"
        return "$EXIT_IO"
    fi

    if [[ -e "$REPORT_FILE" || -L "$REPORT_FILE" ]]; then
        log_error "Report already exists"
        return "$EXIT_PUBLISH"
    fi

    FINAL_ARCHIVE="$DEST_DIR/$BACKUP_NAME.tar.gz"
    FINAL_CHECKSUM="$DEST_DIR/$BACKUP_NAME.tar.gz.sha256"

    if [[ -e "$FINAL_ARCHIVE" || -L "$FINAL_ARCHIVE" ]]; then
        log_error "Archive already exists"
        return "$EXIT_PUBLISH"
    fi

    if [[ -e "$FINAL_CHECKSUM" || -L "$FINAL_CHECKSUM" ]]; then
        log_error "Checksum already exists"
        return "$EXIT_PUBLISH"
    fi

    return 0
}

create_workspace() {
    TEMP_DIR="$(mktemp -d "$DEST_DIR/.backup-work.XXXXXX")" || {
        log_error "Unable to create temporary workspace"
        return "$EXIT_IO"
    }

    TEMP_ARCHIVE="$TEMP_DIR/$BACKUP_NAME.tar.gz"

    return 0
}

create_archive() {
    log_info "Creating backup archive"

    if ! tar -czf "$TEMP_ARCHIVE" -C "$SOURCE_DIR" .; then
        log_error "Archive creation failed"
        return "$EXIT_ARCHIVE"
    fi

    if [[ ! -s "$TEMP_ARCHIVE" ]]; then
        log_error "Archive is empty"
        return "$EXIT_ARCHIVE"
    fi

    return 0
}

verify_archive() {
    log_info "Verifying backup archive"

    if ! tar -tzf "$TEMP_ARCHIVE" >/dev/null; then
        log_error "Archive verification failed"
        return "$EXIT_VERIFY"
    fi

    return 0
}

create_checksum() {
    local checksum_file="$TEMP_DIR/$BACKUP_NAME.tar.gz.sha256"

    if ! (
        cd "$TEMP_DIR" &&
        sha256sum "$BACKUP_NAME.tar.gz" > "$checksum_file"
    ); then
        log_error "Checksum generation failed"
        return "$EXIT_VERIFY"
    fi

    if ! (
        cd "$TEMP_DIR" &&
        sha256sum -c "$BACKUP_NAME.tar.gz.sha256" >/dev/null
    ); then
        log_error "Checksum verification failed"
        return "$EXIT_VERIFY"
    fi

    return 0
}

publish_artifacts() {
    local checksum_file="$TEMP_DIR/$BACKUP_NAME.tar.gz.sha256"

    log_info "Publishing verified artifacts"

    if ! mv -n -- "$TEMP_ARCHIVE" "$FINAL_ARCHIVE"; then
        log_error "Unable to publish archive"
        return "$EXIT_PUBLISH"
    fi

    if [[ -e "$TEMP_ARCHIVE" ]]; then
        log_error "Archive publication was not completed"
        return "$EXIT_PUBLISH"
    fi

    PUBLISHED_ARCHIVE=1

    if ! mv -n -- "$checksum_file" "$FINAL_CHECKSUM"; then
        log_error "Unable to publish checksum"
        return "$EXIT_PUBLISH"
    fi

    if [[ -e "$checksum_file" ]]; then
        log_error "Checksum publication was not completed"
        return "$EXIT_PUBLISH"
    fi

    PUBLISHED_CHECKSUM=1

    return 0
}

write_report() {
    local temporary_report="$TEMP_DIR/report.txt"
    local timestamp=""

    timestamp="$(date -u '+%Y-%m-%dT%H:%M:%SZ')" || {
        log_error "Unable to obtain timestamp"
        return "$EXIT_PUBLISH"
    }

    if ! printf 'Backup: %s\n' "$BACKUP_NAME" > "$temporary_report"; then
        return "$EXIT_PUBLISH"
    fi

    if ! printf 'Status: SUCCESS\n' >> "$temporary_report"; then
        return "$EXIT_PUBLISH"
    fi

    if ! printf 'UTC: %s\n' "$timestamp" >> "$temporary_report"; then
        return "$EXIT_PUBLISH"
    fi

    if ! printf 'Archive: %s\n' "$FINAL_ARCHIVE" >> "$temporary_report"; then
        return "$EXIT_PUBLISH"
    fi

    if ! printf 'Checksum: %s\n' "$FINAL_CHECKSUM" >> "$temporary_report"; then
        return "$EXIT_PUBLISH"
    fi

    if ! mv -n -- "$temporary_report" "$REPORT_FILE"; then
        log_error "Unable to publish report"
        return "$EXIT_PUBLISH"
    fi

    if [[ -e "$temporary_report" ]]; then
        log_error "Report publication was not completed"
        return "$EXIT_PUBLISH"
    fi

    return 0
}

main() {
    local status=0

    if (( $# == 1 )) && [[ "$1" == "--help" ]]; then
        usage
        return 0
    fi

    parse_arguments "$@"
    status=$?

    if (( status != 0 )); then
        usage >&2
        return "$EXIT_USAGE"
    fi

    validate_paths || return "$EXIT_IO"

    create_workspace || return "$EXIT_IO"

    create_archive || return "$EXIT_ARCHIVE"

    verify_archive || return "$EXIT_VERIFY"

    create_checksum || return "$EXIT_VERIFY"

    publish_artifacts || return "$EXIT_PUBLISH"

    write_report || return "$EXIT_PUBLISH"

    log_info "Backup completed successfully"

    printf 'Backup: %s\n' "$FINAL_ARCHIVE"
    printf 'Checksum: %s\n' "$FINAL_CHECKSUM"
    printf 'Report: %s\n' "$REPORT_FILE"

    return "$EXIT_SUCCESS"
}

main "$@"
BASH
```

# 36. Understand the Error-Handling Architecture

The utility separates responsibilities into functions.

| Function | Responsibility |
|---|---|
| `parse_arguments` | Validate command-line syntax |
| `validate_paths` | Check required source and destination paths |
| `create_workspace` | Create a private temporary workspace |
| `create_archive` | Generate the compressed archive |
| `verify_archive` | Check archive readability |
| `create_checksum` | Generate and verify a SHA-256 checksum |
| `publish_artifacts` | Move verified files into the destination |
| `write_report` | Record a successful result |
| `cleanup` | Remove temporary files and attempt rollback |
| `main` | Coordinate operations and return the final status |

The design intentionally checks critical operations instead of relying exclusively on `set -e`.

# 64. Hardening Exercise E — Improve Publication Safety

The baseline implementation uses existence checks followed by `mv -n`.

This is sufficient to demonstrate ordinary collision avoidance in a controlled lab.

It is not a complete atomic transaction.

A production design should consider:

- Exclusive creation of final output names.
- Concurrent backup jobs.
- Trusted destination ownership and permissions.
- Symbolic links and path replacement.
- Atomic rename semantics.
- Partial publication of related files.
- Recovery after interruption.
- Whether rollback is safe when another process can modify outputs.
- Whether a manifest should be published last as a completion marker.

A useful production pattern is to publish a uniquely named backup bundle and publish a completion manifest only after every component has been verified.

Downstream consumers should treat the manifest, not merely the presence of an archive, as the completion signal.

# Part 15 — Troubleshooting Reference

# 66. Common Bash Error-Handling Problems

| Symptom | Likely cause | Corrective action |
|---|---|---|
| Script reports success after a failure | Status masking | Capture and propagate status |
| Function returns `0` unexpectedly | Last command succeeded | Use explicit `return` |
| Script stops unexpectedly | `set -e` behavior | Inspect command context |
| Script continues after failure | Error ignored or handled | Add explicit checks |
| Pipeline reports success | Last command succeeded | Use `pipefail` |
| Error message appears in output file | Streams combined | Separate stdout and stderr |
| Cleanup does not run | No trap or uncatchable termination | Install cleanup trap; document limits |
| Temporary files remain | Cleanup failure | Check cleanup and recovery process |
| Archive exists but is unusable | Incomplete creation | Verify before publishing |
| Backup rerun overwrites data | Output collision | Use unique names and collision protection |
| Report says success but archive is missing | Success recorded too early | Verify before reporting |
| Invalid arguments are accepted | Weak parser | Validate required options |
| Error code changes unexpectedly | Status remapped | Preserve documented codes |
| Test suite passes only happy paths | Missing negative tests | Add failure injection |
| Report cannot be written | Missing directory or I/O failure | Check report publication |
| Signal interrupts backup | No signal handling | Add appropriate traps |
| Checksum does not match | Archive changed or corrupted | Reject backup |
| Missing source passes preflight | Incorrect path checks | Validate and check actual reads |

# Part 17 — Knowledge Assessment

# 68. Thirty Questions and Answers

**1. What is Bash error handling?**  
The process of detecting unsuccessful operations and responding appropriately.

**2. Why is checking exit codes important?**  
Because automation often uses exit codes to decide whether an operation succeeded.

**3. What does exit status `0` mean?**  
Success by convention.

**4. Does every nonzero status mean a fatal error?**  
No. Some represent expected conditions.

**5. What does `$?` contain?**  
The status of the most recently completed foreground pipeline.

**6. Why capture `$?` immediately?**  
Later commands replace the status.

**7. What is status masking?**  
An earlier failure is hidden by a later successful operation.

**8. What does `exit` do?**  
Terminates the current shell process.

**9. What does `return` do?**  
Finishes a function or sourced script with a status.

**10. Why should diagnostics go to standard error?**  
So they remain separate from normal output.

**11. What is a fatal error?**  
A condition that prevents safe continuation.

**12. What is a recoverable error?**  
A failure that can be handled while still meeting the operation's requirements.

**13. What does `set -e` do?**  
It causes Bash to exit on certain unhandled nonzero statuses.

**14. Is `set -e` a complete error-handling solution?**  
No.

**15. What does `set -u` do?**  
It detects many uses of unset variables.

**16. What does `pipefail` do?**  
It makes pipeline status reflect a failed component.

**17. What is an `EXIT` trap?**  
A handler that runs when the shell exits through normal shell-exit paths.

**18. What is an `ERR` trap?**  
A handler that runs in certain command-failure contexts.

**19. Does an `ERR` trap always terminate execution?**  
No.

**20. Why use temporary files?**  
To avoid exposing incomplete artifacts under final names.

**21. Why verify a backup archive?**  
To confirm it can be read before declaring success.

**22. Why create a checksum?**  
To detect changes or corruption when comparing file contents later.

**23. Does a checksum prove the backup contains the correct application data?**  
No. It verifies data consistency against the recorded digest, not business completeness.

**24. Why should cleanup preserve the original status?**  
So the caller receives the correct outcome.

**25. What happens if a script receives SIGKILL?**  
It cannot catch the signal or run a cleanup trap in response.

**26. Why test failure paths?**  
Because success-path tests cannot prove that errors are handled correctly.

**27. What is failure injection?**  
Deliberately simulating failures to test error-handling behavior.

**28. Why avoid publishing incomplete archives?**  
They may be mistaken for valid backups.

**29. Why document exit-code contracts?**  
So automation and operators can respond consistently.

**30. What caused the simulated incident?**  
The archive creation failure was ignored, and a later successful message caused the script to exit with status `0`.

# Part 18 — Interview Preparation

# 69. Twelve Interview Questions

**1. How do you handle errors in a Bash script?**

I validate inputs, check critical command statuses, use meaningful exit codes, write diagnostics to standard error, and clean up temporary resources.

**2. What is the difference between `set -e` and explicit error handling?**

`set -e` exits in certain failure contexts, while explicit handling lets me decide what a particular failure means and how to respond.

**3. What does `set -u` protect against?**

Accidental use of unset variables in many common cases.

**4. What problem does `pipefail` solve?**

It prevents many upstream pipeline failures from being hidden by a successful final command.

**5. How do you clean up temporary files when a script exits?**

I register an `EXIT` trap that removes only temporary resources created by the script.

**6. How do you preserve the original exit status during cleanup?**

I capture `$?` at the beginning of the cleanup handler and avoid replacing it unintentionally.

**7. Why should backup scripts verify archives?**

Because successful-looking output or file existence does not prove that the archive is usable.

**8. How would you handle a failed backup command?**

I would stop publication, log the error, clean up temporary artifacts, and return a documented nonzero status.

**9. What is a recoverable error?**

A failure that can be handled without violating the operation's success requirements.

**10. Why is failure injection useful?**

It makes error paths reproducible and testable.

**11. What is wrong with printing a success message after an unchecked command?**

The command may have failed, and the successful print can mask the failure status.

**12. How would you improve a basic Bash backup utility for production?**

I would strengthen filesystem trust assumptions, add robust publication semantics, verify data completeness, test signal handling, add structured reporting, and integrate failure-path tests into CI.

# 76. Security and Reliability Notes

Before adapting this lab to a real environment, understand these boundaries.

**Do not run untrusted scripts as root.** This lab is designed for a normal user account.

**Do not back up real secrets into a public repository.** The provided configuration files contain only fictional data.

**Do not rely on file existence alone.** A file may exist but be incomplete or corrupted.

**Do not rely solely on a successful `tar` command.** Verification should include archive readability and, for real recovery requirements, restoration testing.

**Do not assume a checksum proves completeness.** It can detect changes relative to a recorded digest but does not prove that the correct source files were selected.

**Do not assume cleanup always runs.** `SIGKILL`, system crashes, and abrupt power loss can prevent shell traps from executing.

**Do not assume preflight checks eliminate races.** Filesystem state can change between validation and use.

**Do not assume `mv -n` provides complete transactional publication.** Concurrent writers and related-file publication require a stronger design.

**Do not trust arbitrary source directories.** The baseline backup tool assumes the source and destination are controlled lab directories.

**Do not store sensitive intermediate data in world-readable locations.** Use private temporary directories and restrictive permissions where appropriate.

**Do not publish an artifact merely because the script reached its final line.** Publish success only after all required completion conditions are satisfied.

# 77. Lessons from the Trenches

**1. Error handling is part of the program's design.**

It should not be added only after the happy path works.

**2. Every critical operation needs an explicit success condition.**

Archive creation, verification, publication, and reporting must each be checked.

**3. Printed messages are not proof of success.**

A script can print `SUCCESS` while returning the wrong status or producing no usable artifact.

**4. `set -e` is helpful but incomplete.**

Its context-sensitive behavior means explicit checks remain necessary.

**5. Cleanup must be planned before failure occurs.**

Temporary resources should be tracked and removed when appropriate.

**6. Preserve the original failure.**

Cleanup and logging should not accidentally turn a failed operation into a successful one.

**7. Different failures deserve different responses.**

Invalid usage, missing input, archive failure, verification failure, and publication failure are operationally distinct.

**8. Failure-path testing is mandatory for reliable automation.**

A script that passes only success tests has not demonstrated robust error handling.

**9. Incomplete artifacts must not look complete.**

Use temporary creation, verification, and carefully designed publication.

**10. Reliability requires evidence.**

A trustworthy backup workflow should produce verifiable artifacts, meaningful statuses, and test results.
