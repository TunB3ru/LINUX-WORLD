# 1. Production Mission — The Environment Variable That Sent a Deployment to the Wrong Target

You are a junior Linux engineer supporting an application deployment team.

The team deploys the same application into three environments:

- Development
- Staging
- Production

The deployment scripts rely on variables to determine which environment receives a deployment.

One afternoon, a deployment job intended for staging unexpectedly attempts to use production configuration.

The team investigates and discovers a script resembling the following:

```bash
#!/usr/bin/env bash

DEPLOY_ENV="staging"

source ./deployment.env

printf 'Deploying to: %s\n' "$DEPLOY_ENV"
```

The script initially assigns `staging` to `DEPLOY_ENV`.

However, the sourced file contains:

```bash
DEPLOY_ENV="production"
```

Because `source` executes the file in the current shell, the second assignment replaces the original value.

The deployment target changes.

The script does not report where the final value came from, whether the override was authorized, or whether the environment is permitted.

This is a simulated production incident, not a claim about a real organization.

## 1.1 Why this matters

A Bash variable may appear simple:

```bash
DEPLOY_ENV="staging"
```

But operational scripts must account for:

- Where the variable was defined.
- Whether it was inherited.
- Whether another file changed it.
- Whether it is exported.
- Whether it is unset or empty.
- Whether it is local or global.
- Whether it can be modified.
- Whether its value contains whitespace.
- Whether it contains special characters.
- Whether it came from a trusted source.
- Whether it is safe to use in a command.
- Whether its value was validated.
- Whether the script accidentally exposes it.
- Whether a child process receives it.
- Whether an external command can modify it.
- Whether the final value is the intended value.

In production, incorrect variable handling can cause:

- Wrong deployment targets.
- Incorrect filesystem operations.
- Broken backup destinations.
- Failed scheduled jobs.
- Unexpected service configuration.
- Incorrect log locations.
- Authentication failures.
- Exposure of sensitive information.
- CI/CD pipeline failures.
- Incorrect operational reports.

## 1.2 Your assignment

You will learn Bash variable behavior from first principles and build a controlled environment-validation tool.

The tool will:

1. Accept a target environment.
2. Validate that environment.
3. Load configuration as data rather than executing an arbitrary configuration file.
4. Apply documented configuration precedence.
5. Reject conflicting or invalid values.
6. Use appropriate variable scope.
7. Export only necessary variables to child processes.
8. Protect sensitive values.
9. Handle empty and unset variables.
10. Produce a clear validation report.
11. Return meaningful exit codes.
12. Detect the type of configuration mismatch that caused the simulated incident.

The entire project will run inside your home directory.

No actual deployment will occur.

# 8. Understanding Bash Variables

A Bash variable is a named shell parameter that can hold a value.

Example:

```bash
application="sample-api"
```

Here:

- `application` is the variable name.
- `=` is the assignment operator.
- `sample-api` is the assigned value.

To retrieve the value:

```bash
printf '%s\n' "$application"
```

Expected:

```text
sample-api
```

## 8.1 Variables are not files

A Bash variable exists in the shell's execution context.

It is not automatically written to disk.

## 8.2 Variables are not automatically global across processes

A variable created in one shell is not automatically visible to every other shell.

## 8.3 Bash variables commonly contain strings

Example:

```bash
count="5"
```

Bash can interpret suitable values numerically in arithmetic contexts.

However, ordinary Bash variables are not strongly typed like variables in many other programming languages.

## 8.4 Variable values can be empty

```bash
application=""
```

This variable is set, but its value is empty.

## 8.5 Variables can be unset

```bash
unset application
```

After this operation, the variable no longer has a normal assignment in the current shell.

Understanding the difference between empty and unset is central to this lab.

# 10. Variable Naming Rules

Bash variable names ordinarily consist of:

- Letters.
- Numbers.
- Underscores.

The first character cannot be a number.

Examples:

```bash
app_name="sample-api"
```

```bash
APP_PORT=8080
```

```bash
deployment_environment="staging"
```

Invalid assignment syntax:

```bash
2environment="staging"
```

A variable name cannot begin with a digit.

## 10.1 No spaces around assignment

Correct:

```bash
name="VERIQTA"
```

Incorrect:

```bash
name = "VERIQTA"
```

Bash interprets the latter as a command invocation rather than a variable assignment.

## 10.2 Case sensitivity

These are different variables:

```bash
environment="staging"
ENVIRONMENT="production"
Environment="development"
```

## 10.3 Naming conventions

Common conventions:

- Lowercase names for script-local variables.
- Uppercase names for intentionally exported configuration values.
- Descriptive names for operational settings.
- Avoid names that collide with special Bash variables.

These are conventions, not enforced rules.

# 12. Variable Assignment and Expansion

Assignment:

```bash
app_name="sample-api"
```

Expansion:

```bash
printf '%s\n' "$app_name"
```

Braced expansion:

```bash
printf '%s\n' "${app_name}"
```

Both forms retrieve the variable value.

Braces are useful when text appears immediately next to the variable name.

Example:

```bash
printf '%s\n' "${app_name}_backup"
```

Expected:

```text
sample-api_backup
```

Without braces:

```bash
printf '%s\n' "$app_name_backup"
```

Bash interprets `app_name_backup` as the variable name.

If that variable is unset, the result is normally empty unless an option such as `set -u` changes the behavior.

# 14. Understanding Quoting and Variable Values

Bash performs expansions before executing many commands.

Incorrect quoting can change the arguments a command receives.

Consider:

```bash
directory="application data"
```

Correct:

```bash
printf '%s\n' "$directory"
```

Risky in an ordinary command argument:

```bash
some_command $directory
```

The unquoted expansion may become two arguments:

```text
application
data
```

## 14.1 Double quotes

Double quotes allow variable expansion.

```bash
printf '%s\n' "$HOME"
```

## 14.2 Single quotes

Single quotes preserve literal text.

```bash
printf '%s\n' '$HOME'
```

Expected:

```text
$HOME
```

## 14.3 Engineering standard

Quote ordinary expansions unless the Bash construct specifically requires otherwise.

# 16. Word Splitting and Pathname Expansion

Two important shell behaviors are:

1. Word splitting.
2. Pathname expansion.

## 16.1 Word splitting

Create a variable:

```bash
value="alpha beta gamma"
```

Unquoted:

```bash
printf '<%s>\n' $value
```

Common result:

```text
<alpha>
<beta>
<gamma>
```

Quoted:

```bash
printf '<%s>\n' "$value"
```

Expected:

```text
<alpha beta gamma>
```

## 16.2 Pathname expansion

An unquoted expansion containing wildcard characters may be expanded into matching filenames.

For example, if a variable contains `*`, Bash may replace that wildcard with filenames in the current directory.

## 16.3 Why this matters

A script that constructs filesystem operations using unquoted variables can operate on unintended arguments.

# 18. Unset Variables Versus Empty Variables

These states are different.

## 18.1 Unset variable

```bash
unset application
```

## 18.2 Set but empty variable

```bash
application=""
```

## 18.3 Set and nonempty variable

```bash
application="sample-api"
```

Production scripts often need to distinguish all three.

Example:

- Unset: no value was provided.
- Empty: a value was explicitly provided but contains nothing.
- Nonempty: a value was provided.

Different applications may treat these states differently.

# 19. Understanding Parameter Expansion Defaults

Bash provides several forms of parameter expansion.

| Expression | Behavior |
|---|---|
| `${var-default}` | Use default if unset |
| `${var:-default}` | Use default if unset or empty |
| `${var=default}` | Assign default if unset |
| `${var:=default}` | Assign default if unset or empty |
| `${var?message}` | Error if unset |
| `${var:?message}` | Error if unset or empty |
| `${var+alternate}` | Use alternate if set, including empty |
| `${var:+alternate}` | Use alternate if set and nonempty |

The presence or absence of the colon changes the meaning.

This distinction is important.

# 21. Assignment Through Parameter Expansion

Consider:

```bash
environment="${environment:=development}"
```

If `environment` is unset or empty, Bash assigns `development`.

Compare:

```bash
environment="${environment=development}"
```

This assigns the default only if the variable is unset.

## 21.1 Important distinction

A default substitution is not always the same as modifying the original variable.

For example:

```bash
printf '%s\n' "${environment:-development}"
```

does not assign `development` to `environment`.

# 23. Required Variable Validation

Bash can enforce required values through parameter expansion.

Example:

```bash
: "${DEPLOY_ENV:?DEPLOY_ENV is required}"
```

This fails when the variable is unset or empty.

## 23.1 Important limitation

This checks presence, not validity.

For example:

```bash
DEPLOY_ENV="unknown"
```

passes the nonempty check.

You must separately validate allowed values.

# 25. Understanding set -u

`set -u`, also known as `nounset`, causes many references to unset variables to produce errors.

Example:

```bash
set -u
printf '%s\n' "$missing_variable"
```

If the variable is unset, Bash reports an error.

## 25.1 What set -u does not do

It does not:

- Validate variable contents.
- Prevent malicious values.
- Prevent incorrect environment selection.
- Prevent accidental overwrites.
- Automatically protect secrets.

## 25.2 Safe optional-value handling

Use:

```bash
optional_value="${1:-}"
```

when an empty default is appropriate.

# 27. Inspecting Whether a Variable Is Set

Sometimes a script must distinguish:

- Unset.
- Set but empty.
- Set and nonempty.

Bash supports:

```bash
[[ -v variable_name ]]
```

This tests whether a variable is set.

For ordinary scalar variables, it is useful for detecting explicit empty assignments.

## 27.1 Example

```bash
unset setting

if [[ -v setting ]]; then
    printf 'Set\n'
else
    printf 'Unset\n'
fi
```

## 27.2 Important caution

Avoid printing all variable values simply to determine whether one variable exists.

Some variables may contain sensitive information.

# 35. Shell Variables Versus Environment Variables

A shell variable exists in the shell.

An exported variable is included in the environment inherited by child processes.

Example:

```bash
DEPLOY_ENV="staging"
```

This assignment alone does not necessarily export the variable.

Export:

```bash
export DEPLOY_ENV
```

A child Bash process can then receive it.

## 35.1 Important distinction

Environment variables flow from parent to child processes.

A child process does not normally modify the parent's environment.

## 35.2 Production relevance

This matters for:

- CI/CD runners.
- Scheduled scripts.
- Service startup.
- Application configuration.
- Child processes.
- Command wrappers.

# 43. Command Substitution and Variable Scope

Command substitution captures standard output:


Changes to variables inside the substitution do not normally persist in the parent shell.

```bash
)"
```

Afterward:

- `result` contains `inside`.

## 43.2 Engineering caution

Do not rely on variable assignments inside command substitutions to modify parent-shell state.

# 48. Bash Dynamic Scoping

Bash local variables use dynamic scoping.

This means a function called by another function can access the caller's local variables if they are not shadowed.

This differs from lexical scoping in many programming languages.

## 48.1 Why it matters

A helper function may unexpectedly depend on a variable defined by its caller.

This can create hidden dependencies.

## 48.2 Engineering recommendation

Prefer passing required values explicitly as function arguments.

Avoid relying on dynamic scope for essential configuration.

# 66. Prefix and Suffix Removal

Example:

```bash
declare -n reference=target
```

Assignments through the nameref affect the referenced variable.

## 74.1 Why this matters

Namerefs can support reusable functions that operate on caller-owned variables.

## 74.2 Engineering caution

Namerefs introduce indirection and can make code harder to understand.

Use them only when they materially improve the design.

Do not construct nameref targets from unvalidated external input.

# 82. Variable Precedence in Operational Scripts

A script may receive configuration from several sources:

1. Built-in defaults.
2. Configuration files.
3. Environment variables.
4. Command-line arguments.

There is no universal precedence rule across all applications.

The script author must define one.

## 82.1 Example precedence

For this lab, use:

**Explicit command-line target > approved environment override > configuration-file declaration > built-in default.**

However, the final validator will not silently accept conflicting deployment targets.

It will require the requested target and the configuration declaration to agree unless an explicitly authorized override is provided.

## 82.2 Why this matters

Silent precedence can conceal mistakes.

For high-impact operations, conflict detection may be safer than silently choosing one value.

# 83. Configuration Files Are Not Automatically Safe

A file containing:

```bash

```

looks like data.

But if the script executes:

```bash

```

the file becomes executable shell code.

A malicious or incorrect file could contain commands, not just assignments.

## 83.1 Safer design for this lab

Use a simple data format:

```text
APP_NAME=sample-api

APP_PORT=8080
```

Parse only the expected keys.

Reject malformed lines.

Do not execute the file.

## 83.2 Scope limitation

The final parser will support a deliberately restricted format.

It will not implement the full `.env` ecosystem or shell assignment syntax.

# 86. Build the Environment Validator

Create:

```bash
nano scripts/environment-validator.sh
```

Enter:

```bash
#!/usr/bin/env bash

# JUN-059 — Bash Variables
# VERIQTA Linux World
#
# Purpose:
# Validate a simulated deployment configuration without
# executing the configuration file or deploying anything.

set -u
set -o pipefail

readonly SCRIPT_ID="JUN-059"

TARGET_ENV=""
CONFIG_FILE=""
REPORT_FILE=""
ALLOW_OVERRIDE="no"

CONFIG_APP_NAME=""
CONFIG_DEPLOY_ENV=""
CONFIG_APP_PORT=""

declare -A SEEN_KEYS=()

PASS_COUNT=0
FAIL_COUNT=0

declare -a RESULTS=()

usage() {
    cat <<'USAGE'
Usage:
  environment-validator.sh \
    --target ENVIRONMENT \
    --config FILE \
    --report FILE \
    [--allow-target-override]

Options:
  --target ENVIRONMENT       development, staging, production
  --config FILE              Restricted key=value configuration
  --report FILE              Output report path
  --allow-target-override    Permit a target/config mismatch
  --help                     Display help

Exit codes:
  0  Validation passed
  1  Validation failed
  2  Invalid arguments
  3  Operational error

Configuration format:
  APP_NAME=value
  DEPLOY_ENV=value
  APP_PORT=value

Blank lines and lines beginning with # are allowed.
Values must not contain whitespace.
Shell syntax is not executed.
USAGE
}

error() {
    printf 'ERROR: %s\n' "$1" >&2
}

record_pass() {
    local message="$1"

    PASS_COUNT=$((PASS_COUNT + 1))
    RESULTS+=("PASS|$message")

    printf 'PASS: %s\n' "$message"
}

record_fail() {
    local message="$1"

    FAIL_COUNT=$((FAIL_COUNT + 1))
    RESULTS+=("FAIL|$message")

    printf 'FAIL: %s\n' "$message" >&2
}

valid_environment() {
    case "$1" in
        development|staging|production)
            return 0
            ;;
        *)
            return 1
            ;;
    esac
}

parse_arguments() {
    while (( $# > 0 )); do
        case "$1" in
            --target)
                if (( $# < 2 )); then
                    error "--target requires a value"
                    return 2
                fi

                TARGET_ENV="$2"
                shift 2
                ;;

            --config)
                if (( $# < 2 )); then
                    error "--config requires a value"
                    return 2
                fi

                CONFIG_FILE="$2"
                shift 2
                ;;

            --report)
                if (( $# < 2 )); then
                    error "--report requires a value"
                    return 2
                fi

                REPORT_FILE="$2"
                shift 2
                ;;

            --allow-target-override)
                ALLOW_OVERRIDE="yes"
                shift
                ;;

            --help)
                usage
                exit 0
                ;;

            *)
                error "Unknown argument: $1"
                return 2
                ;;
        esac
    done

    if [[ -z "$TARGET_ENV" ]]; then
        error "--target is required"
        return 2
    fi

    if [[ -z "$CONFIG_FILE" ]]; then
        error "--config is required"
        return 2
    fi

    if [[ -z "$REPORT_FILE" ]]; then
        error "--report is required"
        return 2
    fi

    if ! valid_environment "$TARGET_ENV"; then
        error "Unsupported target environment: $TARGET_ENV"
        return 2
    fi

    return 0
}

parse_config() {
    local line=""
    local key=""
    local value=""
    local line_number=0

    if [[ ! -f "$CONFIG_FILE" || ! -r "$CONFIG_FILE" ]]; then
        record_fail "Configuration file is readable"
        return 1
    fi

    record_pass "Configuration file is readable"

    while IFS= read -r line || [[ -n "$line" ]]; do
        line_number=$((line_number + 1))

        if [[ -z "$line" || "$line" == \#* ]]; then
            continue
        fi

        if [[ "$line" != *=* ]]; then
            record_fail "Malformed configuration line $line_number"
            continue
        fi

        key="${line%%=*}"
        value="${line#*=}"

        case "$key" in
            APP_NAME|DEPLOY_ENV|APP_PORT)
                ;;
            *)
                record_fail "Unknown configuration key at line $line_number"
                continue
                ;;
        esac

        if [[ -v SEEN_KEYS[$key] ]]; then
            record_fail "Duplicate configuration key: $key"
            continue
        fi

        SEEN_KEYS["$key"]=1

        if [[ -z "$value" || "$value" =~ [[:space:]] ]]; then
            record_fail "Invalid value for key: $key"
            continue
        fi

        case "$key" in
            APP_NAME)
                CONFIG_APP_NAME="$value"
                ;;
            DEPLOY_ENV)
                CONFIG_DEPLOY_ENV="$value"
                ;;
            APP_PORT)
                CONFIG_APP_PORT="$value"
                ;;
        esac
    done < "$CONFIG_FILE"

    return 0
}

validate_required_values() {
    if [[ -n "$CONFIG_APP_NAME" ]]; then
        record_pass "APP_NAME is present"
    else
        record_fail "APP_NAME is present"
    fi

    if [[ -n "$CONFIG_DEPLOY_ENV" ]]; then
        record_pass "DEPLOY_ENV is present"
    else
        record_fail "DEPLOY_ENV is present"
    fi

    if [[ -n "$CONFIG_APP_PORT" ]]; then
        record_pass "APP_PORT is present"
    else
        record_fail "APP_PORT is present"
    fi
}

validate_application_name() {
    if [[ "$CONFIG_APP_NAME" =~ ^[a-z][a-z0-9-]{0,62}$ ]]; then
        record_pass "Application name format is valid"
    else
        record_fail "Application name format is valid"
    fi
}

validate_config_environment() {
    if valid_environment "$CONFIG_DEPLOY_ENV"; then
        record_pass "Configured environment is supported"
    else
        record_fail "Configured environment is supported"
    fi
}

validate_port() {
    local port_text="$CONFIG_APP_PORT"

    if [[ ! "$port_text" =~ ^[0-9]+$ ]]; then
        record_fail "Application port is a valid decimal integer"
        return 0
    fi

    if (( ${#port_text} > 5 )); then
        record_fail "Application port is a valid decimal integer"
        return 0
    fi

    local port_number=$((10#$port_text))

    if (( port_number >= 1 && port_number <= 65535 )); then
        record_pass "Application port is a valid decimal integer"
    else
        record_fail "Application port is a valid decimal integer"
    fi
}

validate_target_match() {
    if [[ "$TARGET_ENV" == "$CONFIG_DEPLOY_ENV" ]]; then
        record_pass "Requested target matches configuration"
        return 0
    fi

    if [[ "$ALLOW_OVERRIDE" == "yes" ]]; then
        record_pass "Target mismatch explicitly permitted by override"
        return 0
    fi

    record_fail "Requested target matches configuration"
}

validate_child_inheritance() {
    local child_value=""

    if ! child_value="$(
        VALIDATED_TARGET="$TARGET_ENV" \
            bash -c 'printf "%s" "${VALIDATED_TARGET-unset}"'
    )"; then
        record_fail "Validated target reaches child process"
        return 0
    fi

    if [[ "$child_value" == "$TARGET_ENV" ]]; then
        record_pass "Validated target reaches child process"
    else
        record_fail "Validated target reaches child process"
    fi
}

write_report() {
    local report_directory=""
    local timestamp=""
    local overall="PASS"
    local result=""
    local status=""
    local description=""

    report_directory="$(dirname -- "$REPORT_FILE")"

    if [[ ! -d "$report_directory" ]]; then
        error "Report directory does not exist"
        return 3
    fi

    if ! timestamp="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; then
        error "Could not determine UTC timestamp"
        return 3
    fi

    if (( FAIL_COUNT > 0 )); then
        overall="FAIL"
    fi

    if ! {
        printf '# JUN-059 Environment Validation Report\n\n'
        printf 'Script ID: %s\n\n' "$SCRIPT_ID"
        printf 'UTC timestamp: %s\n\n' "$timestamp"
        printf 'Requested target: %s\n\n' "$TARGET_ENV"
        printf 'Configured target: %s\n\n' "$CONFIG_DEPLOY_ENV"
        printf 'Application: %s\n\n' "$CONFIG_APP_NAME"
        printf 'Port: %s\n\n' "$CONFIG_APP_PORT"
        printf 'Override permitted: %s\n\n' "$ALLOW_OVERRIDE"
        printf 'Overall result: %s\n\n' "$overall"
        printf 'Passed checks: %d\n' "$PASS_COUNT"
        printf 'Failed checks: %d\n\n' "$FAIL_COUNT"

        printf '## Checks\n\n'

        for result in "${RESULTS[@]}"; do
            status="${result%%|*}"
            description="${result#*|}"

            printf -- '- [%s] %s\n' "$status" "$description"
        done

        printf '\n## Scope Limitation\n\n'
        printf '%s\n' \
            'This report validates a restricted training configuration.'
        printf '%s\n' \
            'It does not deploy software or verify live service health.'
    } > "$REPORT_FILE"; then
        error "Could not write report"
        return 3
    fi

    return 0
}

main() {
    local parse_status=0

    parse_arguments "$@" || {
        parse_status=$?
        return "$parse_status"
    }

    printf 'Starting environment validation...\n'
    printf 'Requested target: %s\n' "$TARGET_ENV"

    if ! parse_config; then
        record_fail "Configuration parsing completed"
    else
        record_pass "Configuration parsing completed"
    fi

    validate_required_values
    validate_application_name
    validate_config_environment
    validate_port
    validate_target_match
    validate_child_inheritance

    if ! write_report; then
        return 3
    fi

    printf '\nValidation summary:\n'
    printf 'Passed: %d\n' "$PASS_COUNT"
    printf 'Failed: %d\n' "$FAIL_COUNT"
    printf 'Report: %s\n' "$REPORT_FILE"

    if (( FAIL_COUNT > 0 )); then
        return 1
    fi

    return 0
}

main "$@"
```

# 112. Production Incident Investigation

**Incident ID:** INC-2026-BASH-059

**Incident type:** Deployment environment selection mismatch.

**Classification:** Simulated production case study.

## 112.1 Business impact

A deployment intended for staging attempted to use production configuration.

The deployment team had to stop the workflow and investigate.

The incident created risk of an unauthorized production change.

No real deployment is performed in this lab.

## 112.2 Initial symptom

The deployment command specified staging.

However, the script reported production.

## 112.3 Evidence A — Script assignment

```bash
DEPLOY_ENV="staging"
```

## 112.4 Evidence B — Configuration loading

```bash
source ./deployment.env
```

## 112.5 Evidence C — Configuration contents

```bash
DEPLOY_ENV="production"
```

## 112.6 Evidence D — Final value

```text
Deploying to: production
```

## 112.7 Competing hypotheses

| Hypothesis | Evidence | Assessment |
|---|---|---|
| Bash ignored the original assignment | Original assignment executed | Not supported |
| The sourced file overwrote the value | Configuration contains reassignment | Supported |
| A child process modified the parent variable | No supporting evidence | Not supported |
| Variable case mismatch caused the change | Same variable name used | Not supported |
| Script validated the target before use | No validation present | Contradicted |
| Configuration was executed in current shell | `source` used | Supported |
| Final value came from the sourced file | Assignment order supports this | Supported |

## 112.8 Supported root cause

The script sourced a configuration file that reassigned `DEPLOY_ENV`.

Because the file executed in the current shell, the original staging value was replaced by production.

The script lacked conflict detection and did not enforce an approved target.

## 112.9 Contributing factors

- Unclear variable precedence.
- Executable configuration loading.
- Missing target validation.
- No mismatch detection.
- No explicit authorization boundary.
- Inadequate negative testing.
- No audit record of value provenance.

## 112.10 Corrective actions

1. Define explicit configuration precedence.
2. Treat configuration as data.
3. Validate allowed environment names.
4. Compare requested and configured targets.
5. Reject mismatches by default.
6. Require controlled approval for exceptions.
7. Use local variables inside functions.
8. Avoid unnecessary exports.
9. Document variable sources.
10. Add regression tests for conflicting values.
11. Ensure deployment tooling enforces the validated target.
12. Verify the final target immediately before any real deployment action.

## 112.11 Recovery verification

A corrected deployment workflow should demonstrate:

- Staging request with staging configuration passes.
- Staging request with production configuration fails.
- Invalid environment fails.
- Missing configuration fails.
- Duplicate keys fail.
- Unauthorized overrides fail.
- Authorized exceptions are audited.
- Deployment tooling does not proceed on validation failure.
- The actual deployment destination matches the approved target.

The last three require authorized integration testing outside this local lab.

# 119. Knowledge Assessment — 30 Questions with Answers

## Question 1 — What is a Bash variable?

A named shell parameter used to store a value.

## Question 2 — How do you assign a variable?

Using `name=value` without spaces around the assignment operator.

## Question 3 — Are Bash variable names case-sensitive?

Yes. `environment` and `ENVIRONMENT` are different variables.

## Question 4 — Why use braces in variable expansion?

To clearly identify the variable name when surrounding text could create ambiguity.

## Question 5 — Why should variable expansions usually be quoted?

To prevent unintended word splitting and pathname expansion.

## Question 6 — What is the difference between single and double quotes?

Single quotes preserve literal text, while double quotes allow selected expansions.

# 120. Interview Preparation — 12 Questions with Worked Answers

## Interview Question 1 — What is the difference between a shell variable and an environment variable?

**Answer:**

A shell variable exists in the current shell.

An exported variable is included in the environment inherited by child processes.

This matters because applications and scripts may depend on configuration values passed through their execution environment.

## Interview Question 2 — What is the difference between unset and empty variables?

**Answer:**

An unset variable has no active assignment.

An empty variable is set but contains an empty string.

Bash parameter expansion can treat these states differently.

For example, `${var-default}` applies only when unset, while `${var:-default}` applies when unset or empty.

## Interview Question 3 — Why is quoting important when expanding variables?

**Answer:**

Quoting preserves argument boundaries and prevents unintended word splitting and pathname expansion.

Without correct quoting, a path containing spaces may be interpreted as multiple arguments.

## Interview Question 4 — What is the difference between local and global variables in Bash?

**Answer:**

Global variables are generally accessible throughout the shell execution context.

Local variables are declared inside functions and are scoped to the function's active execution context.

Using local variables helps prevent accidental modification of shared state.

## Interview Question 5 — What does export do?

**Answer:**

Export marks a variable for inclusion in the environment of child processes.

It does not make the variable universally available across the operating system.

## Interview Question 6 — Can a child process modify a variable in its parent shell?

**Answer:**

Not normally.

A child process receives its own execution environment.

Changes made in the child do not automatically update the parent's variables.

## Interview Question 7 — What is the difference between `${var:-default}` and `${var:=default}`?

**Answer:**

`${var:-default}` substitutes a default without assigning it.

`${var:=default}` assigns the default to the variable when the variable is unset or empty.

## Interview Question 8 — What is the purpose of readonly?

**Answer:**

It prevents normal reassignment or unsetting of a variable.

It is useful for script invariants but is not a security boundary against an attacker controlling the script.

## Interview Question 9 — Why should a deployment script validate environment variables?

**Answer:**

Environment variables may be missing, empty, malformed, inherited unexpectedly, or overridden.

Validation ensures that values meet the script's requirements before they influence operational decisions.

## Interview Question 10 — Why is sourcing a configuration file potentially dangerous?

**Answer:**

Sourcing executes the file as shell code in the current shell.

The file can modify variables and execute commands.

For untrusted or externally maintained configuration, it is safer to use a restricted data format and validate the parsed values.

## Interview Question 11 — How would you investigate a script that unexpectedly selects production instead of staging?

**Answer:**

I would identify the final variable value, trace every assignment, inspect inherited environment values, review sourced files, examine function scope, and determine configuration precedence.

I would reproduce the issue safely, identify the supported root cause, and add explicit target validation and mismatch detection.

## Interview Question 12 — How would you design a reliable variable-driven deployment validator?

**Answer:**

I would define a clear configuration contract, validate allowed environments, reject missing or malformed values, detect conflicts, avoid executing untrusted configuration, minimize exports, return meaningful exit codes, and test both successful and failing scenarios.

I would also ensure the deployment system enforces the validated target and does not proceed after validation failure.

Incorrect expansion can change command arguments.

Choose parameter expansion operators deliberately.

It does not create a globally shared variable.

Understand subshell and process isolation.

Prefer explicit function arguments over hidden dependencies.

**8. Bash dynamic scoping can surprise engineers.**

Avoid relying on it for critical configuration.

**9. Arrays preserve multiple values safely.**

Use them when representing collections of arguments or configuration items.

Defaults, substrings, pattern removal, replacement, and case conversion can simplify scripts.

Indirect expansion and namerefs should use controlled variable names.

**12. Numeric values must be validated.**

A string containing digits is not automatically an acceptable port or threshold.

**13. Configuration precedence must be explicit.**

Silent overrides can create serious operational risk.

**14. Sourcing configuration executes code.**

Treat external configuration as data whenever possible.

**15. A passing validation has a defined scope.**

A configuration validator does not prove live application health or deployment authorization.

**16. Production failures require evidence-driven investigation.**

Trace variable sources, scope, inheritance, expansion, validation, and final operational behavior before concluding root cause.
