# 1. Introduction

A command can print a reassuring message and still fail.

A command can print nothing and succeed.

A command can generate useful output but return a nonzero exit code.

And a script can encounter a serious error, continue executing, and ultimately report success.

For Linux engineers, these distinctions matter.

Consider a deployment pipeline that runs:

```bash
bash scripts/deployment-preflight.sh
```

The pipeline may not inspect every line of the script's output. Instead, it typically relies on the process exit status to decide whether to continue.

If the script exits with status `0`, the pipeline may proceed.

If the script exits with a nonzero status, the pipeline may stop, retry, alert, or mark the job as failed.

A script that reports the wrong exit code can therefore create a much larger operational problem than a misleading terminal message.

In this lab, you will investigate exactly how Bash handles exit codes, reproduce common failure patterns, and build an operational tool with a documented exit-code contract.

You will work with real commands, create deliberately broken scripts, repair them, build regression tests, and investigate a simulated deployment incident.

**This is a follow-along lab.** Every exercise takes place in a disposable workspace. You will create the files yourself, execute them, inspect the results, and record evidence.

# 4. The Exit-Code Contract

Unix-like processes communicate a termination status to their parent process.

In Bash, the most important convention is:

- `0` means success.
- A nonzero value means failure or another documented outcome.

A nonzero status does not always mean that something is broken. Some commands use different nonzero statuses to communicate expected outcomes.

For example, `grep` normally returns:

| Exit code | Meaning |
|---|---|
| `0` | At least one match found |
| `1` | No match found |
| `2` | Error occurred |

A `grep` status of `1` can be a perfectly normal result.

Your automation must interpret statuses according to each command's documented contract rather than treating every nonzero result identically.

## 4.1 Exit-code range

Bash exposes process statuses as integers in the range `0–255`.

For a script, use explicitly documented values within that range.

Avoid relying on unusual or undocumented exit-code conventions.

## 4.2 Codes used in the final project

The final tool will use:

| Code | Meaning |
|---|---|
| `0` | All configuration files passed |
| `2` | Invalid command-line usage |
| `3` | Input or output operational failure |
| `4` | One or more configurations failed validation |
| `6` | No configuration files were discovered |

These codes are specific to this lab's application contract. They are not universal Linux exit-code definitions.

The `true` and `false` commands are useful when testing control flow.

They are not application checks. They are deliberate commands that return predictable statuses.

## What `$?` means

`$?` expands to the status of the most recently completed foreground pipeline.

This makes timing important.

If you execute another command before capturing `$?`, the previous status is no longer available through that variable.

# Part 3 — `exit` Versus `return`

# 10. Understanding `exit`

The `exit` builtin terminates the current shell process.

For a standalone Bash script:

```bash
exit 0
```

means the script finished successfully.

```bash
exit 4
```

means the script finished with status 4.

Do not use `exit` inside a sourced library unless terminating the caller's shell is explicitly intended.

# 12. Understanding `return`

A function uses `return` to finish and communicate its status to the caller.

Example:



Now test an invalid environment:


# Part 4 — Statuses in Conditional Statements

# 14. Commands Are Conditions

Bash conditionals evaluate command statuses.

You can write:

```bash
if grep -q 'ERROR' application.log; then
    printf 'An error record was found.\n'
else
    printf 'No matching record was found, or grep failed.\n'
fi
```

However, that `else` branch combines two different outcomes:

- No match.
- An actual `grep` error.

For reliable operational code, you may need to distinguish them.

## 16.1 A common trap

Consider:

```bash
false && printf 'Success\n' || printf 'Failure\n'
```

It prints `Failure`.

But this construction is not always equivalent to an `if`/`else`.

If the command after `&&` fails, the command after `||` may run even though the first command succeeded.

For important operational decisions, prefer explicit conditionals.

# Part 5 — Exit Codes and Pipelines

# 17. The Pipeline Status Problem

By default, Bash reports the status of the last command in a pipeline.

Consider:

```bash
cat fixtures/missing.log | wc -l
```

The `cat` command fails because the file does not exist.

The `wc` command receives no input, prints `0`, and normally succeeds.

The pipeline therefore returns `0` unless `pipefail` is enabled.

This is one of the most important failure modes in shell automation.

---

# 18. Exercise 7 — Reproduce a Masked Pipeline Failure

Create:

```bash
cat > scripts/04-pipeline-masking.sh <<'EOF'
#!/usr/bin/env bash

set +o pipefail

cat fixtures/missing.log | wc -l

status=$?

printf 'Pipeline status without pipefail: %d\n' "$status"
EOF
```

Run:

```bash
bash scripts/04-pipeline-masking.sh
```

Expected:

```text
cat: fixtures/missing.log: No such file or directory
0
Pipeline status without pipefail: 0
```

The pipeline reports success despite the failed input command.

---

# 19. Exercise 8 — Enable `pipefail`

Create:

```bash
cat > scripts/05-pipefail.sh <<'EOF'
#!/usr/bin/env bash

set -o pipefail

cat fixtures/missing.log | wc -l

status=$?

printf 'Pipeline status with pipefail: %d\n' "$status"
EOF
```

Run:

```bash
bash scripts/05-pipefail.sh
```

Expected:

```text
cat: fixtures/missing.log: No such file or directory
0
Pipeline status with pipefail: 1
```

With `pipefail`, the pipeline returns the status of the rightmost command that failed, or `0` if every command succeeded.

Here, `cat` fails with status `1`, while `wc` succeeds.

# 20. Exercise 9 — Inspect `PIPESTATUS`

Bash provides the `PIPESTATUS` array.

It contains the status of each command in the most recently completed foreground pipeline.

Run:

```bash
set +o pipefail

cat fixtures/missing.log | wc -l

statuses=("${PIPESTATUS[@]}")

printf 'cat status: %d\n' "${statuses[0]}"
printf 'wc status: %d\n' "${statuses[1]}"
```

Expected:

```text
cat: fixtures/missing.log: No such file or directory
0
cat status: 1
wc status: 0
```

### Important

Capture `PIPESTATUS` immediately.

Even an assignment or `printf` executed afterward can replace the previous pipeline's status information.

## 20.1 Why `PIPESTATUS` matters

`pipefail` tells you whether the pipeline failed.

`PIPESTATUS` helps you identify which component failed.

These are related but different capabilities.

# Part 6 — `set -e`, `set -u`, and Error Traps

# 21. Understanding `set -e`

`set -e`, also called `errexit`, causes Bash to exit in certain circumstances when a command returns a nonzero status.

It is useful, but it is not a universal exception-handling mechanism.

Its behavior depends on whether a command appears in a conditional, a logical list, a pipeline, or another context.

You must not assume that enabling `set -e` guarantees every failure will terminate a script.

# 24. Exercise 12 — Understand `ERR` Traps

An `ERR` trap can run when certain commands fail.

Create:

```bash
cat > scripts/09-err-trap.sh <<'EOF'
#!/usr/bin/env bash

set -E

on_error() {
    local status="$1"
    local line_number="$2"

    printf 'ERR trap: status=%d line=%d\n' \
        "$status" "$line_number" >&2
}

trap 'on_error "$?" "$LINENO"' ERR

false

printf 'Script continued after handled trap.\n'
EOF
```

Run:

```bash
bash scripts/09-err-trap.sh

status=$?

printf 'Overall status: %d\n' "$status"
```

You should see an `ERR` trap message followed by the continuation message.

The script exits with status `0` because its final `printf` succeeds.

### Important limitations

An `ERR` trap does not run for every possible nonzero status.

Its triggering rules are closely related to the contexts where `errexit` is ignored.

An `ERR` trap also does not automatically make a script exit.

Use it for diagnostics, not as the sole mechanism for enforcing application correctness.

# Part 7 — Signal-Related Termination

# 25. Exit Statuses and Signals

When a process terminates because of a signal, Bash commonly reports a status greater than 128.

A frequently observed convention is:

```text
128 + signal number
```

For example, termination by `SIGTERM` is commonly reported as `143`.

However, do not assume every program or operating environment exposes identical signal-related statuses in every situation.

---

# Part 8 — Exit-Code Design for Automation

# 27. Why Document Exit Codes?

An automation system cannot reliably interpret a script if the meaning of its statuses changes unpredictably.

For example, imagine:

```text
0 = success
1 = sometimes invalid input, sometimes missing file
2 = sometimes usage error, sometimes validation error
```

A deployment system would have difficulty deciding whether to:

- Continue.
- Stop.
- Retry.
- Request a configuration correction.
- Escalate to an operator.

A documented contract makes those decisions predictable.

For this lab:

| Exit code | Recommended automation response |
|---|---|
| `0` | Continue |
| `2` | Correct invocation |
| `3` | Investigate filesystem or I/O problem |
| `4` | Correct invalid configuration |
| `6` | Investigate empty inventory |

These are recommendations for the fictional workflow, not universal behavior.

---

# 28. Build a Status Interpreter

Create:

```bash
cat > scripts/11-status-interpreter.sh <<'EOF'
#!/usr/bin/env bash

describe_status() {
    local status="${1:-}"

    case "$status" in
        0)
            printf 'SUCCESS: All checks passed.\n'
            ;;
        2)
            printf 'USAGE ERROR: Check arguments.\n'
            ;;
        3)
            printf 'OPERATIONAL ERROR: Check I/O and paths.\n'
            ;;
        4)
            printf 'VALIDATION FAILURE: Correct configuration.\n'
            ;;
        6)
            printf 'EMPTY INVENTORY: No configurations found.\n'
            ;;
        *)
            printf 'UNKNOWN STATUS: %s\n' "$status"
            ;;
    esac
}

for status in 0 2 3 4 6 99; do
    describe_status "$status"
done
EOF
```

Run:

```bash
bash scripts/11-status-interpreter.sh
```

Verify that each code produces the intended description.

# 32. Create the Application

Create the following complete script.

```bash
cat > scripts/config-preflight.sh <<'BASH'
#!/usr/bin/env bash

# VERIQTA Linux World
# JUN-064 — Exit Codes
# Exit-code-aware configuration preflight.

set -u

readonly EXIT_SUCCESS=0
readonly EXIT_USAGE=2
readonly EXIT_IO=3
readonly EXIT_VALIDATION=4
readonly EXIT_EMPTY=6

CONFIG_DIR=""
REPORT_FILE=""

processed=0
passed=0
failed=0

declare -a CONFIG_FILES=()
declare -a RESULT_FILES=()
declare -a RESULT_STATUSES=()

log_info() {
    printf '[INFO] %s\n' "$*" >&2
}

log_error() {
    printf '[ERROR] %s\n' "$*" >&2
}

usage() {
    cat <<'EOF'
Usage:
  config-preflight.sh --config-dir DIRECTORY --report FILE

Exit codes:
  0  All configurations passed
  2  Invalid usage
  3  Operational failure
  4  Validation failure
  6  Empty configuration inventory
EOF
}

parse_arguments() {
    local seen_config=0
    local seen_report=0

    while (( $# > 0 )); do
        case "$1" in
            --config-dir)
                if (( seen_config == 1 || $# < 2 )); then
                    return "$EXIT_USAGE"
                fi

                if [[ -z "$2" || "$2" == --* ]]; then
                    return "$EXIT_USAGE"
                fi

                CONFIG_DIR="$2"
                seen_config=1
                shift 2
                ;;

            --report)
                if (( seen_report == 1 || $# < 2 )); then
                    return "$EXIT_USAGE"
                fi

                if [[ -z "$2" || "$2" == --* ]]; then
                    return "$EXIT_USAGE"
                fi

                REPORT_FILE="$2"
                seen_report=1
                shift 2
                ;;

            *)
                return "$EXIT_USAGE"
                ;;
        esac
    done

    if (( seen_config != 1 || seen_report != 1 )); then
        return "$EXIT_USAGE"
    fi

    return "$EXIT_SUCCESS"
}

validate_port() {
    local text="${1:-}"
    local number=0

    [[ "$text" =~ ^[0-9]+$ ]] || return 1
    (( ${#text} <= 5 )) || return 1

    number=$((10#$text))

    (( number >= 1 && number <= 65535 ))
}

validate_application() {
    local app_name="$1"
    local app_env="$2"
    local app_port="$3"

    [[ "$app_name" =~ ^[a-z][a-z0-9-]*$ ]] || return 1

    case "$app_env" in
        development|staging|production)
            ;;
        *)
            return 1
            ;;
    esac

    validate_port "$app_port" || return 1

    return 0
}

validate_paths() {
    local report_parent=""

    if [[ ! -d "$CONFIG_DIR" || ! -r "$CONFIG_DIR" || ! -x "$CONFIG_DIR" ]]; then
        log_error "Configuration directory is unavailable"
        return "$EXIT_IO"
    fi

    if [[ -d "$REPORT_FILE" || -L "$REPORT_FILE" ]]; then
        log_error "Report target is a directory or symbolic link"
        return "$EXIT_IO"
    fi

    report_parent="${REPORT_FILE%/*}"

    if [[ "$report_parent" == "$REPORT_FILE" ]]; then
        report_parent="."
    elif [[ -z "$report_parent" ]]; then
        report_parent="/"
    fi

    if [[ ! -d "$report_parent" || ! -w "$report_parent" || ! -x "$report_parent" ]]; then
        log_error "Report directory is unavailable"
        return "$EXIT_IO"
    fi

    return 0
}

discover_configs() {
    local file=""

    CONFIG_FILES=()

    shopt -s nullglob

    for file in "$CONFIG_DIR"/*.conf; do
        CONFIG_FILES+=("$file")
    done

    shopt -u nullglob

    if (( ${#CONFIG_FILES[@]} == 0 )); then
        log_error "No configuration files discovered"
        return "$EXIT_EMPTY"
    fi

    return 0
}

parse_config() {
    local file="$1"
    local line=""
    local key=""
    local value=""

    local name=""
    local environment=""
    local port=""

    local seen_name=0
    local seen_environment=0
    local seen_port=0

    [[ -f "$file" && -r "$file" ]] || return 3

    if ! exec 3< "$file"; then
        return 3
    fi

    while IFS= read -r line <&3 || [[ -n "$line" ]]; do
        [[ -z "$line" ]] && continue
        [[ "$line" == \#* ]] && continue

        if [[ "$line" != *=* ]]; then
            exec 3<&-
            return 1
        fi

        key="${line%%=*}"
        value="${line#*=}"

        [[ -n "$value" ]] || {
            exec 3<&-
            return 1
        }

        case "$key" in
            APP_NAME)
                if (( seen_name == 1 )); then
                    exec 3<&-
                    return 1
                fi

                name="$value"
                seen_name=1
                ;;

            APP_ENV)
                if (( seen_environment == 1 )); then
                    exec 3<&-
                    return 1
                fi

                environment="$value"
                seen_environment=1
                ;;

            APP_PORT)
                if (( seen_port == 1 )); then
                    exec 3<&-
                    return 1
                fi

                port="$value"
                seen_port=1
                ;;

            *)
                exec 3<&-
                return 1
                ;;
        esac
    done

    exec 3<&-

    if (( seen_name != 1 || seen_environment != 1 || seen_port != 1 )); then
        return 1
    fi

    validate_application "$name" "$environment" "$port" || return 1

    return 0
}

record_result() {
    local file="$1"
    local status="$2"

    RESULT_FILES+=("$file")
    RESULT_STATUSES+=("$status")
}

process_configs() {
    local file=""
    local filename=""
    local status=0

    for file in "${CONFIG_FILES[@]}"; do
        filename="${file##*/}"
        processed=$((processed + 1))

        log_info "Checking $filename"

        parse_config "$file"
        status=$?

        case "$status" in
            0)
                passed=$((passed + 1))
                record_result "$filename" PASS
                ;;

            1)
                failed=$((failed + 1))
                record_result "$filename" FAIL
                ;;

            3)
                log_error "Unable to read $filename"
                return "$EXIT_IO"
                ;;

            *)
                log_error "Unexpected parser status: $status"
                return "$EXIT_IO"
                ;;
        esac
    done

    return 0
}

write_report() {
    local report_parent=""
    local temporary_report=""
    local index=0
    local filename=""
    local result=""

    report_parent="${REPORT_FILE%/*}"

    if [[ "$report_parent" == "$REPORT_FILE" ]]; then
        report_parent="."
    elif [[ -z "$report_parent" ]]; then
        report_parent="/"
    fi

    temporary_report="$(mktemp "$report_parent/.preflight.XXXXXX")" || {
        log_error "Unable to create temporary report"
        return "$EXIT_IO"
    }

    if ! printf 'file,status\n' > "$temporary_report"; then
        rm -f -- "$temporary_report"
        return "$EXIT_IO"
    fi

    for index in "${!RESULT_FILES[@]}"; do
        filename="${RESULT_FILES[$index]}"
        result="${RESULT_STATUSES[$index]}"

        filename="${filename//\"/\"\"}"

        if ! printf '"%s",%s\n' "$filename" "$result" >> "$temporary_report"; then
            rm -f -- "$temporary_report"
            return "$EXIT_IO"
        fi
    done

    if [[ -e "$REPORT_FILE" || -L "$REPORT_FILE" ]]; then
        rm -f -- "$temporary_report"
        log_error "Report already exists; refusing overwrite"
        return "$EXIT_IO"
    fi

    if ! mv -n -- "$temporary_report" "$REPORT_FILE"; then
        rm -f -- "$temporary_report"
        return "$EXIT_IO"
    fi

    if [[ -e "$temporary_report" ]]; then
        rm -f -- "$temporary_report"
        log_error "Report publication was not completed"
        return "$EXIT_IO"
    fi

    return 0
}

print_summary() {
    printf '\n'
    printf 'VERIQTA Exit-Code Preflight Summary\n'
    printf '==================================\n'
    printf 'Processed: %d\n' "$processed"
    printf 'Passed: %d\n' "$passed"
    printf 'Failed: %d\n' "$failed"
    printf 'Report: %s\n' "$REPORT_FILE"
}

main() {
    local status=0

    if (( $# == 1 )) && [[ "$1" == "--help" ]]; then
        usage
        return 0
    fi

    parse_arguments "$@"
    status=$?

    if (( status != 0 )); then
        usage >&2
        return "$EXIT_USAGE"
    fi

    validate_paths || return "$EXIT_IO"

    discover_configs
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    process_configs || return "$EXIT_IO"

    write_report || return "$EXIT_IO"

    print_summary

    if (( failed > 0 )); then
        return "$EXIT_VALIDATION"
    fi

    return "$EXIT_SUCCESS"
}

main "$@"
BASH
```

# 34. Understand the Framework's Error Propagation

The main script has several layers.

At the lowest level:

```bash
validate_port "$port"
```

returns success or failure.

The application validator calls it:

```bash
validate_application "$name" "$environment" "$port"
```

The parser calls the application validator:

```bash
parse_config "$file"
```

The batch processor calls the parser:

```bash
process_configs
```

The main function calls the batch processor and report writer.

Each layer has a responsibility to interpret or propagate failures correctly.

The important distinction is between:

- A configuration that is invalid.
- A file that cannot be read.
- A report that cannot be written.
- An invalid invocation.
- An empty inventory.

These should not all collapse into the same generic failure code.

# Part 15 — Production Hardening Notes

# 56. Important Limitations of the Training Framework

The final project demonstrates exit-code design and batch validation. It is not presented as a production-ready security boundary.

Before using a similar tool in a production deployment pipeline, address the following limitations.

## 56.1 Input read failures

The configuration parser checks that files exist and are readable before opening them.

However, its line-reading loop does not reliably distinguish every possible read error from normal end-of-file.

A production parser should use a more robust input strategy and test failures that occur during reading, not only before opening.

## 56.2 Concurrent filesystem changes

Another process could change a file between discovery and reading.

A file could also be replaced after an initial path check.

Production tooling should define and enforce a trust model for the configuration directory.

## 56.3 Report publication races

The report writer refuses ordinary overwrites and uses a temporary file in the destination directory.

However, its existence check and rename operation are not an atomic no-replace guarantee.

For security-sensitive use, choose an output publication strategy that provides the required atomicity and collision behavior.

## 56.4 Report filenames

The CSV writer quotes double quotes inside filenames.

It does not reject all control characters or guarantee safe presentation in every spreadsheet application.

For production reporting, define an accepted filename policy and consider CSV formula injection risks when opening reports in spreadsheet software.

## 56.5 Operational errors versus validation errors

The framework distinguishes ordinary parsing failures from failures to open a file.

It does not detect every possible low-level read error during processing.

Do not claim stronger I/O guarantees than your implementation actually provides.

## 56.6 Exit-code stability

Once an automation pipeline depends on specific codes, changing their meanings can break downstream behavior.

Treat exit-code definitions as part of the program's public interface.

# Part 17 — Troubleshooting Guide

# 58. Exit-Code Troubleshooting Matrix

| Symptom | Likely cause | Investigation |
|---|---|---|
| Script exits `0` after an error | Failure masked by later success | Inspect final command and `return`/`exit` |
| `$?` shows an unexpected value | Status was overwritten | Capture immediately |
| Pipeline returns `0` despite failure | Last command succeeded | Enable `pipefail` or inspect `PIPESTATUS` |
| `grep` returns `1` | No match | Check command contract |
| Script stops unexpectedly | `set -e` or explicit `exit` | Inspect failure context |
| Script continues after error | Error was handled or ignored | Inspect conditional logic |
| Function terminates caller | `exit` used instead of `return` | Review function/library |
| Arithmetic increment appears to fail | Expression evaluated to zero | Review `(( ... ))` semantics |
| Status becomes `0` after `!` | Logical negation | Capture original status |
| Empty inventory reports success | No explicit empty check | Add status `6` |
| Invalid config reports success | Aggregate failure count ignored | Check final status decision |
| Report failure reports success | Write error not propagated | Check each critical write |
| Test harness passes unexpectedly | Test checks output but not status | Assert both |
| Test harness fails on rerun | Report path already exists | Use unique temporary paths |
| Status meanings are inconsistent | No documented contract | Define and enforce a status table |

# Part 18 — Knowledge Assessment

# 59. Thirty Review Questions and Answers

**1. What is an exit code?**  
A numeric status communicated when a process or shell command completes.

**2. What does exit code `0` normally mean?**  
Success.

**3. What does a nonzero exit code mean?**  
Failure or another documented outcome.

**4. What does `$?` contain?**  
The status of the most recently completed foreground pipeline.

**5. Why capture `$?` immediately?**  
Another command can overwrite the status.

**6. What does `exit` do?**  
Terminates the current shell or script process.

**7. What does `return` do?**  
Completes a function or sourced script with a status.

**8. Can a function return a string using `return`?**  
No. Use standard output for data.

**9. What is the usual exit-status range exposed by Bash?**  
0–255.

**10. Does every nonzero status indicate an unexpected error?**  
No. Some commands use nonzero statuses for expected conditions.

**11. What does `grep` return when it finds a match?**  
Normally `0`.

**12. What does `grep` return when it finds no match?**  
Normally `1`.

**13. What does `grep` normally return on an error?**  
`2`.

**14. What is a masked failure?**  
An earlier failure hidden by a later successful command.

**15. What is the default exit status of a Bash pipeline?**  
The status of the last command in the pipeline.

**16. What does `pipefail` change?**  
The pipeline fails if any component fails, using the rightmost nonzero status.

**17. What is `PIPESTATUS`?**  
An array containing statuses of the most recently completed foreground pipeline's components.

**18. Why must `PIPESTATUS` be captured immediately?**  
Subsequent commands replace its contents.

**19. What does `set -e` do?**  
It causes Bash to exit for certain unhandled nonzero statuses.

**20. Is `set -e` sufficient for all error handling?**  
No.

**21. What does `set -u` do?**  
It treats many unset-variable references as errors.

**22. What does an `ERR` trap do?**  
It runs a configured handler in certain error contexts.

**23. Does an `ERR` trap always terminate the script?**  
No.

**24. Why can `((counter++))` return status `1`?**  
Because the expression evaluates to the original value, which may be zero.

**25. What does `!` do to a command status?**  
It logically negates success and failure.

**26. Why document application exit codes?**  
So callers and automation systems can respond predictably.

**27. Why distinguish validation failure from I/O failure?**  
They require different corrective actions.

**28. Why aggregate batch results?**  
To communicate whether the overall job passed while still processing multiple inputs.

**29. Why test exit codes separately from output?**  
A script can print correct-looking text while returning the wrong status.

**30. What was the simulated incident's root cause?**  
A validation failure was ignored and a later successful print command caused the script to exit with status `0`.

# Part 19 — Interview Preparation

# 60. Twelve Interview Questions

**1. How do you check whether a Linux command succeeded?**

Inspect its exit status, usually by testing the command in an `if` statement or capturing `$?` immediately.

**2. What is the difference between `exit 0` and `exit 1`?**

`exit 0` conventionally indicates success; `exit 1` indicates a non-success outcome.

**3. Why can a script return success after a command fails?**

The script may continue and finish with a successful command, masking the earlier failure.

**4. What is the difference between `exit` and `return` in Bash?**

`exit` terminates the shell process; `return` finishes a function or sourced script.

**5. How does Bash determine a pipeline's exit status by default?**

It uses the last command's status.

**6. What does `set -o pipefail` do?**

It makes the pipeline's status reflect the rightmost failed component.

**7. How do you inspect all pipeline statuses?**

Use the `PIPESTATUS` array immediately after the pipeline.

**8. Why should you not treat every nonzero `grep` status as an error?**

Because status `1` normally means no match, while status `2` indicates an error.

**9. What are the limitations of `set -e`?**

Its behavior depends on command context, and it does not replace explicit error handling.

**10. How should a deployment preflight communicate invalid configuration?**

Through a documented nonzero exit code and a clear diagnostic message.

**11. How do you test exit-code handling?**

Execute known success and failure cases, capture the status, and compare it against the expected contract.

**12. What is the most important lesson from this lab?**

A script's printed output and its exit status are separate interfaces; both must be correct.

# 66. Lessons from the Trenches

**1. Exit codes are an operational interface.**  
They allow scripts, schedulers, monitoring systems, and deployment pipelines to make decisions without parsing human-readable messages.

**2. Success must be earned, not assumed.**  
A script should return `0` only when its documented success conditions have been met.

**3. Capture failures immediately.**  
A later command can replace the status you needed.

**4. Do not confuse output with status.**  
Printing an error does not automatically make a script fail.

**5. Understand the commands you call.**  
Some nonzero statuses are expected outcomes, such as a `grep` no-match result.

**6. Pipelines require deliberate error handling.**  
Without `pipefail`, upstream failures can be hidden.

**7. `set -e` is not a complete reliability strategy.**  
Critical commands still need explicit checks.

**8. Functions must propagate meaningful failures.**  
A failed validation should not be erased by a later successful logging operation.

**9. Batch tools need aggregate status logic.**  
The final exit code must represent the outcome of the complete job.

**10. Test failure paths as carefully as success paths.**  
A deployment gate that passes valid inputs but also passes invalid inputs is not a reliable gate.
