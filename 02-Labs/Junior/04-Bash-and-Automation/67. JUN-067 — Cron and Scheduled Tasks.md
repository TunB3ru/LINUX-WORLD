# 1. Welcome to the Lab

In the previous lab, you built your first Linux administration script.

You learned how to inspect system conditions, evaluate thresholds, return meaningful exit codes, and produce reports.

But a script that requires someone to remember to run it manually has an operational limitation.

A filesystem check is most useful when it runs consistently.

A housekeeping task is most useful when it runs without depending on an administrator remembering it.

This is the purpose of **scheduled task automation**.

In this lab, you will use cron to schedule a Linux administration job, control its execution environment, capture its results, prevent overlapping runs, investigate failures, and verify that it runs unattended.

You will not stop at writing a line such as:

```cron

```

You will learn why that line might fail even when the script works perfectly in an interactive terminal.

You will also learn why a scheduled command needs more than a schedule: it needs a predictable environment, a reliable execution contract, useful logs, concurrency protection, safe file handling, and a way to prove that it actually ran.

**The central engineering question for this lab is:**

> How can you make a Linux administration script run automatically, reliably, and observably without introducing unnecessary operational risk?

# Part 1 — Understand Cron Before Using It

## 6. What Is Cron?

Cron is a time-based job scheduler commonly used on Unix-like systems.

The cron daemon checks scheduled entries and launches commands when their time expressions match.

A cron job is a command or script scheduled through cron.

A crontab is a table of scheduled commands.

These terms are related but distinct:

| Term | Meaning |
|---|---|
| `cron` | Scheduling service or daemon |
| `crontab` | Schedule configuration |
| Cron job | A command executed on a schedule |
| Cron expression | Time fields determining when a job runs |
| User crontab | Schedule belonging to a specific user |
| System crontab | Administrator-managed schedule with a user field |

Cron launches processes. It does not automatically understand whether an application's business operation succeeded.

For example, cron may successfully start a backup script that then fails to copy its files.

That is why exit codes, logging, and independent verification matter.

---

## 7. Anatomy of a Cron Expression

A standard user crontab entry has five time fields followed by a command:

```text
MINUTE HOUR DAY_OF_MONTH MONTH DAY_OF_WEEK COMMAND
```

Visual representation:

```text
┌──────────── minute (0–59)
│ ┌────────── hour (0–23)
│ │ ┌──────── day of month (1–31)
│ │ │ ┌────── month (1–12)
│ │ │ │ ┌──── day of week (0–7; Sunday is 0 or 7)
│ │ │ │ │
* * * * * command
```

### Examples

| Expression | Meaning |
|---|---|
| `* * * * *` | Every minute |
| `*/5 * * * *` | Every five minutes |
| `0 * * * *` | At the start of every hour |
| `30 2 * * *` | Daily at 02:30 |
| `0 9 * * 1-5` | Monday through Friday at 09:00 |
| `0 0 1 * *` | Midnight on the first day of each month |
| `15 6 * * 0` | Sundays at 06:15 |
| `0 3 1 1 *` | January 1 at 03:00 |

The schedule is interpreted according to the cron implementation and the system's time configuration.

Do not assume cron expressions are portable across all schedulers.

---

## 8. Understand Cron Field Operators

Cron supports several common operators.

### Asterisk: `*`

Matches all permitted values.

Example:

```cron
* * * * *
```

Every minute.

### Comma: `,`

Specifies a list.

Example:

```cron
0 8,12,18 * * *
```

At 08:00, 12:00, and 18:00.

### Hyphen: `-`

Specifies a range.

Example:

```cron
0 9 * * 1-5
```

At 09:00 Monday through Friday.

### Slash: `/`

Specifies a step.

Example:

```cron
*/10 * * * *
```

At minutes 0, 10, 20, 30, 40, and 50 of each hour.

### Important step distinction

This:

```cron
*/15 * * * *
```

does not mean “15 minutes after the previous job finishes.”

It means “at the matching clock minutes.”

Cron scheduling is time-based, not completion-based.

If a job takes longer than its scheduling interval, executions may overlap unless you prevent that.

---

## 9. The Day-of-Month and Day-of-Week Trap

On traditional cron implementations, when both the day-of-month and day-of-week fields are restricted, a job can run when **either** field matches.

Consider:

```cron
0 9 1 * 1
```

You might assume this means:

> At 09:00 only when the first day of the month is Monday.

That is not how traditional Vixie-style cron matching works.

It generally means:

> At 09:00 on the first day of the month **or** on Mondays.

This is a frequent source of scheduling mistakes.

If you need an exact combined calendar condition, verify the implementation's behavior and consider a calendar-aware scheduler or an additional condition inside the script.

---

## 10. Cron Shortcuts

Many cron implementations support special schedule strings:

| Shortcut | Typical meaning |
|---|---|
| `@reboot` | Run when the cron daemon starts |
| `@yearly` | Once a year |
| `@annually` | Alias for yearly |
| `@monthly` | Once a month |
| `@weekly` | Once a week |
| `@daily` | Once a day |
| `@midnight` | Alias for daily |
| `@hourly` | Once an hour |

Example:

```cron
@daily /absolute/path/to/script.sh
```

**Caution:** `@reboot` is tied to cron startup, not necessarily to the moment the entire system has finished booting. Services, mounts, and network dependencies may not be ready.

# Part 4 — Build a Safe Administration Task

## 17. Define the Scheduled Job

Your scheduled task will collect:

- UTC execution timestamp.
- Hostname.
- Kernel release.
- Filesystem utilization for `/`.
- Memory availability from `/proc/meminfo`.
- Uptime in seconds.

It will write one unique report per execution.

It will also return a meaningful status.

For this lab, the administration task will be intentionally small so that the focus remains on scheduling reliability.

You will not depend on the exact JUN-066 script being present.

---

## 18. Create the Administration Script

Run:

```bash
cat > scripts/collect-host-status.sh <<'BASH'
#!/usr/bin/env bash

set -u
set -o pipefail

SCRIPT_DIR="$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P
)" || exit 3

LAB_ROOT="$(
    cd -- "$SCRIPT_DIR/.." && pwd -P
)" || exit 3

REPORT_DIR="$LAB_ROOT/reports"

error() {
    printf '[ERROR] %s\n' "$*" >&2
}

main() {
    local timestamp=""
    local hostname_value=""
    local kernel=""
    local disk_output=""
    local disk_percent=""
    local memory_percent=""
    local uptime_seconds=""
    local uptime_raw=""
    local report_file=""
    local report_id=""

    if [[ ! -d "$REPORT_DIR" ||
          ! -w "$REPORT_DIR" ||
          ! -x "$REPORT_DIR" ]]; then
        error "Report directory is unavailable"
        return 3
    fi

    if ! timestamp="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; then
        error "Unable to obtain timestamp"
        return 3
    fi

    if ! hostname_value="$(hostname)"; then
        error "Unable to obtain hostname"
        return 3
    fi

    if ! kernel="$(uname -r)"; then
        error "Unable to obtain kernel"
        return 3
    fi

    if ! disk_output="$(LC_ALL=C df -P /)"; then
        error "Unable to inspect filesystem"
        return 3
    fi

    disk_percent="$(
        awk '
            NR == 2 {
                value = $5
                sub(/%$/, "", value)
                print value
            }
        ' <<< "$disk_output"
    )"

    if [[ ! "$disk_percent" =~ ^[0-9]+$ ]] ||
       (( 10#$disk_percent > 100 )); then
        error "Invalid filesystem utilization"
        return 3
    fi

    if ! memory_percent="$(
        awk '
            /^MemTotal:/ {
                total = $2
                total_count++
            }

            /^MemAvailable:/ {
                available = $2
                available_count++
            }

            END {
                if (total_count != 1 ||
                    available_count != 1 ||
                    total !~ /^[0-9]+$/ ||
                    available !~ /^[0-9]+$/ ||
                    total <= 0 ||
                    available > total) {
                    exit 1
                }

                printf "%.0f\n", available * 100 / total
            }
        ' /proc/meminfo
    )"; then
        error "Unable to calculate available memory"
        return 3
    fi

    if [[ ! "$memory_percent" =~ ^[0-9]+$ ]] ||
       (( 10#$memory_percent > 100 )); then
        error "Invalid memory percentage"
        return 3
    fi

    if IFS=' ' read -r uptime_raw _ < /proc/uptime; then
        uptime_seconds="${uptime_raw%%.*}"
    else
        error "Unable to inspect uptime"
        return 3
    fi

    if [[ ! "$uptime_seconds" =~ ^[0-9]+$ ]]; then
        error "Invalid uptime"
        return 3
    fi

    report_id="$(date -u '+%Y%m%dT%H%M%SZ')-$$"

    report_file="$REPORT_DIR/host-status-$report_id.txt"

    if [[ -e "$report_file" || -L "$report_file" ]]; then
        error "Report filename collision"
        return 3
    fi

    if ! (
        set -C

        {
            printf 'LAB=JUN-067\n'
            printf 'TIMESTAMP_UTC=%s\n' "$timestamp"
            printf 'HOSTNAME=%s\n' "$hostname_value"
            printf 'KERNEL=%s\n' "$kernel"
            printf 'FILESYSTEM_PATH=/\n'
            printf 'DISK_USED_PERCENT=%d\n' "$((10#$disk_percent))"
            printf 'MEMORY_AVAILABLE_PERCENT=%d\n' \
                "$((10#$memory_percent))"
            printf 'UPTIME_SECONDS=%s\n' "$uptime_seconds"
            printf 'STATUS=COLLECTED\n'
        } > "$report_file"
    ); then
        error "Unable to write host report"
        return 3
    fi

    printf 'Report created: %s\n' "$report_file"
    printf 'Disk used: %s%%\n' "$disk_percent"
    printf 'Memory available: %s%%\n' "$memory_percent"

    return 0
}

main "$@"
BASH
```

This script creates a report containing real host measurements.

It returns `0` when collection and report creation complete successfully.

It returns `3` when it cannot collect or write reliable data.

**Scope:** `STATUS=COLLECTED` means measurements were gathered. It does not mean the host passed health thresholds. That distinction is intentional.

# Part 5 — Understand the Cron Execution Environment

## 20. Why Scripts Behave Differently Under Cron

An interactive terminal often provides:

- Your usual `PATH`.
- Shell startup configuration.
- A familiar working directory.
- Interactive environment variables.
- A terminal for prompts.
- Output visible directly on screen.

Cron may provide a much smaller environment.

Your script should not depend on interactive shell configuration.

Typical problems include:

```text
command not found
```

```text
No such file or directory
```

```text
Permission denied
```

```text
Cannot open configuration file
```

```text
No output file created
```

These failures are often caused by environmental assumptions rather than broken cron scheduling.

# Part 6 — Build the Scheduled Job Wrapper

## 23. Why Use a Wrapper?

You could schedule the administration script directly.

However, a wrapper gives you a stable place to manage:

- Environment settings.
- Working directory.
- Concurrency control.
- Execution logs.
- Exit-code capture.
- Run-history records.
- Operational diagnostics.

This separates **what the administration script does** from **how it is scheduled and observed**.

---

## 24. Define the Wrapper Contract

The wrapper will:

1. Locate the lab workspace.
2. Set a predictable `PATH`.
3. Set a restrictive `umask`.
4. Acquire a nonblocking lock.
5. Record the start time.
6. Execute the administration script.
7. Capture its exit code.
8. Record the finish time.
9. Append a machine-readable run-history entry.
10. Return the child script's exit code.

If another instance already holds the lock, the wrapper will record that the run was skipped.

For this lab, a lock-related skip will return code `75`, a conventional temporary-failure code.

That code is distinct from the administration script's `0` and `3`.

---

## 25. Create the Wrapper

Run:

```bash
cat > scripts/run-scheduled-check.sh <<'BASH'
#!/usr/bin/env bash

set -u
set -o pipefail

export PATH="/usr/sbin:/usr/bin:/sbin:/bin"
export LC_ALL=C

umask 077

SCRIPT_DIR="$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P
)" || exit 3

LAB_ROOT="$(
    cd -- "$SCRIPT_DIR/.." && pwd -P
)" || exit 3

LOG_DIR="$LAB_ROOT/logs"
LOCK_DIR="$LAB_ROOT/locks"

RUN_HISTORY="$LOG_DIR/run-history.tsv"
EXECUTION_LOG="$LOG_DIR/execution.log"
LOCK_FILE="$LOCK_DIR/admin-check.lock"

log() {
    printf '[%s] %s\n' \
        "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" \
        "$*" >> "$EXECUTION_LOG"
}

main() {
    local start_time=""
    local finish_time=""
    local child_status=0

    if [[ ! -d "$LOG_DIR" || ! -d "$LOCK_DIR" ]]; then
        printf 'ERROR: Required runtime directory missing\n' >&2
        return 3
    fi

    if ! command -v flock >/dev/null 2>&1; then
        printf 'ERROR: flock is unavailable\n' >&2
        return 3
    fi

    if ! exec 9> "$LOCK_FILE"; then
        printf 'ERROR: Unable to open lock file\n' >&2
        return 3
    fi

    if ! flock -n 9; then
        log "SKIPPED: Another execution holds the lock"
        return 75
    fi

    if ! cd "$LAB_ROOT"; then
        log "ERROR: Unable to enter lab workspace"
        return 3
    fi

    start_time="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"

    log "START pid=$$"

    if /usr/bin/bash "$LAB_ROOT/scripts/collect-host-status.sh" \
        >> "$EXECUTION_LOG" 2>&1; then
        child_status=0
    else
        child_status=$?
    fi

    finish_time="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"

    if ! printf '%s\t%s\t%d\t%s\n' \
        "$start_time" \
        "$finish_time" \
        "$child_status" \
        "$$" >> "$RUN_HISTORY"; then
        log "ERROR: Unable to append run history"
        return 3
    fi

    log "END pid=$$ status=$child_status"

    return "$child_status"
}

main "$@"
BASH
```

# Part 7 — Test Overlapping Execution Protection

## 27. Why Overlap Matters

Imagine scheduling a job every minute.

One execution starts at:

```text
12:00:00
```

But it takes 90 seconds.

Another execution begins at:

```text
12:01:00
```

Now both jobs may:

- Write to the same file.
- Read or modify the same state.
- Compete for resources.
- Duplicate work.
- Produce confusing logs.

Cron does not automatically prevent overlap.

You must design for it.

---

## 28. Controlled Lock Test

The wrapper uses file descriptor `9` for the lock.

You will hold the same lock in one shell and attempt to start the wrapper in another process.

Run:

```bash
flock -x locks/admin-check.lock \
    bash -c '
        echo "Holding lock for 8 seconds"
        sleep 8
    ' &
```

Capture the background PID:

```bash
lock_holder_pid=$!
```

Wait briefly:

```bash
sleep 1
```

Now run the wrapper:

```bash
./scripts/run-scheduled-check.sh

status=$?

printf 'Overlapping-run exit code: %d\n' "$status"
```

Expected:

```text
Overlapping-run exit code: 75
```

Wait for the lock holder to finish:

```bash
wait "$lock_holder_pid"
```

Inspect:

```bash
tail -n 10 logs/execution.log
```

Expected: a line indicating that another execution held the lock.

### What this proves

The wrapper refuses to start another administration check while the lock is held.

### What this does not prove

It does not prove that every kind of distributed or multi-host concurrency is prevented.

`flock` is a local filesystem locking mechanism. Its behavior depends on the filesystem and how cooperating processes use the lock.

# Part 11 — Capture stdout, stderr, and Exit Codes

## 41. Why Cron Output Must Be Managed

When cron launches a command, stdout and stderr do not automatically appear in your terminal.

Depending on the cron implementation and host configuration, output may be mailed to the user, discarded by surrounding configuration, or otherwise handled by the scheduler.

Do not depend on mail delivery being configured.

A scheduled script should explicitly record useful output.

---

## 42. Standard Redirection Patterns

Append stdout:

```bash
command >> /absolute/path/to/stdout.log
```

Append stderr:

```bash
command 2>> /absolute/path/to/stderr.log
```

Append both to one file:

```bash
command >> /absolute/path/to/combined.log 2>&1
```

Discard stdout:

```bash
command > /dev/null
```

Discard both streams:

```bash
command > /dev/null 2>&1
```

### Caution

Discarding all output can make incident investigation difficult.

For a production administration job, preserve sufficient diagnostic evidence while controlling log growth and sensitive data exposure.

---

# Part 12 — Understand Cron Timing and Timezones

## 44. Cron Uses Clock Time

A cron expression describes matching times on the scheduler's clock.

Inspect the host timezone:

```bash
date '+%Y-%m-%d %H:%M:%S %Z %z'
```

If systemd is available:

```bash
timedatectl
```

Look for:

```text
Time zone:
```

### Daylight saving time

During daylight saving time transitions, local clock times may be skipped or repeated.

Cron behavior depends on the implementation.

Do not assume a job scheduled at 02:30 local time will execute exactly once on every calendar date in every timezone.

For important financial, billing, or compliance workloads, consider UTC scheduling, explicit time-window logic, idempotency, and a scheduler with stronger calendar semantics.

---

## 45. Why `CRON_TZ` Requires Care

Some cron implementations support a `CRON_TZ` setting in crontab files.

Support and behavior vary.

Do not assume that placing:

```cron
CRON_TZ=UTC
```

in a crontab will behave identically across every Linux distribution and cron implementation.

For this Ubuntu lab, use the host's configured cron time and record timestamps in UTC inside the script.

That gives you consistent evidence even if the scheduler uses local time.

# Part 13 — Cron Security and Permissions

## 46. Cron Runs with User Permissions

A user crontab normally launches jobs with that user's permissions.

A job cannot read or write arbitrary protected system files merely because cron started it.

Check your identity:

```bash
id
```

Inspect workspace permissions:

```bash
ls -ld \
    "$LAB_ROOT" \
    "$LAB_ROOT/logs" \
    "$LAB_ROOT/reports" \
    "$LAB_ROOT/locks"
```

Expected: the runtime directories are owned by your user and are not broadly writable.

---

## 47. Protect Sensitive Logs

Set restrictive permissions:

```bash
chmod 700 logs reports state locks
```

The wrapper uses:

```bash
umask 077
```

This causes newly created files to exclude group and other permissions by default, subject to the creating program's requested mode.

### Why this matters

Logs may contain:

- Hostnames.
- Internal paths.
- Operational errors.
- Service names.
- Application metadata.

Do not write passwords, API tokens, private keys, or other secrets into cron commands or logs.

---

## 48. Avoid Dangerous Cron Patterns

Do not schedule commands such as:

```cron
* * * * * rm -rf /some/path
```

without careful validation, scoping, and safeguards.

Avoid running jobs as root unless the task genuinely requires it.

Avoid downloading and executing remote scripts directly from cron.

Avoid relying on untrusted environment variables or writable scripts in shared directories.

Avoid silently ignoring every error with:

```bash
|| true
```

A scheduled job should fail visibly when an important operation fails.

# Part 16 — Troubleshooting Cron Jobs

## 55. Troubleshooting Matrix

| Symptom | Likely cause | Investigation |
|---|---|---|
| Job never starts | Cron daemon stopped | `systemctl status cron` |
| Job not scheduled | Entry missing | `crontab -l` |
| Script works manually but not in cron | Environment difference | Inspect `PATH`, `HOME`, working directory |
| `command not found` | Reduced `PATH` | Use absolute command paths or explicit `PATH` |
| Configuration missing | Relative path | Resolve paths from script directory |
| No report created | Script failure or permission problem | Execution log and exit status |
| No execution log | Wrapper did not start or cannot write | Cron logs and directory permissions |
| Exit code `3` | Collection or report failure | stderr diagnostics |
| Exit code `75` | Lock already held | Check active processes and lock usage |
| Too many reports | Schedule too frequent | Review cron expression |
| Two jobs overlap | No lock | Use `flock` |
| Job runs at unexpected hour | Timezone or expression error | `date`, `timedatectl`, crontab |
| Job runs on unexpected days | Day-of-month/day-of-week matching | Review cron semantics |
| Output missing | No redirection or mail delivery | Configure logging |
| Job starts but does not finish | Hung child process | Inspect process state and timeouts |
| Duplicate runs | Duplicate cron entries | Search `crontab -l` |
| Job stops after reboot | Cron service disabled or entry lost | Verify service and crontab |
| Reports contain sensitive data | Logging design | Review and redact outputs |

## 58. Root Cause

For the simulated incident, the primary defect is the relative-path assumption.

The broken cron entry:


# Part 18 — Cron Versus systemd Timers

## 59. Why Learn Both?

Cron is widely used and remains important in Linux administration.

Modern Linux systems may also use systemd timers.

A systemd timer works with a corresponding service unit and can provide capabilities such as dependency management and journal integration.

| Capability | Cron | systemd timer |
|---|---|---|
| Simple recurring schedule | Yes | Yes |
| Per-user scheduling | Yes | Yes, with user managers |
| Calendar expressions | Five-field cron syntax | `OnCalendar` expressions |
| Monotonic intervals | Limited | Supported |
| Service dependency integration | Manual | Native |
| Journal integration | Host-dependent | Native |
| Missed-run catch-up | Not generally guaranteed | Available with `Persistent=true` for applicable calendar timers |
| Overlap handling | Must be designed | Service-unit activation semantics can help, but workload design still matters |
| Ease of simple setup | High | Moderate |

This lab focuses on cron because it is a foundational Linux administration skill.

You will encounter systemd timers in later automation and service-management work.

# Part 21 — Knowledge Assessment

## 69. Thirty Questions and Answers

**1. What is cron?**  
A time-based job scheduler commonly used on Unix-like systems.

**2. What is a crontab?**  
A configuration table containing scheduled commands.

**3. What is a cron job?**  
A command or script launched according to a schedule.

**4. How many time fields are in a standard user cron expression?**  
Five.

**5. What does the first field represent?**  
Minute.

**6. What does the second field represent?**  
Hour.

**7. What does `* * * * *` mean?**  
Every minute.

**8. What does `*/5 * * * *` mean?**  
At five-minute clock intervals.

**9. What does `0 2 * * *` mean?**  
Daily at 02:00.

**10. What does `0 9 * * 1-5` mean?**  
Monday through Friday at 09:00.

**11. What does `@reboot` mean?**  
Run when the cron daemon starts, subject to implementation behavior.

**12. Why use absolute paths in cron jobs?**  
To avoid depending on an uncertain working directory.

**13. Why explicitly set `PATH`?**  
Cron may not provide the same command search path as an interactive shell.

**14. Why use a wrapper script?**  
To centralize environment setup, logging, locking, and status handling.

**15. What does stdout contain?**  
Normal command output.

**16. What does stderr contain?**  
Diagnostic or error output.

**17. What does `2>&1` do?**  
Redirects stderr to the current stdout destination.

**18. Why capture exit codes?**  
To distinguish successful execution from failures.

**19. What does `flock` do?**  
Provides advisory file locking.

**20. Why prevent overlapping runs?**  
To avoid duplicate work and conflicting access to shared resources.

**21. Does cron automatically prevent overlap?**  
No.

**22. Does cron guarantee missed jobs will be replayed?**  
No, not as a general guarantee.

**23. Why record UTC timestamps?**  
To make logs easier to correlate across timezones.

**24. What is a cron environment problem?**  
A failure caused by differences between scheduled and interactive execution environments.

**25. What is a freshness check?**  
A check that verifies whether a job has completed recently enough.

**26. Why is a cron launch log insufficient?**  
It does not prove the application-level task completed successfully.

**27. What is the difference between user and system crontabs?**  
System crontabs typically include a username field; user crontabs do not.

**28. Why back up a crontab before editing?**  
To preserve existing scheduled tasks and support recovery.

**29. What caused the simulated incident?**  
A relative-path assumption and inadequate scheduled-job verification.

**30. What makes scheduled automation reliable?**  
Correct scheduling, predictable environment, safe execution, logging, locking, monitoring, testing, and cleanup.

# Part 22 — Interview Preparation

## 70. Twelve Interview Questions

**1. How do you schedule a Bash script on Linux?**

I create a cron entry with the required time expression and an absolute command path, then verify the installed crontab and observe an actual scheduled execution.

**2. Why might a script work manually but fail under cron?**

Cron may provide a different working directory, `PATH`, shell environment, and output-handling behavior.

**3. How do you troubleshoot a cron job that does not run?**

I check the cron service, installed crontab, schedule expression, system logs, script permissions, paths, and execution logs.

**4. What is the difference between cron and crontab?**

Cron is the scheduler; a crontab contains the schedule entries.

**5. How do you prevent cron jobs from overlapping?**

I use an appropriate locking mechanism such as `flock` and define how the job behaves when the lock is unavailable.

**6. How do you capture cron output?**

I redirect stdout and stderr to controlled log files or use a wrapper that records execution results.

**7. Why use a wrapper script?**

It provides a consistent environment, working directory, logging, locking, and exit-code handling.

**8. How do you know a scheduled job succeeded?**

I verify its application-level output, exit code, run history, and expected artifacts—not just the cron launch record.

**9. What does `*/15 * * * *` mean?**

Run at minutes 0, 15, 30, and 45 of each hour.

**10. What are common cron security concerns?**

Excessive privileges, unsafe script permissions, secret exposure, uncontrolled file writes, and destructive commands.

**11. What is a limitation of cron?**

It does not generally provide built-in application health monitoring, dependency management, or guaranteed catch-up for missed runs.

**12. When might you prefer a systemd timer?**

When service dependencies, journal integration, monotonic timing, or persistent calendar-timer behavior are important.

# 78. Lessons from the Trenches

**1. Scheduling a script is not the same as making it reliable.**

Cron determines when a command should start. Your script and wrapper must handle everything that happens afterward.

**2. The interactive shell is not your production environment.**

A script that depends on your terminal's working directory or startup configuration is fragile.

**3. Absolute paths eliminate a major category of failures.**

Resolve configuration, logs, and output directories explicitly.

**4. Every scheduled job needs observable results.**

Keep execution logs, exit codes, and meaningful output artifacts.

**5. A launch record is not proof of success.**

Verify the actual work completed.

**6. Repeated schedules create concurrency risks.**

Use locking when overlapping execution could cause problems.

**7. Cron expressions deserve careful review.**

Small syntax mistakes can cause jobs to run too frequently, too rarely, or on unexpected days.

**8. Timezones and daylight saving time matter.**

A schedule is interpreted against a clock, not an abstract sequence of intervals.

**9. Cron jobs should run with the least privilege necessary.**

Do not use root merely for convenience.

**10. A reliable automation design includes cleanup.**

Temporary schedules must be removed, and existing user configuration must be preserved.
