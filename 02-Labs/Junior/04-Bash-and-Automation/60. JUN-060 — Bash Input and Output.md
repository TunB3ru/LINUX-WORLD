- An empty input file.
- Malformed input.
- A failed output operation.
- A failed upstream command.

# Part I — Understanding Standard Streams

## 7. Standard Input, Standard Output, and Standard Error

Linux processes conventionally use three standard file descriptors.

| File descriptor | Name | Abbreviation | Conventional purpose |
|---|---|---|---|
| 0 | Standard input | stdin | Receive input |
| 1 | Standard output | stdout | Produce normal output |
| 2 | Standard error | stderr | Produce diagnostics |

When you execute a command in a terminal, these descriptors commonly refer to your terminal session.

However, they do not have to.

A process can read from a file, write normal output into a second file, and send errors into a third file.

### 7.1 Visual model

```text
                     BASH PROCESS
                          |
           +--------------+--------------+
           |              |              |
           v              v              v
          fd 0           fd 1           fd 2
          stdin          stdout         stderr
           |              |              |
           v              v              v
       Input source   Normal output   Diagnostics
```

### 7.2 A critical distinction

The terminal is a device or interface.

stdin, stdout, and stderr are process-level input/output interfaces.

A terminal may be connected to those interfaces, but a terminal and a standard stream are not the same thing.

## 9. Exercise 2 — Inspect Process Descriptors

Linux exposes information about open file descriptors through `/proc`.

For the current Bash process, run:

```bash

```

You may see symbolic links referring to a terminal, pipe, or another destination.

### What does this not prove?

It does not establish that every future child process will have identical descriptor destinations.

# Part II — Producing Reliable Output

## 10. Understanding printf

`printf` is a Bash builtin used to produce formatted output.

Its general form is:

```bash
printf 'FORMAT' ARGUMENTS
```

Example:

```bash
printf 'Service: %s\n' 'sample-api'
```

Expected:

```text
Service: sample-api
```

Useful formatting directives include:

| Directive | Meaning |
|---|---|
| `%s` | String |
| `%d` | Signed decimal integer |
| `%u` | Unsigned decimal integer |
| `%f` | Floating-point formatting |
| `\n` | Newline |
| `\t` | Tab |
| `%%` | Literal percent sign |

For arbitrary strings, prefer:

```bash
printf '%s\n' "$value"
```

The format string remains controlled while the variable is treated as data.

Do not use untrusted input as the `printf` format string.

---

## 11. Exercise 3 — Create a Formatted Service Report

Create:

```bash
cat > scripts/02-formatted-output.sh <<'EOF'
#!/usr/bin/env bash

service="sample-api"
environment="staging"
port=8080

printf 'Service: %s\n' "$service"
printf 'Environment: %s\n' "$environment"
printf 'Port: %d\n' "$port"

printf '\n'

printf '%-18s %-15s %-8s\n' \
    'SERVICE' 'ENVIRONMENT' 'PORT'

printf '%-18s %-15s %-8d\n' \
    "$service" "$environment" "$port"
EOF
```

Run:

```bash

```

Expected:

```text
Service: sample-api
Environment: staging
Port: 8080

SERVICE            ENVIRONMENT     PORT
sample-api         staging         8080
```

### Explain the formatting

`%-18s` left-aligns a string in a field with a minimum width of 18 characters.

`%-15s` left-aligns a string in a field with a minimum width of 15 characters.

`%-8d` formats an integer in a minimum-width field.

These widths are useful for simple tabular output but do not guarantee perfect visual alignment for every Unicode character.

### Verification

```bash

cat reports/formatted-output.txt
```

**Checkpoint:** You can produce both ordinary messages and aligned tabular output.

## 12. Understanding echo

`echo` is commonly used to display text:

```bash
echo "Hello"
```

It is convenient, but its handling of certain options and backslash sequences can vary across shell implementations.

For example, relying on `echo -e` for formatting is less predictable than using `printf`.

Prefer:

```bash
printf 'First line\nSecond line\n'
```

rather than building critical formatting behavior around `echo -e`.

### Exercise 4 — Compare echo and printf

Run:

```bash
echo "Application started"
printf '%s\n' "Application started"
```

Now:

```bash
printf '%s\n' '-n is ordinary data here'
```

Observe that `printf` treats the string as data because the format string is fixed.

**Engineering lesson:** Use `printf` when output formatting must be explicit and predictable.

# Part III — Reading Input

## 13. Understanding the read Builtin

Bash provides `read` to consume input.

Basic syntax:

```bash
read variable
```

Recommended line-reading form:

```bash
IFS= read -r variable
```

### Why `-r` matters

Without `-r`, backslashes can act as escape characters.

With `-r`, backslashes are preserved.

### Why `IFS=` matters

It prevents `read` from trimming leading and trailing characters that would otherwise be treated as field separators.

### What happens to the newline?

The terminating newline is not stored in the variable.

### What happens at EOF?

`read` returns a nonzero status when it encounters end-of-file before reading the requested delimiter.

A final line without a newline may still contain data.

You must handle that case explicitly in line-processing loops.

## 16. Exercise 7 — Read a File Line by Line

Create a fixture:

```bash
cat > fixtures/services.txt <<'EOF'
sample-api
billing-worker
notification-service
EOF
```

Create the reader:

```bash
cat > scripts/05-read-lines.sh <<'EOF'
#!/usr/bin/env bash

input_file="${1:-}"

if [[ -z "$input_file" ]]; then
    printf 'Usage: %s FILE\n' "$0" >&2
    exit 2
fi

if [[ ! -f "$input_file" || ! -r "$input_file" ]]; then
    printf 'ERROR: Input file unavailable.\n' >&2
    exit 3
fi

line_number=0
line=""

while IFS= read -r line || [[ -n "$line" ]]; do
    line_number=$((line_number + 1))
    printf 'Line %d: <%s>\n' "$line_number" "$line"
done < "$input_file"
EOF
```

Run:

```bash
bash scripts/05-read-lines.sh fixtures/services.txt
```

Expected:

```text
Line 1: <sample-api>
Line 2: <billing-worker>
Line 3: <notification-service>
```

### Understanding the loop

```bash
while IFS= read -r line || [[ -n "$line" ]]; do
```

The first condition reads a line.

The second condition handles a final nonempty line that lacks a terminating newline.

The input redirection:

```bash
done < "$input_file"
```

connects the file to the loop's stdin.

### Important limitation

This example handles normal line-oriented text but does not yet detect every possible read failure occurring after a file has been opened. The final project will use a more controlled input-processing approach.

# Part IV — Here-Documents and Here-Strings

## 19. Here-Documents

A here-document supplies multiple lines to a command.

Example:

```bash
cat <<EOF
Line one
Line two
EOF
```

### Quoted versus unquoted delimiters

An unquoted delimiter allows certain expansions:

```bash
service="sample-api"

cat <<EOF
Service: $service
EOF
```

A quoted delimiter preserves the text literally:

```bash
cat <<'EOF'
Service: $service
EOF
```

### Exercise 10 — Compare Expansion

Run:

```bash
service="sample-api"

cat <<EOF
Expanded value: $service
EOF
```

Expected:

```text
Expanded value: sample-api
```

Now:

```bash
cat <<'EOF'
Literal value: $service
EOF
```

Expected:

```text
Literal value: $service
```

### Operational use

Quoted here-documents are particularly useful for creating training scripts and configuration fixtures without accidentally expanding embedded variables.

---

## 20. Here-Strings

A here-string supplies a string as stdin.

Syntax:

```bash
command <<< "$value"
```

Example:

```bash
record="sample-api:staging:8080"
IFS=':' read -r service environment port <<< "$record"

printf 'Service: %s\n' "$service"
printf 'Environment: %s\n' "$environment"
printf 'Port: %s\n' "$port"
```

Expected:

```text
Service: sample-api
Environment: staging
Port: 8080
```

A Bash here-string supplies a terminating newline.

# Part V — Output Redirection

## 21. Overwrite Redirection

The operator `>` redirects stdout.

Example:

```bash
printf 'first version\n' > tmp/example.txt
```

If the target file exists, it is normally truncated.

### Exercise 12 — Observe Truncation

Run:

```bash
printf 'original data\n' > tmp/overwrite-demo.txt
cat tmp/overwrite-demo.txt
```

Now:

```bash
printf 'replacement data\n' > tmp/overwrite-demo.txt
cat tmp/overwrite-demo.txt
```

Expected:

```text
replacement data
```

The original content is gone.

### Production implication

An incorrect output path can destroy existing data.

Never assume that redirection preserves previous contents.

## 22. Append Redirection

The operator `>>` appends stdout.

### Exercise 13 — Append Records

Appending preserves existing content under normal conditions, but it can still fail because of permissions, storage exhaustion, or filesystem errors.

## 24. Combining stdout and stderr

This form redirects both streams into one file:

```bash
command > output.txt 2>&1
```

The redirections are evaluated left to right.

First stdout is redirected.

Then stderr is duplicated to stdout's current destination.

### Exercise 15 — Combine Streams

Run:

```bash
bash scripts/01-standard-streams.sh \
    > reports/combined-streams.txt \
    2>&1
```

Inspect:

```bash
cat reports/combined-streams.txt
```

Expected: both INFO and ERROR messages.

### Important limitation

Once streams are combined, the resulting file does not inherently identify which stream produced each line.

Clear message prefixes can help, but they do not restore the original stream separation.

## 25. Redirection Order Matters

Compare:

```bash
command > file.txt 2>&1
```

and:

```bash
command 2>&1 > file.txt
```

They are not equivalent.

### Exercise 16 — Demonstrate the Difference

First:

```bash
bash scripts/01-standard-streams.sh \
    > reports/order-a.txt \
    2>&1
```

Second:

```bash
bash scripts/01-standard-streams.sh \
    2>&1 \
    > reports/order-b.txt
```

Inspect:

```bash
printf '%s\n' '--- ORDER A ---'
cat reports/order-a.txt

printf '%s\n' '--- ORDER B ---'
cat reports/order-b.txt
```

Expected:

- `order-a.txt` contains stdout and stderr.
- `order-b.txt` contains stdout.
- The second command's stderr appeared on the terminal.

### Explanation

In the second form, stderr is duplicated to stdout's original destination before stdout is redirected to the file.

**Checkpoint:** You can explain descriptor duplication without treating `2>&1` as a permanent merge.

## 27. Understanding /dev/null

`/dev/null` discards data written to it.

Examples:


Discards stdout.

Discards stderr.

Discards both.

The monitoring logic interpreted the pipeline's numeric output and final status without validating the input source or earlier pipeline stages.

# Part VIII — Build the Final Application Log Processor

## 37. Final Project Design

You will now build a Bash utility named:

```text
log-triage.sh
```

It will support:

```bash
bash scripts/log-triage.sh \
    --input fixtures/application.log \
    --report reports/application-report.txt
```

and:

```bash
bash scripts/log-triage.sh \
    --stdin \
    --report reports/stdin-report.txt \
    < fixtures/application.log
```

The second command supplies input through stdin using direct redirection.

### 37.1 Supported log format

Each record must have exactly four pipe-separated fields:

```text
TIMESTAMP|SEVERITY|SERVICE|MESSAGE
```

Example:

```text
2026-10-12T08:00:00Z|INFO|sample-api|Application started
```

### 37.2 Supported severities

```text
INFO
WARN
ERROR
```

### 37.3 Validation rules

- Timestamp must be a structurally valid UTC date-time string.
- Severity must be one of the three supported values.
- Service name must begin with a lowercase letter and contain only lowercase letters, digits, or hyphens.
- Message must not be empty.
- Extra field delimiters are rejected.
- Empty input is rejected.
- A final line without a newline is accepted.

For this junior lab, timestamp validation checks the expected text structure, not whether every date is calendar-valid.

### 37.4 Exit status contract

| Exit status | Meaning |
|---|---|
| 0 | Analysis succeeded; no ERROR records |
| 1 | Analysis succeeded; ERROR records found |
| 2 | Invalid command-line arguments |
| 3 | Input/output operational failure |
| 4 | Empty or malformed input |

This is an application-specific contract.

It is not a universal Bash exit-code standard.

## 39. Build the Final Script

Create:

```bash
cat > scripts/log-triage.sh <<'BASH'
#!/usr/bin/env bash

# VERIQTA Linux World
# JUN-060 — Bash Input and Output
#
# Training-only application log processor.
# No production files or services are modified.

set -u
set -o pipefail

INPUT_MODE=""
INPUT_FILE=""
REPORT_FILE=""

TOTAL_COUNT=0
INFO_COUNT=0
WARN_COUNT=0
ERROR_COUNT=0
MALFORMED_COUNT=0

declare -a MALFORMED_DETAILS=()

usage() {
    cat <<'USAGE'
Usage:
  log-triage.sh --input FILE --report FILE
  log-triage.sh --stdin --report FILE
  log-triage.sh --help

Exit statuses:
  0  Valid input; no ERROR records
  1  Valid input; ERROR records found
  2  Invalid arguments
  3  Input/output failure
  4  Empty or malformed input
USAGE
}

error() {
    printf 'ERROR: %s\n' "$1" >&2
}

warning() {
    printf 'WARNING: %s\n' "$1" >&2
}

parse_args() {
    while (( $# > 0 )); do
        case "$1" in
            --input)
                if (( $# < 2 )) || [[ -z "$2" ]]; then
                    error "--input requires a nonempty path"
                    return 2
                fi

                if [[ -n "$INPUT_MODE" ]]; then
                    error "Specify exactly one input mode"
                    return 2
                fi

                INPUT_MODE="file"
                INPUT_FILE="$2"
                shift 2
                ;;

            --stdin)
                if [[ -n "$INPUT_MODE" ]]; then
                    error "Specify exactly one input mode"
                    return 2
                fi

                INPUT_MODE="stdin"
                shift
                ;;

            --report)
                if (( $# < 2 )) || [[ -z "$2" ]]; then
                    error "--report requires a nonempty path"
                    return 2
                fi

                if [[ -n "$REPORT_FILE" ]]; then
                    error "Specify --report only once"
                    return 2
                fi

                REPORT_FILE="$2"
                shift 2
                ;;

            --help)
                usage
                exit 0
                ;;

            *)
                error "Unknown argument: $1"
                return 2
                ;;
        esac
    done

    if [[ -z "$INPUT_MODE" ]]; then
        error "Input mode is required"
        return 2
    fi

    if [[ -z "$REPORT_FILE" ]]; then
        error "Report path is required"
        return 2
    fi

    return 0
}

validate_file_input() {
    if [[ ! -f "$INPUT_FILE" ]]; then
        error "Input is missing or is not a regular file"
        return 3
    fi

    if [[ ! -r "$INPUT_FILE" ]]; then
        error "Input file is not readable"
        return 3
    fi

    return 0
}

mark_malformed() {
    local number="$1"
    local reason="$2"

    MALFORMED_COUNT=$((MALFORMED_COUNT + 1))
    MALFORMED_DETAILS+=("Line $number: $reason")

    warning "Line $number: $reason"
}

process_line() {
    local line="$1"
    local number="$2"

    local timestamp=""
    local severity=""
    local service=""
    local message=""
    local remainder=""

    TOTAL_COUNT=$((TOTAL_COUNT + 1))

    if [[ "$line" != *"|"* ]]; then
        mark_malformed "$number" "Missing delimiters"
        return 0
    fi

    timestamp="${line%%|*}"
    remainder="${line#*|}"

    if [[ "$remainder" != *"|"* ]]; then
        mark_malformed "$number" "Missing severity delimiter"
        return 0
    fi

    severity="${remainder%%|*}"
    remainder="${remainder#*|}"

    if [[ "$remainder" != *"|"* ]]; then
        mark_malformed "$number" "Missing service delimiter"
        return 0
    fi

    service="${remainder%%|*}"
    message="${remainder#*|}"

    if [[ "$message" == *"|"* ]]; then
        mark_malformed "$number" "Unexpected extra delimiter"
        return 0
    fi

    if [[ ! "$timestamp" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]]; then
        mark_malformed "$number" "Invalid timestamp structure"
        return 0
    fi

    case "$severity" in
        INFO|WARN|ERROR)
            ;;
        *)
            mark_malformed "$number" "Unsupported severity"
            return 0
            ;;
    esac

    if [[ ! "$service" =~ ^[a-z][a-z0-9-]*$ ]]; then
        mark_malformed "$number" "Invalid service name"
        return 0
    fi

    if [[ -z "$message" ]]; then
        mark_malformed "$number" "Empty message"
        return 0
    fi

    case "$severity" in
        INFO)
            INFO_COUNT=$((INFO_COUNT + 1))
            ;;
        WARN)
            WARN_COUNT=$((WARN_COUNT + 1))
            ;;
        ERROR)
            ERROR_COUNT=$((ERROR_COUNT + 1))
            ;;
    esac
}

analyze_fd() {
    local fd="$1"
    local line=""
    local number=0
    local read_status=0

    while :; do
        line=""

        IFS= read -r -u "$fd" line
        read_status=$?

        if (( read_status == 0 )); then
            number=$((number + 1))
            process_line "$line" "$number"
            continue
        fi

        if [[ -n "$line" ]]; then
            number=$((number + 1))
            process_line "$line" "$number"
        fi

        # Bash read uses nonzero status for EOF.
        # For this training tool, an EOF indication ends
        # line processing. Operational read errors from
        # unusual devices are outside its supported scope.
        break
    done

    return 0
}

analyze_input() {
    if [[ "$INPUT_MODE" == "file" ]]; then
        validate_file_input || return 3

        if ! exec 3< "$INPUT_FILE"; then
            error "Could not open input file"
            return 3
        fi
    else
        if ! exec 3<&0; then
            error "Could not duplicate stdin"
            return 3
        fi
    fi

    analyze_fd 3
    local status=$?

    exec 3<&-

    return "$status"
}

determine_status() {
    if (( TOTAL_COUNT == 0 )); then
        return 4
    fi

    if (( MALFORMED_COUNT > 0 )); then
        return 4
    fi

    if (( ERROR_COUNT > 0 )); then
        return 1
    fi

    return 0
}

write_report() {
    local report_dir=""
    local timestamp=""
    local result=""
    local detail=""

    report_dir="$(dirname -- "$REPORT_FILE")"

    if [[ ! -d "$report_dir" ]]; then
        error "Report directory does not exist"
        return 3
    fi

    if [[ -e "$REPORT_FILE" && ! -f "$REPORT_FILE" ]]; then
        error "Report destination is not a regular file"
        return 3
    fi

    if ! timestamp="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; then
        error "Could not obtain UTC timestamp"
        return 3
    fi

    if (( TOTAL_COUNT == 0 )); then
        result="EMPTY_INPUT"
    elif (( MALFORMED_COUNT > 0 )); then
        result="MALFORMED_INPUT"
    elif (( ERROR_COUNT > 0 )); then
        result="ERROR_RECORDS_FOUND"
    else
        result="NO_ERROR_RECORDS_FOUND"
    fi

    if {
        printf 'JUN-060 Application Log Report\n'
        printf '==============================\n\n'
        printf 'Generated UTC: %s\n' "$timestamp"
        printf 'Input mode: %s\n' "$INPUT_MODE"

        if [[ "$INPUT_MODE" == "file" ]]; then
            printf 'Input path: %s\n' "$INPUT_FILE"
        fi

        printf '\n'
        printf 'Total records: %d\n' "$TOTAL_COUNT"
        printf 'INFO: %d\n' "$INFO_COUNT"
        printf 'WARN: %d\n' "$WARN_COUNT"
        printf 'ERROR: %d\n' "$ERROR_COUNT"
        printf 'Malformed: %d\n' "$MALFORMED_COUNT"
        printf 'Result: %s\n' "$result"

        if (( MALFORMED_COUNT > 0 )); then
            printf '\nValidation details:\n'

            for detail in "${MALFORMED_DETAILS[@]}"; do
                printf '%s\n' "$detail"
            done
        fi

        printf '\n'
        printf '%s\n' \
            'Scope: Supplied training records only.'
        printf '%s\n' \
            'This report does not establish application health.'
    } > "$REPORT_FILE"; then
        return 0
    else
        error "Report write failed"
        return 3
    fi
}

print_summary() {
    printf 'JUN-060 Log Triage\n'
    printf 'Total: %d\n' "$TOTAL_COUNT"
    printf 'INFO: %d\n' "$INFO_COUNT"
    printf 'WARN: %d\n' "$WARN_COUNT"
    printf 'ERROR: %d\n' "$ERROR_COUNT"
    printf 'Malformed: %d\n' "$MALFORMED_COUNT"
    printf 'Report: %s\n' "$REPORT_FILE"
}

main() {
    local status=0

    parse_args "$@" || return $?

    analyze_input || return 3

    if ! write_report; then
        return 3
    fi

    print_summary

    determine_status
    status=$?

    return "$status"
}

main "$@"
BASH
```

### 39.1 Implementation scope and limitations

This is a training parser for regular text files and ordinary stdin.

It deliberately does not provide:

- Arbitrary binary-input support.
- Full detection of every low-level read error.
- Calendar-valid timestamp verification.
- Atomic report replacement.
- Secure handling of hostile output paths.
- Real-time streaming of unbounded input.
- Production-grade log provenance verification.
- Guaranteed report durability after a storage failure.

It does, however, provide the documented behaviors required for the controlled exercises.

For production deployment, those limitations must be addressed based on the environment and risk level.

# Part X — Automated Regression Checks

## 61. Why Regression Testing Matters

A script that works with one valid fixture may still fail under operational conditions.

Regression tests protect against future changes that accidentally alter:

- Input validation.
- Severity counts.
- Exit statuses.
- Report generation.
- Error handling.
- EOF behavior.

The following test runner checks the documented exit-status contract.

---

## 62. Build the Regression Test Runner

Create:

```bash
cat > scripts/run-tests.sh <<'BASH'
#!/usr/bin/env bash

set -u

ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd -P)" || exit 3

PASS=0
FAIL=0

run_case() {
    local name="$1"
    local expected="$2"
    local input="$3"
    local actual=0

    if bash "$ROOT/scripts/log-triage.sh" \
        --input "$ROOT/fixtures/$input" \
        --report "$ROOT/reports/test-$input.txt" \
        > "$ROOT/tmp/test-stdout.txt" \
        2> "$ROOT/tmp/test-stderr.txt"
    then
        actual=0
    else
        actual=$?
    fi

    if (( actual == expected )); then
        printf 'PASS: %s (status %d)\n' "$name" "$actual"
        PASS=$((PASS + 1))
    else
        printf 'FAIL: %s (expected %d, got %d)\n' \
            "$name" "$expected" "$actual"
        FAIL=$((FAIL + 1))
    fi
}

run_case "Valid log with errors" 1 "application.log"
run_case "Valid log without errors" 0 "no-errors.log"
run_case "Empty input" 4 "empty.log"
run_case "Malformed input" 4 "malformed.log"
run_case "Unsupported severity" 4 "unsupported-severity.log"
run_case "Empty message" 4 "empty-message.log"
run_case "Extra delimiter" 4 "extra-delimiter.log"
run_case "No final newline" 0 "no-final-newline.log"
run_case "Invalid timestamp" 4 "invalid-timestamp.log"
run_case "Invalid service" 4 "invalid-service.log"
run_case "Missing file" 3 "missing.log"

printf '\n'
printf 'Passed: %d\n' "$PASS"
printf 'Failed: %d\n' "$FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
BASH
```

Validate:

```bash
bash -n scripts/run-tests.sh
```

Run:

```bash
bash scripts/run-tests.sh
```

Expected:

```text
PASS: Valid log with errors (status 1)
PASS: Valid log without errors (status 0)
PASS: Empty input (status 4)
PASS: Malformed input (status 4)
PASS: Unsupported severity (status 4)
PASS: Empty message (status 4)
PASS: Extra delimiter (status 4)
PASS: No final newline (status 0)
PASS: Invalid timestamp (status 4)
PASS: Invalid service (status 4)
PASS: Missing file (status 3)

Passed: 11
Failed: 0
```

### Important test limitation

This runner verifies expected exit statuses.

It does not independently verify every report field, file permission, stream destination, or failure mode.

A mature test suite would add content assertions and more detailed negative tests.

# Part XI — Simulated Production Incident

## 63. Incident INC-2026-BASHIO-060

**Incident classification:** Monitoring false success.

**Environment:** Fictional application platform.

**Affected component:** Scheduled Bash log inspection.

**Business impact:** Monitoring reported zero application errors even though the log inspection had not completed successfully.

### 63.1 Symptom

The dashboard displayed:

```text
Application errors: 0
Job status: SUCCESS
```

### 63.2 Original command

```bash
cat /var/log/example-app/application.log | grep ERROR | wc -l
```

### 63.3 Evidence

The file-read command produced:

```text
No such file or directory
```

The pipeline's final command produced:

```text
0
```

Without `pipefail`, the final command's successful status masked the upstream failure.

### 63.4 Competing hypotheses

| Hypothesis | Evidence | Assessment |
|---|---|---|
| Application had no ERROR records | Input was not successfully read | Not established |
| Log file was missing | File-read diagnostic | Supported |
| Log inspection succeeded | Upstream failure | Contradicted |
| Pipeline status masked failure | Default pipeline semantics | Supported |
| Monitoring interpreted zero as success | Incident scenario | Supported |
| Application was healthy | No independent health evidence | Not established |

### 63.5 Supported root cause

The monitoring script failed to validate its input and relied on a pipeline whose final command succeeded even though the upstream file-read command failed.

The monitoring integration incorrectly treated the resulting zero count and successful pipeline status as a valid analysis.

### 63.6 Contributing factors

- No input existence check.
- No input readability check.
- No explicit empty-input policy.
- No upstream failure propagation.
- No differentiated exit-code contract.
- Inadequate negative testing.
- No independent verification of the monitoring result.

### 63.7 Authorized remediation approach

In a real environment, a proposed change would require review and authorization.

The corrective design should:

1. Validate input availability.
2. Distinguish missing input from zero matching records.
3. Preserve upstream command failures.
4. Separate normal output and diagnostics.
5. Return documented statuses.
6. Check report-write results.
7. Add negative regression tests.
8. Update monitoring to interpret statuses correctly.
9. Verify actual application behavior independently.

### 63.8 Recovery verification

A successful correction must show:

- A valid no-error log is reported as valid.
- A valid error-containing log produces the expected alert condition.
- Missing input causes an operational failure.
- Empty input is not reported as healthy.
- Malformed input is rejected.
- Pipeline failures remain visible.
- Reports are written successfully or failures are surfaced.
- Monitoring interprets the exit-code contract correctly.

The last point requires an authorized integration test in the real monitoring environment.

### 63.9 Prevention

Add these cases to the monitoring job's automated test suite:

- Missing log file.
- Empty log file.
- Unreadable input.
- Malformed record.
- No matching errors.
- Multiple matching errors.
- Report-write failure.
- Upstream producer failure.
- Unexpected exit status.

**Core lesson:** A monitoring job must distinguish successful observation from failure to observe.

# Part XIV — Knowledge Assessment

## 68. Thirty Questions and Answers

**1. What is stdin?**

Standard input is file descriptor 0, conventionally used by a process to receive data.

**2. What is stdout?**

Standard output is file descriptor 1, conventionally used for normal program output.

**3. What is stderr?**

Standard error is file descriptor 2, conventionally used for diagnostics.

**4. Is a terminal the same as stdout?**

No. A terminal is one possible destination for stdout.

**5. What does `>` do?**

It redirects stdout and normally truncates an existing target file.

**6. What does `>>` do?**

It appends stdout to a file.

**7. What does `2>` do?**

It redirects stderr.

**8. What does `2>&1` do?**

It duplicates stdout's current destination for stderr.

**9. Why does redirection order matter?**

Because Bash processes redirections from left to right.

**10. What is `/dev/null`?**

A device that discards data written to it.

**11. Why use `printf`?**

It provides explicit, predictable output formatting.

**12. Why use `printf '%s\n' "$value"`?**

It treats the value as data instead of allowing it to control the format string.

**13. What does `read -r` do?**

It prevents backslashes from being interpreted as escape characters during input reading.

**14. What does `IFS= read -r` help preserve?**

Leading and trailing whitespace and literal backslashes.

**15. What is a here-document?**

A shell construct that supplies multiline input to a command.

**16. Why quote a here-document delimiter?**

To prevent the relevant expansions within the here-document body.

**17. What is a here-string?**

A Bash construct that supplies a string to a command's stdin.

**18. What is a pipeline?**

A connection from one command's stdout to another command's stdin.

**19. Does stderr normally enter a pipe?**

No. It remains separate unless redirected or combined.

**20. What is the default Bash pipeline exit status?**

Generally, the status of the last command.

**21. What does `pipefail` change?**

It makes the pipeline report the status of the rightmost failing stage, or zero if all stages succeed.

**22. What is `PIPESTATUS`?**

An array containing exit statuses from the most recently executed foreground pipeline.

**23. Why capture `PIPESTATUS` immediately?**

Because subsequent commands can overwrite its values.

**24. What does `tee` do?**

It copies stdin to stdout and one or more files.

**25. What is command substitution?**

A shell feature that captures command stdout for use in another expression or assignment.

**26. What happens to trailing newlines in command substitution?**

Bash removes them.

**27. Why can pipeline loops affect variable scope?**

Because pipeline components may execute in subshell environments.

**28. Why use NUL delimiters for filenames?**

Because filenames may contain newlines but cannot contain NUL bytes.

**29. Why must a script distinguish empty input from zero matching errors?**

Because empty input may mean that no observation occurred, whereas zero matches is a result from successfully inspected valid input.

**30. What caused the simulated monitoring incident?**

An upstream input failure was masked by the successful final command in a pipeline, and the monitoring workflow lacked adequate input validation and status interpretation.

# Part XV — Interview Preparation

## 69. Twelve Interview Questions with Worked Answers

### Interview Question 1

**Explain standard input, standard output, and standard error.**

They are conventional process interfaces represented by file descriptors 0, 1, and 2. They allow input, normal output, and diagnostics to be routed independently.

### Interview Question 2

**What is the difference between `>` and `>>`?**

`>` normally truncates an existing file before writing, while `>>` appends output. Both can fail, and scripts should check the outcome of required writes.

### Interview Question 3

**Why is `command > file 2>&1` different from `command 2>&1 > file`?**

Redirections are processed from left to right. In the first command, both streams go to the file. In the second, stderr retains stdout's earlier destination while stdout is redirected to the file.

### Interview Question 4

**Why should diagnostic messages be written to stderr?**

Separating diagnostics from normal output prevents consumers from accidentally interpreting error messages as valid data.

### Interview Question 5

**How can a pipeline hide an upstream failure?**

Without `pipefail`, Bash generally reports the last command's status. If the last command succeeds despite an earlier failure, the pipeline can appear successful.

### Interview Question 6

**What does `pipefail` do?**

It makes the pipeline's status reflect the rightmost failed command, or zero when all commands succeed.

### Interview Question 7

**How would you inspect individual pipeline stages?**

Capture `PIPESTATUS` immediately after the pipeline and examine each element.

### Interview Question 8

**How do you safely read a text file line by line in Bash?**

Use `IFS= read -r` and handle the final nonempty line without a newline. Validate the file before processing it and account for the input source's limitations.

### Interview Question 9

**Why prefer `printf` to `echo` in operational scripts?**

`printf` offers predictable formatting and avoids differences in how some `echo` implementations interpret options and escape sequences.

### Interview Question 10

**How would you distinguish a missing log file from a valid log with zero errors?**

Validate input availability, check read status, reject empty or invalid input according to a documented policy, and use different exit statuses for successful analysis and operational failure.

### Interview Question 11

**Can a script print SUCCESS and still fail?**

Yes. Printed text and process exit status are separate. The script can print SUCCESS and then exit nonzero. Automation should evaluate the documented status contract.

### Interview Question 12

**What would you improve before deploying this training parser into production?**

I would add robust low-level input-error detection, stronger timestamp validation, secure and atomic report writing, output-path controls, explicit resource limits, more comprehensive tests, and integration with the monitoring system's alerting contract. I would also verify application health using independent evidence.

## 73. Final Lessons from the Trenches

**Lesson 1 — Output is not proof of success.** A command can print useful-looking data while failing to complete its intended operation.

**Lesson 2 — Standard streams serve different purposes.** stdin carries input, stdout carries normal output, and stderr carries diagnostics.

**Lesson 3 — Redirection is operationally significant.** The wrong operator or destination can overwrite files or hide diagnostic evidence.

**Lesson 4 — Redirection order matters.** File descriptors are duplicated according to the order in which redirections are processed.

**Lesson 5 — Empty input and zero errors are not equivalent.** A monitoring system must distinguish successful inspection from failure to observe.

**Lesson 6 — Pipelines require explicit failure handling.** A successful final command can mask an earlier failure unless the workflow checks the relevant statuses.

**Lesson 7 — `pipefail` is useful but not sufficient.** It improves pipeline failure visibility; it does not validate data quality or prove application health.

**Lesson 8 — Input must be treated as data.** Never execute untrusted input or assume a record is valid simply because it can be read.

**Lesson 9 — Exit statuses form an interface.** Other programs and automation systems depend on a clear, documented interpretation.

**Lesson 10 — Report generation is a separate operation.** A valid analysis can still fail to produce its required output artifact.

**Lesson 11 — Negative tests are essential.** Missing files, empty input, malformed records, and failed writes reveal reliability gaps that successful-path tests miss.

**Lesson 12 — Engineering conclusions must match the evidence.** Finding zero ERROR records in a supplied log does not prove that the application, its dependencies, or its users are healthy.
