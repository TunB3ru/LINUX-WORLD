# 1. Production Mission — The Deployment Script That Reported Success After Failure

You are a junior Linux engineer working with an application operations team.

The team maintains a small Bash script used to check whether an application is ready for deployment.

The script is supposed to:

1. Confirm that the deployment directory exists.
2. Confirm that the application configuration file is readable.
3. Confirm that the application process is running.
4. Check available disk space.
5. Print a final deployment readiness result.

During a scheduled deployment, the script prints:

```text
Deployment preflight completed successfully.
```

However, the application configuration file is missing.

The deployment proceeds and fails.

An investigation finds the following script:

```bash
#!/usr/bin/env bash

echo "Checking application configuration..."
ls /opt/example-app/config/app.conf

echo "Checking application process..."

```

The script contains multiple problems.

It assumes that displaying a command's output is equivalent to validating the command's result.

It does not make a deliberate decision when a check fails.

It does not distinguish successful checks from failed checks.

It prints a success message regardless of what the earlier commands returned.

And its process check is too broad to serve as reliable evidence of application health.

Bash is often the first programming language a Linux engineer uses in operational environments.

It is used for:

- System inspection.
- Application deployment preparation.
- Log processing.
- Scheduled maintenance.
- File validation.
- Backup verification.

- Configuration inspection.
- Troubleshooting.
- CI/CD automation.
- Infrastructure support.
- Incident evidence collection.

But Bash is also easy to misuse.

A short script can silently produce the wrong result because of:

- Incorrect quoting.
- Unchecked exit codes.
- Incorrect variable expansion.
- Unsafe wildcard expansion.
- Unexpected empty variables.
- Word splitting.
- Missing files.
- Incorrect conditionals.
- Pipelines hiding failures.
- Confusion between standard output and standard error.
- Commands running in unexpected directories.
- Uncontrolled environment variables.
- Poor cleanup logic.

Your goal is not merely to memorize Bash syntax.

# 7. Understanding the Shell

A shell is a program that interprets commands and provides an interface between a user or script and the operating system.

When you enter:

```bash
pwd
```

the shell interprets the command and executes the appropriate operation.

When you enter:

```bash
ls -l
```

the shell interprets the command name and its arguments.

A shell also performs operations before a command runs, including:

- Variable expansion.
- Command substitution.
- Arithmetic expansion.
- Word splitting in applicable contexts.
- Pathname expansion.
- Quote removal.
- Redirection setup.

Understanding these operations is essential.

## 7.1 What is Bash?

Bash stands for **Bourne Again SHell**.

It is a widely used command interpreter and scripting language on Linux.

Bash supports:

- Variables.
- Conditionals.
- Loops.
- Functions.
- Arrays.
- Arithmetic.
- Command substitution.
- Redirection.
- Pipelines.
- Job control.
- Shell options.

## 7.2 Bash is not the Linux kernel

The shell is a user-space program.

It communicates with the operating system through system interfaces and external commands.

## 7.3 Bash is not every shell

Other shells include:

- `sh`
- `dash`
- `zsh`
- `fish`
- `ksh`

A script using Bash-specific syntax should explicitly run with Bash.

# 11. Understanding Bash Comments

A comment normally begins with:

```bash
#
```

Example:

```bash
# Explain why this check exists.
```

Comments are useful for documenting:

- Purpose.
- Preconditions.
- Assumptions.
- Safety requirements.
- Non-obvious behavior.
- Expected outputs.

Avoid comments that merely repeat the command.

Weak:

```bash
# Print hello
printf 'hello\n'
```

Better:

```bash
# Record a UTC timestamp so incident evidence can be correlated.
date -u '+%Y-%m-%dT%H:%M:%SZ'
```

The shebang is a special interpreter directive when placed at the beginning of an executable script.

`printf` provides explicit formatting.

It is generally more predictable than relying on implementation-specific `echo` handling of options or escape sequences.

## 12.2 Important formatting examples



```bash

```

instead of:

```bash

```

when the value is not a trusted format string.

# 13. Understanding Bash Variables

A variable stores a value that can be referenced later.

Example:

```bash
environment="staging"
```

Reference it:

```bash
printf '%s\n' "$environment"
```

## 13.1 Assignment syntax

Correct:

```bash
name="VERIQTA"
```

Incorrect:

```bash
name = "VERIQTA"
```

Spaces around `=` change how Bash interprets the command.

## 13.2 Variables are usually strings

Bash variables commonly hold strings, even when the text represents a number.

Arithmetic contexts can interpret suitable values numerically.

## 13.3 Variable names

Common valid names:

```bash
app_name="sample-api"
check_count=5
deployment_ready="yes"
```

Use descriptive names.

Avoid overriding important shell variables such as `PATH` without a specific reason.

# 15. Understanding Quoting

Quoting is one of the most important Bash skills.

## 15.1 Unquoted expansion

```bash
file_path=$HOME/my file.txt
```

This is not a safe way to represent a path containing spaces.

## 15.2 Double quotes

```bash
file_path="$HOME/my file.txt"
```

Double quotes allow parameter and command expansion while preserving the expanded text as one argument in ordinary command contexts.

## 15.3 Single quotes

```bash
file_path='$HOME/my file.txt'
```

Single quotes preserve the literal text.

The `$HOME` variable is not expanded.

## 15.4 General rule

Quote ordinary variable expansions:

```bash
"$variable"
```

Exceptions exist in specific Bash syntactic contexts, but quoting is a strong default.

# 17. Understanding Word Splitting and Pathname Expansion

Consider:

```bash
value="one two three"
```

Unquoted:

```bash
printf '<%s>\n' $value
```

This commonly produces three arguments:

```text
<one>
<two>
<three>
```

Quoted:

```bash
printf '<%s>\n' "$value"
```

Produces one argument:

```text
<one two three>
```

## 17.1 Pathname expansion

An unquoted `*` can expand to matching filenames.

This is useful when intentional.

It is dangerous when unexpected.

## 17.2 Engineering rule

Do not rely on unquoted variable expansion to represent a list of arguments.

Use Bash arrays when you need multiple distinct arguments.

# 19. Understanding Command Substitution

Command substitution captures a command's standard output.

Syntax:

```bash
result="$(command)"
```

Example:

```bash
current_user="$(id -un)"
```

## 19.1 What happens?

Bash runs the command and substitutes its standard output.

Trailing newline characters are removed from command-substitution output.

## 19.2 Important limitation

Command substitution does not automatically mean the command succeeded.

You must handle failures when they matter.

# 23. Understanding Environment Variables

A shell variable is not automatically exported to child processes.

Example:

```bash
environment="staging"
```

A child Bash process will not necessarily receive it.

Exporting:

```bash
export environment
```

makes it available in the environment of subsequently launched child processes.

## 23.1 Security concern

Environment variables can contain sensitive values.

Do not assume environment variables are a secure secrets store.

Avoid logging complete environments.

# 25. Understanding Positional Parameters

Scripts can accept arguments.

Example:

```bash
bash script.sh staging sample-api
```

Inside the script:

```bash
$0
```

represents the script invocation name.

```bash
$1
```

is the first argument.

```bash
$2
```

is the second argument.

```bash
$#
```

is the number of positional arguments.

## 25.1 Important distinction

`"$@"` preserves each positional argument as a separate argument.

`"$*"` combines the positional arguments into one word when double-quoted, using the first character of `IFS` as the separator.

For argument forwarding, `"$@"` is generally the correct choice.

Every completed command provides an exit status.



`$?` refers to the most recently completed foreground pipeline or command.

# 50. Understanding && and ||

Bash supports command lists.

```bash
command_a && command_b
```

runs `command_b` only if `command_a` succeeds.

```bash
command_a || command_b
```

runs `command_b` only if `command_a` fails.

## 50.1 Important caution

Do not assume:

```bash
command_a && command_b || command_c
```

is always equivalent to a complete `if/else`.

If `command_b` fails, `command_c` also runs.

For operational decisions, explicit conditionals are often clearer.

# 54. Understanding Redirection

Common operators:

| Operator | Meaning |
|---|---|
| `>` | Redirect output, overwrite target |
| `>>` | Append output |
| `<` | Redirect input |
| `2>` | Redirect standard error |
| `2>>` | Append standard error |
| `2>&1` | Redirect standard error to current standard output destination |
| `&>` | Bash shorthand for redirecting stdout and stderr |

## 54.1 Order matters

These are not always equivalent:

```bash
command > file 2>&1
```

```bash
command 2>&1 > file
```

Redirections are processed from left to right.

## 54.2 Safety warning

`>` can truncate an existing file.

Always confirm the destination before redirecting important output.

# 56. Understanding Pipelines

A pipeline connects one command's standard output to another command's standard input.

Example:

```bash
printf '%s\n' alpha beta gamma | grep beta
```

## 56.1 Pipeline status

By default, Bash generally reports the status of the final command in a pipeline.

This can hide failures in earlier commands.

## 56.2 pipefail

```bash
set -o pipefail
```

changes pipeline status behavior so a pipeline fails when an earlier component fails, with the status of the rightmost failing command.

## 56.3 Important limitation

`pipefail` does not make all pipelines semantically correct.

For example, a producer may receive SIGPIPE when a consumer intentionally exits early.

You must understand the expected behavior of each pipeline.

# 72. Create the Production Preflight Script

Create:

```bash
nano scripts/application-preflight.sh
```

Enter the complete script:

```bash
#!/usr/bin/env bash

# JUN-058 — Bash Fundamentals
# VERIQTA Linux World
#
# Purpose:
# Perform read-only checks against a simulated application
# directory and produce a structured preflight report.
#
# This script does not verify a real application process,
# network endpoint, or production service health.

set -u
set -o pipefail

APP_DIR=""
REPORT_FILE=""

PASS_COUNT=0
FAIL_COUNT=0

declare -a RESULTS=()

usage() {
    cat <<'USAGE'
Usage:
  application-preflight.sh --app-dir DIRECTORY --report FILE

Options:
  --app-dir DIRECTORY   Simulated application directory
  --report FILE         Output report path
  --help                Display this help message

Exit codes:
  0  All checks passed
  1  One or more checks failed
  2  Invalid arguments
  3  Operational error
USAGE
}

error() {
    printf 'ERROR: %s\n' "$1" >&2
}

record_pass() {
    local description="$1"

    PASS_COUNT=$((PASS_COUNT + 1))
    RESULTS+=("PASS|$description")

    printf 'PASS: %s\n' "$description"
}

record_fail() {
    local description="$1"

    FAIL_COUNT=$((FAIL_COUNT + 1))
    RESULTS+=("FAIL|$description")

    printf 'FAIL: %s\n' "$description" >&2
}

require_regular_readable_file() {
    local file_path="$1"
    local description="$2"

    if [[ -f "$file_path" && -r "$file_path" ]]; then
        record_pass "$description"
    else
        record_fail "$description"
    fi
}

parse_arguments() {
    while (( $# > 0 )); do
        case "$1" in
            --app-dir)
                if (( $# < 2 )); then
                    error "--app-dir requires a value"
                    return 2
                fi

                APP_DIR="$2"
                shift 2
                ;;

            --report)
                if (( $# < 2 )); then
                    error "--report requires a value"
                    return 2
                fi

                REPORT_FILE="$2"
                shift 2
                ;;

            --help)
                usage
                exit 0
                ;;

            *)
                error "Unknown argument: $1"
                return 2
                ;;
        esac
    done

    if [[ -z "$APP_DIR" ]]; then
        error "--app-dir is required"
        return 2
    fi

    if [[ -z "$REPORT_FILE" ]]; then
        error "--report is required"
        return 2
    fi

    return 0
}

check_application_directory() {
    if [[ -d "$APP_DIR" ]]; then
        record_pass "Application directory exists"
    else
        record_fail "Application directory exists"
    fi
}

check_configuration() {
    local config_file="$APP_DIR/config/app.conf"

    require_regular_readable_file \
        "$config_file" \
        "Application configuration is readable"

    if [[ ! -f "$config_file" || ! -r "$config_file" ]]; then
        record_fail "Required configuration fields are present"
        return 0
    fi

    local field
    local missing=0

    for field in APP_NAME ENVIRONMENT PORT; do
        if ! grep -Eq \
            "^[[:space:]]*${field}=[^[:space:]].*" \
            "$config_file"; then
            missing=1
        fi
    done

    if (( missing == 0 )); then
        record_pass "Required configuration fields are present"
    else
        record_fail "Required configuration fields are present"
    fi
}

check_log_file() {
    require_regular_readable_file \
        "$APP_DIR/logs/application.log" \
        "Application log is readable"
}

check_data_file() {
    require_regular_readable_file \
        "$APP_DIR/data/application data.txt" \
        "Application data file is readable"
}

check_simulated_service_state() {
    local state_file="$APP_DIR/state/service.status"

    require_regular_readable_file \
        "$state_file" \
        "Simulated service state file is readable"

    if [[ ! -f "$state_file" || ! -r "$state_file" ]]; then
        record_fail "Simulated service state equals running"
        return 0
    fi

    local state

    if ! state="$(< "$state_file")"; then
        record_fail "Simulated service state equals running"
        return 0
    fi

    if [[ "$state" == "running" ]]; then
        record_pass "Simulated service state equals running"
    else
        record_fail "Simulated service state equals running"
    fi
}

check_disk_inspection() {
    local disk_output

    if disk_output="$(df -P -- "$APP_DIR" 2>/dev/null)"; then
        record_pass "Disk filesystem information is available"
    else
        record_fail "Disk filesystem information is available"
    fi
}

write_report() {
    local report_directory

    report_directory="$(dirname -- "$REPORT_FILE")"

    if [[ ! -d "$report_directory" ]]; then
        error "Report directory does not exist: $report_directory"
        return 3
    fi

    local timestamp

    if ! timestamp="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; then
        error "Could not determine UTC timestamp"
        return 3
    fi

    local overall="PASS"

    if (( FAIL_COUNT > 0 )); then
        overall="FAIL"
    fi

    if ! {
        printf '# Application Preflight Report\n\n'
        printf 'UTC timestamp: %s\n\n' "$timestamp"
        printf 'Application directory: %s\n\n' "$APP_DIR"
        printf 'Overall result: %s\n\n' "$overall"
        printf 'Passed checks: %d\n' "$PASS_COUNT"
        printf 'Failed checks: %d\n\n' "$FAIL_COUNT"
        printf '## Individual Checks\n\n'

        local result
        local status
        local description

        for result in "${RESULTS[@]}"; do
            status="${result%%|*}"
            description="${result#*|}"

            printf -- '- [%s] %s\n' "$status" "$description"
        done

        printf '\n## Scope Limitation\n\n'
        printf '%s\n' \
            'This report checks local files and simulated state only.'
        printf '%s\n' \
            'It does not establish live application readiness.'
    } > "$REPORT_FILE"; then
        error "Could not write report: $REPORT_FILE"
        return 3
    fi

    return 0
}

main() {
    local parse_status=0

    parse_arguments "$@" || {
        parse_status=$?
        return "$parse_status"
    }

    printf 'Starting application preflight...\n'
    printf 'Application directory: %s\n' "$APP_DIR"

    check_application_directory

    if [[ -d "$APP_DIR" ]]; then
        check_configuration
        check_log_file
        check_data_file
        check_simulated_service_state
    else
        record_fail "Application configuration is readable"
        record_fail "Required configuration fields are present"
        record_fail "Application log is readable"
        record_fail "Application data file is readable"
        record_fail "Simulated service state file is readable"
        record_fail "Simulated service state equals running"
    fi

    check_disk_inspection

    if ! write_report; then
        return 3
    fi

    printf '\nPreflight summary:\n'
    printf 'Passed: %d\n' "$PASS_COUNT"
    printf 'Failed: %d\n' "$FAIL_COUNT"
    printf 'Report: %s\n' "$REPORT_FILE"

    if (( FAIL_COUNT > 0 )); then
        return 1
    fi

    return 0
}

main "$@"
```

# 88. Production Incident Investigation

**Incident ID:** INC-2026-BASH-058

**Incident type:** Deployment preflight false success.

## 88.1 Business impact

A deployment proceeded without a required application configuration file.

The application failed during startup.

The deployment team lost time investigating the failure.

## 88.2 Initial symptom

The preflight script printed:

```text
Deployment preflight completed successfully.
```

## 88.3 Evidence A — Missing configuration

The required file did not exist.

## 88.4 Evidence B — Original script

```bash
#!/usr/bin/env bash

echo "Checking application configuration..."
ls /opt/example-app/config/app.conf

echo "Checking application process..."
pgrep -f example-app

echo "Deployment preflight completed successfully."
```

## 88.5 Evidence C — Exit behavior

The script did not explicitly fail when earlier checks failed.

Its final command was a successful `echo`.

The overall script could therefore exit zero.

## 88.6 Evidence D — Deployment automation

The deployment system interpreted exit status zero as a successful preflight.

## 88.7 Competing hypotheses

| Hypothesis | Evidence | Assessment |
|---|---|---|
| Configuration was present | File inspection showed it missing | Contradicted |
| Preflight detected failure correctly | Final success output and exit zero | Contradicted |
| SSH caused deployment failure | No supporting evidence | Not supported |
| Deployment system ignored a nonzero exit | Script exited zero | Contradicted |
| Script did not handle command failure | Script inspection confirms | Supported |
| Process check proved readiness | Broad `pgrep -f` check | Not established |
| Final echo masked earlier failure | Last-command exit behavior | Supported |

## 88.8 Supported root cause

The preflight script lacked explicit error handling and meaningful overall status calculation.

It printed success regardless of failed checks.

The deployment system received exit status zero and proceeded.

## 88.9 Corrective actions

1. Replace display-only checks with explicit validations.
2. Record individual check results.
3. Fail the preflight when required conditions are not met.
4. Return documented exit codes.
5. Test missing-file scenarios.
6. Test invalid configuration.
7. Validate reporting.
8. Review automation integration.
9. Require approval before production deployment.
10. Add regression tests.

## 88.10 Recovery verification

The corrected workflow must demonstrate:

- Valid fixture returns zero.
- Missing configuration returns nonzero.
- Invalid required fields return nonzero.
- Missing report destination produces a distinct operational error.
- Logs and reports match exit status.
- Deployment automation blocks on a failing preflight.
- The original missing-configuration scenario is prevented.

The last two items require testing in an authorized deployment test environment; the local lab alone does not prove deployment-system integration.

| `"${name}"` | Braced expansion | Clarifies variable boundary |
| `$(command)` | Command substitution | Capture stdout |
| `$((expression))` | Arithmetic expansion | Integer arithmetic |
| `export` | Export variable | Child processes inherit |
| `unset` | Remove variable | Affects current shell |
| `$0` | Invocation name | Not always absolute path |
| `$1` | First positional argument | Validate before use |
| `$#` | Argument count | Useful for validation |
| `"$@"` | All arguments separately | Preferred forwarding form |
| `shift` | Consume positional arguments | Validate count |
| `read -r` | Read input | Preserves backslashes |
| `if` | Conditional execution | Tests command status |
| `elif` | Alternative condition | Part of if structure |
| `else` | Fallback branch | Runs if prior conditions fail |

# 96. Interview Preparation — 12 Questions with Worked Answers

## Interview Question 1 — What is Bash, and why is it important for Linux engineers?

**Answer:**

Bash is a shell and scripting language used to execute commands and automate Linux operations.

It is important because engineers use it for system inspection, maintenance, troubleshooting, deployment preparation, and operational workflows.

A reliable Bash script must handle inputs, quoting, errors, and exit statuses correctly.

## Interview Question 2 — What is the difference between running a script with Bash and executing it directly?

**Answer:**

`bash script.sh` explicitly invokes Bash to read the script.

`./script.sh` requests direct execution, which requires executable permission and normally uses the interpreter specified by the shebang.

## Interview Question 3 — Why is quoting important in Bash?

**Answer:**

Quoting prevents unintended word splitting and pathname expansion.

Without correct quoting, a path containing spaces may be interpreted as multiple arguments.

This can cause commands to fail or operate on unintended paths.

## Interview Question 4 — What is the difference between a shell variable and an environment variable?

**Answer:**

A shell variable exists in the current shell.

An exported variable is included in the environment inherited by child processes.

Exporting a variable does not automatically make it a secure place to store secrets.

## Interview Question 5 — What is the difference between `"$@"` and `"$*"`?

**Answer:**

`"$@"` preserves each positional argument as a separate argument.

`"$*"` combines the positional parameters into a single word when quoted.

For forwarding command-line arguments, `"$@"` is generally preferred.

## Interview Question 6 — How do you handle command failures in Bash?

**Answer:**

I check command exit statuses explicitly using `if command; then ... else ... fi`, return meaningful error codes, and ensure the script's final status reflects its result.

I also consider pipeline behavior and validate operational outcomes rather than relying only on printed messages.

## Interview Question 7 — What does `set -euo pipefail` do?

**Answer:**

It enables several Bash behaviors commonly used for error detection.

`-e` requests exit in certain unhandled failure situations.

`-u` treats many unset-variable references as errors.

`pipefail` makes upstream pipeline failures affect the pipeline status.

These settings have limitations and do not replace deliberate error handling.

## Interview Question 8 — What is the difference between stdout and stderr?

**Answer:**

Standard output is used for normal program output.

Standard error is used for diagnostic or error messages.

Separating them allows automation to capture results and failures independently.

## Interview Question 9 — What are Bash functions useful for?

**Answer:**

Functions group related commands into reusable units.

They improve readability, consistency, and testability.

Function-local variables help reduce unintended interactions between different parts of a script.

## Interview Question 10 — How would you debug a failing Bash script?

**Answer:**

I would reproduce the issue safely, confirm the interpreter, run `bash -n`, inspect inputs and working directory, review quoting and exit statuses, and use `bash -x` only when it will not expose secrets.

I would then test the smallest correction against both success and failure scenarios.

## Interview Question 11 — How do you safely handle temporary files?

**Answer:**

I use tools such as `mktemp`, keep track of the generated path, and use controlled cleanup logic.

I ensure cleanup cannot accidentally target unrelated files.

I also understand that traps do not run under every termination condition.

## Interview Question 12 — How would you prevent a deployment script from reporting success after a failed check?

**Answer:**

I would make each required check produce an explicit result, aggregate failures, return a nonzero exit status when any required check fails, and test negative scenarios.

I would verify that the deployment automation actually respects the script's exit status.

**11. A file existing does not prove an application is healthy.**

Checks must match the operational requirement.

**12. A simulated state file does not prove a real process is running.**

Do not overstate evidence.

**13. Syntax validation is necessary but insufficient.**

A script can parse correctly and still be logically wrong.

**14. Negative testing is essential.**

A preflight tool that passes the success scenario but fails to detect missing configuration is not reliable.

**15. Production automation must be evidence-driven.**

Good Bash engineering combines clear requirements, controlled execution, meaningful statuses, failure testing, and recovery verification.
