# 1. Welcome to the Lab

A Linux administrator regularly performs the same operational checks:

- Is the server responding?
- Is disk space becoming exhausted?
- Is memory pressure increasing?
- Are important directories present?
- Is a critical service running?
- Can an application write to its required directories?
- Are any conditions serious enough to require intervention?
- Can the results be collected and reviewed later?

Performing these checks manually is useful while learning Linux. But in a real environment, administrators must perform them consistently across many systems.

That is where Bash scripting becomes valuable.

In previous labs, you worked with Bash commands, variables, input and output, conditionals, loops, functions, exit codes, and error handling.

In this lab, you will combine those skills into your **first complete Linux administration script**.

You will not simply write a few commands into a file and call it automation.

You will design a small administrative utility with a defined interface, explicit checks, configurable thresholds, predictable output, meaningful exit codes, a report, a test suite, and a documented failure-handling strategy.

By the end, you will have built a script that can serve as a starting point for real operational automation.

**You will work entirely inside a disposable lab workspace.** The script will inspect your local system using read-only commands. It will not restart services, install packages, delete system files, or change production configuration.

# 2. The Production Scenario

## Incident INC-2026-LINUXADMIN-066 — The Server That Reported Healthy

You are a junior Linux engineer supporting a fictional internal service named `veriqta-orders`.

A senior engineer has asked you to review a simple server health-check script used during morning operations.

The original script looks like this:

```bash
#!/usr/bin/env bash

echo "Checking server..."

df -h /
free -h
uptime

echo "Server is healthy."
```

At first glance, the script appears useful.

It prints filesystem information, memory information, and uptime.

However, during a simulated incident, the application filesystem reaches a critical utilization level.

The script still prints:

```text
Server is healthy.
```

The job also exits with status `0`.

The operations dashboard interprets that result as success.

The problem is not that `df`, `free`, or `uptime` are useless. They provide valuable information.

The problem is that the script does not **interpret** that information.

It never compares filesystem utilization against a threshold.

It never distinguishes warnings from critical conditions.

It never validates whether a required service is running.

It never establishes a reliable contract for success and failure.

Your assignment is to replace that script with a structured Linux administration utility.

The replacement must be able to identify unhealthy conditions, produce a readable report, and return a status that automation can interpret.

# 3. Your Engineering Mission

You will build a utility named:

```text
linux-admin-check.sh
```

It will perform five administrative checks:

1. **Filesystem utilization:** Read the percentage of space used on a selected filesystem and compare it with warning and critical thresholds.
2. **Memory availability:** Read `/proc/meminfo` and calculate the percentage of available memory.
3. **Required directory:** Confirm that a specified application directory exists and is accessible.
4. **Service state:** Optionally check whether a specified systemd service is active.
5. **Host information:** Record the hostname, operating system, kernel, uptime, and timestamp for context.

The script will then:

- Assign `OK`, `WARN`, `CRITICAL`, or `UNKNOWN` to each check.
- Calculate an overall status.
- Print a human-readable summary.
- Write a structured report.
- Return a meaningful exit code.
- Keep normal output separate from diagnostics.
- Handle missing commands, invalid configuration, and unexpected output.
- Support repeatable testing using controlled fixtures.

## 3.1 Important design distinction

A server health check is not the same as a server repair script.

Your first administration script will **observe and report**.

It will not automatically delete files, restart services, change permissions, or terminate processes.

This separation is intentional.

Reliable administrative automation begins with accurate observation. Automated remediation should be introduced only after the detection logic has been validated and appropriate safeguards have been designed.

## 11. Exercise 2 — Inspect Filesystem Utilization

Run:

```bash
df -h /
```

Example output:

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        40G   12G   26G  32% /
```

Your filesystem name, size, and percentage will differ.

The `Use%` column indicates filesystem utilization.

For an automated check, you need the numeric percentage without the percent sign.

Run:

```bash
df -P /
```

The `-P` option requests a portable output format.

Now extract the utilization percentage:

```bash
df -P / | awk 'NR == 2 { gsub(/%/, "", $5); print $5 }'
```

Expected: a number such as `32`.

### Understand the pipeline

`df -P /` prints filesystem information.

`awk 'NR == 2'` selects the second output record.

`gsub(/%/, "", $5)` removes the percent sign from field five.

`print $5` prints the numeric utilization.

**Reliability limitation:** This example assumes the expected `df` output format and does not separately verify the upstream command's status. The final script will validate the measurement more carefully.

## 12. Exercise 3 — Build a Filesystem Threshold Check

Create:

```bash
cat > scripts/02-filesystem-check.sh <<'EOF'
#!/usr/bin/env bash

set -u
set -o pipefail

warning_threshold=75
critical_threshold=90

if ! output="$(df -P /)"; then
    printf 'UNKNOWN: Unable to read filesystem utilization.\n' >&2
    exit 3
fi

used_percent="$(
    awk 'NR == 2 {
        value = $5
        gsub(/%/, "", value)
        print value
    }' <<< "$output"
)"

if [[ ! "$used_percent" =~ ^[0-9]+$ ]]; then
    printf 'UNKNOWN: Invalid filesystem utilization.\n' >&2
    exit 3
fi

if (( used_percent > 100 )); then
    printf 'UNKNOWN: Utilization exceeds expected range.\n' >&2
    exit 3
fi

if (( used_percent >= critical_threshold )); then
    printf 'CRITICAL: Filesystem is %d%% used.\n' "$used_percent"
    exit 2
elif (( used_percent >= warning_threshold )); then
    printf 'WARN: Filesystem is %d%% used.\n' "$used_percent"
    exit 1
else
    printf 'OK: Filesystem is %d%% used.\n' "$used_percent"
    exit 0
fi
EOF
```

Validate:

```bash
bash -n scripts/02-filesystem-check.sh
```

Run:

```bash
bash scripts/02-filesystem-check.sh

status=$?

printf 'Check status: %d\n' "$status"
```

Expected: an `OK`, `WARN`, or `CRITICAL` message depending on your actual filesystem utilization.

The script does not assume that your host is healthy.

### Threshold rules

| Utilization | Warning threshold | Critical threshold | Status |
|---|---|---|---|
| 42% | 75% | 90% | OK |
| 75% | 75% | 90% | WARN |
| 89% | 75% | 90% | WARN |
| 90% | 75% | 90% | CRITICAL |
| 97% | 75% | 90% | CRITICAL |

The comparisons are inclusive at the threshold boundaries.

## 13. Exercise 4 — Inspect Memory Availability

Run:

```bash
free -h
```

This provides a human-readable memory summary.

Now inspect the kernel's memory statistics:

```bash
grep -E '^(MemTotal|MemAvailable):' /proc/meminfo
```

Example:

```text
MemTotal:       16384000 kB
MemAvailable:   10485760 kB
```

The actual values depend on your system.

`MemAvailable` estimates how much memory is available for new applications without swapping.

For a basic Linux administration check, it is generally more useful than interpreting the `MemFree` field alone.

Calculate the percentage of memory available:

```bash
awk '
    /^MemTotal:/ { total = $2 }
    /^MemAvailable:/ { available = $2 }
    END {
        if (total > 0) {
            printf "%.0f\n", (available * 100) / total
        }
    }
' /proc/meminfo
```

Expected: an integer percentage between `0` and `100`.

### Why use available memory?

Linux uses memory for caches and buffers.

A low `MemFree` value does not necessarily indicate memory exhaustion.

The `MemAvailable` estimate accounts for memory that the kernel expects can be reclaimed.

## 14. Exercise 5 — Build a Memory Check

Create:

```bash
cat > scripts/03-memory-check.sh <<'EOF'
#!/usr/bin/env bash

set -u

warning_available=20
critical_available=10

if [[ ! -r /proc/meminfo ]]; then
    printf 'UNKNOWN: /proc/meminfo is unavailable.\n' >&2
    exit 3
fi

if ! available_percent="$(
    awk '
        /^MemTotal:/ { total = $2 }
        /^MemAvailable:/ { available = $2; found = 1 }
        END {
            if (total <= 0 || !found) {
                exit 1
            }

            printf "%.0f\n", (available * 100) / total
        }
    ' /proc/meminfo
)"; then
    printf 'UNKNOWN: Unable to calculate available memory.\n' >&2
    exit 3
fi

if [[ ! "$available_percent" =~ ^[0-9]+$ ]] ||
   (( available_percent > 100 )); then
    printf 'UNKNOWN: Invalid memory percentage.\n' >&2
    exit 3
fi

if (( available_percent <= critical_available )); then
    printf 'CRITICAL: Only %d%% memory available.\n' \
        "$available_percent"
    exit 2
elif (( available_percent <= warning_available )); then
    printf 'WARN: Only %d%% memory available.\n' \
        "$available_percent"
    exit 1
else
    printf 'OK: %d%% memory available.\n' \
        "$available_percent"
    exit 0
fi
EOF
```

Validate and run:

```bash
bash -n scripts/03-memory-check.sh

bash scripts/03-memory-check.sh

status=$?

printf 'Memory check status: %d\n' "$status"
```

Expected: an `OK`, `WARN`, or `CRITICAL` result based on your host.

### Important threshold distinction

For disk utilization, **higher** percentages are worse.

For memory availability, **lower** percentages are worse.

A reusable administration script must understand that different metrics have different threshold directions.

## 16. Exercise 7 — Check a systemd Service

On Ubuntu Server, systemd commonly manages services.

Check whether `systemctl` is available:

```bash
command -v systemctl
```

If available, run:

```bash
systemctl is-active ssh
```

Possible results include:

```text
active
```

or:

```text
inactive
```

The `ssh` service may not be installed on your machine.

**Do not install or start services solely to satisfy this lab.**

Create:

```bash
cat > scripts/05-service-check.sh <<'EOF'
#!/usr/bin/env bash

service_name="${1:-ssh}"

if ! command -v systemctl >/dev/null 2>&1; then
    printf 'UNKNOWN: systemctl is unavailable.\n'
    exit 3
fi

if systemctl is-active --quiet "$service_name"; then
    printf 'OK: Service is active: %s\n' "$service_name"
    exit 0
else
    printf 'CRITICAL: Service is not active: %s\n' "$service_name"
    exit 2
fi
EOF
```

Run:

```bash
bash scripts/05-service-check.sh ssh

status=$?

printf 'Service check status: %d\n' "$status"
```

Your result depends on whether the SSH service exists and is active.

### Important limitation

A nonzero result from `systemctl is-active` does not always mean that a service is simply stopped.

The service might be missing, the system might not use systemd as PID 1, or the service manager might be unavailable.

The final script will distinguish service-manager failures from ordinary inactive service states where practical.

# Part 3 — Design the Administration Script

## 17. Define the Script Interface

Your final script will support:

```text
linux-admin-check.sh --config FILE --report FILE
```

It will also support:

```text
linux-admin-check.sh --help
```

Example:

```bash
bash scripts/linux-admin-check.sh \
    --config config/admin-check.conf \
    --report reports/host-health.txt
```

The configuration file will define:

- Filesystem mount point.
- Disk warning threshold.
- Disk critical threshold.
- Memory warning threshold.
- Memory critical threshold.
- Required application directory.
- Optional systemd service name.

### Why separate configuration from code?

If the threshold changes from `80%` to `85%`, you should not need to edit the script's logic.

Separating configuration also makes testing easier.

You can run the same script with different thresholds to simulate warnings and critical conditions without filling a real filesystem.

---

## 18. Define the Exit-Code Contract

The final script will use monitoring-style statuses:

| Exit code | Status | Meaning |
|---|---|---|
| `0` | OK | All enabled checks passed |
| `1` | WARN | At least one warning; no critical or unknown results |
| `2` | CRITICAL | At least one critical result |
| `3` | UNKNOWN | A measurement or operational check could not be evaluated reliably |
| `4` | USAGE | Invalid command-line arguments or configuration |

### Aggregation priority

For this lab, the overall result will use this precedence:

```text
UNKNOWN > CRITICAL > WARN > OK
```

This is a documented design choice.

Some monitoring systems use different aggregation rules.

The key is to make the policy explicit and test it.

---

## 19. Define the Report Format

The script will write a line-oriented report.

Example:

```text
LAB=JUN-066
HOSTNAME=lab-server
TIMESTAMP_UTC=2026-10-17T12:00:00Z
FILESYSTEM_STATUS=OK
FILESYSTEM_USED_PERCENT=42
MEMORY_STATUS=OK

DIRECTORY_STATUS=OK
SERVICE_STATUS=SKIPPED
OVERALL_STATUS=OK
EXIT_CODE=0
```

The report is designed to be easy to inspect with `cat`, `grep`, and other standard Linux tools.

It is not a general-purpose parser for arbitrary untrusted values.

For this lab, configuration values will be validated and test fixtures will use controlled data.

## 23. Script Design Requirements

Before writing the code, confirm the requirements.

### Functional requirements

The script must:

- Accept a configuration path.
- Accept a report path.
- Reject unknown arguments.
- Reject duplicate options.
- Validate numeric thresholds.
- Validate threshold ordering.
- Read host information.
- Read disk utilization.
- Read memory availability.
- Check a required directory.
- Optionally check a systemd service.
- Aggregate results.
- Write a report.
- Print a summary.
- Return the correct status.

### Reliability requirements

The script must:

- Check critical command failures.
- Avoid treating malformed metrics as healthy.
- Keep diagnostics on stderr.
- Avoid executing configuration as shell code.
- Reject unsupported configuration keys.
- Validate test fixture paths.
- Avoid overwriting existing reports.
- Clean up temporary report files.
- Distinguish live data from fixture data.

### Security requirements

The script must:

- Run without root.
- Avoid `eval`.
- Avoid `source` for the configuration file.
- Avoid unsafe word splitting.
- Quote path variables.
- Reject unsafe report paths.
- Keep generated reports inside the lab workspace.
- Treat configuration as data, not executable Bash.

## 24. Create `linux-admin-check.sh`

Run the following complete heredoc.

```bash
cat > scripts/linux-admin-check.sh <<'BASH'
#!/usr/bin/env bash

# VERIQTA Linux World
# JUN-066 — Writing Your First Linux Administration Script
#
# Read-only host health checks with validated configuration,
# deterministic test fixtures, structured reporting, and exit codes.

set -u
set -o pipefail

readonly STATUS_OK=0
readonly STATUS_WARN=1
readonly STATUS_CRITICAL=2
readonly STATUS_UNKNOWN=3
readonly STATUS_USAGE=4

SCRIPT_DIR="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P)" || exit 3
LAB_ROOT="$(cd -- "$SCRIPT_DIR/.." && pwd -P)" || exit 3

CONFIG_FILE=""
REPORT_FILE=""

FILESYSTEM_PATH="/"
DISK_WARNING_PERCENT=""
DISK_CRITICAL_PERCENT=""
MEMORY_WARNING_AVAILABLE_PERCENT=""
MEMORY_CRITICAL_AVAILABLE_PERCENT=""
REQUIRED_DIRECTORY=""
SERVICE_NAME=""

FILESYSTEM_STATUS="UNKNOWN"
FILESYSTEM_USED_PERCENT="N/A"

MEMORY_STATUS="UNKNOWN"
MEMORY_AVAILABLE_PERCENT="N/A"

DIRECTORY_STATUS="UNKNOWN"
SERVICE_STATUS="SKIPPED"

HOSTNAME_VALUE="UNKNOWN"
KERNEL_VALUE="UNKNOWN"
TIMESTAMP_UTC="UNKNOWN"
UPTIME_SECONDS="UNKNOWN"

OVERALL_STATUS="UNKNOWN"
OVERALL_CODE=3

DATA_MODE="LIVE"

TEMP_REPORT=""

log_info() {
    printf '[INFO] %s\n' "$*" >&2
}

log_error() {
    printf '[ERROR] %s\n' "$*" >&2
}

usage() {
    cat <<'EOF'
Usage:
  linux-admin-check.sh --config FILE --report FILE

Options:
  --config FILE   Validated key=value configuration
  --report FILE   New report path inside the lab workspace
  --help          Show help

Exit codes:
  0  OK
  1  WARN
  2  CRITICAL
  3  UNKNOWN
  4  USAGE / invalid configuration

Test-only environment variables:
  VERIQTA_TEST_MODE=1
  VERIQTA_TEST_DISK_FILE=PATH
  VERIQTA_TEST_MEMINFO_FILE=PATH

Do not use fixture mode for production monitoring.
EOF
}

cleanup() {
    local original_status=$?

    trap - EXIT

    if [[ -n "$TEMP_REPORT" && -e "$TEMP_REPORT" ]]; then
        if ! rm -f -- "$TEMP_REPORT"; then
            log_error "Unable to remove temporary report"
            if (( original_status == 0 )); then
                original_status=3
            fi
        fi
    fi

    exit "$original_status"
}

trap cleanup EXIT

parse_arguments() {
    local seen_config=0
    local seen_report=0

    while (( $# > 0 )); do
        case "$1" in
            --config)
                (( $# >= 2 && seen_config == 0 )) || return 1
                [[ -n "$2" && "$2" != --* ]] || return 1

                CONFIG_FILE="$2"
                seen_config=1
                shift 2
                ;;

            --report)
                (( $# >= 2 && seen_report == 0 )) || return 1
                [[ -n "$2" && "$2" != --* ]] || return 1

                REPORT_FILE="$2"
                seen_report=1
                shift 2
                ;;

            *)
                return 1
                ;;
        esac
    done

    (( seen_config == 1 && seen_report == 1 ))
}

is_uint() {
    [[ "$1" =~ ^[0-9]+$ ]]
}

is_percent() {
    is_uint "$1" || return 1

    (( 10#$1 <= 100 ))
}

validate_thresholds() {
    is_percent "$DISK_WARNING_PERCENT" || return 1
    is_percent "$DISK_CRITICAL_PERCENT" || return 1

    is_percent "$MEMORY_WARNING_AVAILABLE_PERCENT" || return 1
    is_percent "$MEMORY_CRITICAL_AVAILABLE_PERCENT" || return 1

    (( 10#$DISK_WARNING_PERCENT < 10#$DISK_CRITICAL_PERCENT )) ||
        return 1

    (( 10#$MEMORY_CRITICAL_AVAILABLE_PERCENT <
       10#$MEMORY_WARNING_AVAILABLE_PERCENT )) ||
        return 1

    return 0
}

read_config() {
    local line=""
    local key=""
    local value=""
    local line_number=0

    local seen_filesystem=0
    local seen_disk_warn=0
    local seen_disk_critical=0
    local seen_memory_warn=0
    local seen_memory_critical=0
    local seen_directory=0
    local seen_service=0

    if [[ ! -f "$CONFIG_FILE" || ! -r "$CONFIG_FILE" ]]; then
        log_error "Configuration file is unavailable"
        return 1
    fi

    while IFS= read -r line || [[ -n "$line" ]]; do
        line_number=$((line_number + 1))

        [[ -z "$line" || "$line" == \#* ]] && continue

        if [[ "$line" != *=* ]]; then
            log_error "Invalid configuration line: $line_number"
            return 1
        fi

        key="${line%%=*}"
        value="${line#*=}"

        case "$key" in
            FILESYSTEM_PATH)
                (( seen_filesystem == 0 )) || return 1
                FILESYSTEM_PATH="$value"
                seen_filesystem=1
                ;;

            DISK_WARNING_PERCENT)
                (( seen_disk_warn == 0 )) || return 1
                DISK_WARNING_PERCENT="$value"
                seen_disk_warn=1
                ;;

            DISK_CRITICAL_PERCENT)
                (( seen_disk_critical == 0 )) || return 1
                DISK_CRITICAL_PERCENT="$value"
                seen_disk_critical=1
                ;;

            MEMORY_WARNING_AVAILABLE_PERCENT)
                (( seen_memory_warn == 0 )) || return 1
                MEMORY_WARNING_AVAILABLE_PERCENT="$value"
                seen_memory_warn=1
                ;;

            MEMORY_CRITICAL_AVAILABLE_PERCENT)
                (( seen_memory_critical == 0 )) || return 1
                MEMORY_CRITICAL_AVAILABLE_PERCENT="$value"
                seen_memory_critical=1
                ;;

            REQUIRED_DIRECTORY)
                (( seen_directory == 0 )) || return 1
                REQUIRED_DIRECTORY="$value"
                seen_directory=1
                ;;

            SERVICE_NAME)
                (( seen_service == 0 )) || return 1
                SERVICE_NAME="$value"
                seen_service=1
                ;;

            *)
                log_error "Unsupported configuration key: $key"
                return 1
                ;;
        esac
    done < "$CONFIG_FILE"

    (( seen_filesystem == 1 )) || return 1
    (( seen_disk_warn == 1 )) || return 1
    (( seen_disk_critical == 1 )) || return 1
    (( seen_memory_warn == 1 )) || return 1
    (( seen_memory_critical == 1 )) || return 1
    (( seen_directory == 1 )) || return 1
    (( seen_service == 1 )) || return 1

    [[ -n "$FILESYSTEM_PATH" ]] || return 1
    [[ -n "$REQUIRED_DIRECTORY" ]] || return 1

    validate_thresholds || return 1

    return 0
}

validate_report_path() {
    local parent=""

    case "$REPORT_FILE" in
        "$LAB_ROOT"/reports/*)
            ;;
        *)
            log_error "Report must be inside $LAB_ROOT/reports"
            return 1
            ;;
    esac

    parent="${REPORT_FILE%/*}"

    if [[ ! -d "$parent" || ! -w "$parent" || ! -x "$parent" ]]; then
        log_error "Report parent directory is unavailable"
        return 1
    fi

    if [[ -e "$REPORT_FILE" || -L "$REPORT_FILE" ]]; then
        log_error "Report already exists"
        return 1
    fi

    return 0
}

validate_test_mode() {
    if [[ "${VERIQTA_TEST_MODE:-0}" == "0" ]]; then
        if [[ -n "${VERIQTA_TEST_DISK_FILE:-}" ||
              -n "${VERIQTA_TEST_MEMINFO_FILE:-}" ]]; then
            log_error "Fixture paths require VERIQTA_TEST_MODE=1"
            return 1
        fi

        DATA_MODE="LIVE"
        return 0
    fi

    if [[ "${VERIQTA_TEST_MODE:-}" != "1" ]]; then
        log_error "Invalid test mode value"
        return 1
    fi

    if [[ -z "${VERIQTA_TEST_DISK_FILE:-}" ||
          -z "${VERIQTA_TEST_MEMINFO_FILE:-}" ]]; then
        log_error "Both fixture files are required in test mode"
        return 1
    fi

    if [[ ! -f "$VERIQTA_TEST_DISK_FILE" ||
          ! -r "$VERIQTA_TEST_DISK_FILE" ||
          ! -f "$VERIQTA_TEST_MEMINFO_FILE" ||
          ! -r "$VERIQTA_TEST_MEMINFO_FILE" ]]; then
        log_error "Test fixture file is unavailable"
        return 1
    fi

    DATA_MODE="FIXTURE"

    return 0
}

collect_host_info() {
    local uptime_raw=""

    if ! HOSTNAME_VALUE="$(hostname)"; then
        HOSTNAME_VALUE="UNKNOWN"
    fi

    if ! KERNEL_VALUE="$(uname -r)"; then
        KERNEL_VALUE="UNKNOWN"
    fi

    if ! TIMESTAMP_UTC="$(date -u '+%Y-%m-%dT%H:%M:%SZ')"; then
        log_error "Unable to obtain timestamp"
        return 1
    fi

    if IFS=' ' read -r uptime_raw _ < /proc/uptime; then
        UPTIME_SECONDS="${uptime_raw%%.*}"
    else
        UPTIME_SECONDS="UNKNOWN"
    fi

    return 0
}

read_disk_percent() {
    local output=""
    local value=""

    if [[ "$DATA_MODE" == "FIXTURE" ]]; then
        if ! IFS= read -r value < "$VERIQTA_TEST_DISK_FILE"; then
            [[ -n "$value" ]] || return 1
        fi
    else
        if ! output="$(df -P -- "$FILESYSTEM_PATH")"; then
            return 1
        fi

        if ! value="$(
            awk '
                NR == 2 {
                    value = $5
                    gsub(/%/, "", value)
                    print value
                }
            ' <<< "$output"
        )"; then
            return 1
        fi
    fi

    is_percent "$value" || return 1

    FILESYSTEM_USED_PERCENT="$((10#$value))"

    return 0
}

check_filesystem() {
    if ! read_disk_percent; then
        FILESYSTEM_STATUS="UNKNOWN"
        log_error "Unable to determine filesystem utilization"
        return 0
    fi

    if (( FILESYSTEM_USED_PERCENT >= 10#$DISK_CRITICAL_PERCENT )); then
        FILESYSTEM_STATUS="CRITICAL"
    elif (( FILESYSTEM_USED_PERCENT >= 10#$DISK_WARNING_PERCENT )); then
        FILESYSTEM_STATUS="WARN"
    else
        FILESYSTEM_STATUS="OK"
    fi

    return 0
}

read_memory_percent() {
    local meminfo_file="/proc/meminfo"
    local result=""

    if [[ "$DATA_MODE" == "FIXTURE" ]]; then
        meminfo_file="$VERIQTA_TEST_MEMINFO_FILE"
    fi

    if ! result="$(
        awk '
            /^MemTotal:/ {
                total = $2
                total_seen++
            }

            /^MemAvailable:/ {
                available = $2
                available_seen++
            }

            END {
                if (total_seen != 1 ||
                    available_seen != 1 ||
                    total !~ /^[0-9]+$/ ||
                    available !~ /^[0-9]+$/ ||
                    total <= 0 ||
                    available > total) {
                    exit 1
                }

                printf "%.0f\n", (available * 100) / total
            }
        ' "$meminfo_file"
    )"; then
        return 1
    fi

    is_percent "$result" || return 1

    MEMORY_AVAILABLE_PERCENT="$((10#$result))"

    return 0
}

check_memory() {
    if ! read_memory_percent; then
        MEMORY_STATUS="UNKNOWN"
        log_error "Unable to determine available memory"
        return 0
    fi

    if (( MEMORY_AVAILABLE_PERCENT <=
          10#$MEMORY_CRITICAL_AVAILABLE_PERCENT )); then
        MEMORY_STATUS="CRITICAL"
    elif (( MEMORY_AVAILABLE_PERCENT <=
            10#$MEMORY_WARNING_AVAILABLE_PERCENT )); then
        MEMORY_STATUS="WARN"
    else
        MEMORY_STATUS="OK"
    fi

    return 0
}

check_directory() {
    if [[ -d "$REQUIRED_DIRECTORY" &&
          -r "$REQUIRED_DIRECTORY" &&
          -x "$REQUIRED_DIRECTORY" ]]; then
        DIRECTORY_STATUS="OK"
    else
        DIRECTORY_STATUS="CRITICAL"
    fi

    return 0
}

check_service() {
    local state=""

    if [[ -z "$SERVICE_NAME" ]]; then
        SERVICE_STATUS="SKIPPED"
        return 0
    fi

    if ! command -v systemctl >/dev/null 2>&1; then
        SERVICE_STATUS="UNKNOWN"
        return 0
    fi

    if ! state="$(systemctl is-active "$SERVICE_NAME" 2>/dev/null)"; then
        case "$state" in
            inactive|failed|activating|deactivating)
                SERVICE_STATUS="CRITICAL"
                ;;
            *)
                SERVICE_STATUS="UNKNOWN"
                ;;
        esac

        return 0
    fi

    if [[ "$state" == "active" ]]; then
        SERVICE_STATUS="OK"
    else
        SERVICE_STATUS="UNKNOWN"
    fi

    return 0
}

status_rank() {
    case "$1" in
        OK|SKIPPED) printf '0\n' ;;
        WARN) printf '1\n' ;;
        CRITICAL) printf '2\n' ;;
        UNKNOWN) printf '3\n' ;;
        *) printf '3\n' ;;
    esac
}

aggregate_status() {
    local status=""
    local rank=0
    local highest=0

    for status in \
        "$FILESYSTEM_STATUS" \
        "$MEMORY_STATUS" \
        "$DIRECTORY_STATUS" \
        "$SERVICE_STATUS"
    do
        rank="$(status_rank "$status")"

        if (( rank > highest )); then
            highest="$rank"
        fi
    done

    OVERALL_CODE="$highest"

    case "$highest" in
        0) OVERALL_STATUS="OK" ;;
        1) OVERALL_STATUS="WARN" ;;
        2) OVERALL_STATUS="CRITICAL" ;;
        3) OVERALL_STATUS="UNKNOWN" ;;
    esac
}

write_report() {
    if ! TEMP_REPORT="$(mktemp "$LAB_ROOT/reports/.admin-report.XXXXXX")"; then
        log_error "Unable to create temporary report"
        return 1
    fi

    if ! {
        printf 'LAB=JUN-066\n'
        printf 'DATA_MODE=%s\n' "$DATA_MODE"
        printf 'HOSTNAME=%s\n' "$HOSTNAME_VALUE"
        printf 'KERNEL=%s\n' "$KERNEL_VALUE"
        printf 'TIMESTAMP_UTC=%s\n' "$TIMESTAMP_UTC"
        printf 'UPTIME_SECONDS=%s\n' "$UPTIME_SECONDS"
        printf 'FILESYSTEM_PATH=%s\n' "$FILESYSTEM_PATH"
        printf 'FILESYSTEM_STATUS=%s\n' "$FILESYSTEM_STATUS"
        printf 'FILESYSTEM_USED_PERCENT=%s\n' "$FILESYSTEM_USED_PERCENT"
        printf 'MEMORY_STATUS=%s\n' "$MEMORY_STATUS"
        printf 'MEMORY_AVAILABLE_PERCENT=%s\n' "$MEMORY_AVAILABLE_PERCENT"
        printf 'DIRECTORY_STATUS=%s\n' "$DIRECTORY_STATUS"
        printf 'SERVICE_STATUS=%s\n' "$SERVICE_STATUS"
        printf 'OVERALL_STATUS=%s\n' "$OVERALL_STATUS"
        printf 'EXIT_CODE=%d\n' "$OVERALL_CODE"
    } > "$TEMP_REPORT"; then
        log_error "Unable to write report"
        return 1
    fi

    if ! mv -n -- "$TEMP_REPORT" "$REPORT_FILE"; then
        log_error "Unable to publish report"
        return 1
    fi

    if [[ -e "$TEMP_REPORT" ]]; then
        log_error "Report publication was not completed"
        return 1
    fi

    TEMP_REPORT=""

    return 0
}

print_summary() {
    printf 'VERIQTA Linux Administration Health Check\n'
    printf '-----------------------------------------\n'
    printf 'Host: %s\n' "$HOSTNAME_VALUE"
    printf 'Data mode: %s\n' "$DATA_MODE"
    printf 'Filesystem: %s (%s%% used)\n' \
        "$FILESYSTEM_STATUS" "$FILESYSTEM_USED_PERCENT"
    printf 'Memory: %s (%s%% available)\n' \
        "$MEMORY_STATUS" "$MEMORY_AVAILABLE_PERCENT"
    printf 'Required directory: %s\n' "$DIRECTORY_STATUS"
    printf 'Service: %s\n' "$SERVICE_STATUS"
    printf 'Overall: %s\n' "$OVERALL_STATUS"
    printf 'Report: %s\n' "$REPORT_FILE"
}

main() {
    if (( $# == 1 )) && [[ "$1" == "--help" ]]; then
        usage
        return 0
    fi

    if ! parse_arguments "$@"; then
        usage >&2
        return "$STATUS_USAGE"
    fi

    if ! read_config; then
        log_error "Configuration validation failed"
        return "$STATUS_USAGE"
    fi

    if ! validate_test_mode; then
        return "$STATUS_USAGE"
    fi

    if ! validate_report_path; then
        return "$STATUS_USAGE"
    fi

    if ! collect_host_info; then
        return "$STATUS_UNKNOWN"
    fi

    check_filesystem
    check_memory
    check_directory
    check_service

    aggregate_status

    if ! write_report; then
        return "$STATUS_UNKNOWN"
    fi

    if ! print_summary; then
        log_error "Unable to print summary"
        return "$STATUS_UNKNOWN"
    fi

    return "$OVERALL_CODE"
}

main "$@"
```

# Part 8 — Status Aggregation

## 38. Why Aggregate Multiple Checks?

A host can have mixed conditions.

For example:

```text
Filesystem: OK
Memory: WARN
Directory: OK
Service: SKIPPED
```

The overall result should be:

```text
WARN
```

Another example:

```text
Filesystem: CRITICAL
Memory: OK
Directory: OK
Service: SKIPPED
```

The overall result should be:

```text
CRITICAL
```

The final script uses the highest-ranked result.

## 39. Exercise 8 — Build a Small Aggregator

Create:

```bash
cat > scripts/06-status-aggregation.sh <<'EOF'
#!/usr/bin/env bash

rank_status() {
    case "$1" in
        OK|SKIPPED) printf '0\n' ;;
        WARN) printf '1\n' ;;
        CRITICAL) printf '2\n' ;;
        UNKNOWN) printf '3\n' ;;
        *) printf '3\n' ;;
    esac
}

statuses=(OK WARN CRITICAL OK)

highest=0

for status in "${statuses[@]}"; do
    rank="$(rank_status "$status")"

    if (( rank > highest )); then
        highest="$rank"
    fi
done

case "$highest" in
    0) overall="OK" ;;
    1) overall="WARN" ;;
    2) overall="CRITICAL" ;;
    3) overall="UNKNOWN" ;;
esac

printf 'Overall status: %s\n' "$overall"
printf 'Exit code: %d\n' "$highest"

exit "$highest"
EOF
```

```bash

status=$?

printf 'Shell-observed status: %d\n' "$status"
```

Expected:

```text
Overall status: CRITICAL
Exit code: 2
Shell-observed status: 2
```

Change the array to:

```bash
statuses=(OK WARN OK)
```

Expected:

```text
Overall status: WARN
Exit code: 1
```

## 43. Incident Root Cause Analysis

### Incident identifier

`INC-2026-LINUXADMIN-066`

### Symptom

A Linux administration script printed a healthy status without evaluating whether monitored metrics were within acceptable limits.

### Technical root cause

The original script collected data but did not apply health criteria.

### Contributing factors

- No threshold configuration.
- No explicit status model.
- No aggregation logic.
- No structured report.
- No negative-path testing.
- No machine-readable distinction between healthy and unhealthy results.
- No documented operational contract.

### Corrective actions

- Add threshold evaluation.
- Introduce `OK`, `WARN`, `CRITICAL`, and `UNKNOWN`.
- Validate metrics before comparison.
- Produce structured reports.
- Return meaningful exit codes.
- Add deterministic fixtures.
- Test healthy, warning, critical, and malformed conditions.

### Preventive controls

- Review scripts against documented requirements.
- Test abnormal conditions.
- Reject malformed measurements.
- Keep fixture mode clearly labeled.
- Include health-check tests in CI.
- Monitor script execution failures separately from host health conditions.

```bash

assert_case() {
    local name="$1"
    local expected_code="$2"
    local disk_fixture="$3"
    local memory_fixture="$4"
    local expected_status="$5"

    local actual_code=0
    local actual_status=""
```

# Part 13 — Production Hardening Review

## 56. Hardening A — Fix `N/A%` Presentation

The baseline summary uses:

```bash
printf 'Filesystem: %s (%s%% used)\n' \
    "$FILESYSTEM_STATUS" "$FILESYSTEM_USED_PERCENT"
```

When a measurement is unavailable, this prints:

```text
UNKNOWN (N/A% used)
```

Improve the display:

```bash
if [[ "$FILESYSTEM_USED_PERCENT" == "N/A" ]]; then
    printf 'Filesystem: %s (measurement unavailable)\n' \
        "$FILESYSTEM_STATUS"
else
    printf 'Filesystem: %s (%s%% used)\n' \
        "$FILESYSTEM_STATUS" "$FILESYSTEM_USED_PERCENT"
fi
```

Apply the same principle to memory.

**Lesson:** Operational output should be accurate even when data is unavailable.

---

## 57. Hardening B — Strengthen Report Publication

The baseline script uses a temporary report and `mv -n`.

This avoids ordinary overwrites but does not provide a complete race-free no-replace guarantee.

For a production-grade design, consider:

- An exclusively created report file.
- A trusted destination directory.
- Rejection of symlinks.
- Canonical path validation.
- A single writer or lock.
- Atomic publication where supported.
- Recovery after interrupted publication.

Also review the grouped report-writing block.

A brace group returns the status of its final command, so a failed earlier `printf` may be hidden if a later `printf` succeeds.

For stronger write validation, check each write operation or use a report-generation mechanism with reliable failure propagation.

---

## 58. Hardening C — Avoid Configuration Path Traversal

The baseline checks whether the report path begins with the expected directory prefix.

However, a path such as:

```text
.../reports/../outside.txt
```

may pass a string-prefix test while resolving outside the intended directory.

Improve the design by:

1. Resolving the report parent directory to a canonical path.
2. Comparing it against the trusted reports directory.
3. Rejecting paths outside the trusted directory.
4. Rejecting symlink destinations.
5. Considering concurrent path replacement.

For a real deployment, prefer a fixed trusted report directory and a validated report basename over arbitrary paths.

---

## 59. Hardening D — Improve Configuration Parsing

The baseline parser is intentionally simple.

It does not support:

- Inline comments.
- Quoted values.
- Escaped characters.
- Spaces around `=`.
- Multiline values.

That is acceptable if the format is clearly documented.

However, for production use, consider rejecting:

- Control characters.
- Newline injection in values.
- Invalid service names.
- Unsafe relative paths.
- Duplicate keys with clear diagnostics.
- Unexpected leading or trailing whitespace.

A strict, limited configuration format is often safer than a permissive parser.

---

## 60. Hardening E — Validate Actual systemd Behavior

Service states can include:

```text
active
inactive
failed
activating
deactivating
unknown
```

A robust monitoring tool should distinguish:

- A service that is installed but inactive.
- A service that failed.
- A service that does not exist.
- A host without systemd.
- A service-manager communication failure.

For this junior lab, service monitoring is optional.

Do not make the whole lab depend on a specific service being installed.

---

## 61. Hardening F — Improve Memory Parsing

The memory parser should be reviewed for:

- Duplicate `MemTotal` entries.
- Duplicate `MemAvailable` entries.
- Negative values.
- Missing fields.
- Invalid units.
- Numeric overflow.
- Values outside the expected range.

The current script checks several of these cases.

A production implementation should also validate units explicitly and ensure the parser's arithmetic is appropriate for the supported platform.

---

## 62. Hardening G — Improve Disk Measurement Parsing

The baseline assumes a predictable `df -P` output structure.

Consider testing:

- Missing mount points.
- Inaccessible paths.
- Unexpected output.
- Non-numeric percentages.
- Multiple output records.
- Locale differences.
- Filesystem types that report unusual capacity values.

You can improve consistency by using an appropriate fixed locale, such as `LC_ALL=C`, when invoking external commands.

# Part 14 — Knowledge Assessment

## 64. Thirty Questions and Answers

**1. What is a Linux administration script?**  
A script that automates one or more Linux operational tasks.

**2. Why use Bash for administration?**  
Bash integrates directly with Linux commands and is widely available.

**3. Why start with read-only checks?**  
They reduce the risk of unintended system changes while developing and validating automation.

**4. What is the purpose of a shebang?**  
It identifies the interpreter used to execute a script.

**5. Why use functions?**  
To organize responsibilities and improve readability, reuse, and testing.

**6. What does `df` measure?**  
Filesystem space usage and availability.

**7. What does `df -P` provide?**  
A portable-style filesystem output format.

**8. Why validate a disk percentage?**  
To avoid comparing malformed or missing values as if they were valid measurements.

**9. What is `MemAvailable`?**  
A kernel estimate of memory available for new applications without swapping.

**10. Why not rely only on `MemFree`?**  
Because Linux uses memory for caches and buffers that may be reclaimable.

**11. What is a warning threshold?**  
A value indicating that a condition requires attention before becoming critical.

**12. What is a critical threshold?**  
A value indicating that a condition has reached an unacceptable level.

**13. Why do disk and memory thresholds have opposite directions?**  
High disk utilization is undesirable, while low available memory is undesirable.

**14. What is `UNKNOWN`?**  
A state indicating that a check could not be evaluated reliably.

**15. Why should malformed data not become `OK`?**  
Because missing information is not evidence of health.

**16. What does exit code `0` mean in this lab?**  
All enabled checks passed.

**17. What does exit code `1` mean?**  
A warning condition exists.

**18. What does exit code `2` mean?**  
A critical condition exists.

**19. What does exit code `3` mean?**  
An unknown or operational measurement failure exists.

**20. What does exit code `4` mean?**  
Invalid usage or configuration.

**21. Why separate configuration from code?**  
To change operational parameters without modifying script logic.

**22. Why avoid sourcing untrusted configuration?**  
Because sourcing executes shell code.

**23. Why use fixture data?**  
To test specific conditions safely and repeatably.

**24. Why label fixture mode?**  
To prevent simulated results from being mistaken for live monitoring.

**25. What is status aggregation?**  
Combining individual check results into an overall status.

**26. Why write reports?**  
To preserve structured evidence of an execution.

**27. Why capture stderr separately?**  
To distinguish diagnostics from normal output.

**28. Why validate report paths?**  
To reduce accidental or unsafe writes.

**29. What caused the simulated incident?**  
The original script collected metrics but never evaluated their health.

**30. What makes an administration script reliable?**  
Clear requirements, validated inputs, checked operations, meaningful statuses, safe outputs, tests, and documentation.

# Part 15 — Interview Preparation

## 65. Twelve Interview Questions

**1. Describe your first Linux administration script.**

I built a Bash utility that checks filesystem utilization, memory availability, a required directory, and an optional systemd service. It validates configuration, produces a report, and returns meaningful exit codes.

**2. How do you determine whether disk usage is critical?**

I read the utilization percentage, validate it, and compare it against configured warning and critical thresholds.

**3. How do you monitor available memory in Linux?**

I use `MemTotal` and `MemAvailable` from `/proc/meminfo` to calculate the available-memory percentage.

**4. Why should a monitoring script return nonzero exit codes?**

So calling automation can distinguish healthy, warning, critical, and unknown outcomes.

**5. How do you avoid executing configuration files as code?**

I parse a restricted set of supported keys instead of using `source` or `eval`.

**6. Why do you use functions in your script?**

Functions separate responsibilities, improve readability, and make testing easier.

**7. How do you test critical disk conditions without filling the disk?**

I use controlled fixture data representing a critical utilization percentage.

**8. What is the difference between `CRITICAL` and `UNKNOWN`?**

`CRITICAL` means a valid measurement violated a threshold. `UNKNOWN` means the script could not reliably determine the condition.

**9. How do you test a Bash script before deployment?**

I run syntax checks, execute controlled scenarios, inspect stdout and stderr, validate report contents, and run regression tests.

**10. What are the risks of automatically restarting a service when a check fails?**

The failure may be misdiagnosed, the restart may worsen the incident, and the action may interrupt active work.

**11. How would you improve this script for production?**

I would strengthen path safety, publication semantics, service-state handling, metric parsing, regression coverage, and integration with monitoring systems.

**12. What did the incident teach you?**

Collecting information is not the same as evaluating it. A reliable health check must turn measurements into explicit, verifiable decisions.

# 74. Lessons from the Trenches

**1. A script is not reliable just because it runs.**

It must produce correct results under both normal and abnormal conditions.

**2. Collecting metrics is not the same as monitoring.**

Monitoring requires interpretation, thresholds, and explicit status decisions.

**3. Missing information must not be treated as health.**

If a measurement fails, report the uncertainty.

**4. Exit codes are part of the interface.**

Other tools may rely on them to make decisions.

**5. Configuration should be validated data.**

Avoid executing configuration files when a restricted parser will meet the requirement.

**6. Read-only automation is a good starting point.**

Observation and reporting should be trustworthy before remediation is automated.

**7. Test fixtures make operational failures reproducible.**

You can simulate a nearly full filesystem without risking the host.

**8. Human-readable and machine-readable outputs serve different purposes.**

Operators need clear summaries. Automation needs stable fields and exit codes.

**9. Production reliability requires more than the happy path.**

Invalid input, missing dependencies, malformed metrics, and output failures must be tested.

**10. Your first administration script should establish habits you can reuse.**

Clear interfaces, modular functions, input validation, error handling, test coverage, and documentation are foundational engineering practices.
