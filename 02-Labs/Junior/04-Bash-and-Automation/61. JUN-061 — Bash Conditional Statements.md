## 1. The Production Scenario

It is 08:40 on a Monday morning.

You are a junior Linux engineer supporting a team responsible for deploying a small application.

The deployment pipeline runs a Bash script before starting the application.

The script checks whether the required configuration file exists.

The original implementation looks like this:

```
#!/usr/bin/env bash

if [[ -f /etc/example-app/application.conf ]]; then
    printf 'Configuration found. Deployment can continue.\n'
else
    printf 'Configuration missing.\n'
fi
```

At first glance, this seems reasonable.

However, the deployment fails.

The application starts with an invalid database port and an unsupported environment setting.

You investigate and discover that the configuration file existed, but its contents were invalid.

The script answered only one question:

Does the file exist as a regular file?

It did not answer:

- Is the file readable?
- Does it contain the required settings?
- Are those settings valid?
- Is the selected deployment environment supported?
- Is the application port within the accepted range?
- Does the application have enough available disk space?
- Should the deployment continue or stop?

The deployment script treated one successful condition as proof that the entire configuration was valid.

That assumption was incorrect.

This is a fictional incident created for training. You will reproduce the failure and investigate it using disposable files in your own workspace.

### 1.1 Your mission

You have been assigned to build a Bash preflight checker that evaluates multiple conditions before an application deployment.

Your checker must distinguish:

1. A configuration file that exists and contains valid settings.
2. A missing configuration file.
3. An unreadable configuration file.
4. An empty configuration file.
5. A configuration with missing required values.
6. An unsupported environment.
7. An invalid application port.
8. A valid configuration with insufficient available disk space.
9. A configuration with duplicate or unexpected keys.
10. An operational failure that prevents the checks from completing.

Your final script will not deploy an application.

It will evaluate whether the supplied training configuration satisfies a documented set of preflight requirements.

### 1.2 Why this matters in production

Conditional statements control decisions in almost every operational Bash script.

Examples include:

- Checking prerequisites before deployment.
- Verifying that a backup source exists.
- Rejecting invalid configuration.
- Checking whether a service is active.
- Testing whether a command succeeded.
- Selecting behavior based on an environment.
- Detecting low disk space.
- Preventing unsafe maintenance operations.
- Validating CI/CD inputs.
- Deciding whether automation should continue.

A condition that checks the wrong property can be more dangerous than a condition that is missing entirely.

# Part II — How Bash Makes Decisions

## 6. Understanding Exit Statuses

Before writing conditional statements, you must understand how Bash decides whether a command succeeded.

Linux commands return an exit status.

By convention:

| Exit status | Meaning                                 |
| ----------- | --------------------------------------- |
| 0           | Success                                 |
| Nonzero     | Failure or another documented condition |

The exact meaning of a nonzero status depends on the command.

For example, `grep` commonly uses:

- `0` when a match is found.
- `1` when no match is found.
- `2` for an error.

A nonzero result does not always mean something unexpected happened.

Sometimes it represents an ordinary negative answer.

### Exercise 1 — Inspect a Successful Command

Run:

```
true

printf 'Exit status: %d\n' "$?"
```

Expected:

```
Exit status: 0
```

Now:

```
false

printf 'Exit status: %d\n' "$?"
```

Expected:

```
Exit status: 1
```

### Why this matters

Bash conditionals evaluate command statuses, not English words such as `true` or `false`.

The commands `true` and `false` are simply convenient commands that return known statuses.

### Exercise 2 — Test a Real Command

```

```

Engineering lesson: A conditional is a decision based on the result of a command or expression.

## 7. The if Statement

The basic syntax is:

```
if command_or_condition; then
    commands_if_successful
fi
```

The condition is evaluated first.

If its exit status is zero, Bash executes the commands inside the `then` branch.

### Exercise 3 — Your First Conditional

Create:

```
cat > scripts/01-basic-if.sh <<'EOF'
#!/usr/bin/env bash

service="sample-api"

if [[ "$service" == "sample-api" ]]; then
    printf 'The expected service was selected.\n'
fi
EOF
```

Validate:

```
bash -n scripts/01-basic-if.sh
```

Run:

```
bash scripts/01-basic-if.sh
```

Expected:

```
The expected service was selected.
```

### Change the condition

Edit the script:

```
nano scripts/01-basic-if.sh
```

Change:

```
service="sample-api"
```

to:

```
service="billing-worker"
```

Run it again.

Expected: no output.

The condition was false, so the `then` branch did not execute.

### What does this prove?

The script can execute a block of commands conditionally.

### What does it not prove?

It does not establish whether the service exists or is running.

## 8. The if...else Statement

An `else` branch handles the situation where the condition does not succeed.

Syntax:

```
if condition; then
    commands_if_true
else
    commands_if_false
fi
```

### Exercise 4 — Check an Environment

Create:

```
cat > scripts/02-if-else.sh <<'EOF'
#!/usr/bin/env bash

environment="staging"

if [[ "$environment" == "production" ]]; then
    printf 'Production environment selected.\n'
else
    printf 'Non-production environment selected.\n'
fi
EOF
```

Run:

```
bash scripts/02-if-else.sh
```

Expected:

```
Non-production environment selected.
```

Now change:

```
environment="production"
```

Run again.

Expected:

```
Production environment selected.
```

### Production connection

An environment decision can determine whether automation requires additional checks.

However, a production safety check should never rely solely on a freely editable variable without validating its source.

## 9. The if...elif...else Statement

Use `elif` when you need to evaluate multiple conditions in order.

Syntax:

```
if condition_one; then
    action_one
elif condition_two; then
    action_two
else
    fallback_action
fi
```

Only the first successful branch executes.

### Exercise 5 — Classify Disk Usage

Create:

```
cat > scripts/03-elif.sh <<'EOF'
#!/usr/bin/env bash

usage=82

if (( usage >= 90 )); then
    printf 'CRITICAL: Disk usage is high.\n'
elif (( usage >= 75 )); then
    printf 'WARNING: Disk usage is elevated.\n'
else
    printf 'OK: Disk usage is within the configured threshold.\n'
fi
EOF
```

Run:

```
bash scripts/03-elif.sh
```

Expected:

```
WARNING: Disk usage is elevated.
```

### Test other values

Change `usage` to:

```
usage=95
```

Expected:

```
CRITICAL: Disk usage is high.
```

Change it to:

```
usage=40
```

Expected:

```
OK: Disk usage is within the configured threshold.
```

### Why ordering matters

Consider:

```
if (( usage >= 75 )); then
    printf 'WARNING\n'
elif (( usage >= 90 )); then
    printf 'CRITICAL\n'
fi
```

For a value of 95, the first condition succeeds.

The critical branch is never reached.

Checkpoint: You understand that condition ordering affects the final decision.

# Part III — Comparing Values

## 10. String Comparisons

Bash provides string comparison operators.

| Operator | Meaning                                       |
| -------- | --------------------------------------------- |
| `==`     | Strings are equal                             |
| `!=`     | Strings are different                         |
| `-z`     | String is empty                               |
| `-n`     | String is not empty                           |
| `<`      | Lexicographically less than inside `[[ ]]`    |
| `>`      | Lexicographically greater than inside `[[ ]]` |

For this lab, use `[[ ]]` for Bash string tests.

### Exercise 7 — Detect Empty Values

```
service=""

    printf 'ERROR: Service name is empty.\n'

fi
```

### Exercise 8 — Detect Nonempty Values

```
service="billing-worker"

if [[ -n "$service" ]]; then
    printf 'Service value supplied.\n'
fi
```

Expected:

```
Service value supplied.
```

### Important distinction

An empty string and an unset variable are not always equivalent.

With `set -u`, referencing an unset variable can terminate the script.

You can safely provide a fallback:

```
service="${service:-}"
```

Or test whether a variable is set:

```
if [[ -v service ]]; then
    printf 'Variable is set.\n'
fi
```

## 11. Integer Comparisons

Bash supports numeric comparisons using arithmetic contexts.

Example:

```
if (( count > 10 )); then
    printf 'Count exceeds ten.\n'
fi
```

Traditional numeric test operators include:

| Operator | Meaning               |
| -------- | --------------------- |
| `-eq`    | Equal                 |
| `-ne`    | Not equal             |
| `-gt`    | Greater than          |
| `-ge`    | Greater than or equal |
| `-lt`    | Less than             |
| `-le`    | Less than or equal    |

Example:

```
if [[ "$count" -gt 10 ]]; then
    printf 'Count exceeds ten.\n'
fi
```

### Exercise 9 — Validate a Port Range

Create:

```
cat > scripts/04-port-check.sh <<'EOF'
#!/usr/bin/env bash

port="8080"

if [[ ! "$port" =~ ^[0-9]+$ ]]; then
    printf 'ERROR: Port must contain digits only.\n' >&2
    exit 2
fi

if (( 10#$port >= 1 && 10#$port <= 65535 )); then
    printf 'Port is within the valid TCP/UDP port-number range.\n'
else
    printf 'ERROR: Port is outside the accepted range.\n' >&2
    exit 2
fi
EOF
```

Run:

```
bash scripts/04-port-check.sh
```

Expected:

```
Port is within the valid TCP/UDP port-number range.
```

### Why use `10#`?

Bash arithmetic can interpret some numbers beginning with zero as octal.

For example, a value such as `08` is not valid octal notation.

The `10#` prefix tells Bash to interpret the value in base 10.

### Important limitation

For extremely large or malicious numeric strings, Bash arithmetic can overflow or behave unexpectedly.

The final checker will validate the length and structure of the port before converting it.

### Negative tests

Change the port to each of these values:

| Input   | Expected              |
| ------- | --------------------- |
| `8080`  | Valid                 |
| `443`   | Valid                 |
| `0`     | Invalid               |
| `65536` | Invalid               |
| `abc`   | Invalid               |
| `8080x` | Invalid               |
| `00080` | Valid numeric port 80 |

## 12. String Comparison Is Not Numeric Comparison

Consider:

```
first="9"
second="10"
```

This is a string comparison:

```
[[ "$first" > "$second" ]]
```

Lexicographically, `"9"` sorts after `"10"`.

That is not the same as numeric ordering.

For numeric comparisons, use:

```
(( first > second ))
```

Expected: false.

### Exercise 10 — Demonstrate the Difference

```
first=9
second=10

if [[ "$first" > "$second" ]]; then
    printf 'String comparison: first is greater.\n'
else
    printf 'String comparison: first is not greater.\n'
fi

if (( first > second )); then
    printf 'Numeric comparison: first is greater.\n'
else
    printf 'Numeric comparison: first is not greater.\n'
fi
```

Expected:

```
String comparison: first is greater.
Numeric comparison: first is not greater.
```

Engineering lesson: Choosing the wrong comparison operator can produce a valid Bash execution with an incorrect operational decision.

## 17. Short-Circuit Evaluation

Bash evaluates `&&` and `||` command lists from left to right.

For:

```
command_one && command_two
```

The second command runs only if the first succeeds.

For:

```
command_one || command_two
```

The second command runs only if the first fails.

### Exercise 18 — Observe Short-Circuit Behavior

Run:

```
false && printf 'This will not run.\n'
```

Expected: no output.

Now:

```
false || printf 'Fallback executed.\n'
```

Expected:

```
Fallback executed.
```

### Production caution

Avoid replacing every `if` statement with complicated `&&` and `||` chains.

This pattern can be misleading:

```
condition && action_one || action_two
```

If `action_one` fails, `action_two` executes even when the original condition was true.

Use a full `if` statement when you need clear branching semantics.

# Part VI — Nested Conditions and case

## 18. Nested if Statements

A nested condition is an `if` statement inside another `if` statement.

### Exercise 19 — Deployment Approval

Create:

```
cat > scripts/06-nested-if.sh <<'EOF'
#!/usr/bin/env bash

environment="production"
config_valid="yes"
approval="no"

if [[ "$environment" == "production" ]]; then
    if [[ "$config_valid" == "yes" ]]; then
        if [[ "$approval" == "yes" ]]; then
            printf 'Production checks passed.\n'
        else
            printf 'ERROR: Approval missing.\n' >&2
        fi
    else
        printf 'ERROR: Configuration invalid.\n' >&2
    fi
else
    printf 'Non-production environment selected.\n'
fi
EOF
```

Run:

```
bash scripts/06-nested-if.sh
```

Expected:

```
ERROR: Approval missing.
```

### What this teaches

Nested conditions allow dependent decisions.

However, excessive nesting makes scripts harder to read.

A more maintainable design often uses early validation and returns immediately when a requirement fails.

## 19. Understanding case

The `case` statement selects behavior based on a string pattern.

Syntax:

```
case "$value" in
    pattern_one)
        commands
        ;;
    pattern_two)
        commands
        ;;
    *)
        fallback
        ;;
esac
```

### Exercise 20 — Environment Selection

Create:

```
cat > scripts/07-case.sh <<'EOF'
#!/usr/bin/env bash

environment="${1:-}"

case "$environment" in
    development)
        printf 'Development environment selected.\n'
        ;;
    staging)
        printf 'Staging environment selected.\n'
        ;;
    production)
        printf 'Production environment selected.\n'
        ;;
    *)
        printf 'ERROR: Unsupported environment.\n' >&2
        exit 2
        ;;
esac
EOF
```

Run:

```
bash scripts/07-case.sh staging
```

Expected:

```
Staging environment selected.
```

Test:

```
bash scripts/07-case.sh testing

status=$?
printf 'Exit status: %d\n' "$status"
```

Expected:

```
ERROR: Unsupported environment.
Exit status: 2
```

### Why case is useful

`case` is particularly suitable for:

- Environment selection.
- Command-line options.
- Application modes.
- Supported action names.
- Explicit state classification.

It avoids long chains of string comparisons when one value can match several alternatives.

# Part VII — Common Conditional Mistakes

## 20. Mistake 1 — Missing Spaces Around Brackets

Incorrect:

```
if ["$value" == "yes"]; then
    printf 'Accepted\n'
fi
```

Correct:

```
if [[ "$value" == "yes" ]]; then
    printf 'Accepted\n'
fi
```

The spaces are part of the shell syntax.

## 21. Mistake 2 — Using String Operators for Numbers

Incorrect:

```
if [[ "$port" > "1024" ]]; then
    printf 'Port accepted.\n'
fi
```

This performs lexicographic comparison.

Correct, after validating numeric input:

```
if (( port > 1024 )); then
    printf 'Port accepted.\n'
fi
```

## 22. Mistake 3 — Treating File Existence as Validity

Incorrect:

```
if [[ -f "$config" ]]; then
    printf 'Configuration valid.\n'
fi
```

Correct reasoning:

1. Check file type.
2. Check readability.
3. Check whether it contains data.
4. Parse expected fields.
5. Validate each value.
6. Reject unknown or duplicate keys.
7. Return a meaningful status.

## 23. Mistake 4 — Ignoring Command Failure

Incorrect:

```
df -Pk "$path" > reports/disk.txt

printf 'Disk check completed.\n'
```

The script prints the completion message regardless of whether `df` succeeded.

Better:

```
if df -Pk "$path" > reports/disk.txt; then
    printf 'Disk inspection completed.\n'
else
    printf 'ERROR: Disk inspection failed.\n' >&2
    exit 3
fi
```

## 24. Mistake 5 — Assuming Every Nonzero Status Means the Same Thing

Consider:

```
grep -q 'ERROR' fixtures/application.log
```

Possible outcomes:

- Match found.
- No match found.
- Search failed.

A robust script must interpret the command's documented statuses.

### Exercise 21 — Handle grep Status Correctly

Create:

```
cat > scripts/08-grep-status.sh <<'EOF'
#!/usr/bin/env bash

file="fixtures/basic.conf"

grep -q '^APP_ENV=' "$file"
status=$?

case "$status" in
    0)
        printf 'Required setting found.\n'
        ;;
    1)
        printf 'Required setting not found.\n'
        ;;
    *)
        printf 'ERROR: Search operation failed.\n' >&2
        exit 3
        ;;
esac
EOF
```

Run:

```
bash scripts/08-grep-status.sh
```

Expected:

```
Required setting found.
```

## 27. Write the Final Script

Create the file:

```
cat > scripts/application-preflight.sh <<'BASH'
#!/usr/bin/env bash

# VERIQTA Linux World
# JUN-061 — Bash Conditional Statements
#
# Training-only application preflight checker.
# Configuration is parsed as data, never executed.

set -u

CONFIG_FILE=""
CHECK_PATH=""

APP_NAME=""
APP_ENV=""
APP_PORT=""
MIN_FREE_MB=""

declare -A SEEN_KEYS=()

error() {
    printf 'ERROR: %s\n' "$1" >&2
}

info() {
    printf 'INFO: %s\n' "$1"
}

usage() {
    cat <<'EOF'
Usage:
  application-preflight.sh --config FILE --check-path DIRECTORY
  application-preflight.sh --help

Exit statuses:
  0  All checks passed
  2  Invalid arguments
  3  Operational failure
  4  Invalid configuration
  5  Insufficient disk space
EOF
}

parse_arguments() {
    while (( $# > 0 )); do
        case "$1" in
            --config)
                if (( $# < 2 )) || [[ -z "$2" ]]; then
                    error "--config requires a path"
                    return 2
                fi

                if [[ -n "$CONFIG_FILE" ]]; then
                    error "--config specified more than once"
                    return 2
                fi

                CONFIG_FILE="$2"
                shift 2
                ;;

            --check-path)
                if (( $# < 2 )) || [[ -z "$2" ]]; then
                    error "--check-path requires a directory"
                    return 2
                fi

                if [[ -n "$CHECK_PATH" ]]; then
                    error "--check-path specified more than once"
                    return 2
                fi

                CHECK_PATH="$2"
                shift 2
                ;;

            --help)
                usage
                exit 0
                ;;

            *)
                error "Unknown argument: $1"
                return 2
                ;;
        esac
    done

    if [[ -z "$CONFIG_FILE" || -z "$CHECK_PATH" ]]; then
        error "Both --config and --check-path are required"
        return 2
    fi

    return 0
}

validate_input_paths() {
    if [[ ! -f "$CONFIG_FILE" ]]; then
        error "Configuration is missing or not a regular file"
        return 3
    fi

    if [[ ! -r "$CONFIG_FILE" ]]; then
        error "Configuration is not readable"
        return 3
    fi

    if [[ ! -d "$CHECK_PATH" ]]; then
        error "Disk check path is not a directory"
        return 3
    fi

    if [[ ! -x "$CHECK_PATH" ]]; then
        error "Disk check path is not searchable"
        return 3
    fi

    return 0
}

parse_configuration() {
    local line=""
    local key=""
    local value=""
    local line_number=0

    if ! exec 3< "$CONFIG_FILE"; then
        error "Unable to open configuration"
        return 3
    fi

    while IFS= read -r line <&3 || [[ -n "$line" ]]; do
        line_number=$((line_number + 1))

        if [[ -z "$line" ]]; then
            continue
        fi

        if [[ "$line" == \#* ]]; then
            continue
        fi

        if [[ "$line" != *=* ]]; then
            error "Line $line_number: Missing equals sign"
            exec 3<&-
            return 4
        fi

        key="${line%%=*}"
        value="${line#*=}"

        case "$key" in
            APP_NAME|APP_ENV|APP_PORT|MIN_FREE_MB)
                ;;
            *)
                error "Line $line_number: Unknown key"
                exec 3<&-
                return 4
                ;;
        esac

        if [[ -v SEEN_KEYS[$key] ]]; then
            error "Line $line_number: Duplicate key $key"
            exec 3<&-
            return 4
        fi

        SEEN_KEYS["$key"]=1

        if [[ -z "$value" ]]; then
            error "Line $line_number: Empty value for $key"
            exec 3<&-
            return 4
        fi

        case "$key" in
            APP_NAME)
                APP_NAME="$value"
                ;;
            APP_ENV)
                APP_ENV="$value"
                ;;
            APP_PORT)
                APP_PORT="$value"
                ;;
            MIN_FREE_MB)
                MIN_FREE_MB="$value"
                ;;
        esac
    done

    exec 3<&-

    return 0
}

validate_required_keys() {
    local key=""

    for key in APP_NAME APP_ENV APP_PORT MIN_FREE_MB; do
        if [[ ! -v SEEN_KEYS[$key] ]]; then
            error "Missing required key: $key"
            return 4
        fi
    done

    return 0
}

validate_app_name() {
    if [[ ! "$APP_NAME" =~ ^[a-z][a-z0-9-]*$ ]]; then
        error "APP_NAME contains unsupported characters"
        return 4
    fi

    return 0
}

validate_environment() {
    case "$APP_ENV" in
        development|staging|production)
            return 0
            ;;
        *)
            error "Unsupported APP_ENV: $APP_ENV"
            return 4
            ;;
    esac
}

validate_decimal() {
    local value="$1"
    local maximum_digits="$2"

    if [[ ! "$value" =~ ^[0-9]+$ ]]; then
        return 1
    fi

    if (( ${#value} > maximum_digits )); then
        return 1
    fi

    return 0
}

validate_port() {
    if ! validate_decimal "$APP_PORT" 5; then
        error "APP_PORT must be a decimal integer of at most five digits"
        return 4
    fi

    local port_number=$((10#$APP_PORT))

    if (( port_number < 1 || port_number > 65535 )); then
        error "APP_PORT must be between 1 and 65535"
        return 4
    fi

    APP_PORT="$port_number"

    return 0
}

validate_disk_threshold() {
    if ! validate_decimal "$MIN_FREE_MB" 7; then
        error "MIN_FREE_MB must be a decimal integer of at most seven digits"
        return 4
    fi

    local threshold=$((10#$MIN_FREE_MB))

    if (( threshold > 1000000 )); then
        error "MIN_FREE_MB exceeds the supported maximum"
        return 4
    fi

    MIN_FREE_MB="$threshold"

    return 0
}

validate_configuration() {
    validate_required_keys || return 4
    validate_app_name || return 4
    validate_environment || return 4
    validate_port || return 4
    validate_disk_threshold || return 4

    return 0
}

check_disk_space() {
    local available_kib=""
    local available_mib=""

    if ! available_kib="$(
        df -Pk -- "$CHECK_PATH" |
        awk 'NR == 2 { print $4 }'
    )"; then
        error "Disk inspection command failed"
        return 3
    fi

    if [[ ! "$available_kib" =~ ^[0-9]+$ ]]; then
        error "Unable to obtain valid disk capacity"
        return 3
    fi

    available_mib=$((available_kib / 1024))

    info "Available disk space: ${available_mib} MiB"
    info "Required disk space: ${MIN_FREE_MB} MiB"

    if (( available_mib < MIN_FREE_MB )); then
        error "Insufficient available disk space"
        return 5
    fi

    return 0
}

print_summary() {
    printf '\n'
    printf 'VERIQTA Application Preflight\n'
    printf '============================\n'
    printf 'Application: %s\n' "$APP_NAME"
    printf 'Environment: %s\n' "$APP_ENV"
    printf 'Port: %s\n' "$APP_PORT"
    printf 'Disk requirement: %s MiB\n' "$MIN_FREE_MB"
    printf 'Result: PASS\n'
}

main() {
    local status=0

    parse_arguments "$@" || return $?

    validate_input_paths || return 3

    parse_configuration
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    validate_configuration || return 4

    check_disk_space
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    print_summary

    return 0
}

main "$@"
BASH
```

### Important implementation notes

This script is intentionally designed for controlled, junior-level training.

Its key teaching purpose is conditional decision-making.

It does not execute configuration as Bash code.

It does not deploy an application.

It does not modify the filesystem beyond reading training input.

The disk check uses `df` to inspect available capacity, and the resulting decision is based on the reported available space.

Limitations: The parser does not fully distinguish every possible low-level read error from EOF. The disk-inspection pipeline also relies on the expected `df` output format and does not independently verify every pipeline stage. These limitations matter before adapting this training script for production. You will investigate the relevant failure-handling principles in this lab.

| Symptom                                 | Investigate                                  |
| --------------------------------------- | -------------------------------------------- |
| `syntax error near unexpected token`    | Missing spaces, brackets, `then`, or `fi`    |
| Condition never succeeds                | Wrong operator or unexpected variable value  |
| Numeric comparison behaves strangely    | String comparison used instead of arithmetic |
| Empty value accepted                    | Missing `-z` validation                      |
| Unsupported environment accepted        | Missing fallback branch                      |
| Critical condition reported as warning  | Branch ordering                              |
| Missing file reported as empty          | Overly broad `-s` test                       |
| Script continues after failure          | Missing status check or return               |
| File exists but application fails       | Content validation missing                   |
| Port `08` fails arithmetic              | Leading-zero interpretation                  |
| Unknown key accepted                    | Parser lacks key allowlist                   |
| Duplicate key silently overwrites value | Duplicate detection missing                  |
| Report says PASS but deployment fails   | Preflight scope insufficient                 |
| Wrong exit status                       | Return-code contract or status propagation   |

# Part XIII — Knowledge Checks

## 47. Twenty-Five Questions and Answers

1\. What is a Bash conditional statement?

A construct that executes commands based on the result of a condition or command.

2\. What exit status normally represents success?

Zero.

3\. What does `if` do?

It evaluates a command or condition and executes a branch when that evaluation succeeds.

4\. What does `else` do?

It provides an alternative branch when the preceding conditions do not succeed.

5\. What does `elif` do?

It evaluates another condition if earlier conditions did not succeed.

6\. What does `fi` mean?

It closes an `if` statement.

7\. What is `[[ ]]`?

A Bash conditional expression construct.

8\. What is `[ ]`?

Traditional test syntax, commonly implemented by the shell's `test` builtin.

9\. What is the difference between `==` and `-eq`?

`==` compares strings in a conditional expression, while `-eq` performs numeric equality comparison.

10\. What does `-z` check?

Whether a string has zero length.

11\. What does `-n` check?

Whether a string has nonzero length.

12\. What does `-f` check?

Whether a path refers to a regular file.

13\. What does `-d` check?

Whether a path refers to a directory.

14\. What does `-r` check?

Whether a file is readable according to the current process's access context.

15\. What does `-s` check?

Whether a file exists and has a size greater than zero.

16\. Why is `-s` insufficient for distinguishing missing and empty files?

Because it is false for both conditions.

17\. What does `&&` do?

It evaluates the next command only when the preceding command succeeds.

18\. What does `||` do?

It evaluates the next command only when the preceding command fails.

19\. What does `!` do?

It negates the success or failure result of a command or condition.

20\. What is short-circuit evaluation?

Evaluation that stops once the result of a logical command list has been determined.

21\. Why does branch order matter?

Because Bash executes the first successful branch and skips the remaining alternatives.

22\. When is `case` useful?

When selecting among multiple supported string values or patterns.

23\. Why validate numeric input before arithmetic?

To reject invalid input and avoid unintended arithmetic interpretation.

24\. Why should configuration files not automatically be sourced?

Because sourcing executes shell syntax contained in the file, which may perform unintended or malicious actions.

25\. Why does a successful preflight not guarantee deployment success?

Because the checker validates only its documented prerequisites, not every runtime dependency or application behavior.

# Part XIV — Interview Preparation

## 48. Twelve Interview Questions with Worked Answers

### Question 1 — Deployment Safety

A deployment script checks whether a configuration file exists and then proceeds. The application fails because the configuration contains an invalid port.

What is the design problem?

Answer: The script validates only file existence, not configuration correctness. It should validate required keys, accepted values, numeric ranges, and operational prerequisites before proceeding.

### Question 2 — Conditional Ordering

A script checks whether disk usage is above 70% before checking whether it is above 90%. A filesystem at 96% is reported as WARNING.

Why?

Answer: The first matching branch executes. The 70% condition matches before the critical threshold is evaluated. The checks should be ordered from highest severity to lowest.

### Question 3 — Numeric Comparison

A script uses:

```
[[ "$usage" > "90" ]]
```

Why might the result be incorrect?

Answer: The expression performs string comparison rather than numeric comparison. After validating numeric input, arithmetic comparison should be used.

### Question 4 — Missing Files

A script uses:

```
[[ ! -s "$file" ]]
```

to determine whether a file is empty.

What is the problem?

Answer: The condition also succeeds when the file is missing. The script must distinguish existence, type, and size.

### Question 5 — Error Handling

A Bash script runs a command and prints SUCCESS without checking its exit status.

What should be changed?

Answer: The script should inspect the command's status and print success only when the required operation succeeds.

### Question 6 — Environment Validation

A deployment tool supports development, staging, and production.

How would you validate the selected environment?

Answer: Use a `case` statement with explicit supported values and a fallback branch that rejects unsupported input.

### Question 7 — Short-Circuit Evaluation

Why is this expression potentially misleading?

```
condition && action_one || action_two
```

Answer: If `action_one` fails, `action_two` executes even when the original condition succeeded. An explicit `if` statement is clearer when selecting between alternatives.

### Question 8 — Configuration Security

Why is parsing a configuration file as data safer than sourcing it?

Answer: Parsing treats the file contents as values to validate. Sourcing executes shell code, which can have unintended effects.

### Question 9 — File Permissions

Does `[[ -r "$file" ]]` guarantee that a later read operation will succeed?

Answer: No. Filesystem state and access conditions may change between the check and the operation. The actual open and read operations must also be checked.

### Question 10 — Exit Status Design

Why should a preflight tool distinguish invalid configuration from operational failure?

Answer: They require different remediation. Invalid configuration may require changing settings, while an operational failure may involve missing files, permissions, or unavailable system resources.

### Question 11 — Production Readiness

A preflight checker returns zero. Does that mean deployment is safe?

Answer: It means the implemented checks passed. Additional deployment authorization, dependency verification, and runtime validation may still be required.

### Question 12 — Troubleshooting

A Bash script produces an unexpected branch result. What should you inspect first?

Answer: Confirm the actual input value, the comparison operator, the condition order, and the status returned by the tested command. Then reproduce the behavior with controlled inputs.

## 53. Final Lessons from the Trenches

Lesson 1 — A condition is only as useful as the question it asks. Checking that a file exists does not establish that its contents are correct.

Lesson 2 — Exit statuses are part of the program interface. Scripts and automation must distinguish successful operations from failure conditions.

Lesson 3 — Comparison operators must match the data type. String comparison and numeric comparison are not interchangeable.

Lesson 4 — Branch order can change operational decisions. A critical condition can be hidden by an earlier, broader condition.

Lesson 5 — Validate before calculating. Numeric input must be checked before it is used in arithmetic expressions.

Lesson 6 — Missing and empty are different states. A monitoring or deployment script should not collapse distinct failure conditions into one misleading result.

Lesson 7 — Short-circuit evaluation is useful but must be understood. Compact command chains can obscure the intended control flow.

Lesson 8 — Configuration is data, not executable code. Validate supported keys and values instead of blindly sourcing configuration.

Lesson 9 — Filesystem checks are not guarantees. A successful preliminary test does not replace checking the actual operation.

Lesson 10 — Failures should stop unsafe progression. A preflight script should not continue when a required condition has failed.

Lesson 11 — Negative testing reveals hidden assumptions. Invalid ports, duplicate keys, missing files, and unsupported environments expose problems that successful-path tests may miss.

Lesson 12 — A successful preflight is not a successful deployment. It establishes only that the implemented prerequisites passed at the time they were checked.
