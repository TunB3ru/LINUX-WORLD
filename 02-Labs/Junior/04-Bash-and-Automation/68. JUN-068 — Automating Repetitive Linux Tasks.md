## 1. Welcome to the Lab

Linux engineers frequently repeat the same operational tasks:

- Checking whether important directories exist.
- Inspecting files for naming or format problems.
- Creating backups before changes.
- Finding old files for review.
- Producing filesystem inventories.
- Validating configuration files.
- Generating routine reports.
- Recording which tasks succeeded or failed.

Performing these tasks manually is sometimes appropriate. But when the same procedure is repeated across many files, environments, or systems, manual execution becomes slower, less consistent, and more difficult to audit.

Automation solves part of that problem.

However, automating a task does not automatically make it safe.

An incorrectly written script can repeat a mistake hundreds of times. A cleanup script can select the wrong files. A backup script can overwrite its previous backup. A batch operation can silently skip failures and still report success.

In this lab, you will progress from simple repetitive shell commands to a structured, reusable automation utility with dry-run behavior, validation, reporting, safe file handling, and regression tests.

You will learn to think beyond:

> “How do I make Bash repeat this command?”

You will instead ask:

> “How do I make this repeated operation predictable, safe, observable, recoverable, and easy for another engineer to understand?”

That distinction is central to professional Linux administration.

# Part 3 — Understand Repetitive Tasks

## 10. What Makes a Task a Good Automation Candidate?

A task is often suitable for automation when it has:

- Clearly defined inputs.
- Consistent processing rules.
- Predictable outputs.
- A repeatable execution sequence.
- Measurable success conditions.
- Well-understood failure behavior.

Examples include:

| Task                           | Automation suitability   | Main concern                     |
| ------------------------------ | ------------------------ | -------------------------------- |
| Generate a directory inventory | High                     | Filenames and permissions        |
| Validate configuration syntax  | High                     | Correct validation rules         |
| Check disk usage               | High                     | Reliable measurement             |
| Archive approved log files     | Moderate to high         | Data integrity and retention     |
| Delete old files               | Higher risk              | Incorrect selection and recovery |
| Restart a production database  | Requires controls        | Availability and dependencies    |
| Rotate credentials             | Requires strong controls | Secrets and access management    |
| Approve a security exception   | Usually human decision   | Risk and accountability          |

A good engineer does not automate every action merely because automation is possible.

## 11. Automation Versus Scheduling

These concepts are related but different.

Automation defines how work is performed without repeated manual steps.

Scheduling defines when automated work begins.

For example:

```
bash scripts/inventory.sh
```

is automated processing, even when you launch it manually.

A cron entry such as:

```
0 2 * * * /absolute/path/to/inventory.sh
```

adds scheduling.

This lab focuses on designing reliable automation.

You learned cron in JUN-067. Do not schedule the final project until its behavior has been independently validated.

# Part 5 — Safe Filename Processing

## 16. Why `for file in $(find ...)` Is Unsafe

Consider:

```
for file in $(find fixtures/source -type f); do
    printf 'File: %s\n' "$file"
done
```

This is a deliberately unsafe example.

The shell performs command substitution and word splitting.

A filename such as:

```
payment worker.log
```

can be split into separate words.

This means the loop may process nonexistent paths or unintended values.

Do not use this pattern in the final project.

## 17. Use Null-Delimited Filenames

The safer approach is:

```
while IFS= read -r -d '' file; do
    printf 'File: %s\n' "$file"
done < <(
    find fixtures/source -type f -print0
)
```

Here:

- `find -print0` separates paths using a null byte.
- `IFS=` prevents whitespace trimming.
- `read -r` preserves backslashes.
- `read -d ''` reads until the null delimiter.
- Quoted `"$file"` preserves the filename as one argument.

This pattern handles spaces, tabs, and newline characters in filenames.

Important limitation: When `find` runs inside process substitution, its exit status is not automatically propagated by the `while` loop. A production implementation must check traversal failures separately or use a design that preserves the producer's status.

## 18. Create a Filename-Safe Inventory

Run:

```
cat > scripts/02-safe-inventory.sh <<'BASH'
#!/usr/bin/env bash

set -u

ROOT="${1:-fixtures/source}"

if [[ ! -d "$ROOT" ]]; then
    printf 'ERROR: Directory not found: %s\n' "$ROOT" >&2
    exit 2
fi

count=0

while IFS= read -r -d '' file; do
    count=$((count + 1))
    printf 'FILE[%d]=%q\n' "$count" "$file"
done < <(
    find "$ROOT" -type f -print0
)

printf 'TOTAL=%d\n' "$count"
BASH
```

Run:

```
bash scripts/02-safe-inventory.sh
```

Expected:

```
TOTAL=7
```

The preceding file order may differ because `find` does not guarantee a portable traversal order.

The `%q` format makes unusual filenames easier to inspect in Bash-oriented diagnostics.

# Part 6 — Automation with Arrays and Functions

## 19. Use Arrays for Collections

Create:

```
cat > scripts/03-array-processing.sh <<'BASH'
#!/usr/bin/env bash

set -u

directories=(
    "fixtures/source/config"
    "fixtures/source/logs"
    "fixtures/source/reports"
)

for directory in "${directories[@]}"; do
    printf 'Checking: %s\n' "$directory"

    if [[ -d "$directory" ]]; then
        printf 'PASS: Directory exists\n'
    else
        printf 'FAIL: Directory missing\n'
    fi
done
BASH
```

Run:

```
bash scripts/03-array-processing.sh
```

Expected: all three directories pass.

### Why arrays matter

The expression:

```
"${directories[@]}"
```

preserves each array element as a separate argument.

Do not replace it with unquoted array expansion.

## 20. Refactor Repeated Logic into Functions

Create:

```
cat > scripts/04-functions.sh <<'BASH'
#!/usr/bin/env bash

set -u

check_directory() {
    local directory="$1"

    if [[ -d "$directory" ]]; then
        printf 'PASS: %s\n' "$directory"
        return 0
    fi

    printf 'FAIL: %s\n' "$directory" >&2
    return 1
}

main() {
    local failures=0
    local directory=""

    for directory in \
        fixtures/source/config \
        fixtures/source/logs \
        fixtures/source/reports
    do
        if ! check_directory "$directory"; then
            failures=$((failures + 1))
        fi
    done

    printf 'Failures: %d\n' "$failures"

    if (( failures > 0 )); then
        return 1
    fi

    return 0
}

main "$@"
BASH
```

Run:

```
bash scripts/04-functions.sh
```

Expected:

```
Failures: 0
```

This script is easier to extend because directory validation lives in one function.

# Part 7 — Define the Automation Safety Model

## 21. Preview Before Changing Anything

A safe automation workflow often has two distinct phases.

### Phase A — Discovery

Identify candidate files.

Produce a report.

Do not modify them.

### Phase B — Execution

Apply an explicitly approved operation to the selected files.

Record the outcome.

For this lab, you will implement:

```
Discovery → Validation → Preview → Archive Copy → Verification → Report
```

You will not implement deletion.

## 22. Define Dry-Run Semantics

A proper dry run should answer:

> What would this automation attempt to do if execution were enabled?

It must not perform the controlled change.

For your final project:

```
--dry-run
```

will:

- Inspect candidate files.
- Validate the requested action.
- Display the intended archive destinations.
- Produce a preview report.

It will not copy source files into the archive.

A dry run may still create diagnostic or preview reports. This is acceptable if clearly documented.

## 23. Define the Exit-Code Contract

Use these exit codes:

| Code | Meaning                                           |
| ---- | ------------------------------------------------- |
| `0`  | Requested operation completed successfully        |
| `2`  | Invalid command-line arguments                    |
| `3`  | Operational or filesystem error                   |
| `4`  | One or more configuration validation failures     |
| `5`  | One or more archive-copy or verification failures |
| `6`  | No matching candidate files                       |
| `75` | Another execution holds the lock                  |

Exit codes are part of the script's interface.

A calling engineer or scheduler should not need to parse human-readable text to determine whether the operation succeeded.

## 26. Define the Configuration Format

For this exercise, each application configuration file must contain exactly these keys:

```
APP_NAME
APP_ENV
APP_PORT
```

Example:

```
APP_NAME=orders
APP_ENV=production
APP_PORT=8080
```

The validator will enforce:

- Each required key appears exactly once.
- Unknown keys are rejected.
- Duplicate keys are rejected.
- Blank lines and lines beginning with `#` are allowed.
- `APP_NAME` contains lowercase letters, digits, or hyphens, beginning with a lowercase letter.
- `APP_ENV` is `development`, `staging`, or `production`.
- `APP_PORT` is a decimal integer from `1` through `65535`.
- Values must not contain shell commands or substitutions.

These are data files, not shell scripts. Never `source` an untrusted configuration file.

The final program will parse values as text.

# Part 10 — Build the Final Automation Utility

## 30. Implementation Strategy

You will create one Bash program with separate functions for:

1. Command-line parsing.
2. Workspace verification.
3. Report initialization.
4. Inventory generation.
5. Configuration validation.
6. Archive candidate discovery.
7. Dry-run reporting.
8. Safe archive copying.
9. Copy verification.
10. Exit-code handling.

The script will use `flock` to prevent simultaneous runs of the same toolkit.

It will use a dedicated archive directory, and it will refuse to overwrite an existing archive destination.

For safe processing, it will first collect file paths into a null-delimited temporary manifest. This lets it check whether `find` succeeded before acting on the results.

### Deliberate scope restrictions

The final project supports only the lab's controlled fixture tree. It does not accept arbitrary source directories.

The archive operation handles regular `.log` files directly inside `fixtures/source/logs`. It does not recursively archive arbitrary nested paths.

These restrictions make the first implementation easier to reason about and test.

```
    printf 'INFO: %s\n' "$*"
}

parse_arguments() {
    if (( $# == 0 )); then
        usage >&2
        return 2
    fi

    if [[ "$1" == "--help" ]]; then
        if (( $# == 1 )); then
            usage
            return 0
        fi

        error "--help cannot be combined with other arguments"
        return 2
    fi

    MODE="$1"
    shift

    case "$MODE" in
        inventory|validate)
            if (( $# != 0 )); then
                error "$MODE does not accept additional arguments"
                return 2
            fi
            ;;

        archive)
            ACTION=""

            while (( $# > 0 )); do
                case "$1" in
                    --older-than-days)
                        if (( $# < 2 )); then
                            error "Missing age value"
                            return 2
                        fi

                        OLDER_THAN_DAYS="$2"
                        shift 2
                        ;;

                    --dry-run)
                        if [[ -n "$ACTION" ]]; then
                            error "Specify exactly one archive action"
                            return 2
                        fi

                        ACTION="dry-run"
                        shift
                        ;;

                    --apply)
                        if [[ -n "$ACTION" ]]; then
                            error "Specify exactly one archive action"
                            return 2
                        fi

                        ACTION="apply"
                        shift
                        ;;

                    *)
                        error "Unknown archive option: $1"
                        return 2
                        ;;
                esac
            done

            if [[ -z "$ACTION" ]]; then
                error "Archive requires --dry-run or --apply"
                return 2
            fi

            if [[ ! "$OLDER_THAN_DAYS" =~ ^[0-9]+$ ]]; then
                error "Age must contain decimal digits only"
                return 2
            fi

            if (( ${#OLDER_THAN_DAYS} > 4 )); then
                error "Age is too large"
                return 2
            fi

            OLDER_THAN_DAYS=$((10#$OLDER_THAN_DAYS))

            if (( OLDER_THAN_DAYS > 3650 )); then
                error "Age must not exceed 3650 days"
                return 2
            fi
            ;;

        *)
            error "Unknown command: $MODE"
            return 2
            ;;
    esac

    return 0
}

verify_directory() {
    local directory="$1"

    if [[ -L "$directory" ]]; then
        error "Symbolic-link directory rejected: $directory"
        return 3
    fi

    if [[ ! -d "$directory" ||
          ! -r "$directory" ||
          ! -x "$directory" ]]; then
        error "Required directory unavailable: $directory"
        return 3
    fi

    return 0
}

verify_workspace() {
    local directory=""

    for directory in \
        "$SOURCE_ROOT" \
        "$CONFIG_DIR" \
        "$LOG_DIR" \
        "$OUTPUT_ROOT" \
        "$INVENTORY_DIR" \
        "$ARCHIVE_DIR" \
        "$REPORT_DIR" \
        "$STATE_DIR"
    do
        verify_directory "$directory" || return 3
    done

    for directory in \
        "$INVENTORY_DIR" \
        "$ARCHIVE_DIR" \
        "$REPORT_DIR" \
        "$STATE_DIR"
    do
        if [[ ! -w "$directory" ]]; then
            error "Output directory is not writable: $directory"
            return 3
        fi
    done

    return 0
}

acquire_lock() {
    if [[ -L "$LOCK_FILE" ]]; then
        error "Symbolic-link lock file rejected"
        return 3
    fi

    if ! exec 9> "$LOCK_FILE"; then
        error "Unable to open lock file"
        return 3
    fi

    if ! flock -n 9; then
        error "Another maintenance execution is active"
        return 75
    fi

    return 0
}

initialize_run() {
    local timestamp=""

    timestamp="$(date -u '+%Y%m%dT%H%M%SZ')" || return 3

    RUN_ID="${timestamp}-$$"

    REPORT_FILE="$REPORT_DIR/${MODE}-${RUN_ID}.tsv"

    if [[ -e "$REPORT_FILE" || -L "$REPORT_FILE" ]]; then
        error "Report filename collision"
        return 3
    fi

    if ! (
        set -C
        printf 'RESULT\tPATH\tDETAIL\n' > "$REPORT_FILE"
    ); then
        error "Unable to initialize report"
        return 3
    fi

    return 0
}

record_result() {
    local result="$1"
    local path="$2"
    local detail="$3"

    # Report fields are kept on one line.
    # The lab rejects newline/tab-bearing paths before recording.
    printf '%s\t%s\t%s\n' \
        "$result" \
        "$path" \
        "$detail" >> "$REPORT_FILE"
}

validate_report_path() {
    local path="$1"

    if [[ "$path" == *$'\n'* ||
          "$path" == *$'\r'* ||
          "$path" == *$'\t'* ]]; then
        error "Unsupported control character in filename"
        return 3
    fi

    return 0
}

make_manifest() {
    local source_directory="$1"
    local name_pattern="$2"
    local max_depth="$3"

    MANIFEST_FILE="$(mktemp "$STATE_DIR/manifest.XXXXXXXX")" ||
        return 3

    if ! find "$source_directory" \
        -maxdepth "$max_depth" \
        -type f \
        -name "$name_pattern" \
        -print0 > "$MANIFEST_FILE"; then
        error "File discovery failed"
        return 3
    fi

    return 0
}

remove_manifest() {
    if [[ -n "$MANIFEST_FILE" &&
          -f "$MANIFEST_FILE" &&
          ! -L "$MANIFEST_FILE" ]]; then
        rm -f -- "$MANIFEST_FILE"
    fi

    MANIFEST_FILE=""
}

print_summary() {
    printf '%s\n' '----------------------------------------'
    printf 'Mode: %s\n' "$MODE"
    printf 'Processed: %d\n' "$PROCESSED"
    printf 'Passed: %d\n' "$PASSED"
    printf 'Failed: %d\n' "$FAILED"
    printf 'Candidates: %d\n' "$CANDIDATES"
    printf 'Report: %s\n' "$REPORT_FILE"
}

run_inventory() {
    local file=""
    local relative=""
    local size=""

    make_manifest "$SOURCE_ROOT" "*" 10 || return 3

    while IFS= read -r -d '' file; do
        PROCESSED=$((PROCESSED + 1))

        relative="${file#"$SOURCE_ROOT"/}"

        if ! validate_report_path "$relative"; then
            FAILED=$((FAILED + 1))
            continue
        fi

        if ! size="$(stat -c '%s' -- "$file")"; then
            FAILED=$((FAILED + 1))

            record_result "FAIL" "$relative" \
                "Unable to inspect file" || return 3

            continue
        fi

        if ! record_result "PASS" "$relative" \
            "size_bytes=$size"; then
            return 3
        fi

        PASSED=$((PASSED + 1))
    done < "$MANIFEST_FILE"

    remove_manifest

    print_summary

    if (( FAILED > 0 )); then
        return 3
    fi

    return 0
}

validate_config_file() {
    local file="$1"
    local line=""
    local key=""
    local value=""
    local line_number=0
    local name=""
    local environment=""
    local port=""

    local seen_name=0
    local seen_environment=0
    local seen_port=0

    if [[ -L "$file" || ! -f "$file" || ! -r "$file" ]]; then
        return 1
    fi

    while IFS= read -r line || [[ -n "$line" ]]; do
        line_number=$((line_number + 1))

        if [[ -z "$line" || "$line" == \#* ]]; then
            continue
        fi

        if [[ "$line" != *=* ]]; then
            return 1
        fi

        key="${line%%=*}"
        value="${line#*=}"

        case "$key" in
            APP_NAME)
                if (( seen_name != 0 )); then
                    return 1
                fi

                seen_name=1
                name="$value"
                ;;

            APP_ENV)
                if (( seen_environment != 0 )); then
                    return 1
                fi

                seen_environment=1
                environment="$value"
                ;;

            APP_PORT)
                if (( seen_port != 0 )); then
                    return 1
                fi

                seen_port=1
                port="$value"
                ;;

            *)
                return 1
                ;;
        esac
    done < "$file"

    if (( seen_name != 1 ||
          seen_environment != 1 ||
          seen_port != 1 )); then
        return 1
    fi

    if [[ ! "$name" =~ ^[a-z][a-z0-9-]*$ ]]; then
        return 1
    fi

    case "$environment" in
        development|staging|production)
            ;;
        *)
            return 1
            ;;
    esac

    if [[ ! "$port" =~ ^[0-9]+$ ]]; then
        return 1
    fi

    if (( ${#port} > 5 )); then
        return 1
    fi

    port=$((10#$port))

    if (( port < 1 || port > 65535 )); then
        return 1
    fi

    return 0
}

run_validation() {
    local file=""
    local relative=""

    make_manifest "$CONFIG_DIR" "*.conf" 1 || return 3

    while IFS= read -r -d '' file; do
        PROCESSED=$((PROCESSED + 1))

        relative="${file#"$SOURCE_ROOT"/}"

        if ! validate_report_path "$relative"; then
            FAILED=$((FAILED + 1))
            continue
        fi

        if validate_config_file "$file"; then
            PASSED=$((PASSED + 1))

            record_result "PASS" "$relative" \
                "Configuration valid" || return 3
        else
            FAILED=$((FAILED + 1))

            record_result "FAIL" "$relative" \
                "Configuration invalid" || return 3
        fi
    done < "$MANIFEST_FILE"

    remove_manifest

    print_summary

    if (( PROCESSED == 0 )); then
        return 6
    fi

    if (( FAILED > 0 )); then
        return 4
    fi

    return 0
}

archive_one_file() {
    local source_file="$1"
    local filename="$2"
    local destination="$3"

    if [[ -L "$source_file" || ! -f "$source_file" ]]; then
        error "Archive source is no longer a regular file"
        return 1
    fi

    if [[ -e "$destination" || -L "$destination" ]]; then
        error "Archive destination already exists"
        return 1
    fi

    # -n is an additional overwrite safeguard.
    # The dedicated run directory is created exclusively.
    if ! cp --no-clobber -- "$source_file" "$destination"; then
        error "Copy failed: $filename"
        return 1
    fi

    if [[ ! -f "$destination" ]]; then
        error "Destination was not created: $filename"
        return 1
    fi

    if ! cmp -s -- "$source_file" "$destination"; then
        error "Archive verification failed: $filename"
        return 1
    fi

    return 0
}

run_archive() {
    local file=""
    local filename=""
    local destination=""
    local relative=""
    local age_seconds=0
    local now_epoch=0
    local modified_epoch=0
    local cutoff_epoch=0

    age_seconds=$((OLDER_THAN_DAYS * 86400))

    now_epoch="$(date -u '+%s')" || return 3
    cutoff_epoch=$((now_epoch - age_seconds))

    make_manifest "$LOG_DIR" "*.log" 1 || return 3

    if [[ "$ACTION" == "apply" ]]; then
        RUN_ARCHIVE_DIR="$ARCHIVE_DIR/$RUN_ID"

        if [[ -e "$RUN_ARCHIVE_DIR" ||
              -L "$RUN_ARCHIVE_DIR" ]]; then
            error "Archive run directory already exists"
            return 3
        fi

        if ! mkdir -m 700 -- "$RUN_ARCHIVE_DIR"; then
            error "Unable to create archive run directory"
            return 3
        fi
    fi

    while IFS= read -r -d '' file; do
        filename="${file##*/}"
        relative="${file#"$SOURCE_ROOT"/}"

        if ! validate_report_path "$relative"; then
            FAILED=$((FAILED + 1))
            continue
        fi

        if ! modified_epoch="$(stat -c '%Y' -- "$file")"; then
            FAILED=$((FAILED + 1))

            record_result "FAIL" "$relative" \
                "Unable to inspect modification time" || return 3

            continue
        fi

        if [[ ! "$modified_epoch" =~ ^[0-9]+$ ]]; then
            FAILED=$((FAILED + 1))
            record_result "FAIL" "$relative" \
                "Invalid modification time" || return 3
            continue
        fi

        if (( modified_epoch > cutoff_epoch )); then
            continue
        fi

        CANDIDATES=$((CANDIDATES + 1))
        PROCESSED=$((PROCESSED + 1))

        if [[ "$ACTION" == "dry-run" ]]; then
            PASSED=$((PASSED + 1))

            record_result "PREVIEW" "$relative" \
                "Would archive" || return 3

            printf 'PREVIEW: %s\n' "$relative"
            continue
        fi

        destination="$RUN_ARCHIVE_DIR/$filename"

        if archive_one_file "$file" "$filename" "$destination"; then
            PASSED=$((PASSED + 1))

            record_result "PASS" "$relative" \
                "Copied and verified" || return 3

            printf 'ARCHIVED: %s\n' "$relative"
        else
            FAILED=$((FAILED + 1))

            record_result "FAIL" "$relative" \
                "Archive operation failed" || return 3
        fi
    done < "$MANIFEST_FILE"

    remove_manifest

    print_summary

    if (( FAILED > 0 )); then
        return 5
    fi

    if (( CANDIDATES == 0 )); then
        return 6
    fi

    return 0
}

main() {
    local status=0

    if [[ "${1:-}" == "--help" && $# -eq 1 ]]; then
        usage
        return 0
    fi

    parse_arguments "$@"
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    verify_workspace || return 3

    acquire_lock
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    initialize_run || return 3

    case "$MODE" in
        inventory)
            run_inventory
            status=$?
            ;;

        validate)
            run_validation
            status=$?
            ;;

        archive)
            run_archive
            status=$?
            ;;
    esac

    remove_manifest

    printf 'EXIT_STATUS=%d\n' "$status"

    return "$status"
}
```

# Part 13 — Follow Along: Archive Preview

## 40. Understand the Age Rule

The archive command uses:

```
--older-than-days 7
```

The script computes an epoch-time cutoff:

```
current time − (7 × 86,400 seconds)
```

A log file qualifies when its modification time is at or before that cutoff.

This is an elapsed-seconds threshold, not a calendar-day calculation.

That distinction matters near midnight and daylight saving time changes.

# Part 15 — Repeatability and Idempotency

## 48. Run the Archive Again

Run:

```
./scripts/veriqta-maintain.sh \
    archive \
    --older-than-days 7 \
    --apply
```

A second run should create another unique archive directory rather than overwrite the first.

This is repeatable execution, but not full idempotency.

The operation produces additional copies each time.

### Important distinction

A repeatable script can run successfully more than once.

An idempotent script produces the same intended final state when repeated with the same inputs.

Your archive design is intentionally append-only.

That is suitable for demonstrating evidence preservation, but a production implementation would need a retention policy and a way to avoid unnecessary duplicate archives.

## 49. Consider Three Archive Policies

| Policy                         | Behavior                    | Trade-off                             |
| ------------------------------ | --------------------------- | ------------------------------------- |
| New directory per run          | Preserves each run's copies | Storage growth                        |
| Skip previously archived files | Reduces duplicates          | Requires reliable tracking            |
| Replace one latest archive     | Maintains one current copy  | Needs atomic publication and recovery |

There is no universal best choice.

The correct policy depends on business requirements, recovery expectations, and storage constraints.

## 56. Why Manual Testing Is Not Enough

Manual testing helps you understand what the script does.

Automated testing helps you detect when later changes break existing behavior.

A useful regression suite should test more than whether a script exits successfully.

It should verify:

- Expected exit codes.
- Expected output artifacts.
- Correct file selection.
- Preservation of source files.
- Correct handling of spaces in filenames.
- No archive copies during dry-run.
- Correct validation failures.
- Successful recovery after fixture correction.
- Rejection of invalid arguments.
- Lock contention behavior.

For this lab, you will create a test runner that uses an isolated temporary copy of the project.

This prevents regression tests from changing the main workspace's fixtures and reports.

## 57. Create the Test Runner

Run:

```
cat > tests/run-tests.sh <<'BASH'
#!/usr/bin/env bash

set -u
set -o pipefail

SCRIPT_DIR="$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P
)" || exit 1

LAB_ROOT="$(
    cd -- "$SCRIPT_DIR/.." && pwd -P
)" || exit 1

PASSED=0
FAILED=0
TEST_ROOT=""

pass() {
    PASSED=$((PASSED + 1))
    printf 'PASS: %s\n' "$1"
}

fail() {
    FAILED=$((FAILED + 1))
    printf 'FAIL: %s\n' "$1"
}

assert_status() {
    local description="$1"
    local expected="$2"
    shift 2

    local actual=0

    "$@" > "$TEST_ROOT/last.stdout" \
         2> "$TEST_ROOT/last.stderr" || actual=$?

    if (( actual == expected )); then
        pass "$description"
    else
        fail "$description (expected=$expected actual=$actual)"

        printf '%s\n' '--- stdout ---'
        cat "$TEST_ROOT/last.stdout"

        printf '%s\n' '--- stderr ---'
        cat "$TEST_ROOT/last.stderr"

}

setup_test_environment() {

    printf 'recent log\n' \

        -mindepth 1 \

    local archive_directory=""
    local archive_count=0

        printf 'FAIL: Main script syntax\n'

    assert_status \
        "Help returns success" \
        0 \
        bash "$tool" --help

    assert_status \
        "Unknown command rejected" \
        2 \

        "Missing archive action rejected" \
        2 \

    assert_status \
        "Invalid age rejected" \
        2 \

    assert_status \
        "Excessive age rejected" \
        2 \

    assert_status \
        "Inventory succeeds" \
        0 \

        "$TEST_ROOT"/output/reports/inventory-*.tsv; then
        pass "Inventory preserves filename with spaces"
    else
        fail "Inventory preserves filename with spaces"

        "Invalid configuration detected" \
        4 \

APP_ENV=production
APP_PORT=9090
EOF

        "Repaired configurations pass" \
        0 \
        bash "$tool" validate

        "Archive dry run succeeds" \
        0 \

    archive_count="$(
        find "$TEST_ROOT/output/archive" \
            -type f \
            -print |
        wc -l
    )"

    if (( archive_count == 0 )); then

    else

    fi

    if grep -q 'Candidates: 2' "$TEST_ROOT/last.stdout"; then
```

# Part 19 — Reliability and Security Hardening

## 66. Understand the Limits of the Current Implementation

The final project demonstrates several important controls, but it is not a fully hardened production tool.

Before adapting it to a real environment, address the following concerns.

### 66.1 Symbolic links and path races

The program rejects symbolic-link directories during initial validation.

However, another process could replace a path after that check.

This is a time-of-check/time-of-use problem, often abbreviated TOCTOU.

The script also uses pathname-based copy operations rather than secure descriptor-relative filesystem operations.

Do not run it against directories writable by untrusted users.

### 66.2 Report write failures

The script checks many report writes, but it does not implement transactional publication of the entire report.

A storage failure or process interruption may leave an incomplete report.

A stronger implementation would:

1. Write to a private temporary file.
2. Check every write.
3. Flush and close the file successfully.
4. Atomically publish the completed report.
5. Clearly mark failed or incomplete runs.

### 66.3 Archive copy failures

The archive copy is verified with `cmp`.

However, if copying fails partway through, a partial destination file may remain.

A production implementation should copy to a temporary file, verify it, then publish it atomically.

### 66.4 Source-file changes during copying

If another process modifies a log while it is being copied, the archive may not represent a consistent point-in-time snapshot.

For real workloads, coordinate with log rotation or use an application-supported snapshot mechanism.

### 66.5 Disk space

The script does not estimate available disk space before copying.

A production archival system should account for:

- Available capacity.
- Filesystem quotas.
- Inodes.
- Expected archive size.
- Partial-copy recovery.
- Storage retention.

### 66.6 File metadata

The script verifies file contents.

It does not promise to preserve all original ownership, permissions, timestamps, access-control lists, or extended attributes.

If those properties matter, define and test an explicit metadata-preservation policy.

### 66.7 Unusual filenames

The script rejects paths containing tabs, carriage returns, or newlines for reporting.

It does not provide a general binary-safe reporting format for every possible Linux filename.

A production system may need structured encoding rather than raw TSV fields.

### 66.8 Concurrency scope

The lock protects cooperating executions on the same host using the same lock file.

It is not a distributed lock across multiple hosts.

### 66.9 Report and archive retention

Repeated executions create additional reports and archives.

Without a retention policy, storage usage will grow.

### 66.10 Error classification

The validator currently classifies unreadable or invalid configuration content together as validation failures.

A production design should distinguish:

- Invalid application configuration.
- Missing input.
- Permission failure.
- Filesystem read failure.
- Interrupted read.
- Unexpected encoding.

These are different operational conditions and may require different responses.

# Part 20 — A More Robust Archive Design

## 67. Design an Atomic Archive Workflow

A production-oriented archival sequence should resemble:

```
Discover candidate
        |
        v
Validate candidate
        |
        v
Open source safely
        |
        v
Copy to private temporary destination
        |
        v
Verify content and required metadata
        |
        v
Atomically publish completed copy
        |
        v
Record successful archive
```

If any stage fails, the automation should not present an incomplete file as a successful archive.

### Example conceptual workflow

```
temporary_file="$(mktemp "$archive_dir/.copy.XXXXXXXX")"
```

Then:

```
cp -- "$source_file" "$temporary_file"
```

Then:

```
cmp -s -- "$source_file" "$temporary_file"
```

Then publish only after verification.

This simplified sequence still needs careful error checking, collision handling, cleanup traps, and concurrency control before production use.

## 68. Design a Retention Policy

Suppose the application generates 100 MB of logs per day.

If you create a complete new archive copy every day, storage grows quickly.

A retention policy should define:

- What qualifies for archival.
- Whether duplicate archives are allowed.
- How long copies are retained.
- Whether copies are stored locally or remotely.
- Whether integrity checks are repeated.
- Who authorizes deletion.
- How restoration works.
- What evidence must be retained.

Archival and deletion are separate decisions.

Do not add deletion merely because the copy operation succeeded.

# Part 26 — Knowledge Review

## 86. Thirty Questions and Answers

1\. What is Linux task automation? Using scripts or tools to perform repeatable Linux operations with minimal manual intervention.

2\. Why automate repetitive tasks? To improve consistency, efficiency, auditability, and repeatability.

3\. Does automation automatically make a task safe? No. It can repeat mistakes at scale.

4\. What is a dry run? An execution mode that previews intended changes without performing the controlled operation.

5\. Why separate discovery from execution? So candidate inputs can be reviewed before changes occur.

6\. Why avoid `for file in $(find ...)`? Command substitution and word splitting can corrupt filenames.

7\. What does `find -print0` do? Separates output paths with null bytes.

8\. Why use `IFS= read -r -d ''`? To read null-delimited filenames without unwanted splitting or backslash interpretation.

9\. Why use Bash arrays? To preserve and process collections of separate values safely.

10\. Why use functions? To organize logic into reusable, testable units.

11\. What is an exit-code contract? A documented mapping between numeric statuses and operational outcomes.

12\. What does exit code `0` mean? Successful completion under the script's defined contract.

13\. Why distinguish invalid configuration from filesystem failure? They have different causes and require different responses.

14\. What is idempotency? Repeating an operation produces the same intended final state.

15\. Is creating a new archive directory every run idempotent? No. It creates additional artifacts.

16\. Why verify archived files? To confirm that copied content matches the source.

17\. Why preserve source files during the lab? To avoid destructive changes and permit independent verification.

18\. What does `flock` provide? Advisory file locking for cooperating processes.

19\. Why is locking important? To prevent conflicting concurrent executions.

20\. What is a TOCTOU race? A race between checking a filesystem object and later using it.

21\. Why reject untrusted symbolic-link directories? They can redirect operations outside the intended location.

22\. Why should a report contain per-file results? To identify exactly which operations succeeded or failed.

23\. What is a regression test? A test that detects whether a change breaks previously expected behavior.

24\. Why use temporary test workspaces? To isolate tests from real project data.

25\. What is a counter invariant? A relationship between counters that should always hold, such as `processed = passed + failed`.

26\. Why can a partial copy be dangerous? It may appear to be a valid archive despite containing incomplete data.

27\. What is atomic publication? Making a completed artifact visible in one filesystem operation, typically through an appropriate rename on the same filesystem.

28\. Why is retention important? Repeated automation can consume storage indefinitely.

29\. What caused the simulated incident? An insufficiently constrained destructive cleanup command.

30\. What makes automation operationally trustworthy? Explicit scope, validation, safe execution, observability, meaningful failures, testing, recovery, and ownership.

## 87. Twelve Interview Questions

1\. How would you automate a repetitive Linux administration task?

I would first document the manual process, identify inputs and outputs, define success and failure conditions, then implement a script with validation, safe defaults, logging, and tests.

2\. What makes an automation script safe?

Restricted scope, least privilege, explicit arguments, dry-run support, controlled side effects, meaningful exit codes, and recovery procedures.

3\. How do you handle filenames containing spaces?

I quote expansions and use null-delimited filename processing where appropriate.

4\. What is the difference between automation and scheduling?

Automation defines how work is performed; scheduling defines when it starts.

5\. How do you prevent concurrent script executions?

I use a suitable locking mechanism such as `flock` and define how lock contention is reported.

6\. How do you know an automated operation succeeded?

I verify exit codes, expected artifacts, data integrity, and per-item outcomes.

7\. What is idempotency, and why does it matter?

Idempotency means repeating an operation does not create unintended additional effects. It makes retries and recovery safer.

8\. How would you safely automate log archival?

I would constrain the source directory, select approved filenames, preview candidates, copy into protected storage, verify content, and record results before considering deletion.

9\. Why should automation have a dry-run mode?

It lets engineers review the intended changes before applying them.

10\. What is a common problem with `find` in shell scripts?

Unsafe filename processing or overly broad selection criteria can cause incorrect operations.

11\. How would you test an automation script?

I would create isolated fixtures, test successful and failing inputs, verify exit codes and side effects, and run regression tests.

# 94. Lessons from the Trenches

1\. Automate a defined process, not an assumption. Before writing a script, understand exactly what the manual task is supposed to accomplish.

2\. Start with discovery. A list of proposed changes is easier to review than a completed destructive operation.

3\. Use dry-run modes for operations with side effects. Make the difference between preview and execution explicit.

4\. Handle filenames correctly. Spaces and other special characters are ordinary parts of Linux filenames, not exceptional conditions.

5\. Treat exit codes as an interface. A caller must be able to distinguish success, invalid input, operational failure, and partial completion.

6\. Validate the result, not just the command. A successful copy command is less useful than a verified archive artifact.

7\. Prevent concurrent operations when shared state is involved. Overlapping runs can corrupt results or duplicate work.

8\. Keep test data separate from real data. Synthetic fixtures make controlled failures safe and repeatable.

9\. Repeatability is not the same as idempotency. A script can run successfully twice while producing unwanted duplicate effects.

10\. Production readiness requires more than passing happy-path tests. Filesystem races, interrupted writes, capacity limits, monitoring, recovery, and retention all matter.
