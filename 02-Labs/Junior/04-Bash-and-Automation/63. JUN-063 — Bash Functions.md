# 1. Introduction

A Bash script may begin with only a few commands.

As it grows, the same operations often appear in multiple places:

- Checking whether a file exists.
- Validating an application name.
- Printing an error message.
- Checking a port number.
- Reading configuration files.
- Writing reports.
- Counting failures.
- Cleaning temporary files.

Repeating these operations throughout a script creates maintenance problems.

Imagine discovering that your application port validation is incorrect.

If the same validation logic appears in fifteen places, you must identify and fix all fifteen copies. Missing even one can leave inconsistent behavior in your automation.

Bash functions solve this problem by allowing you to organize commands into named, reusable units.

Instead of repeating validation logic, you can write:

```bash
validate_port "$port"
```

Instead of repeating logging commands:

```bash
log_info "Checking application configuration"
```

Instead of embedding the entire application validation process inside one large script:

```bash
validate_application "$config_file"
```

Functions are fundamental to maintainable shell automation.

However, reliable functions require more than knowing how to define them.

You must understand how Bash handles:

- Function arguments.
- Positional parameters.
- Return statuses.
- Standard output and standard error.
- Local and global variables.
- Arrays.
- Function scope.
- Subshells.
- Recursion.
- Error propagation.
- Traps and cleanup.
- Reusable libraries.
- Testing and mocking.

In this lab, you will work through these concepts and apply them to a realistic Linux operations scenario.

The final result will be a modular application configuration preflight framework that you can demonstrate, test, and explain.

# Part 2 — Bash Function Fundamentals

# 7. What Is a Bash Function?

A Bash function is a named collection of shell commands.

When you call the function, Bash executes those commands.

The common syntax is:

```bash
function_name() {
    commands
}
```

Example:

```bash
say_hello() {
    printf 'Hello from a Bash function.\n'
}
```

The function definition does not execute its body.

You must call it:

```bash
say_hello
```

Expected:

```text
Hello from a Bash function.
```

## 7.1 Function lifecycle

A typical function has three stages:

1. Definition.
2. Invocation.
3. Completion.

Bash reads the definition and stores the function in the current shell.

When you invoke it, Bash executes the body.

When the function completes, control returns to the calling code.

# 9. Function Naming Conventions

Bash function names should be meaningful.

Good examples:

```bash
validate_port
load_configuration
print_summary
write_report
log_error
```

Less useful examples:

```bash
doit
check
func1
stuff
```

A descriptive function name helps communicate its responsibility.

For public-facing scripts, use a consistent convention such as lowercase words separated by underscores.

Avoid names that conflict with important shell builtins or external commands.

For example, defining a function named `test` can create confusing behavior.

# Part 3 — Function Arguments

# 10. Positional Parameters

Functions can receive arguments.

Inside a function:

| Parameter | Meaning |
|---|---|
| `$1` | First argument |
| `$2` | Second argument |
| `$3` | Third argument |
| `$#` | Number of arguments |
| `"$@"` | All arguments, preserving boundaries |
| `$?` | Exit status of the most recent command |

Example:

```bash
greet_user() {
    printf 'Hello, %s\n' "$1"
}

greet_user "Linux Engineer"
```

Expected:

```text
Hello, Linux Engineer
```

The function receives `Linux Engineer` as its first argument.

# 12. Understanding `"$@"`

When a function receives multiple arguments, you often need to process all of them.

The safest general-purpose expansion is:

```bash
"$@"
```

This preserves each argument as a separate value.

**Engineering rule:** Use `"$@"` when forwarding or iterating over positional arguments.

# Part 4 — Function Return Statuses

# 13. Understanding `return`

A Bash function returns an exit status.

The conventional meaning is:

- `0`: success.
- Nonzero: failure or another documented outcome.

Example:

```bash
check_success() {
    return 0
}
```

Another example:

```bash
check_failure() {
    return 1
}
```

The return status is not the same as returning a string or an arbitrary integer value.

Bash exit statuses are limited to the range 0–255; values outside that range are reduced modulo 256.

A function can also complete without an explicit `return`. In that case, its status is normally the status of the last command executed.

# 14. Exercise 4 — Return Success or Failure

Create:

```bash
cat > scripts/03-return-status.sh <<'EOF'
#!/usr/bin/env bash

validate_environment() {
    local environment="${1:-}"

    case "$environment" in
        development|staging|production)
            return 0
            ;;
        *)
            return 1
            ;;
    esac
}

if validate_environment "staging"; then
    printf 'PASS: staging is supported.\n'
else
    printf 'FAIL: staging is unsupported.\n'
fi

if validate_environment "testing"; then
    printf 'PASS: testing is supported.\n'
else
    printf 'FAIL: testing is unsupported.\n'
fi
EOF
```

Run:

```bash
bash scripts/03-return-status.sh
```

Expected:

```text
PASS: staging is supported.
FAIL: testing is unsupported.
```

## 14.1 Why use the function in an `if`?

This is clear:

```bash
if validate_environment "$environment"; then
    ...
fi
```

It also avoids accidentally losing the status by running another command before checking `$?`.

Compare:

```bash
validate_environment "testing"
printf 'Validation completed.\n'
printf 'Status: %d\n' "$?"
```

The printed status belongs to the immediately preceding `printf`, not the validation function.

**Engineering rule:** Capture or test the status immediately.

# 15. Exercise 5 — Validate an Application Port

Create:

```bash
cat > scripts/03-port-validation.sh <<'EOF'
#!/usr/bin/env bash

validate_port() {
    local port_text="${1:-}"
    local port_number=0

    if [[ ! "$port_text" =~ ^[0-9]+$ ]]; then
        return 1
    fi

    if (( ${#port_text} > 5 )); then
        return 1
    fi

    port_number=$((10#$port_text))

    if (( port_number < 1 || port_number > 65535 )); then
        return 1
    fi

    return 0
}

for port in 8080 443 65535 0 70000 invalid 080; do
    if validate_port "$port"; then
        printf 'PASS: %s\n' "$port"
    else
        printf 'FAIL: %s\n' "$port"
    fi
done
EOF
```

Run:

```bash
bash scripts/03-port-validation.sh
```

Expected:

```text
PASS: 8080
PASS: 443
PASS: 65535
FAIL: 0
FAIL: 70000
FAIL: invalid
PASS: 080
```

### Why use `10#`?

Bash arithmetic may interpret a number with a leading zero as octal.

The `10#` prefix explicitly selects decimal interpretation.

For example, the text `080` represents decimal 80 rather than an invalid octal number.

### Important limitation

This validation intentionally rejects numeric strings longer than five characters, including longer zero-padded values.

For a production interface, document whether leading zeros are permitted and implement the chosen policy consistently.

# Part 5 — Output Versus Return Status

# 16. Functions Have Two Different Result Channels

A Bash function can communicate through:

1. Its exit status.
2. Its output streams.

These serve different purposes.

A return status answers:

> Did the operation succeed?

Standard output can carry:

> What value did the operation produce?

Standard error can carry:

> What went wrong?

For example:

```bash
get_application_name() {
    printf 'api-01\n'
}
```

You can capture the output:

```bash
application="$(get_application_name)"
```

But this is not the same as:

```bash
return "api-01"
```

Bash `return` does not return arbitrary strings.

## 17.1 Separate data from diagnostics

Consider:

```bash
get_environment() {
    printf 'Starting lookup...\n'
    printf 'staging\n'
}
```

If you capture its output, both lines become part of the result.

That may break downstream logic.

A better implementation is:

```bash
get_environment() {
    printf 'Starting lookup...\n' >&2
    printf 'staging\n'
}
```

The diagnostic message goes to standard error.

The data value goes to standard output.

**Engineering rule:** Functions that produce machine-readable output should keep that output predictable.

# Part 6 — Variable Scope

# 18. Global Variables

By default, variables assigned inside Bash functions can affect variables in the surrounding shell.

Example:

```bash

change_environment() {
    environment="production"
}

change_environment

printf '%s\n' "$environment"
```

Expected:

```text
production
```

The function changed the global variable.

This can be intentional, but it can also cause serious defects.

# 21. Bash Dynamic Scoping

Bash uses dynamic scoping for local variables.

This means a function called by another function can see the caller's local variables unless it shadows them.

Run:

```bash
inner_function() {
    printf 'Inner sees: %s\n' "$message"
}

outer_function() {
    local message="From outer function"
    inner_function
}

outer_function
```

Expected:

```text
Inner sees: From outer function
```

This behavior differs from lexical scoping in many other programming languages.

### Engineering recommendation

Do not rely on dynamic scoping for ordinary application data.

Pass required values as function arguments whenever practical.

This makes dependencies explicit and functions easier to test.

Each array element remains separate.

# Part 8 — Function Dispatch

# 25. Selecting Functions with `case`

A dispatcher selects an operation based on a command or subcommand.

This pattern is common in command-line tools.

Example:

```bash
case "$command" in
    validate)
        run_validation
        ;;
    report)
        generate_report
        ;;
    *)
        show_usage
        ;;
esac
```

This makes it possible to create a script with multiple operations.

---

# 26. Exercise 10 — Build a Function Dispatcher

```bash
show_usage() {
    printf 'Usage: %s {start|status|stop}\n' "$0"

    printf 'Simulated application start.\n'
}

    printf 'Simulated application status: healthy.\n'

            show_status
            ;;

}

main "$@"
EOF
```

# Part 9 — Command Substitution and Function Scope

# 27. Understanding Command Substitution

Command substitution captures a command's standard output:

```bash
value="$(command)"
```

When Bash executes a function through command substitution, the function runs in a subshell environment.

Variable changes made there do not update the parent shell.

## Exercise 11 — Reproduce the Scope Behavior

```bash
cat > scripts/08-command-substitution.sh <<'EOF'
#!/usr/bin/env bash

    counter=$((counter + 1))
    printf '%d\n' "$counter"
}

result="$(increment_counter)"

printf 'Captured result: %s\n' "$result"
printf 'Parent counter: %d\n' "$counter"
EOF
```

Run:

```bash

```

Expected:

```text
Captured result: 1
Parent counter: 0
```

### Why?

The function modified `counter` inside the command substitution environment.

That modification did not propagate to the parent.

### Engineering lesson

Do not use command substitution when you expect a function to update global state in the calling shell.

Prefer explicit output values or well-defined state updates.

# Part 10 — Recursive Functions

# 28. What Is Recursion?

Recursion occurs when a function calls itself.

Example:

```bash
count_down() {
    local number="$1"

    if (( number <= 0 )); then
        return 0
    fi

    printf '%d\n' "$number"

    count_down "$((number - 1))"
}
```

Recursion requires a base case.

Without one, the function can continue calling itself until resources are exhausted.

---

Use recursion only when it meaningfully simplifies the problem.

# Part 11 — Error Propagation

# 30. The Masked Failure Problem

Consider:

```bash
perform_check() {
    false
    printf 'Check finished.\n'
}
```

The `false` command fails.

But the final `printf` succeeds.

The function therefore returns success unless you explicitly handle the earlier failure.

This is dangerous in operational automation.

---

# 35. Create the Configuration Library

Your configuration files will use a deliberately restricted format:

```ini
APP_NAME=api-01
APP_ENV=staging
APP_PORT=8081
```

The parser will not execute the file.

It will reject:

- Unknown keys.
- Duplicate keys.
- Missing keys.
- Empty values.
- Malformed lines.

## 35.1 Why not use `source`?

Consider:

```bash
source application.conf
```

This executes the file as shell code.

A configuration file containing command substitutions or shell commands could execute unintended operations.

For this lab, configuration files are data, not executable scripts.

## 35.2 Create the parser

Run:

```bash
cat > lib/configuration.sh <<'EOF'
#!/usr/bin/env bash

# Restricted configuration parser for JUN-063.
# This parser accepts only APP_NAME, APP_ENV, and APP_PORT.

load_config() {
    local config_file="${1:-}"
    local line=""
    local key=""
    local value=""

    local seen_name=0
    local seen_env=0
    local seen_port=0

    local parsed_name=""
    local parsed_env=""
    local parsed_port=""

    [[ -n "$config_file" ]] || return 2
    [[ -f "$config_file" && -r "$config_file" ]] || return 3

    if ! exec 3< "$config_file"; then
        return 3
    fi

    while IFS= read -r line <&3 || [[ -n "$line" ]]; do
        [[ -z "$line" ]] && continue
        [[ "$line" == \#* ]] && continue

        if [[ "$line" != *=* ]]; then
            exec 3<&-
            return 1
        fi

        key="${line%%=*}"
        value="${line#*=}"

        if [[ -z "$value" ]]; then
            exec 3<&-
            return 1
        fi

        case "$key" in
            APP_NAME)
                if (( seen_name == 1 )); then
                    exec 3<&-
                    return 1
                fi

                seen_name=1
                parsed_name="$value"
                ;;

            APP_ENV)
                if (( seen_env == 1 )); then
                    exec 3<&-
                    return 1
                fi

                seen_env=1
                parsed_env="$value"
                ;;

            APP_PORT)
                if (( seen_port == 1 )); then
                    exec 3<&-
                    return 1
                fi

                seen_port=1
                parsed_port="$value"
                ;;

            *)
                exec 3<&-
                return 1
                ;;
        esac
    done

    exec 3<&-

    if (( seen_name != 1 || seen_env != 1 || seen_port != 1 )); then
        return 1
    fi

    # Publish values only after the complete file has been parsed.
    CONFIG_APP_NAME="$parsed_name"
    CONFIG_APP_ENV="$parsed_env"
    CONFIG_APP_PORT="$parsed_port"

    return 0
}
EOF
```

Verify syntax:

```bash
bash -n lib/configuration.sh
```

### Function contract

`load_config` returns:

| Status | Meaning |
|---|---|
| `0` | File parsed successfully |
| `1` | Invalid configuration format |
| `2` | Missing function argument |
| `3` | File unavailable |

On success, it populates:

```bash
CONFIG_APP_NAME
CONFIG_APP_ENV
CONFIG_APP_PORT
```

This is an intentional use of shared state.

The main script will consume those values immediately after a successful call.

For a larger framework, you could use a caller-provided associative array or nameref instead.

# 39. Create the Modular Preflight Script

Copy the complete script below.

```bash
cat > scripts/preflight.sh <<'BASH'
#!/usr/bin/env bash

# VERIQTA Linux World
# JUN-063 — Bash Functions
# Modular application preflight framework.

set -u

SCRIPT_DIR="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P)"
LAB_ROOT="$(cd -- "$SCRIPT_DIR/.." && pwd -P)"

source "$LAB_ROOT/lib/logging.sh"
source "$LAB_ROOT/lib/validation.sh"
source "$LAB_ROOT/lib/configuration.sh"

CONFIG_DIR=""
REPORT_FILE=""

processed=0
passed=0
failed=0

declare -a CONFIG_FILES=()
declare -a RESULT_NAMES=()
declare -a RESULT_STATUSES=()

usage() {
    cat <<'EOF'
Usage:
  preflight.sh --config-dir DIRECTORY --report FILE

Exit statuses:
  0  All configurations passed
  2  Invalid arguments
  3  Operational failure
  4  Validation failure
  6  Empty configuration inventory
EOF
}

parse_arguments() {
    while (( $# > 0 )); do
        case "$1" in
            --config-dir)
                if (( $# < 2 )) || [[ -z "$2" || "$2" == --* ]]; then
                    log_error "--config-dir requires a value"
                    return 2
                fi

                CONFIG_DIR="$2"
                shift 2
                ;;

            --report)
                if (( $# < 2 )) || [[ -z "$2" || "$2" == --* ]]; then
                    log_error "--report requires a value"
                    return 2
                fi

                REPORT_FILE="$2"
                shift 2
                ;;

            --help)
                usage
                return 10
                ;;

            *)
                log_error "Unknown argument: $1"
                return 2
                ;;
        esac
    done

    if [[ -z "$CONFIG_DIR" || -z "$REPORT_FILE" ]]; then
        log_error "Both required arguments must be provided"
        return 2
    fi

    return 0
}

validate_paths() {
    local report_parent=""

    if [[ ! -d "$CONFIG_DIR" || ! -r "$CONFIG_DIR" || ! -x "$CONFIG_DIR" ]]; then
        log_error "Configuration directory is unavailable"
        return 3
    fi

    if [[ -d "$REPORT_FILE" ]]; then
        log_error "Report path must not be a directory"
        return 3
    fi

    report_parent="${REPORT_FILE%/*}"

    if [[ "$report_parent" == "$REPORT_FILE" ]]; then
        report_parent="."
    elif [[ -z "$report_parent" ]]; then
        report_parent="/"
    fi

    if [[ ! -d "$report_parent" || ! -w "$report_parent" ]]; then
        log_error "Report parent directory is unavailable"
        return 3
    fi

    return 0
}

discover_configs() {
    shopt -s nullglob
    CONFIG_FILES=("$CONFIG_DIR"/*.conf)
    shopt -u nullglob

    if (( ${#CONFIG_FILES[@]} == 0 )); then
        log_error "No configuration files discovered"
        return 6
    fi

    return 0
}

record_result() {
    local filename="$1"
    local result="$2"

    RESULT_NAMES+=("$filename")
    RESULT_STATUSES+=("$result")
}

process_one_config() {
    local file="$1"
    local filename="${file##*/}"
    local load_status=0

    CONFIG_APP_NAME=""
    CONFIG_APP_ENV=""
    CONFIG_APP_PORT=""

    log_info "Checking $filename"

    load_config "$file"
    load_status=$?

    if (( load_status != 0 )); then
        log_warn "Configuration parsing failed: $filename"
        return 1
    fi

    if ! validate_application \
        "$CONFIG_APP_NAME" \
        "$CONFIG_APP_ENV" \
        "$CONFIG_APP_PORT"
    then
        log_warn "Configuration validation failed: $filename"
        return 1
    fi

    return 0
}

process_configs() {
    local file=""
    local filename=""

    for file in "${CONFIG_FILES[@]}"; do
        filename="${file##*/}"
        processed=$((processed + 1))

        if process_one_config "$file"; then
            passed=$((passed + 1))
            record_result "$filename" PASS
        else
            failed=$((failed + 1))
            record_result "$filename" FAIL
        fi
    done

    return 0
}

write_report() {
    local index=0
    local filename=""
    local status=""
    local temporary_report=""

    temporary_report="$(mktemp "$LAB_ROOT/tmp/preflight.XXXXXX")" || {
        log_error "Unable to create temporary report"
        return 3
    }

    if ! printf 'file,status\n' > "$temporary_report"; then
        rm -f -- "$temporary_report"
        return 3
    fi

    for index in "${!RESULT_NAMES[@]}"; do
        filename="${RESULT_NAMES[$index]}"
        status="${RESULT_STATUSES[$index]}"

        filename="${filename//\"/\"\"}"

        if ! printf '"%s",%s\n' \
            "$filename" "$status" >> "$temporary_report"
        then
            rm -f -- "$temporary_report"
            log_error "Unable to write temporary report"
            return 3
        fi
    done

    if ! mv -- "$temporary_report" "$REPORT_FILE"; then
        rm -f -- "$temporary_report"
        log_error "Unable to publish report"
        return 3
    fi

    return 0
}

print_summary() {
    printf '\n'
    printf 'VERIQTA Modular Preflight Summary\n'
    printf '=================================\n'
    printf 'Discovered: %d\n' "${#CONFIG_FILES[@]}"
    printf 'Processed: %d\n' "$processed"
    printf 'Passed: %d\n' "$passed"
    printf 'Failed: %d\n' "$failed"
    printf 'Report: %s\n' "$REPORT_FILE"
}

main() {
    local status=0

    parse_arguments "$@"
    status=$?

    if (( status == 10 )); then
        return 0
    fi

    if (( status != 0 )); then
        return 2
    fi

    validate_paths || return 3

    discover_configs
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    process_configs || return 3

    write_report || return 3

    print_summary

    if (( failed > 0 )); then
        return 4
    fi

    return 0
}

main "$@"
BASH
```


## 39.2 Understand the function boundaries

The main script deliberately avoids embedding all logic inside `main`.

Instead, `main` coordinates smaller functions:

```bash

discover_configs
process_configs
write_report
print_summary
```

Each function has a distinct responsibility.

This makes failures easier to isolate.

For example, a report-generation defect should be investigated in `write_report`, not throughout the entire script.

# Part 17 — Traps and Cleanup Functions

# 47. Why Cleanup Functions Matter

Operational scripts often create temporary files.

If a script fails halfway through, temporary resources may remain.

Bash traps allow you to register functions that run when specific events occur.

A common pattern is:

```bash
trap cleanup EXIT
```

This requests that Bash call `cleanup` when the shell exits.

## 47.1 Important distinction

An `EXIT` trap runs when the shell exits normally or because of many ordinary failures.

It is not guaranteed to run after every possible termination event, such as `SIGKILL`.

Cleanup code should therefore be safe to repeat and should not assume every previous operation succeeded.

```bash
        rm -f -- "$temporary_file"
```

# Part 18 — Controlled Failure Investigations

# 49. Investigation 1 — Accidental Global Variable Modification

## Symptom

A helper function unexpectedly changes the deployment environment.

## Reproduce

```bash
environment="staging"

helper() {
    environment="production"
}

helper

printf 'Environment: %s\n' "$environment"
```

Expected:

```text
Environment: production
```

## Root cause

The helper assigned a global variable.

## Corrective action

Use a local variable:

```bash
helper() {
    local environment="production"
    printf 'Helper environment: %s\n' "$environment"
}
```

## Prevention

Use `local` for function-owned temporary variables and pass dependencies explicitly.

# 50. Investigation 2 — Missing Function Argument

## Symptom

A function processes an empty value.

## Reproduce

The function did not enforce its argument contract.

```bash
show_target() {
```

# 51. Investigation 3 — Returning Data with `return`

## Incorrect implementation

```bash
get_port() {
    return 8080
}
```

This does not return the number 8080 as application data.

Exit statuses are limited to 0–255.

## Correct implementation

```bash
get_port() {
    printf '8080\n'
}

port="$(get_port)"

printf 'Port: %s\n' "$port"
```

Expected:

```text
Port: 8080
```

### Root cause

Confusing function output with function status.

### Prevention

Use `return` for status and standard output for data.

# 52. Investigation 4 — Masked Failure

## Reproduce

```bash
bad_function() {
    false
    printf 'Completed.\n'
}

bad_function

printf 'Status: %d\n' "$?"
```

Expected status:

```text
Status: 0
```

## Root cause

The final successful command masks the earlier failure.

## Corrective action

```bash
good_function() {
    if ! false; then
        return 1
    fi

    printf 'Completed.\n'
}
```

The failure is now propagated.

# 53. Investigation 5 — Unsafe Library Sourcing

## Problem

The `source` builtin executes shell code.

It is appropriate for trusted Bash libraries that you control.

It is not appropriate for untrusted configuration data.

## Safe distinction

Trusted library:

```bash
source "$LAB_ROOT/lib/validation.sh"
```

Restricted configuration data:

```bash
load_config "$config_file"
```

The parser interprets only the supported keys.

### Security rule

Never treat an arbitrary downloaded or user-supplied configuration file as a trusted shell library.

---

# 54. Investigation 6 — Function Name Collision

## Reproduce

Run in a disposable subshell:

```bash
bash -c '
date() {
    printf "Function replaced date command.\n"
}

date
'
```

Expected:

```text
Function replaced date command.
```

The function shadows the external `date` command.

## Root cause

Bash command resolution can select functions before external executables.

## Prevention

Use distinctive function names.

Avoid redefining standard utilities unintentionally.

# 55. Investigation 7 — Recursive Function Without a Base Case

A recursive function that calls itself without a reachable termination condition can exhaust resources.

Do not run an unbounded recursive example.

Instead, use a controlled guard:

```bash
recursive_demo() {
    local depth="$1"

    if (( depth >= 5 )); then
        printf 'Safety limit reached.\n'
        return 0
    fi

    printf 'Depth: %d\n' "$depth"

    recursive_demo "$((depth + 1))"
}

recursive_demo 1
```

Expected:

```text
Depth: 1
Depth: 2
Depth: 3
Depth: 4
Safety limit reached.
```

### Prevention

Every recursive function needs a reachable base case.

# Part 22 — Knowledge Assessment

# 59. Thirty Review Questions and Answers

**1. What is a Bash function?**  
A named group of shell commands that can be invoked repeatedly.

**2. How do you define a function?**  
Using `name() { commands; }` or Bash's `function` syntax.

**3. How do you call a function?**  
By writing its name followed by any arguments.

**4. What does `$1` represent inside a function?**  
The first positional argument.

**5. What does `$#` represent?**  
The number of positional arguments.

**6. Why use `"$@"`?**  
It preserves each argument as a separate value.

**7. What does `return 0` mean?**  
The function completed successfully according to its contract.

**8. What does a nonzero return status mean?**  
A failure or another documented non-success condition.

**9. Can `return` return arbitrary strings?**  
No. Use standard output for string data.

**10. How do you capture a function's output?**  
With command substitution, such as `value="$(function_name)"`.

**11. What does `local` do?**  
It creates a variable scoped to a function and its dynamic call chain.

**12. Why avoid unnecessary global variables?**  
They can be modified unintentionally and make functions harder to test.

**13. What is dynamic scoping?**  
A called function can access local variables belonging to its callers unless they are shadowed.

**14. What does `readonly` do?**  
It prevents a variable from being reassigned or unset.

**15. What is a reusable function library?**  
A shell file containing functions intended to be sourced by other scripts.

**16. What does `source` do?**  
It executes another shell file in the current shell environment.

**17. Why is sourcing untrusted configuration dangerous?**  
Because it can execute arbitrary shell code.

**18. What is function dispatch?**  
Selecting and invoking a function based on a command or argument.

**19. What is recursion?**  
A function calling itself.

**20. What is a base case?**  
A condition that stops recursive calls.

**21. Why can function failures be masked?**  
A later successful command can become the function's final status.

**22. Why separate standard output and standard error?**  
To keep data output distinct from diagnostics.

**23. Why test functions individually?**  
To isolate defects and verify contracts.

**24. What is a side effect?**  
A change outside a function's returned status or output, such as modifying a global variable or file.

**25. Why document side effects?**  
They affect how safely functions can be reused.

**26. What is a trap?**  
A shell mechanism that executes commands when specified events occur.

**27. What is an `EXIT` trap used for?**  
Often for cleanup when the shell exits.

**28. Why use `mktemp`?**  
To create temporary files with unpredictable, collision-resistant names.

**29. What makes a function maintainable?**  
A clear purpose, explicit inputs, predictable outputs, limited side effects, and tests.

**30. What makes a Bash framework production-ready?**  
Reliable error handling, secure input handling, controlled filesystem behavior, tests, observability, and operational review.

# 60. Twelve Technical Interview Questions

## Question 1 — What is the difference between a Bash function and a separate script?

A function executes within its shell environment when called normally, while a separately executed script typically runs in another process.

Functions can access and modify shell variables according to Bash scoping rules.

## Question 2 — How do you pass arguments to a Bash function?

Provide them after the function name:

```bash
validate_application "api-01" "staging" "8081"
```

Inside the function, access them through positional parameters.

## Question 3 — What is the difference between `return` and `exit`?

`return` finishes a function or sourced script.

`exit` terminates the shell or script process.

## Question 4 — Why use `local`?

To reduce accidental changes to surrounding variables and make function behavior easier to understand.

## Question 5 — How do you return a string from a function?

Print the string to standard output and capture it with command substitution.

## Question 6 — What is the risk of global variables?

Functions may overwrite shared state unexpectedly.

## Question 7 — Why separate functions into libraries?

To improve reuse, organization, testing, and maintenance.

## Question 8 — Why should functions validate arguments?

To reject invalid inputs early and make their contracts reliable.

## Question 9 — What is a masked failure?

A failure that is followed by a successful command, causing the function to return success incorrectly.

## Question 10 — Why should you avoid sourcing untrusted configuration files?

Because `source` executes shell code.

## Question 11 — How do you test a Bash function?

Call it with known inputs and assert its status, output, and side effects.

## Question 12 — What is the benefit of a `main` function?

It provides a clear entry point and separates program coordination from individual operations.

# Part 27 — Lessons from the Trenches

# 63. Engineering Principles

**1. A function should have one clear responsibility.**

Functions that perform many unrelated operations are harder to test and maintain.

**2. Validate inputs at function boundaries.**

Do not assume every caller provides valid arguments.

**3. Use `local` deliberately.**

Unexpected changes to global variables can create difficult operational failures.

**4. Return statuses are not data values.**

Use `return` for success or failure and standard output for data.

**5. Keep diagnostic output separate from data output.**

Use standard error for logs and standard output for predictable results.

**6. Propagate failures explicitly.**

Do not allow a successful final command to hide an earlier failure.

**7. Source only trusted libraries.**

Configuration files should not be executed unless they are explicitly trusted executable shell code.

**8. Document function contracts.**

Every reusable function should have clear inputs, outputs, statuses, and side effects.

**9. Test individual functions and the complete workflow.**

Unit tests and integration tests detect different classes of defects.

**10. Design for troubleshooting.**

A modular script makes it easier to isolate a failing component.

**11. Treat temporary resources carefully.**

Use safe temporary file creation and cleanup mechanisms.

**12. Keep production limitations visible.**

A training framework demonstrates engineering concepts; production readiness requires additional security, reliability, and operational controls.
