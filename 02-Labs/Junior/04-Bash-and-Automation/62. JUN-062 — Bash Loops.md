## 1. Introduction

A Linux engineer rarely performs an operational task only once.

You may need to check ten application configurations, inspect hundreds of log records, verify a list of service names, retry a temporary failure, or validate a directory before a deployment.

Bash loops allow you to repeat operations without writing the same commands over and over.

But writing a loop is not the same as writing reliable automation.

Consider this command:

```
for file in $(ls configs); do
    echo "Checking $file"
done
```

It may appear to work until a configuration file is named:

```
worker east.conf
```

Bash can split that filename into two separate words.

Or consider:

```
while true; do
    check_application
done
```

Without a termination strategy, the loop can run indefinitely.

Or consider a script that processes five configurations, discovers two failures, and still exits successfully because its last `echo` command succeeded.

In this lab, you will learn to prevent those mistakes.

Your focus is not simply repetition. Your focus is safe, bounded, observable, and testable repetition.

# Part 3 — Understanding Loop Execution

## 6. The Four Core Concepts

Every condition-controlled loop involves four ideas:

1. Initialization: Establish the starting state.
2. Condition: Decide whether the loop should execute.
3. Body: Perform the repeated work.
4. Update: Change the state so the loop can eventually terminate.

General condition-controlled loop execution. `until` reverses which condition result causes repetition.

### Example

```
counter=1

while (( counter <= 3 )); do
    printf 'Counter: %d\n' "$counter"
    counter=$((counter + 1))
done
```

Expected:

```
Counter: 1
Counter: 2
Counter: 3
```

When `counter` becomes 4, the condition is false and the loop ends.

### Check your understanding

What happens if the counter is never incremented?

The condition remains true, so the loop can run indefinitely.

# Part 4 — Basic `for` Loops

## 7. The `for` Loop

A `for` loop is suitable when you have a defined list of values.

Syntax:

```
for variable in value1 value2 value3; do
    commands
done
```

Bash assigns each value to the loop variable in turn.

## 8. Exercise 1 — Iterate Over Application Names

Create the script:

```
cat > scripts/01-for-basics.sh <<'EOF'
#!/usr/bin/env bash

for application in api worker scheduler; do
    printf 'Checking application: %s\n' "$application"
done
EOF
```

Validate syntax:

```
bash -n scripts/01-for-basics.sh
```

Run:

```
bash scripts/01-for-basics.sh
```

Expected:

```
Checking application: api
Checking application: worker
Checking application: scheduler
```

Verify the iteration count:

```
bash scripts/01-for-basics.sh | wc -l
```

Expected:

```
3
```

### Why this works

The list contains three words.

Bash performs three iterations.

The loop variable is replaced with the next list item each time.

## 9. Exercise 2 — Use Brace Expansion

Run:

```
for number in {1..5}; do
    printf 'Instance: api-%02d\n' "$number"
done
```

Expected:

```
Instance: api-01
Instance: api-02
Instance: api-03
Instance: api-04
Instance: api-05
```

The `%02d` format produces two-digit numbers.

### Count backward

```
for number in {5..1}; do
    printf 'Remaining: %d\n' "$number"
done
```

Expected:

```
Remaining: 5
Remaining: 4
Remaining: 3
Remaining: 2
Remaining: 1
```

### Use a step

```
for number in {2..10..2}; do
    printf '%d\n' "$number"
done
```

Expected:

```
2
4
6
8
10
```

### Important limitation

Brace expansion is performed before ordinary parameter expansion.

This does not dynamically create a range:

```
limit=5

for number in {1..$limit}; do
    printf '%s\n' "$number"
done
```

For a variable-controlled numeric range, use an arithmetic loop.

# Part 5 — Arithmetic `for` Loops

## 10. Arithmetic Loop Syntax

```
for (( initialization; condition; update )); do
    commands
done
```

For example:

```
for (( number=1; number<=5; number++ )); do
    printf '%d\n' "$number"
done
```

The three expressions mean:

| Expression  | Meaning                              |
| ----------- | ------------------------------------ |
| `number=1`  | Start at 1                           |
| `number<=5` | Continue while number is at most 5   |
| `number++`  | Increase number after each iteration |

## 11. Exercise 3 — Generate Instance IDs

Create:

```
cat > scripts/02-arithmetic-for.sh <<'EOF'
#!/usr/bin/env bash

limit=5

for (( instance=1; instance<=limit; instance++ )); do
    printf 'api-%02d\n' "$instance"
done
EOF
```

Run:

```
bash scripts/02-arithmetic-for.sh
```

Expected:

```
api-01
api-02
api-03
api-04
api-05
```

### Change the limit

Create a variable-controlled example:

```
limit=3

for (( number=1; number<=limit; number++ )); do
    printf 'Check %d of %d\n' "$number" "$limit"
done
```

Expected:

```
Check 1 of 3
Check 2 of 3
Check 3 of 3
```

### Controlled failure: off-by-one error

Run:

```
for (( number=1; number<5; number++ )); do
    printf '%d\n' "$number"
done
```

Expected:

```
1
2
3
4
```

Why is 5 missing?

Because `<5` excludes the upper boundary.

Now change the condition:

```
for (( number=1; number<=5; number++ )); do
    printf '%d\n' "$number"
done
```

The fifth iteration now executes.

Engineering lesson: A one-character comparison mistake can cause a batch to skip its final target.

# Part 6 — Arrays and Safe Iteration

## 12. Why Arrays Are Important

Consider three application names:

```
api
worker east
scheduler
```

The second name contains a space.

You must preserve it as one value.

## 13. Exercise 4 — Create an Array

Run:

```
applications=(
    "api"
    "worker east"
    "scheduler"
)

printf 'Number of applications: %d\n' "${#applications[@]}"
```

Expected:

```
Number of applications: 3
```

Iterate safely:

```
for application in "${applications[@]}"; do
    printf 'Application: <%s>\n' "$application"
done
```

Expected:

```
Application: <api>
Application: <worker east>
Application: <scheduler>
```

### Why `"${applications[@]}"`?

Inside double quotes, this expansion preserves each array element as a separate argument.

Compare with:

```
for application in ${applications[@]}; do
    printf 'Application: <%s>\n' "$application"
done
```

The unquoted expansion can split `worker east` into two words.

### Create the reusable script

```
cat > scripts/03-array-loop.sh <<'EOF'
#!/usr/bin/env bash

applications=(
    "api-01"
    "api-02"
    "worker east"
    "scheduler-01"
)

processed=0

for application in "${applications[@]}"; do
    processed=$((processed + 1))
    printf '%d. %s\n' "$processed" "$application"
done

printf 'Total processed: %d\n' "$processed"
EOF
```

Run:

```
bash scripts/03-array-loop.sh
```

Expected final line:

```
Total processed: 4
```

## 14. Loop Over Array Indices

Sometimes you need the index as well as the value.

Run:

```
applications=("api" "worker" "scheduler")

for index in "${!applications[@]}"; do
    printf 'Index %d: %s\n' "$index" "${applications[$index]}"
done
```

Expected:

```
Index 0: api
Index 1: worker
Index 2: scheduler
```

Bash arrays normally use zero-based indices.

### When indices are useful

You may need to:

- Update an element.
- Associate an item with its position.
- Compare adjacent elements.
- Display numbered results.
- Match parallel arrays.

For ordinary processing, iterating directly over the values is usually simpler.

# Part 7 — `while` Loops

## 15. The `while` Construct

A `while` loop repeats while its condition returns a successful exit status.

Syntax:

```
while condition; do
    commands
done
```

## 16. Exercise 5 — Basic Counter Loop

Create:

```
cat > scripts/04-while-basics.sh <<'EOF'
#!/usr/bin/env bash

counter=1
limit=5

while (( counter <= limit )); do
    printf 'Iteration %d of %d\n' "$counter" "$limit"
    counter=$((counter + 1))
done

printf 'Loop completed.\n'
EOF
```

Run:

```

```

Expected:

```
Iteration 1 of 5
Iteration 2 of 5
Iteration 3 of 5
Iteration 4 of 5
Iteration 5 of 5

```

### Inspect the condition

The arithmetic expression:

```
(( counter <= limit ))
```

returns status 0 while the comparison is true.

When the comparison becomes false, the loop ends.

```
    counter=$((counter + 1))
```

Expected:


The final counter is one greater than the last value processed.

## 18. Why `IFS= read -r` Matters

The recommended basic pattern is:

```
while IFS= read -r line; do
    printf '%s\n' "$line"
done < input-file
```

`IFS=` prevents leading and trailing IFS whitespace from being stripped.

`-r` prevents backslash interpretation.

The file redirection supplies input directly to the loop.

### A more robust form

```
while IFS= read -r line || [[ -n "$line" ]]; do
    printf '%s\n' "$line"
done < input-file
```

The additional condition processes a final nonempty line even when the file lacks a terminating newline.

# Part 9 — `until` Loops

## 21. Understanding `until`

An `until` loop repeats while its condition fails.

It stops once the condition succeeds.

Syntax:

```
until condition; do
    commands
done
```

## 22. Exercise 8 — Basic `until`

Create:

```
cat > scripts/06-until-basics.sh <<'EOF'
#!/usr/bin/env bash

counter=1

until (( counter > 5 )); do
    printf 'Counter: %d\n' "$counter"
    counter=$((counter + 1))
done
EOF
```

Run:

```
bash scripts/06-until-basics.sh
```

Expected:

```
Counter: 1
Counter: 2
Counter: 3
Counter: 4
Counter: 5
```

### Compare `while` and `until`

These express equivalent stopping behavior:

```
while (( counter <= 5 )); do
    ...
done
```

```
until (( counter > 5 )); do
    ...
done
```

Use whichever makes the operational condition easiest to understand.

# Part 10 — `break` and `continue`

## 23. `break`: Stop the Loop

`break` exits the innermost enclosing loop.

### Exercise 9 — Stop After a Critical Failure

Run:

```
for result in PASS PASS FAIL PASS; do
    if [[ "$result" == "FAIL" ]]; then
        printf 'Critical failure detected.\n'
        break
    fi

    printf 'Accepted: %s\n' "$result"
done
```

Expected:

```
Accepted: PASS
Accepted: PASS
Critical failure detected.
```

The final `PASS` is never processed.

### Production use cases

Use `break` when:

- A critical dependency fails.
- A failure threshold is reached.
- A valid match has been found.
- A retry succeeds.
- Continuing would create unnecessary risk.

## 24. `continue`: Skip an Iteration

`continue` skips the remaining commands in the current iteration.

### Exercise 10 — Skip Disabled Applications

Run:

```
for application in api-01 disabled worker-01; do
    if [[ "$application" == "disabled" ]]; then
        printf 'Skipping disabled entry.\n'
        continue
    fi

    printf 'Checking: %s\n' "$application"
done
```

Expected:

```
Checking: api-01
Skipping disabled entry.
Checking: worker-01
```

### Important distinction

`break` means:

> Stop this loop.

`continue` means:

> Skip the rest of this iteration and proceed with the loop.

## 25. Exercise 11 — Combine `break` and `continue`

Create:

```
cat > scripts/07-break-continue.sh <<'EOF'
#!/usr/bin/env bash

statuses=(PASS SKIP PASS FAIL PASS)

passed=0
skipped=0

for status in "${statuses[@]}"; do
    if [[ "$status" == "SKIP" ]]; then
        skipped=$((skipped + 1))
        printf 'Skipping item.\n'
        continue
    fi

    if [[ "$status" == "FAIL" ]]; then
        printf 'Stopping on failure.\n'
        break
    fi

    passed=$((passed + 1))
    printf 'Passed item.\n'
done

printf 'Passed: %d\n' "$passed"
printf 'Skipped: %d\n' "$skipped"
EOF
```

Run:

```
bash scripts/07-break-continue.sh
```

Expected:

```
Passed item.
Skipping item.
Passed item.
Stopping on failure.
Passed: 2
Skipped: 1
```

The final `PASS` is not reached.

# Part 11 — Nested Loops

## 26. What Is a Nested Loop?

A nested loop is a loop inside another loop.

Example:

```
for environment in development staging; do
    for application in api worker; do
        printf '%s / %s\n' "$environment" "$application"
    done
done
```

Expected:

```
development / api
development / worker
staging / api
staging / worker
```

For every environment, the inner loop processes both applications.

## 27. Exercise 12 — Environment Matrix

Create:

```
cat > scripts/08-nested-loops.sh <<'EOF'
#!/usr/bin/env bash

environments=(development staging production)
applications=(api worker scheduler)

count=0

for environment in "${environments[@]}"; do
    for application in "${applications[@]}"; do
        count=$((count + 1))

        printf '%02d: %-12s %s\n' \
            "$count" "$environment" "$application"
    done
done

printf 'Total combinations: %d\n' "$count"
EOF
```

Run:

```
bash scripts/08-nested-loops.sh
```

Expected: nine combinations.

Verify:

```
bash scripts/08-nested-loops.sh | tail -n 1
```

Expected:

```
Total combinations: 9
```

### Workload calculation

Three environments multiplied by three applications produces nine combinations.

In general:

\\[ \text{Total operations} = \text{Outer iterations} \times \text{Inner iterations} \\]

A loop over 100 hosts and 20 services can produce 2,000 checks.

Nested loops should be reviewed for performance and operational impact.

# Part 12 — Counters and Aggregated Results

## 28. Why a Finished Loop Is Not Necessarily Successful

A loop can process five items and encounter two failures.

If you only print:

```
printf 'Done.\n'
```

at the end, the script may return status 0.

That does not mean every item passed.

You must explicitly track the results.

## 29. Exercise 13 — Count PASS and FAIL

Run:

```
statuses=(PASS FAIL PASS PASS FAIL)

passed=0
failed=0

for status in "${statuses[@]}"; do
    case "$status" in
        PASS)
            passed=$((passed + 1))
            ;;
        FAIL)
            failed=$((failed + 1))
            ;;
    esac
done

printf 'Passed: %d\n' "$passed"
printf 'Failed: %d\n' "$failed"
printf 'Total: %d\n' "$((passed + failed))"
```

Expected:

```
Passed: 3
Failed: 2
Total: 5
```

### Engineering principle

A reliable batch process must define what its final success condition means.

For this lab:

- All items passed: success.
- One or more validation failures: validation failure.
- Invalid arguments: usage error.
- Filesystem or report failure: operational error.
- No matching files: empty inventory error.
- Threshold reached: stopped early.

# Part 13 — The Subshell Counter Trap

## 30. Understanding the Problem

Consider:

```
count=0

printf 'one\ntwo\nthree\n' |
while IFS= read -r line; do
    count=$((count + 1))
done

printf 'Count: %d\n' "$count"
```

In Bash's normal pipeline execution, the loop runs in a subshell.

Variable changes in that subshell do not update the parent shell.

Expected under standard Bash defaults:

```
Count: 0
```

## 31. Exercise 14 — Reproduce and Fix

Create the broken example:

```
cat > scripts/09-subshell-bug.sh <<'EOF'
#!/usr/bin/env bash

count=0

printf 'one\ntwo\nthree\n' |
while IFS= read -r line; do
    count=$((count + 1))
done

printf 'Count after pipeline: %d\n' "$count"
EOF
```

Run:

```
bash scripts/09-subshell-bug.sh
```

Expected:

```
Count after pipeline: 0
```

### Fix it

Create:

```
printf 'one\ntwo\nthree\n' > fixtures/lists/three-items.txt
```

Then:

```
cat > scripts/09-subshell-fixed.sh <<'EOF'
#!/usr/bin/env bash

count=0

while IFS= read -r line; do
    count=$((count + 1))
done < fixtures/lists/three-items.txt

printf 'Count after loop: %d\n' "$count"
EOF
```

Run:

```
bash scripts/09-subshell-fixed.sh
```

Expected:

```
Count after loop: 3
```

### Why the fix works

The input redirection is attached directly to the loop.

The loop can update the counter in the current shell environment.

Bash's `lastpipe` option can change pipeline behavior in certain circumstances, but a direct input redirection avoids relying on that option.

# Part 14 — Safe File Discovery

## 32. Avoid Parsing `ls`

Do not use this pattern for operational file processing:

```
for file in $(ls fixtures/configs); do
    printf '%s\n' "$file"
done
```

It can break filenames containing whitespace.

Use pathname expansion with quoting instead.

A safe retry loop defines:

- Maximum attempts.
- Success condition.
- Failure condition.
- Delay policy.
- Final exit status.

## 39. Create the Batch Validator

Copy the entire block below into your terminal.

```
cat > scripts/application-batch-check.sh <<'BASH'
#!/usr/bin/env bash

# VERIQTA Linux World
# JUN-062 — Bash Loops
# Training application configuration batch validator.

set -u

CONFIG_DIR=""
REPORT_FILE=""
MAX_FAILURES=0

processed=0
passed=0
failed=0
stopped_early=0

declare -a CONFIG_FILES=()

error() {
    printf 'ERROR: %s\n' "$1" >&2
}

usage() {
    cat <<'EOF'
Usage:
  application-batch-check.sh \
    --config-dir DIRECTORY \
    --report FILE \
    --max-failures NUMBER

Exit statuses:
  0  All configurations passed
  2  Invalid arguments
  3  Operational failure
  4  Validation failures
  5  Failure threshold reached
  6  No configuration files found
EOF
}

parse_arguments() {
    while (( $# > 0 )); do
        case "$1" in
            --config-dir)
                if (( $# < 2 )) || [[ -z "$2" || "$2" == --* ]]; then
                    error "--config-dir requires a directory"
                    return 2
                fi
                CONFIG_DIR="$2"
                shift 2
                ;;

            --report)
                if (( $# < 2 )) || [[ -z "$2" || "$2" == --* ]]; then
                    error "--report requires a file path"
                    return 2
                fi
                REPORT_FILE="$2"
                shift 2
                ;;

            --max-failures)
                if (( $# < 2 )) || [[ -z "$2" || "$2" == --* ]]; then
                    error "--max-failures requires a number"
                    return 2
                fi
                MAX_FAILURES="$2"
                shift 2
                ;;

            --help)
                usage
                return 10
                ;;

            *)
                error "Unknown argument: $1"
                return 2
                ;;
        esac
    done

    if [[ -z "$CONFIG_DIR" || -z "$REPORT_FILE" ]]; then
        error "Both --config-dir and --report are required"
        return 2
    fi

    if [[ ! "$MAX_FAILURES" =~ ^[0-9]+$ ]]; then
        error "Maximum failures must be a nonnegative integer"
        return 2
    fi

    if (( ${#MAX_FAILURES} > 6 )); then
        error "Maximum failures value is too large"
        return 2
    fi

    MAX_FAILURES=$((10#$MAX_FAILURES))

    return 0
}

validate_paths() {
    local report_parent=""

    if [[ ! -d "$CONFIG_DIR" || ! -r "$CONFIG_DIR" || ! -x "$CONFIG_DIR" ]]; then
        error "Configuration directory is unavailable"
        return 3
    fi

    if [[ -d "$REPORT_FILE" ]]; then
        error "Report path is a directory"
        return 3
    fi

    report_parent="${REPORT_FILE%/*}"

    if [[ "$report_parent" == "$REPORT_FILE" ]]; then
        report_parent="."
    elif [[ -z "$report_parent" ]]; then
        report_parent="/"
    fi

    if [[ ! -d "$report_parent" || ! -w "$report_parent" ]]; then
        error "Report parent directory is unavailable or not writable"
        return 3
    fi

    return 0
}

discover_files() {
    local file=""

    shopt -s nullglob
    CONFIG_FILES=("$CONFIG_DIR"/*.conf)
    shopt -u nullglob

    if (( ${#CONFIG_FILES[@]} == 0 )); then
        error "No configuration files found"
        return 6
    fi

    for file in "${CONFIG_FILES[@]}"; do
        if [[ ! -f "$file" ]]; then
            error "Not a regular file: $file"
            return 3
        fi
    done

    return 0
}

validate_config() {
    local file="$1"
    local line=""
    local key=""
    local value=""

    local app_name=""
    local app_env=""
    local app_port=""

    local seen_name=0
    local seen_env=0
    local seen_port=0

    if [[ ! -r "$file" ]]; then
        return 1
    fi

    if ! exec 3< "$file"; then
        return 1
    fi

    while IFS= read -r line <&3 || [[ -n "$line" ]]; do
        [[ -z "$line" ]] && continue
        [[ "$line" == \#* ]] && continue

        if [[ "$line" != *=* ]]; then
            exec 3<&-
            return 1
        fi

        key="${line%%=*}"
        value="${line#*=}"

        if [[ -z "$value" ]]; then
            exec 3<&-
            return 1
        fi

        case "$key" in
            APP_NAME)
                if (( seen_name == 1 )); then
                    exec 3<&-
                    return 1
                fi
                seen_name=1
                app_name="$value"
                ;;

            APP_ENV)
                if (( seen_env == 1 )); then
                    exec 3<&-
                    return 1
                fi
                seen_env=1
                app_env="$value"
                ;;

            APP_PORT)
                if (( seen_port == 1 )); then
                    exec 3<&-
                    return 1
                fi
                seen_port=1
                app_port="$value"
                ;;

            *)
                exec 3<&-
                return 1
                ;;
        esac
    done

    exec 3<&-

    if (( seen_name != 1 || seen_env != 1 || seen_port != 1 )); then
        return 1
    fi

    if [[ ! "$app_name" =~ ^[a-z][a-z0-9-]*$ ]]; then
        return 1
    fi

    case "$app_env" in
        development|staging|production)
            ;;
        *)
            return 1
            ;;
    esac

    if [[ ! "$app_port" =~ ^[0-9]+$ ]]; then
        return 1
    fi

    if (( ${#app_port} > 5 )); then
        return 1
    fi

    local port_number=$((10#$app_port))

    if (( port_number < 1 || port_number > 65535 )); then
        return 1
    fi

    return 0
}

initialize_report() {
    if ! printf 'file,status\n' > "$REPORT_FILE"; then
        error "Unable to initialize report"
        return 3
    fi
}

write_result() {
    local filename="$1"
    local status="$2"

    # Double embedded quotes for ordinary CSV filenames.
    filename="${filename//\"/\"\"}"

    if ! printf '"%s",%s\n' "$filename" "$status" >> "$REPORT_FILE"; then
        error "Unable to write report"
        return 3
    fi
}

process_files() {
    local file=""
    local filename=""

    for file in "${CONFIG_FILES[@]}"; do
        processed=$((processed + 1))
        filename="${file##*/}"

        printf 'Checking: %s\n' "$filename"

        if validate_config "$file"; then
            passed=$((passed + 1))
            printf '  Result: PASS\n'
            write_result "$filename" PASS || return 3
        else
            failed=$((failed + 1))
            printf '  Result: FAIL\n'
            write_result "$filename" FAIL || return 3

            if (( MAX_FAILURES > 0 && failed >= MAX_FAILURES )); then
                stopped_early=1
                printf 'Failure threshold reached.\n' >&2
                break
            fi
        fi
    done

    return 0
}

print_summary() {
    printf '\n'
    printf 'VERIQTA Batch Validation Summary\n'
    printf '================================\n'
    printf 'Discovered: %d\n' "${#CONFIG_FILES[@]}"
    printf 'Processed: %d\n' "$processed"
    printf 'Passed: %d\n' "$passed"
    printf 'Failed: %d\n' "$failed"
    printf 'Stopped early: %d\n' "$stopped_early"
    printf 'Report: %s\n' "$REPORT_FILE"
}

main() {
    local status=0

    parse_arguments "$@"
    status=$?

    if (( status == 10 )); then
        return 0
    fi

    if (( status != 0 )); then
        return 2
    fi

    validate_paths || return 3

    discover_files
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    initialize_report || return 3

    process_files || return 3

    print_summary

    if (( stopped_early == 1 )); then
        return 5
    fi

    if (( failed > 0 )); then
        return 4
    fi

    return 0
}

main "$@"
BASH
```

### Understand the loops inside the script

The script uses three different loop patterns.

Argument parsing:

```
while (( $# > 0 )); do
    ...
done
```

This repeats until all command-line arguments have been processed.

Configuration parsing:

```
while IFS= read -r line <&3 || [[ -n "$line" ]]; do
    ...
done
```

This processes configuration lines while preserving whitespace and handling an unterminated final line.

File processing:

```
for file in "${CONFIG_FILES[@]}"; do
    ...
done
```

This processes every discovered configuration without splitting filenames containing spaces.

### Understand the stop condition

```
if (( MAX_FAILURES > 0 && failed >= MAX_FAILURES )); then
    stopped_early=1
    break
fi
```

This means:

- Threshold 0: process all files.
- Threshold 1: stop after the first failure.
- Threshold 2: stop after the second failure.
- Higher threshold: stop only when that many failures have occurred.

The script counts failures explicitly rather than relying on the loop's exit status.

### Important engineering limitations

This is a deliberately scoped training validator.

It is not a general-purpose configuration parser or production deployment gate. In particular, it does not provide atomic report replacement, locking, race-resistant filesystem access, or full handling of arbitrary filenames containing embedded newlines. It also assumes trusted local training directories.

Do not use this implementation to validate real deployment configurations without a separate security and reliability review.

```
    printf 'Batch failed: %d failed item(s).\n' "$failures" >&2
    exit 4

EOF
```

# Part 20 — Operational Troubleshooting Reference

## 53. Common Loop Failures

| Symptom                              | Likely cause                   | Corrective action                               |
| ------------------------------------ | ------------------------------ | ----------------------------------------------- |
| Loop runs forever                    | Condition never changes        | Add a reachable stop condition                  |
| Loop runs zero times                 | Initial condition false        | Inspect initial values                          |
| Last item missing                    | Off-by-one boundary            | Review `<` versus `<=`                          |
| Filename split                       | Unquoted expansion             | Use quoted arrays or globs                      |
| Empty directory treated as one item  | Unmatched glob                 | Use `nullglob`                                  |
| Counter remains zero                 | Pipeline subshell              | Redirect input into the loop                    |
| Final input line missing             | No trailing newline            | Handle unsuccessful `read` with nonempty buffer |
| Batch returns success after failures | No failure aggregation         | Track failures explicitly                       |
| Loop stops too early                 | Incorrect `break` condition    | Inspect threshold logic                         |
| Required item skipped                | Incorrect `continue` condition | Inspect skip conditions                         |
| Retry never ends                     | No maximum attempts            | Add a bound                                     |
| Nested loop takes too long           | Multiplicative work            | Estimate total operations                       |
| Duplicate work                       | Duplicate input entries        | Validate or deduplicate inventory               |
| Wrong files processed                | Broad glob or wrong directory  | Inspect and constrain target selection          |

# Part 23 — Interview Preparation

## 56. Twelve Technical Interview Questions

1\. Why is `for file in $(ls directory)` unsafe? Because the command substitution output is subject to word splitting and pathname expansion. Use quoted arrays, direct globs, or null-delimited discovery.

2\. How do you prevent an infinite retry loop? Set a maximum attempt count, enforce a deadline where appropriate, and define the final failure behavior.

3\. Why might a counter remain zero after a `while` loop? The loop may have run in a pipeline subshell, so variable changes did not propagate to the parent shell.

4\. What is the difference between `break` and `continue`? `break` exits the loop; `continue` skips the rest of the current iteration.

5\. How do you read a file without stripping whitespace? Use `IFS= read -r` with input redirection.

6\. What is an off-by-one error? A boundary error that causes a loop to execute too many or too few times.

7\. Why should a batch script track failures explicitly? Because loop completion does not prove that every iteration succeeded.

8\. What is `nullglob`? A Bash option that makes unmatched pathname patterns expand to no arguments.

9\. Why should an empty configuration directory be treated carefully? It may indicate that discovery failed or that required configurations are missing.

10\. What is the risk of nested loops? The number of operations multiplies across loop dimensions.

11\. What should a retry loop log? Attempt number, result, limit, and final outcome, without exposing secrets.

12\. What distinguishes production-grade loop automation from a basic script? Validated targets, safe input handling, bounded execution, meaningful exit statuses, accurate reporting, and tested failure behavior.

# Part 27 — Lessons from the Trenches

## 60. Final Engineering Principles

1\. Repetition multiplies impact. A safe command applied to the wrong target set can still cause a serious incident.

2\. Preserve input boundaries. Use quoted arrays and safe filename discovery.

3\. Avoid parsing `ls`. Its output is not a reliable machine-readable file inventory.

4\. Bound retries. Every polling or retry loop should have a stopping strategy.

5\. Completion is not success. Aggregate per-item results.

6\. Treat empty input deliberately. Processing zero files is not automatically a successful validation.

7\. Understand shell execution context. Subshell behavior can invalidate counters and other state changes.

8\. Use `break` and `continue` intentionally. They express different operational decisions.

9\. Estimate nested-loop workload. Repeated operations can grow rapidly.

10\. Make failures observable. Log useful outcomes and return meaningful exit statuses.

11\. Test the failure paths. Positive-only testing leaves important defects undiscovered.

12\. Document limitations. A successful training demonstration is not the same as a production-hardened system.
