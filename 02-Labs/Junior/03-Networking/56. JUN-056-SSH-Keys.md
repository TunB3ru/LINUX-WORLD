# 1. Production Mission — The SSH Server Is Healthy, but Key Authentication Fails

You are a junior Linux engineer supporting an internal application platform.

The infrastructure team has recently standardized SSH public-key authentication for administrative access.

Password authentication is disabled on the affected servers.

At 08:40 UTC, an engineer reports that SSH access to a Linux application server has stopped working.

The target system is:

```text
Hostname: app-server-02
IP address: 10.20.30.41
SSH port: 22
Account: deploy
Authentication: public key
```

The engineer runs:

```bash
ssh deploy@10.20.30.41
```

The connection fails:

```text
deploy@10.20.30.41: Permission denied (publickey).
```

A second engineer checks network connectivity.

```bash
ping -c 4 10.20.30.41
```

The host responds.

The server's SSH listener is also confirmed to be active.

```text
LISTEN 0 128 10.20.30.41:22 0.0.0.0:*
```

The operations team asks:

> The server is reachable, SSH is running, and the engineer has an SSH key. Why is authentication failing?

That is your investigation.

You must not immediately replace the user's key, enable password authentication, or modify the SSH server.

You must establish which authentication requirement is failing.

Possible causes include:

- The client is offering the wrong key.
- The private key is missing.
- The private key cannot be read.
- The public key is absent from the server's authorized-keys file.
- The remote username is incorrect.
- The account's home directory is incorrect.
- The server cannot read the authorized-keys file.
- File ownership or permissions violate server policy.
- The SSH agent is not available.
- The expected key is not loaded into the agent.
- The client is offering too many identities.
- The key has been revoked or removed.
- The account is restricted.
- The server's authentication policy does not accept the attempted key or signature algorithm.

Your task is to distinguish these possibilities using evidence.

# 6. SSH Public-Key Authentication — The Big Picture

SSH public-key authentication uses asymmetric cryptography.

A keypair contains:

```text
PRIVATE KEY
PUBLIC KEY
```

These keys are mathematically related, but they have different responsibilities.

## 6.1 Private key

The private key is retained by the client.

It is used to produce cryptographic signatures during authentication.

It must be protected.

## 6.2 Public key

The public key can be distributed to an authorized SSH server.

The server can use it to verify a signature produced by the corresponding private key.

## 6.3 Authentication architecture

```text
                  SSH PUBLIC-KEY AUTHENTICATION

        CLIENT                              SERVER

   +------------------+               +--------------------+
   |                  |               |                    |
   | Private key      |               | authorized_keys    |
   |                  |               |                    |
   | Public key       |               | Accepted public key|
   |                  |               |                    |
   +--------+---------+               +---------+----------+
            |                                   |
            |        SSH connection             |
            |---------------------------------->|
            |                                   |
            |        Server host identity       |
            |<--------------------------------->|
            |                                   |
            |        Public-key auth request    |
            |---------------------------------->|
            |                                   |
            |        Signature proof            |
            |---------------------------------->|
            |                                   |
            |        Signature verification     |
            |                                   |
            |        Authentication result      |
            |<----------------------------------|
```

## 6.4 Critical principle

The private key is not sent to the SSH server.

The client proves possession of the private key by creating a signature.

The server verifies that signature using the corresponding public key.

## 6.5 Why this matters

An attacker who obtains only the public key should not be able to derive the private key using practical known attacks against properly generated modern keys.

An attacker who obtains an unprotected private key may be able to impersonate the key holder if other access controls permit it.

# 7. Authentication Is Not the Same as Encryption

SSH provides an encrypted transport.

SSH public-key authentication is one mechanism for authenticating a user.

These are related but separate functions.

## 7.1 Transport encryption

SSH negotiates cryptographic keys to protect the connection.

## 7.2 Server authentication

The client verifies the SSH server's host identity.

## 7.3 User authentication

The server verifies that the user possesses an acceptable credential.

## 7.4 Authorization

The server determines what the authenticated user may do.

A successful public-key authentication does not automatically grant root privileges or unrestricted shell access.

# 8. Understanding SSH Key Algorithms

OpenSSH supports multiple public-key algorithms, subject to its build and security policy.

Three important families are:

| Algorithm | Description | Practical Consideration |
|---|---|---|
| Ed25519 | Modern elliptic-curve signature algorithm | Commonly preferred for new general-purpose SSH user keys when supported |
| RSA | Widely deployed public-key algorithm | Useful for compatibility; key size and signature algorithm policy matter |
| ECDSA | Elliptic-curve digital signature algorithm | Supported in many environments; organizational policy may determine suitability |

## 8.1 Ed25519

Ed25519 offers compact keys and efficient signing and verification.

It is an appropriate default for this training environment.

## 8.2 RSA

RSA remains relevant in environments requiring compatibility with certain systems.

For new RSA keys, organizations commonly require at least 3072 bits, depending on policy.

Do not confuse an RSA key type with the deprecated `ssh-rsa` SHA-1 signature algorithm.

Modern RSA keys may use SHA-2 signature algorithms.

## 8.3 ECDSA

ECDSA is another supported key family.

Selection depends on compatibility, security policy, and cryptographic requirements.

## 8.4 What about FIDO security keys?

OpenSSH can support hardware-backed security-key authentication, including `ed25519-sk` and `ecdsa-sk`, when supported by the platform and device.

These are important in production environments, but require additional hardware and configuration.

They are outside this lab's required exercises.

## 8.5 Key selection rule

Use an algorithm supported by both client and server and approved by organizational policy.

Do not weaken algorithm settings merely to make a legacy connection work.

# 9. Understanding Key Files

A common Ed25519 keypair uses:

```text
id_ed25519
id_ed25519.pub
```

The files have different meanings.

| File | Purpose | Confidentiality |
|---|---|---|
| `id_ed25519` | Private key | Secret |
| `id_ed25519.pub` | Public key | Shareable with authorized recipients |

## 9.1 Private key permissions

A typical private-key permission is:

```text
600
```

This means:

- Owner: read and write.
- Group: no access.
- Others: no access.

## 9.2 SSH directory permissions

A typical user SSH directory permission is:

```text
700
```

## 9.3 authorized_keys permissions

A common setting is:

```text
600
```

## 9.4 Important nuance

SSH permission validation depends on ownership, directory accessibility, server policy, and platform behavior.

A single `chmod` command does not solve every authentication problem.

# 14. Follow-Along Lab 4 — Understand Key Comments and Filenames

SSH key comments are metadata.

Example:

```text
JUN-056 primary training identity
```

A comment is not an access-control mechanism.

## 14.1 Does changing the comment change the cryptographic identity?

No.

The key material determines the identity.

## 14.2 Does changing the filename change the key?

No.

However, it can change how client configuration selects the key.

## 14.3 Why use descriptive filenames?

Descriptive filenames help prevent:

- Using the wrong identity.
- Overwriting keys.
- Confusing personal and service accounts.
- Losing track of rotation status.

## 14.4 Production naming examples

```text
id_ed25519_workstation_admin
id_ed25519_lab_training
id_ed25519_project_deploy
```

These are naming examples, not required standards.

Never encode private secrets into filenames or comments.

# 18. Understanding authorized_keys Syntax

An `authorized_keys` entry may contain:

```text
OPTIONS KEY_TYPE KEY_DATA COMMENT
```

The options field is optional.

Example structure:

```text
ssh-ed25519 AAAA... engineer@example
```

## 18.1 Common authorized_keys restrictions

OpenSSH supports restrictions such as:

- `from=`
- `command=`
- `no-pty`
- `no-port-forwarding`
- `no-agent-forwarding`
- `no-X11-forwarding`
- `restrict`

These controls can limit how a key may be used.

## 18.2 Important distinction

An authorized key is not necessarily an unrestricted shell credential.

A key may be limited to:

- Specific source addresses.
- A forced command.
- No terminal allocation.
- No forwarding.
- Other policy restrictions.

## 18.3 Production principle

Apply least privilege.

Do not grant broader SSH capabilities than the identity requires.

Advanced authorized-key restrictions will be studied more deeply in later security and SSH configuration work.

# 25. Understanding SSH Key Deployment

In production, public keys must be distributed through an approved process.

Common approaches include:

- Configuration management.
- Identity and access management systems.
- Infrastructure provisioning.
- Approved administrative workflows.
- `ssh-copy-id` where permitted.
- Centrally managed SSH certificates.

## 25.1 ssh-copy-id

The command:

```bash
ssh-copy-id
```

can help install a public key into a remote account's authorized-keys file.

However, it modifies the remote account.

It may rely on an existing authentication method.

Do not run it against a production host without authorization.

## 25.2 Why manual copying can fail

Common problems include:

- Wrong remote account.
- Wrong home directory.
- Wrong file.
- Incorrect permissions.
- Incorrect ownership.
- Public key pasted incorrectly.
- Duplicate or outdated keys.
- Incorrect server policy.

## 25.3 Important security principle

A public key can be shared, but the recipient must still verify that the key belongs to the intended person or system.

An attacker who convinces an administrator to authorize the attacker's public key can gain access even without stealing an existing private key.

# 28. Understanding ssh-agent

An SSH agent is a process that holds unlocked private-key identities and performs signing operations on behalf of an SSH client.

It can reduce repeated passphrase prompts.

## 28.1 What does an agent do?

The agent can use a loaded private key to produce authentication signatures.

The SSH client communicates with the agent.

## 28.2 Does the agent send private keys to the server?

No.

## 28.3 Is an SSH agent automatically safe?

No.

Access to an agent socket can be security-sensitive.

Processes or users able to access the agent may be able to request signing operations, depending on the environment and controls.

## 28.4 Production principle

Treat agent access as sensitive.

Avoid unnecessary agent forwarding.

# 36. Understanding SSH Key Rotation

Key rotation replaces an existing authentication key with a new one.

Rotation may be required because of:

- Security policy.
- Scheduled lifecycle management.
- Employee role changes.
- Credential age.
- Suspected compromise.
- Cryptographic policy changes.
- Migration to hardware-backed credentials.

## 36.1 Safe rotation sequence

A typical approved rotation includes:

1. Generate a new keypair.
2. Protect the new private key.
3. Verify the new public-key fingerprint.
4. Associate the key with the correct identity.
5. Authorize the new public key.
6. Test authentication using the new key.
7. Verify required operations.
8. Remove the old authorization.
9. Verify the old key no longer authenticates.
10. Update inventory and audit records.

## 36.2 Why test before removing the old key?

Removing the old key before verifying the replacement can cause lockout.

## 36.3 Important production consideration

Rotation must account for all systems where the key is authorized.

Removing one authorized-keys entry may not revoke the key everywhere.

# 38. Understanding SSH Key Revocation

Revocation removes or invalidates an identity's authorization.

## 38.1 Common revocation methods

Depending on the environment:

- Remove a public key from authorized_keys.
- Update centrally managed access records.
- Revoke an SSH certificate.
- Update a server-side revoked-key list.
- Disable the associated account.
- Remove authorization from managed systems.

## 38.2 Important distinction

Deleting a local private-key file is not server-side revocation.

A copied private key could still exist elsewhere.

## 38.3 Revocation verification

After revocation, verify that the old credential is rejected.

Also confirm that the intended replacement identity still works.

## 38.4 Production caution

Do not revoke keys on shared or production accounts without identifying all dependencies.

# 39. Understanding SSH Key Compromise

A key may be compromised if an unauthorized party gains access to the private key or can misuse its signing capability.

Potential indicators include:

- Private key exposed in a public repository.
- Private key included in a container image.
- Private key sent through an insecure channel.
- Unexpected use of a key.
- Unauthorized agent access.
- Suspicious authentication logs.
- Lost device containing private keys.
- Credentials found in an unapproved backup.

## 39.1 Does a passphrase eliminate compromise risk?

No.

A passphrase can help protect an encrypted private-key file at rest.

It does not eliminate every risk, especially if an attacker can access an unlocked key or agent.

## 39.2 Response to suspected compromise

1. Report the incident.
2. Preserve relevant evidence.
3. Identify affected identities.
4. Identify systems that trust the key.
5. Revoke or disable the compromised authorization through approved procedures.
6. Generate replacement credentials.
7. Investigate unauthorized activity.
8. Rotate related credentials if required.
9. Review logs.
10. Document containment and recovery.

## 39.3 Do not conceal compromise

A leaked private key is a security event, not merely a configuration inconvenience.

No.

It derives the public key from a private key.

A file commonly used by SSH servers to identify public keys authorized for an account.

No.

Owner read and write; no permissions for group or others.

A process that can hold private-key identities and perform signing operations for SSH clients.

# 59. Interview Preparation — 12 Questions with Worked Answers

## Interview Question 1 — Explain SSH public-key authentication.

**Answer:**

SSH public-key authentication allows a client to prove possession of a private key without transmitting that private key to the server.

The server verifies a signature using the corresponding authorized public key.

Authentication succeeds only when the key and relevant account and server policies permit it.

## Interview Question 2 — What is the difference between a private key and a public key?

**Answer:**

The private key must remain confidential and is used for signing operations.

The public key can be distributed and is used to verify signatures.

The server normally stores the authorized public key, not the user's private key.

## Interview Question 3 — Why use a passphrase on an SSH private key?

**Answer:**

A passphrase protects the private-key file at rest.

If the file is copied, the attacker may still need to overcome the passphrase protection before using the key.

However, a passphrase does not eliminate risks from unlocked keys, agent misuse, or compromised endpoints.

## Interview Question 4 — What is authorized_keys?

**Answer:**

It is a server-side file that commonly lists public keys permitted for user authentication.

It may also contain restrictions controlling how a key can be used.

## Interview Question 5 — Why would SSH reject a valid private key?

**Answer:**

A cryptographically valid key may still be unauthorized.

Possible reasons include an incorrect remote account, missing public key, wrong identity selection, server policy, file permissions, or account restrictions.

## Interview Question 6 — What is ssh-agent?

**Answer:**

An SSH agent manages unlocked identities and performs signing operations for SSH clients.

It can reduce repeated passphrase prompts, but access to the agent must be protected.

## Interview Question 7 — What is the purpose of IdentitiesOnly=yes?

**Answer:**

It helps ensure the SSH client offers only the identities selected through its configuration rather than unrelated agent identities.

This is useful when managing multiple SSH keys.

## Interview Question 8 — How would you troubleshoot Permission denied (publickey)?

**Answer:**

I would confirm the target username and server, inspect the offered key using verbose SSH output, compare its fingerprint with the server's authorized key, verify ownership and permissions, review account policy, and correlate server logs.

I would avoid changing access controls until the cause was supported by evidence.

## Interview Question 9 — How do you rotate SSH keys safely?

**Answer:**

I would generate and protect a replacement key, verify its fingerprint, authorize it through the approved process, test authentication and required operations, remove the old authorization, confirm the old key is rejected, and update the key inventory.

## Interview Question 10 — Is deleting a private key enough to revoke it?

**Answer:**

No.

Other copies may exist.

Revocation requires removing or invalidating authorization on the systems that trust the key, followed by verification.

## Interview Question 11 — What would you do if a private key were committed to a public Git repository?

**Answer:**

I would treat it as potentially compromised, report the exposure, identify affected systems, revoke the credential, generate a replacement, investigate unauthorized use, and address repository history and secret-scanning controls through the incident process.

Deleting the file from the latest commit alone would not be sufficient.

## Interview Question 12 — What caused the simulated production SSH authentication failure?

**Answer:**

The engineer generated a replacement keypair after rebuilding the workstation, but the new public key was not authorized on the server.

The SSH connection reached the authentication stage, but the server rejected the offered key.

The authorized recovery was to verify and deploy the replacement public key, test access, and revoke the obsolete key where appropriate.

# 63. Final Engineering Lessons

You have now completed a comprehensive introduction to SSH key authentication and lifecycle management.

The most important lessons are:

**1. A private key is an authentication credential.**

It must be protected throughout its lifecycle.

**2. A public key is shareable, but authorization must be controlled.**

An attacker can gain access if their public key is mistakenly authorized.

**3. Key possession does not guarantee server access.**

The server must accept the corresponding public key for the intended account.

**4. Passphrases protect private-key files at rest.**

They do not eliminate every credential risk.

**5. Host keys and user keys serve different purposes.**

One authenticates the server; the other can authenticate the user.

**6. File permissions and ownership are part of SSH security.**

But permissions alone do not explain every failure.

**7. ssh-agent is a convenience and security-sensitive component.**

Its socket and loaded identities must be managed carefully.

**8. Multiple SSH identities require deliberate selection.**

Using the wrong key can cause authentication failure.

**9. Key rotation must be verified before old access is removed.**

Otherwise, administrators can lock themselves out.

**10. Deleting a private key is not the same as revoking access.**

Server-side authorization must be removed or invalidated.

**11. A leaked private key is a potential security incident.**

It requires containment, revocation, replacement, and investigation.

**12. Permission denied (publickey) is an authentication-stage symptom.**

It should not automatically be blamed on DNS, routing, or firewalls.

**13. Production access changes require evidence and authorization.**

Do not weaken controls merely to restore convenience.

**14. Recovery is not complete until the intended operation works.**

Verify authentication, authorization, and the actual administrative workflow.

**15. Professional engineers document the entire credential lifecycle.**

Creation, distribution, authorization, use, rotation, revocation, and incident response all matter.
