# 1. Production Mission — SSH Works by IP but Fails Through the Configured Alias

You are a junior Linux engineer supporting a company that operates Linux application servers across development, staging, and production environments.

The engineering team uses SSH client configuration files to simplify remote administration.

Instead of typing:

```bash
ssh -p 2222 -i ~/.ssh/company_deploy engineer@10.20.30.41
```

engineers normally use:

```bash
ssh app-staging
```

At 09:15 UTC, an engineer reports:

> I can connect when I specify the correct IP, username, port, and key manually. But `ssh app-staging` fails with `Permission denied (publickey)`. Nothing seems wrong with the server.

The operations team initially suspects a problem with the SSH server.

However, the server is healthy.

The issue may be on the client.

Your task is to investigate how the SSH client interprets its configuration and determine whether it is connecting to the intended destination with the intended identity.

## 1.1 Simulated production environment

| Component | Value |
|---|---|
| Incident ID | INC-2026-SSHCFG-057 |
| Client | admin-workstation-01 |
| Alias | app-staging |
| Expected destination | 10.20.30.41 |

| Root cause | Initially unknown |
| Business impact | Approved remote administration through the standard alias is unavailable |

All addresses and hostnames in the production scenario are illustrative. Do not attempt to connect to them.

## 1.2 Why this incident matters

SSH configuration files can silently change:

- The destination hostname.
- The destination IP address.
- The username.
- The port.
- The identity file.
- The identities offered.
- The jump host.
- Host key verification behavior.
- Connection timeout behavior.
- Session keepalive behavior.

A working SSH server does not guarantee that every client alias is correct.

An incorrect client configuration can produce symptoms that resemble authentication, DNS, routing, or server problems.

This lab teaches you to identify the configuration actually being used rather than relying on assumptions about what the configuration file appears to say.

# 5. Safety Rules

SSH configuration affects remote access.

A configuration error can send connections to the wrong system, offer unintended credentials, or weaken server identity verification.

Follow these rules.

## 5.1 Do not modify your production SSH configuration

Do not edit:

```text
~/.ssh/config
```

or:

```text
/etc/ssh/ssh_config
```

for this lab.

Instead, use a dedicated configuration file selected with:

```bash
ssh -F FILE
```

## 5.2 Do not modify the system SSH server

Do not edit:

```text
/etc/ssh/sshd_config
```

Do not restart the system SSH service.

## 5.3 Do not disable host key checking

Avoid insecure settings such as:

```sshconfig
StrictHostKeyChecking no
```

as a troubleshooting shortcut.

Never use an empty or discarded known-host database to conceal unexpected host identity changes.

## 5.4 Do not expose private keys

The lab generates temporary credentials.

Do not publish them.

## 5.5 Do not enable agent forwarding unnecessarily

Agent forwarding introduces security risks when remote systems are not fully trusted.

This lab does not require agent forwarding.

## 5.6 Do not connect to unauthorized hosts

All required connection exercises use:

```text
127.0.0.1
```

## 5.7 Do not change firewall or routing rules

The lab does not require those changes.

## 5.8 Do not enable root login

Use your normal non-root account.

## 5.9 Keep console access

Use a disposable VM with independent console access.

## 5.10 Sanitize evidence

SSH debug output may contain internal paths, addresses, usernames, and key fingerprints.

Review evidence before publishing it.

# 6. Understanding SSH Client Configuration

The OpenSSH client can read configuration directives from files.

These directives define how the client should connect to different destinations.

Instead of typing a long command every time:

```bash
ssh -p 2222 -i ~/.ssh/work_key engineer@server.example
```

you can define an alias.

Example:

```sshconfig
Host staging
    HostName server.example
    User engineer
    Port 2222
    IdentityFile ~/.ssh/work_key
    IdentitiesOnly yes
```

Then connect using:

```bash
ssh staging
```

The client uses the settings associated with the alias.

## 6.1 Why engineers use SSH configuration

SSH configuration improves:

- Consistency.
- Readability.
- Operational efficiency.
- Identity separation.
- Troubleshooting.
- Automation.
- Documentation.
- Access governance.

## 6.2 Why configuration can become dangerous

A configuration file may contain incorrect or overlapping settings.

For example:

```sshconfig
Host *
    User admin

Host staging
    User engineer
```

A learner might expect `engineer` to override `admin`.

But OpenSSH commonly uses the first obtained value for many parameters.

Because the broad `Host *` block appears first, the later `User engineer` may not take effect.

That is why configuration ordering matters.

---

# 7. SSH Client Versus SSH Server Configuration

Do not confuse these two.

| Configuration | Purpose | Typical Location |
|---|---|---|
| SSH client configuration | Controls outgoing SSH connections | `~/.ssh/config` |
| System SSH client configuration | Provides system-wide client defaults | `/etc/ssh/ssh_config` |
| SSH server configuration | Controls incoming SSH connections | `/etc/ssh/sshd_config` |

## 7.1 Client configuration controls

Examples:

- Target hostname.
- Remote username.
- Destination port.
- Identity selection.
- Connection timeout.
- Jump host.
- Host key checking.

## 7.2 Server configuration controls

Examples:

- Listening address.
- Listening port.
- Allowed authentication methods.
- Root login policy.
- User restrictions.
- Authorized-key handling.

## 7.3 Important distinction

Setting:

```sshconfig
Port 22257
```

in the client configuration does not cause a server to listen on port 22257.

The server must already be listening on that port.

# 8. SSH Configuration File Locations

The usual per-user SSH client configuration is:

```text
~/.ssh/config
```

The usual system-wide client configuration is:

```text
/etc/ssh/ssh_config
```

Ubuntu may also include configuration fragments under:

```text
/etc/ssh/ssh_config.d/
```

## 8.1 Inspect system configuration

Run:

```bash
ls -l /etc/ssh/ssh_config
```

Then:

```bash
grep -nE '^[[:space:]]*(Include|Host|HostName|User|Port|IdentityFile)' \
  /etc/ssh/ssh_config
```

## 8.2 Inspect the user directory

```bash
ls -ld ~/.ssh 2>/dev/null
```

A missing user SSH directory is not automatically an error.

## 8.3 Configuration precedence

For many SSH client parameters, configuration is obtained from:

1. Command-line options.
2. User configuration.
3. System configuration.

The first obtained value is generally used.

However, certain options, including `IdentityFile`, can accumulate multiple values.

Do not treat every SSH directive as a simple last-value-wins setting.

# 11. Understanding the Host Directive

The `Host` directive defines which destination names or patterns a configuration block applies to.

Example:

```sshconfig
Host app-staging
```

This matches the alias:

```bash
ssh app-staging
```

## 11.1 Host is not necessarily a DNS hostname

The alias can be an arbitrary local name.

For example:

```sshconfig
Host my-training-server
    HostName 127.0.0.1
```

The client connects to `127.0.0.1` when you request `my-training-server`.

## 11.2 Multiple aliases

A Host block can match more than one pattern.

Example:

```sshconfig
Host staging staging-app
    HostName 127.0.0.1
```

Both aliases use the same settings.

## 11.3 Why aliases matter

Aliases allow engineers to represent operational roles instead of repeatedly typing addresses.

However, aliases must be maintained when infrastructure changes.

---

# 12. Understanding the HostName Directive

`HostName` defines the actual destination hostname or IP address.

Example:

```sshconfig
Host app-staging
    HostName 10.20.30.41
```

Here:

```text
app-staging
```

is the local alias.

```text
10.20.30.41
```

is the configured destination.

## 12.1 Common failure

An engineer updates a server's IP address but forgets to update the SSH alias.

The client may connect to the old address.

## 12.2 Troubleshooting command

```bash
ssh -G app-staging
```

Inspect:

```text
hostname
```

Do not assume the alias and actual destination are identical.

---

# 13. Understanding the User Directive

The `User` directive selects the remote login account.

Example:

```sshconfig
Host app-staging
    HostName 10.20.30.41
    User engineer
```

The client attempts to authenticate as:

```text
engineer
```

## 13.1 Why username matters

SSH authorization is account-specific.

A public key authorized for one account may not be authorized for another.

## 13.2 Common failure

The client connects to the correct server but uses the wrong username.

The result may be:

```text
Permission denied (publickey).
```

## 13.3 Troubleshooting

Inspect:

```bash
ssh -G app-staging | grep '^user '
```

For this lab, always include `-F client-config/config` when inspecting the isolated configuration.

---

# 14. Understanding the Port Directive

The `Port` directive specifies the destination TCP port.

Example:

```sshconfig
Host app-staging
    HostName 10.20.30.41
    Port 2222
```

## 14.1 Default port

Without an override, SSH normally uses TCP port 22.

## 14.2 Important distinction

The SSH client port must match the server's listening port.

## 14.3 Troubleshooting

```bash
ssh -F client-config/config -G jun057-demo \
  | grep '^port '
```

Expected:

```text
port 22257
```

# 23. Understanding IdentityFile

The `IdentityFile` directive identifies a private-key file or other supported identity source.

Example:

```sshconfig
IdentityFile ~/.ssh/work_ed25519
```

## 23.1 Common mistake

An engineer configures:

```sshconfig
IdentityFile ~/.ssh/old_key
```

but the authorized key belongs to:

```text
~/.ssh/new_key
```

Authentication may fail.

## 23.2 Important nuance

`IdentityFile` can be specified multiple times.

Unlike many scalar directives, multiple identity files can accumulate.

## 23.3 Why this matters

A configuration may offer more identities than expected.

Use:

```bash
ssh -G HOST
```

to inspect the effective identity file list.

---

# 24. Understanding IdentitiesOnly

The directive:

```sshconfig
IdentitiesOnly yes
```

helps restrict identity use to configured identities.

It is especially useful when an SSH agent contains multiple keys.

## 24.1 Does IdentitiesOnly disable ssh-agent?

No.

The client can still use the agent for a configured identity.

## 24.2 Does IdentitiesOnly guarantee authentication?

No.

The selected public key must still be authorized by the server.

## 24.3 Production lesson

Identity selection and server authorization are separate requirements.

# 27. Understanding Configuration Precedence

SSH configuration precedence is one of the most important topics in this lab.

For many directives, OpenSSH uses the first obtained value.

This means broad configuration blocks are commonly placed after specific blocks.

## 27.1 Correct ordering

```sshconfig
Host staging
    User engineer

Host *
    User defaultuser
```

For `staging`, the specific user is obtained first.

## 27.2 Problematic ordering

```sshconfig
Host *
    User defaultuser

Host staging
    User engineer
```

For `staging`, the broad block may set `User` before the specific block.

The later value may not override it.

## 27.3 Important exception

Some directives, such as `IdentityFile`, can accumulate values.

Always verify actual behavior using:

```bash
ssh -G
```

# 29. Understanding Wildcard Host Patterns

Matches a single character.

## 29.3 Negated patterns


Host patterns match the destination name being processed by SSH.

# 31. Understanding Include

The `Include` directive allows SSH configuration to load additional files.

- Team.
- Project.
- Cloud provider.
- Account type.

A large configuration file becomes difficult to maintain.

## 31.2 Important behavior

## 31.3 Security concern

An unexpected included file can introduce connection parameters that are difficult to notice.

Review included files and their ownership.

# 38. Understanding ServerAliveInterval

The directive:

```sshconfig
ServerAliveInterval 30
```

configures SSH protocol-level keepalive behavior.

## 38.1 What does it do?

When no data has been received from the server for the configured interval, the client can send a server-alive message.

## 38.2 What does it not do?

It does not repair broken networks.

It does not replace application health checks.

It is not the same as ICMP ping.

---

# 39. Understanding ServerAliveCountMax

The directive:

```sshconfig
ServerAliveCountMax 3
```

sets how many unanswered server-alive messages may be tolerated before the client disconnects.

## 39.1 Combined example

```sshconfig
ServerAliveInterval 30
ServerAliveCountMax 3
```

This can help the client detect an unresponsive SSH server.

## 39.2 Important nuance

The actual disconnection behavior depends on protocol activity and the specific OpenSSH implementation.

Do not treat the simple product of the two values as an exact universal wall-clock deadline.

# 46. Understanding StrictHostKeyChecking

This directive controls SSH client behavior when checking server host keys.

Important values include:

- `yes`
- `ask`
- `accept-new`
- `no`

## 46.1 StrictHostKeyChecking yes

Requires strict host key checking and does not automatically add new host keys.

This is appropriate when trusted host keys are provisioned in advance.

## 46.2 StrictHostKeyChecking ask

Prompts for confirmation when encountering a new host key.

Changed host keys remain security-sensitive.

## 46.3 StrictHostKeyChecking accept-new

Can automatically accept previously unknown host keys while refusing changed host keys.

This is not equivalent to independently verifying the identity of a new host.

## 46.4 StrictHostKeyChecking no

Weakens host key checking behavior and is not an appropriate routine troubleshooting shortcut.

## 46.5 Production rule

Choose host key checking policy according to the organization's trust model.

Never suppress an unexpected host key warning merely to complete a connection.

unless an approved workflow specifically requires forwarding.

# 75. Interview Preparation — 12 Questions with Worked Answers

## Interview Question 1 — Why do engineers use SSH configuration files?

**Answer:**

SSH configuration files make remote access more consistent by defining reusable aliases, usernames, ports, identities, and connection policies.

They reduce repetitive commands and help separate access between environments.

However, they must be maintained carefully because incorrect settings can cause authentication or destination errors.

## Interview Question 2 — What is the difference between Host and HostName?

**Answer:**

Host defines the alias or pattern matched by the SSH client.

HostName defines the actual destination hostname or IP address.

For example, `app-staging` may be the alias while `10.20.30.41` is the configured destination.

## Interview Question 3 — How does SSH configuration precedence work?

**Answer:**

For many directives, OpenSSH uses the first obtained value.

Command-line options generally have priority over user configuration, which generally precedes system configuration.

Specific Host blocks should normally appear before broad defaults.

Some directives, such as IdentityFile, are additive.

## Interview Question 4 — What does ssh -G do?

**Answer:**

It prints the effective SSH client configuration for a destination without establishing a network connection.

It is useful for verifying the selected hostname, username, port, identity files, and other settings.

## Interview Question 5 — What does ssh -F do?

**Answer:**

It selects an alternate SSH client configuration file.

This is useful for testing configuration safely without changing the user's normal SSH settings.

## Interview Question 6 — Why might an SSH alias use the wrong port?

**Answer:**

The Port directive may be incorrect, or an earlier matching Host block may have already supplied a different value.

I would inspect the effective configuration with `ssh -G` and review matching Host blocks and Include ordering.

## Interview Question 7 — What is the difference between IdentityFile and IdentitiesOnly?

**Answer:**

IdentityFile identifies an SSH identity file.

IdentitiesOnly helps restrict which identities the client offers.

Using both can make authentication more predictable when multiple keys or an SSH agent are present.

## Interview Question 8 — Why does Include ordering matter?

**Answer:**

Included configuration files are processed at the point where the Include directive appears.

Because many SSH options use first-value-wins behavior, an earlier broad setting can prevent a later included value from taking effect.

## Interview Question 9 — What is the purpose of ServerAliveInterval?

**Answer:**

It configures SSH protocol-level messages that help detect an unresponsive server connection.

It does not repair network failures or replace application monitoring.

## Interview Question 10 — What is ProxyJump?

**Answer:**

ProxyJump allows an SSH client to connect to a destination through an intermediate SSH host.

It is useful in controlled administrative access architectures where direct connections to internal systems are restricted.

## Interview Question 11 — Why should agent forwarding be disabled by default?

**Answer:**

Agent forwarding can expose an authentication capability to the remote environment.

A compromised remote host may misuse access to the forwarded agent while it is available.

It should only be enabled for an approved need.

## Interview Question 12 — What caused the simulated production SSH alias failure?

**Answer:**

The client's SSH alias still referenced an obsolete private key after key rotation.

The server authorized the replacement public key, but the alias offered the old identity.

The fix was to update the client configuration to select the approved replacement key and verify the complete connection workflow.

# 79. Final Engineering Lessons

You have now completed SSH Configuration Basics.

The most important lessons are:

**1. SSH configuration is part of the connection path.**

An incorrect client configuration can cause failures even when the server is healthy.

**2. Host aliases are conveniences, not guarantees.**

You must verify where an alias actually connects.

**3. Effective configuration is more reliable than assumptions.**

Use `ssh -G` to inspect the parameters OpenSSH will use.

**4. Configuration ordering matters.**

For many options, the first obtained value wins.

**5. Some directives accumulate values.**

IdentityFile is an important example.

**6. Include files are part of the effective configuration.**

Their ordering can change connection behavior.

**7. Identity selection must be deliberate.**

A client can offer the wrong key even when the correct key exists.

**8. Host key verification remains essential.**

Do not weaken server identity checks to resolve authentication problems.

**9. Keepalive settings do not repair network failures.**

They help detect certain connection problems.

**10. Jump-host settings are security-sensitive.**

They must follow approved access architecture.

**11. Agent forwarding should not be enabled casually.**

It exposes an authentication capability to the remote environment.

**12. Manual SSH success is valuable comparison evidence.**

If an explicit command works while an alias fails, compare the effective parameters.

**13. Production remediation should be minimal and authorized.**

Correct the configuration defect without unnecessarily changing server security.

**14. Recovery must verify the original workflow.**

The alias must connect to the intended host, authenticate with the intended identity, and complete the required operation.

**15. Good SSH configuration is documented, reviewed, and testable.**

Reliable access depends on both security and operational consistency.
