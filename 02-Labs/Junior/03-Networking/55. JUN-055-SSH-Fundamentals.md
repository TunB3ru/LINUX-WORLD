# 1. Production Mission — The Server Responds to Ping, but the Application Is Broken

You are a junior Linux engineer supporting a production application.

**Customer API requests are failing.**

# 5. Safety and Operational Boundaries

## 5.1 Authorized targets only

Use the local test server for all mandatory exercises.

Do not send requests to production APIs, administrative endpoints, payment systems, or third-party services without permission.

## 5.2 Never test state-changing operations against production casually

HTTP requests are not always harmless.

A POST request might:

- Create an order.
- Charge a payment method.
- Send an email.
- Trigger a deployment.
- Modify a database record.

A DELETE request might permanently remove information.

In this lab, POST requests go only to the controlled local server.

## 5.3 Protect credentials

Never publish:

- Authorization headers.
- API keys.
- Bearer tokens.
- Session cookies.
- Passwords.
- Private certificates.
- Sensitive request bodies.

Avoid putting real secrets directly into terminal commands, because commands can be recorded in shell history or exposed through process inspection.

## 5.4 Do not bypass TLS verification

Do not use:

```bash
curl -k https://production.example
```

as a routine workaround.

The `-k` option disables certificate verification for that request.

It can conceal certificate problems and expose the connection to interception risks.

This lab explains the option but does not require it.

## 5.5 Do not modify system networking

You will not:

- Change routes.
- Modify DNS settings.
- Change firewall rules.
- Restart networking.
- Disable certificate verification globally.
- Replace trusted certificate authorities.
- Expose a new listener on all interfaces.
- Restart production web services.

## 5.6 Evidence handling

Before publishing evidence:

- Remove sensitive hostnames and addresses.
- Remove credentials and tokens.
- Review response bodies.
- Remove cookies.
- Remove private API data.
- Confirm that the material is approved for public sharing.

# 6. Understanding HTTP Before Using curl

HTTP stands for **Hypertext Transfer Protocol**.

It is an application-layer protocol used to exchange requests and responses between clients and servers.

A client sends a request.

A server returns a response.

A web browser is an HTTP client.

The `curl` command-line tool can also act as an HTTP client.

## 6.1 Simplified HTTP exchange

```text
CLIENT                                  SERVER
curl                                    HTTP service

   |                                         |
   |  GET /health HTTP/1.1                   |
   |---------------------------------------->|
   |                                         |
   |  HTTP/1.1 200 OK                        |
   |  Content-Type: application/json         |
   |                                         |
   |  {"status":"ok"}                        |
   |<----------------------------------------|
   |                                         |
```

This is a simplified representation.

Real requests may include additional headers, authentication, redirects, and other protocol behavior.

## 6.2 HTTP request components

A request commonly includes:

- Method.
- Target path and query.
- Protocol version.
- Headers.
- Optional body.

Example:

```http
GET /health HTTP/1.1
Host: 127.0.0.1:18054
Accept: application/json
```

The method is `GET`.

The target is `/health`.

The request includes a `Host` header.

The client indicates that JSON is an acceptable response format.

## 6.3 HTTP response components

A response commonly includes:

- Status code.
- Response headers.
- Optional response body.

Example:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 15

{"status":"ok"}
```

The response status is `200`.

The content type is JSON.

The body contains a JSON object.

# 7. HTTP Versus HTTPS

HTTP and HTTPS are related, but they are not equivalent.

## 7.1 HTTP

A conventional HTTP/1.1 request over TCP does not provide transport encryption by itself.

Example:

```text
http://127.0.0.1:18054/health
```

The lab server uses HTTP because it is isolated to loopback and intended for controlled training.

## 7.2 HTTPS

HTTPS protects HTTP exchanges using TLS.

Example:

```text
https://api.internal.example:8443/health
```

TLS provides mechanisms for:

- Encryption.
- Integrity protection.
- Authentication of the server through certificate validation.

HTTPS does not guarantee that the application is free of vulnerabilities or that every request will succeed.

## 7.3 Simplified HTTPS connection sequence

```text
1. Resolve hostname
          |
          v
2. Select destination address
          |
          v
3. Establish TCP connection
          |
          v
4. Negotiate TLS
          |
          v
5. Validate certificate
          |
          v
6. Send HTTP request
          |
          v
7. Receive HTTP response
```

This is a useful model for typical HTTPS over TCP.

Modern HTTP/3 uses QUIC over UDP instead, so not every HTTP connection follows the TCP-based sequence.

This lab focuses primarily on HTTP/1.1 and HTTPS over TCP.

## 7.4 Why this matters

A request can fail at different stages.

| Stage | Example Failure |
|---|---|
| DNS | Hostname cannot be resolved |
| Routing | No usable route |
| TCP | Connection refused |
| TCP | Connection timed out |
| TLS | Certificate not trusted |
| TLS | Hostname mismatch |
| HTTP | 404 Not Found |
| HTTP | 503 Service Unavailable |
| Application | Response is syntactically valid but business result is wrong |

A good investigation identifies the failing stage rather than labeling every failure as a network problem.

# 9. Understanding curl

`curl` is a command-line tool for transferring data using supported protocols, including HTTP and HTTPS.

It is widely used by:

- Linux administrators.
- DevOps engineers.
- SREs.
- Platform engineers.
- Backend developers.
- Security engineers.
- Technical support teams.

## 9.1 Why engineers use curl

It allows you to inspect application behavior without requiring a graphical browser.

You can:

- Make requests.
- Inspect headers.
- Send JSON.
- Test methods.
- Control timeouts.
- Measure request timing.
- Inspect TLS behavior.
- Save responses.
- Investigate redirects.
- Reproduce API failures.

## 9.2 Basic syntax

```bash
curl [OPTIONS] URL
```

Example:

```bash
curl http://127.0.0.1:18054/health
```

The URL tells curl where to send the request.

Options control how the request is made and how the result is displayed.

# 11. Build the Local HTTP Test Server

You will now create the controlled application used throughout the lab.

The server uses Python's standard library.

It does not require Flask, Django, FastAPI, Docker, or external packages.

It binds only to:

```text
127.0.0.1:18054
```

This means it is not intentionally exposed to external interfaces.

## 11.1 Create the server file

Run:

```bash
nano server/http_lab_server.py
```

Paste the complete code below.

```python
#!/usr/bin/env python3

import json
import time
from datetime import datetime, timezone
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import parse_qs, urlsplit


HOST = "127.0.0.1"
PORT = 18054


class LabHandler(BaseHTTPRequestHandler):
    server_version = "VERIQTA-LabHTTP/1.0"
    protocol_version = "HTTP/1.1"

    def log_message(self, format_string, *args):
        timestamp = datetime.now(timezone.utc).isoformat()
        print(
            f"[{timestamp}] "
            f"{self.client_address[0]} "
            f"{format_string % args}",
            flush=True,
        )

    def send_bytes(self, status, body, content_type, extra_headers=None):
        self.send_response(status)
        self.send_header("Content-Type", content_type)
        self.send_header("Content-Length", str(len(body)))
        self.send_header("Cache-Control", "no-store")
        self.send_header("X-Lab-Server", "JUN-054")
        self.send_header("X-Request-ID", "jun054-local-request")

        if extra_headers:
            for name, value in extra_headers.items():
                self.send_header(name, value)

        self.end_headers()

        if self.command != "HEAD":
            try:
                self.wfile.write(body)
            except (BrokenPipeError, ConnectionResetError):
                pass

    def send_json(self, status, payload, extra_headers=None):
        body = json.dumps(
            payload,
            separators=(",", ":"),
        ).encode("utf-8")

        self.send_bytes(
            status,
            body,
            "application/json; charset=utf-8",
            extra_headers,
        )

    def do_HEAD(self):
        self.route_request()

    def do_GET(self):
        self.route_request()

    def do_POST(self):
        parsed = urlsplit(self.path)

        if parsed.path != "/api/v1/items":
            self.send_json(
                404,
                {"error": "endpoint_not_found"},
            )
            return

        content_type = self.headers.get("Content-Type", "")

        if "application/json" not in content_type.lower():
            self.send_json(
                415,
                {"error": "unsupported_media_type"},
            )
            return

        try:
            length = int(self.headers.get("Content-Length", "0"))
        except ValueError:
            self.send_json(
                400,
                {"error": "invalid_content_length"},
            )
            return

        if length < 1 or length > 4096:
            self.send_json(
                413,
                {"error": "invalid_body_size"},
            )
            return

        try:
            raw_body = self.rfile.read(length)
            payload = json.loads(raw_body.decode("utf-8"))
        except (UnicodeDecodeError, json.JSONDecodeError):
            self.send_json(
                400,
                {"error": "invalid_json"},
            )
            return

        if not isinstance(payload, dict):
            self.send_json(
                400,
                {"error": "json_object_required"},
            )
            return

        name = payload.get("name")

        if not isinstance(name, str) or not name.strip():
            self.send_json(
                422,
                {"error": "name_is_required"},
            )
            return

        self.send_json(
            201,
            {
                "id": 101,
                "name": name.strip(),
                "created": True,
                "persisted": False,
            },
            {"Location": "/api/v1/items/101"},
        )

    def route_request(self):
        parsed = urlsplit(self.path)
        path = parsed.path
        query = parse_qs(parsed.query)

        if path == "/":
            self.send_json(
                200,
                {
                    "service": "VERIQTA HTTP Lab",
                    "version": "1.0",
                    "endpoints": [
                        "/health",
                        "/ready",
                        "/api/v1/items",
                        "/redirect",
                        "/missing",
                        "/unauthorized",
                        "/forbidden",
                        "/server-error",
                        "/slow",
                        "/download",
                    ],
                },
            )

        elif path == "/health":
            self.send_json(
                200,
                {
                    "status": "ok",
                    "service": "http-lab",
                },
            )

        elif path == "/ready":
            self.send_json(
                200,
                {
                    "status": "ready",
                    "dependencies": {
                        "database": "simulated-ok",
                    },
                },
            )

        elif path == "/api/v1/items":
            try:
                limit = int(query.get("limit", ["3"])[0])
            except ValueError:
                self.send_json(
                    400,
                    {"error": "limit_must_be_integer"},
                )
                return

            if limit < 0 or limit > 10:
                self.send_json(
                    422,
                    {"error": "limit_out_of_range"},
                )
                return

            items = [
                {"id": 1, "name": "linux"},
                {"id": 2, "name": "networking"},
                {"id": 3, "name": "http"},
            ]

            self.send_json(
                200,
                {
                    "items": items[:limit],
                    "count": len(items[:limit]),
                },
            )

        elif path == "/redirect":
            self.send_bytes(
                302,
                b"",
                "text/plain",
                {"Location": "/health"},
            )

        elif path == "/missing":
            self.send_json(
                404,
                {"error": "resource_not_found"},
            )

        elif path == "/unauthorized":
            self.send_json(
                401,
                {"error": "authentication_required"},
                {"WWW-Authenticate": 'Bearer realm="lab"'},
            )

        elif path == "/forbidden":
            self.send_json(
                403,
                {"error": "access_denied"},
            )

        elif path == "/server-error":
            self.send_json(
                500,
                {"error": "simulated_internal_failure"},
            )

        elif path == "/unavailable":
            self.send_json(
                503,
                {
                    "status": "unavailable",
                    "dependency": "simulated-database",
                },
                {"Retry-After": "30"},
            )

        elif path == "/slow":
            try:
                delay = float(query.get("seconds", ["3"])[0])
            except ValueError:
                self.send_json(
                    400,
                    {"error": "invalid_delay"},
                )
                return

            if delay < 0 or delay > 10:
                self.send_json(
                    422,
                    {"error": "delay_out_of_range"},
                )
                return

            time.sleep(delay)

            self.send_json(
                200,
                {
                    "status": "completed",
                    "delay_seconds": delay,
                },
            )

        elif path == "/download":
            content = (
                "VERIQTA JUN-054 HTTP DOWNLOAD LAB\n"
                "This is a controlled local test file.\n"
            ).encode("utf-8")

            self.send_bytes(
                200,
                content,
                "text/plain; charset=utf-8",
                {
                    "Content-Disposition":
                    'attachment; filename="lab-download.txt"'
                },
            )

        else:
            self.send_json(
                404,
                {"error": "endpoint_not_found"},
            )


if __name__ == "__main__":
    server = ThreadingHTTPServer((HOST, PORT), LabHandler)

    print(
        f"VERIQTA HTTP lab listening on "
        f"http://{HOST}:{PORT}",
        flush=True,
    )

    try:
        server.serve_forever()
    except KeyboardInterrupt:
        print("\nStopping HTTP lab server.", flush=True)
    finally:
        server.server_close()
```

Save the file.

# 15. Understanding HTTP Methods

HTTP methods describe the intended operation on a resource.

| Method | Common Purpose | Important Consideration |
|---|---|---|
| GET | Retrieve a representation | Should have safe semantics |
| HEAD | Retrieve headers | No response body |
| POST | Submit data or trigger processing | May change server state |
| PUT | Create or replace resource state | Defined as idempotent |
| PATCH | Apply partial modifications | Idempotency depends on operation |
| DELETE | Remove a resource | Defined as idempotent, but may have side effects |

HTTP method semantics are defined by protocol specifications, but real applications can implement them incorrectly.

**Do not assume a request is safe merely because a developer labeled an endpoint as a health check.**

## 15.1 What does idempotent mean?

An operation is idempotent when repeating the same operation has the same intended effect on server state as performing it once.

For example, a correctly implemented PUT that sets a resource to a specific representation is idempotent.

Idempotency does not mean:

- Every repeated request returns the same response.
- The request cannot create logs.
- The request cannot trigger monitoring.
- The request is safe to perform without authorization.

## 15.2 GET is not POST

GET is normally used to retrieve information.

POST commonly submits information for processing.

The next exercise uses POST against the controlled local server only.

# 18. Understanding HTTP Status Codes

HTTP status codes are grouped into classes.

| Class | Range | General Meaning |
|---|---|---|
| 1xx | 100–199 | Informational |
| 2xx | 200–299 | Successful |
| 3xx | 300–399 | Redirection |
| 4xx | 400–499 | Client-error class |
| 5xx | 500–599 | Server-error class |

## 18.1 Common 2xx statuses

| Code | Meaning |
|---|---|
| 200 | OK |
| 201 | Created |
| 202 | Accepted |
| 204 | No Content |

A 202 response means the request has been accepted for processing, not necessarily completed.

## 18.2 Common 3xx statuses

| Code | Meaning |
|---|---|
| 301 | Moved Permanently |
| 302 | Found |
| 303 | See Other |
| 307 | Temporary Redirect |
| 308 | Permanent Redirect |

Redirect handling can affect methods and request bodies.

For example, 307 and 308 preserve the request method during redirect handling.

Do not blindly follow redirects for state-changing operations.

## 18.3 Common 4xx statuses

| Code | Meaning |
|---|---|
| 400 | Bad Request |
| 401 | Unauthorized |
| 403 | Forbidden |
| 404 | Not Found |
| 405 | Method Not Allowed |
| 408 | Request Timeout |
| 409 | Conflict |
| 413 | Content Too Large |
| 415 | Unsupported Media Type |
| 422 | Unprocessable Content |
| 429 | Too Many Requests |

The exact reason phrase displayed by a server may vary.

## 18.4 Common 5xx statuses

| Code | Meaning |
|---|---|
| 500 | Internal Server Error |
| 502 | Bad Gateway |
| 503 | Service Unavailable |
| 504 | Gateway Timeout |

These statuses help classify the observed HTTP outcome.

They do not, by themselves, identify the root cause.

For example, HTTP 502 may arise from several reverse-proxy-to-upstream problems.

# 21. curl Exit Codes Versus HTTP Status Codes

This is one of the most important concepts in the lab.

An HTTP status code is returned by the HTTP server.

A curl exit code describes the result of curl's own operation.

They are different.

## 21.1 Example — HTTP 404 with curl exit code 0

Run:

```bash
curl --noproxy '*' \
  -sS \
  -o /dev/null \
  -w 'HTTP=%{http_code}\n' \
  "$BASE_URL/missing"

echo "curl_exit=$?"
```

Expected:

```text
HTTP=404
curl_exit=0
```

Why?

Because curl successfully completed the HTTP transfer.

The server returned a valid HTTP 404 response.

By default, curl does not treat HTTP 404 as a transport failure.

## 21.2 Use --fail

Run:

```bash
curl --noproxy '*' \
  --fail \
  -sS \
  -o /dev/null \
  -w 'HTTP=%{http_code}\n' \
  "$BASE_URL/missing"

echo "curl_exit=$?"
```

Expected:

```text
HTTP=404
curl_exit=22
```

The `--fail` option causes curl to return a failure exit code for many HTTP responses with status 400 or higher.

Some authentication-related cases have documented limitations, so do not treat `--fail` as a complete policy engine.

## 21.3 Use --fail-with-body

Run:

```bash
curl --noproxy '*' \
  --fail-with-body \
  -sS \
  "$BASE_URL/unavailable"

echo "curl_exit=$?"
```

The response body remains available, and curl reports an HTTP-related failure.

This can be useful when error bodies contain diagnostic information.

## 21.4 Practical difference

| Behavior | Default curl | `--fail` | `--fail-with-body` |
|---|---|---|---|
| HTTP 200 | Successful transfer | Successful | Successful |
| HTTP 404 | Normally exit 0 | Normally exit 22 | Normally exit 22 |
| HTTP 503 | Normally exit 0 | Normally exit 22 | Normally exit 22 |
| Error body displayed | Yes | Usually suppressed | Preserved |
| Useful for scripts | With explicit status check | Yes | Yes |

## 21.5 Common curl exit codes

| Exit Code | Typical Meaning |
|---|---|
| 0 | Transfer completed successfully under curl's rules |
| 3 | URL malformed |
| 5 | Proxy could not be resolved |
| 6 | Host could not be resolved |
| 7 | Connection to host failed |
| 22 | HTTP response treated as failure with `--fail` behavior |
| 28 | Operation timed out |
| 35 | TLS/SSL connection error |
| 47 | Too many redirects |
| 60 | Certificate verification failed |

These codes are diagnostic categories, not complete root-cause explanations.

# 27. Follow-Along Lab 12 — Measure HTTP Request Timing

You will now inspect how long an HTTP request takes.

Run:

```bash
curl --noproxy '*' \
  -sS \
  -o /dev/null \
  -w 'DNS: %{time_namelookup}s\nConnect: %{time_connect}s\nStart Transfer: %{time_starttransfer}s\nTotal: %{time_total}s\n' \
  "$BASE_URL/health"
```

Illustrative output:

```text
DNS: 0.000021s
Connect: 0.000130s
Start Transfer: 0.000610s
Total: 0.000680s
```

Your values will differ.

## 27.1 time_namelookup

Time elapsed until name resolution is completed.

For a numeric loopback address, this is typically very small.

## 27.2 time_connect

Time elapsed from the start until the TCP connection is established, or the corresponding connection stage completes for the transport being used.

It is a cumulative timestamp, not merely an isolated TCP duration.

## 27.3 time_starttransfer

Time elapsed until the first response byte is received.

This includes preceding stages and server processing before the first byte.

## 27.4 time_total

Total time for the transfer.

## 27.5 Why cumulative timing matters

Suppose:

```text
time_namelookup = 0.020
time_connect = 0.080
time_starttransfer = 0.300
time_total = 0.350
```

The approximate time between DNS completion and connection completion is:

```text
0.080 - 0.020 = 0.060 seconds
```

The approximate time between connection completion and first response byte is:

```text
0.300 - 0.080 = 0.220 seconds
```

These differences help separate stages.

However, connection reuse, proxies, TLS, HTTP versions, and other factors can change interpretation.

Do not treat every difference as an exact measurement of one isolated component.

# 33. Understanding TLS Certificate Verification

HTTPS relies on TLS to protect the connection.

Certificate validation is a critical part of HTTPS security.

## 33.1 What curl normally checks

Depending on the TLS backend and configuration, curl validates:

- Certificate trust chain.
- Certificate validity.
- Requested hostname against certificate identity.
- Other relevant certificate constraints.

## 33.2 Common TLS problems

| Problem | Possible Symptom |
|---|---|
| Untrusted certificate authority | Certificate verification failure |
| Expired certificate | Certificate validity failure |
| Hostname mismatch | Certificate identity failure |
| Missing intermediate certificate | Trust-chain failure |
| Unsupported TLS configuration | TLS handshake failure |
| Protocol mismatch | Connection or TLS error |

## 33.3 What `-k` does

The option:

```text
-k
```

is shorthand for:

```text
--insecure
```

It disables certificate verification for the request.

It does not repair the certificate.

It does not make an insecure connection secure.

## 33.4 Correct engineering response

If a certificate fails verification:

1. Record the exact error.
2. Confirm the requested hostname.
3. Inspect the certificate identity.
4. Check validity dates.
5. Check the issuing authority.
6. Check the chain.
7. Review the server TLS configuration.
8. Escalate for authorized correction.
9. Retest with verification enabled.

Do not normalize certificate bypassing.

# 36. Follow-Along Lab 17 — Understand --resolve

The `--resolve` option lets curl use a specified address for a hostname and port combination.

It is useful when investigating:

- DNS cutovers.
- New backend deployments.
- Virtual-host routing.
- Certificate identity.
- Specific server addresses.

## 36.1 Local demonstration

Run:

```bash
curl --noproxy '*' \
  --resolve jun054.local:18054:127.0.0.1 \
  http://jun054.local:18054/health
```

Expected:

```json
{"status":"ok","service":"http-lab"}
```

## 36.2 What happened?

curl used:

```text
jun054.local
```

as the URL hostname while connecting to:

```text
127.0.0.1
```

on port:

```text
18054
```

No system-wide DNS record was created.

## 36.3 Why this matters for HTTPS

With HTTPS, the URL hostname remains important for TLS hostname verification and related connection behavior.

This is useful when testing a specific authorized server before DNS changes.

## 36.4 Important limitation

`--resolve` does not prove that normal DNS works.

It deliberately overrides address selection for the specified hostname and port.

## 36.5 Related option: --connect-to

The `--connect-to` option can direct a connection to a different host and port while preserving the original URL's application-level identity in relevant ways.

It is useful for advanced endpoint diagnostics.

Do not confuse it with changing the application's public DNS records.

## 51.1 Essential interpretation rules

1. HTTP 200 does not automatically mean the business operation succeeded.
2. HTTP 404 does not automatically mean the server is down.
3. HTTP 503 means the server or intermediary returned an HTTP unavailability response.
4. curl exit code 0 can accompany HTTP 4xx or 5xx responses.
5. `--fail` changes curl's handling of many HTTP error responses.
6. DNS success does not prove TCP connectivity.
7. TCP success does not prove TLS success.
8. TLS success does not prove HTTP success.
9. HTTP success does not prove backend dependency health.
10. A timeout does not identify its root cause by itself.
11. Redirects can change the effective destination.
12. Proxy configuration can change the observed connection path.
13. Certificate verification must remain enabled for normal HTTPS diagnostics.
14. Timing values are often cumulative.
15. Evidence must distinguish observation from inference.

# 56. Knowledge Assessment — 30 Questions and Answers

## Question 1 — What is HTTP?

HTTP is an application-layer protocol used for exchanging requests and responses between clients and servers.

## Question 2 — What is HTTPS?

HTTPS is HTTP protected using TLS.

## Question 3 — What does curl do?

curl transfers data using supported protocols and can make HTTP and HTTPS requests from the command line.

## Question 4 — Does ping test HTTP?

No. Ping normally tests ICMP Echo responsiveness.

## Question 5 — What is an HTTP method?

It identifies the intended operation, such as GET, HEAD, POST, PUT, PATCH, or DELETE.

## Question 6 — What does GET normally do?

It requests a representation of a resource.

## Question 7 — What does HEAD do?

It requests response headers without a response body.

## Question 8 — What does POST commonly do?

It submits data for processing and may change server state.

## Question 9 — What does HTTP 200 mean?

The server reports successful handling of the request under HTTP semantics.

It does not automatically prove business correctness.

## Question 10 — What does HTTP 201 mean?

The request resulted in a resource-creation outcome.

## Question 11 — What does HTTP 302 mean?

The resource is temporarily available at another location according to the redirect response.

## Question 12 — What does HTTP 400 mean?

The server reports that the request is invalid in a way covered by the Bad Request status.

## Question 13 — What does HTTP 401 mean?

The request lacks valid authentication credentials for the requested resource.

## Question 14 — What does HTTP 403 mean?

The server understands the request but refuses to fulfill it.

## Question 15 — What does HTTP 404 mean?

The server cannot find the requested resource or is not willing to disclose its existence.

## Question 16 — What does HTTP 500 mean?

The server reports an internal error condition that prevented it from fulfilling the request.

## Question 17 — What does HTTP 502 mean?

A gateway or proxy received an invalid response from an upstream server.

## Question 18 — What does HTTP 503 mean?

The service is currently unable to handle the request, commonly because of overload or maintenance, though application-specific causes vary.

## Question 19 — What does HTTP 504 mean?

A gateway or proxy did not receive a timely response from an upstream server.

## Question 20 — Can curl return exit code 0 for HTTP 500?

Yes. By default, a completed HTTP transfer can produce exit code 0 even when the server returns HTTP 500.

## Question 21 — What does --fail do?

It causes curl to treat many HTTP responses with status 400 or higher as failures.

## Question 22 — What does --fail-with-body do?

It preserves the response body while reporting HTTP failure behavior.

## Question 23 — What does -L do?

It tells curl to follow redirects.

## Question 24 — What does -H do?

It adds a request header.

## Question 25 — What does --max-time control?

The overall time limit for the curl operation.

## Question 26 — What does --connect-timeout control?

The allowed time for establishing the connection, including relevant preliminary stages.

## Question 27 — What does time_starttransfer measure?

The cumulative time until the first response byte is received.

## Question 28 — Why is curl -k dangerous as a routine fix?

It disables TLS certificate verification and can conceal trust or identity problems.

## Question 29 — Why might /health return 200 while /ready returns 503?

The application process may be alive but unable to serve traffic because a required dependency or readiness condition is not satisfied.

## Question 30 — What is the most important verification after fixing an HTTP incident?

Confirm that the original affected application operation succeeds, including its expected response and business behavior.

# 57. Interview Preparation — 12 Questions with Worked Answers

## Interview Question 1 — How would you investigate an HTTP endpoint that users say is down?

**Answer:**

I would first identify the exact URL, method, expected response, affected clients, and business impact.

Then I would investigate DNS, route selection, TCP connectivity, TLS verification, HTTP status, headers, body, and request timing.

I would correlate the results with application logs and monitoring before confirming a root cause.

I would verify the original user operation after any authorized remediation.

## Interview Question 2 — What is the difference between curl and ping?

**Answer:**

Ping normally tests ICMP Echo responsiveness.

curl can make HTTP and HTTPS requests and inspect application-layer responses.

A host can respond to ping while its HTTP application is failing.

## Interview Question 3 — Why can curl return exit code 0 when the server returns HTTP 404?

**Answer:**

Because curl may have completed the HTTP transfer successfully.

The HTTP status describes the server's response, while the curl exit code describes curl's operation.

Using `--fail` changes how many HTTP error responses affect the exit code.

## Interview Question 4 — How would you investigate HTTP 503?

**Answer:**

I would confirm whether the response comes from the application, reverse proxy, or another intermediary.

Then I would inspect readiness, dependencies, resource utilization, application logs, upstream health, and request correlation.

I would not assume that the host or network is down.

## Interview Question 5 — What is the difference between connection refused and HTTP 503?

**Answer:**

Connection refused indicates that the TCP connection attempt was rejected before a normal HTTP exchange could complete.

HTTP 503 means an HTTP response was received indicating service unavailability.

They represent different failure stages.

## Interview Question 6 — How do you inspect response headers with curl?

**Answer:**

I can use:

```bash
curl -i URL
```

to display headers with the body, or:

```bash
curl -D - -o /dev/null URL
```

to display response headers while discarding the body.

## Interview Question 7 — How would you measure API response time?

**Answer:**

I would use curl's write-out variables, including `time_namelookup`, `time_connect`, `time_appconnect`, `time_starttransfer`, and `time_total`.

I would interpret them as cumulative timing measurements and compare them with server-side telemetry.

## Interview Question 8 — Why should you not use curl -k in production troubleshooting?

**Answer:**

Because it disables certificate verification and can hide certificate trust or hostname problems.

I would investigate the actual certificate and TLS configuration instead.

## Interview Question 9 — What is the difference between liveness and readiness?

**Answer:**

Liveness generally indicates whether the application process should be considered alive.

Readiness generally indicates whether it can accept traffic and perform required operations.

An application can be alive but not ready.

## Interview Question 10 — How do proxies affect curl?

**Answer:**

A proxy can change the connection path, destination resolution, TLS behavior, headers, and error origin.

I would inspect proxy configuration and determine whether the observed response came from the proxy or the application.

## Interview Question 11 — What is --resolve used for?

**Answer:**

It allows curl to use a specified address for a hostname and port.

It is useful for authorized virtual-host, certificate, and deployment testing without changing system-wide DNS.

It does not prove normal DNS resolution works.

## Interview Question 12 — What would you do if HTTP 200 is returned but users still report failures?

**Answer:**

I would validate the response body, schema, required fields, authentication context, business operation, and downstream dependencies.

HTTP 200 alone is not sufficient evidence that the complete user workflow is functioning correctly.

# 61. Final Engineering Lessons

You have now completed a practical introduction to HTTP and application-layer troubleshooting on Linux.

The most important lessons are:

**1. Network reachability and application availability are not the same thing.**

A host may respond to ping while its HTTP service is unavailable.

**2. HTTP failures must be classified by stage.**

DNS, routing, TCP, TLS, HTTP, and application dependencies can fail independently.

**3. An HTTP status code is not a curl exit code.**

A completed transfer can return curl exit code 0 even when the server reports HTTP 500.

**4. HTTP 200 is not a complete business-health guarantee.**

The response body and expected operation still matter.

**5. Headers are important diagnostic evidence.**

They can reveal redirects, content types, authentication challenges, request identifiers, and retry guidance.

**6. Timeouts require careful interpretation.**

A timeout indicates that an operation exceeded a configured time limit. It does not automatically identify the underlying cause.

**7. Timing fields help narrow the investigation.**

DNS, connection, TLS, first-byte, and total-time measurements can guide the next diagnostic step.

**8. TLS verification is a security requirement.**

Disabling verification is not an acceptable routine workaround.

**9. Proxies can change what you observe.**

The response may originate from an intermediary rather than the destination application.

**10. Liveness and readiness are different.**

A process can be alive but unable to serve traffic because a dependency is unhealthy.

**11. Production incidents require corroborating evidence.**

Use client observations together with logs, metrics, traces, and deployment information.

**12. Recovery must be verified at the level of the original user problem.**

A successful ping, TCP connection, or basic HTTP 200 response is not enough if the affected business operation still fails.
