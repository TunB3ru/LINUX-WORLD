# 1. Welcome to the Lab

Linux systems continuously produce information about their operation.

Services start and stop. Applications accept requests. Authentication attempts succeed or fail. Scheduled jobs execute. Filesystems report problems. The kernel records important events. Scripts write diagnostics.

Much of this information appears in logs.

A Linux engineer who understands logging can reconstruct events, identify failure patterns, distinguish symptoms from root causes, and provide evidence for operational decisions.

A Linux engineer who does not understand logging may be forced to guess.

In this lab, you will learn how Linux logging works from the ground up. You will examine traditional log files, investigate the systemd journal, generate your own events, build a structured application log, and create a command-line investigation tool.

You will also practice one of the most important operational distinctions:

> A log message is evidence of something that was recorded. It is not automatically proof of everything that happened before or after that message.

For example, an application might log:

```
INFO deployment started
```

That does not prove the deployment completed.

Similarly:

```
ERROR database unavailable
```

does not prove the database server itself failed. The cause could be a network interruption, invalid credentials, a timeout, or an application configuration error.

Your job is to interpret logs carefully, correlate them with other evidence, and avoid unsupported conclusions.

# Part 1 — Understand Linux Logging

## 6. What Is a Log?

A log is a record of events emitted by software or a system component.

A useful log entry commonly includes:

- Timestamp.
- Source.
- Severity.
- Event description.
- Contextual identifiers.
- Relevant operational details.

Example:

```
2026-10-17T09:13:05Z ERROR orders-api request_id=req-1042 event=database_timeout
```

This tells you:

- When: `2026-10-17T09:13:05Z`
- Severity: `ERROR`
- Source: `orders-api`
- Request: `req-1042`
- Event: `database_timeout`

The message does not, by itself, establish why the database request timed out.

That requires additional investigation.

## 7. Major Linux Log Categories

| Category           | Typical information                         | Common source                  |
| ------------------ | ------------------------------------------- | ------------------------------ |
| Kernel             | Hardware, drivers, filesystem events        | Kernel, journal, `dmesg`       |
| System services    | Service starts, stops, failures             | systemd units, daemons         |
| Authentication     | Login and authorization activity            | PAM, sshd, sudo                |
| Application        | Requests, failures, lifecycle events        | Application logging            |
| Scheduled tasks    | Cron launches, script output                | Cron, application logs         |
| Package management | Installations and upgrades                  | APT and dpkg logs              |
| Security auditing  | Policy-relevant events                      | Audit subsystem, if configured |
| Boot               | Startup sequence and service initialization | systemd journal                |
| Network            | Interface and connection events             | Network services and kernel    |

Different systems store and route these records differently.

A modern Ubuntu host may use both the systemd journal and traditional text log files.

## 8. Logging Is Not the Same as Monitoring

Logging records events.

Monitoring evaluates system conditions and may produce alerts.

For example:

```
Log:
2026-10-17T09:13:05Z ERROR database timeout
```

A monitoring rule might detect:

```
More than 20 database timeout errors in 5 minutes
```

and trigger an alert.

Logs provide evidence.

Monitoring turns selected evidence and measurements into operational signals.

The two are complementary.

## 9. Logging Is Not the Same as Auditing

Operational logs primarily help with troubleshooting and understanding system behavior.

Audit logs are designed to record security-relevant actions under defined controls.

For example:

- A service log may record that a configuration reload occurred.
- An audit record may identify the process and security context involved in modifying a protected file.

Audit systems can provide stronger controls, but their effectiveness depends on configuration, integrity protections, and access policies.

Do not assume ordinary application logs are tamper-proof.

# Part 2 — Logging Architecture on Ubuntu

## 10. Understand the Main Components

A simplified Ubuntu logging architecture may look like:

```
Applications ──────┐
                   │
systemd services ──┼──> systemd-journald ──> journalctl
                   │             │
Kernel ────────────┘             │
                                 └──> Optional forwarding
                                            │
                                            v
                                      rsyslog / syslog
                                            │
                                            v
                                       /var/log files
```

Not every host uses the same configuration.

Some environments:

- Use journald without rsyslog.
- Forward logs to remote collectors.
- Use container logging drivers.
- Write application logs directly to files.
- Store logs in centralized observability platforms.

The diagram is a conceptual model, not a guarantee about every Ubuntu installation.

## 11. What Is systemd-journald?

`systemd-journald` is the systemd service responsible for collecting and storing journal records.

It can collect information from sources including:

- Service stdout and stderr.
- Syslog-compatible messages.
- Kernel messages.
- Native journal APIs.
- Other supported logging interfaces.

You typically inspect these records using:

```
journalctl
```

Journal entries may contain structured metadata in addition to the visible message text.

## 12. What Is rsyslog?

`rsyslog` is a logging daemon commonly used for syslog-compatible collection, processing, routing, and forwarding.

On systems where it is installed and configured, it may write records to files such as:

```
/var/log/syslog
/var/log/auth.log
```

Do not assume those files exist on every host.

Verify the actual configuration.

## 13. What Is the syslog Protocol?

Syslog is a family of conventions and standards for representing and transporting log messages.

Traditional syslog concepts include:

- Facility.
- Severity.
- Timestamp.
- Host.
- Application or program.
- Message.

Syslog can be used locally or across a network.

A remote logging design must consider transport security, authentication, reliability, and retention.

This lab focuses on local fundamentals.

# Part 4 — Your First journalctl Commands

## 19. Display Recent Journal Entries

Run:

```
journalctl -n 20 --no-pager
```

This requests the most recent 20 journal entries visible to your user.

If the journal is accessible, you should see timestamped records.

If access is restricted, you may see a permissions-related notice or a limited set of entries.

Record what your environment allows.

## 20. Follow the Journal Live

Run:

```
journalctl -f
```

This follows new journal records as they arrive.

To stop:

```
Ctrl+C
```

Do not leave a long-running follow command unattended.

For a bounded observation, use:

```
timeout 15s journalctl -f --no-pager
```

A timeout exit status does not necessarily mean journald failed. It may simply indicate that the observation window ended.

## 21. Inspect Journal Entries from the Current Boot

Run:

```
journalctl -b -n 30 --no-pager
```

The `-b` option selects the current boot.

To list available boots:

```
journalctl --list-boots --no-pager
```

You may see only the current boot if persistent journal history is unavailable.

## 22. Filter by systemd Unit

Inspect the SSH service if present:

```
systemctl list-unit-files 'ssh.service' --no-pager
```

Then:

```
journalctl -u ssh.service -n 20 --no-pager
```

The unit may be named differently or may not be installed.

Another useful service on a systemd-based Ubuntu host is:

```
journalctl -u systemd-journald.service -n 20 --no-pager
```

### Why unit filtering matters

On a busy host, the journal may contain events from hundreds of processes.

Filtering by unit narrows the investigation to the relevant service context.

## 23. Filter by Time

Run:

```
journalctl --since '1 hour ago' --no-pager
```

Then:

```
journalctl \
    --since '30 minutes ago' \
    --until '10 minutes ago' \
    --no-pager
```

Relative time expressions are useful for exploratory investigation.

For formal incident evidence, record exact timestamps and the timezone used.

## 24. Use UTC Timestamps

Run:

```
journalctl \
    --utc \
    --since '1 hour ago' \
    -n 30 \
    --no-pager
```

UTC simplifies correlation across systems in different timezones.

For a distributed incident, one server may use local time while another logs in UTC.

Without normalization, a timeline can be misleading.

## 25. Filter by Priority

Run:

```
journalctl -p warning -n 30 --no-pager
```

This selects messages at warning severity and more severe priorities.

Try:

```
journalctl -p err -n 30 --no-pager
```

The absence of visible errors does not prove the system has no problems.

It may mean:

- No matching records exist.
- Your account lacks access.
- The application did not log the failure.
- The selected time or boot scope excludes relevant entries.

## 26. Use a Precise Priority Range

Run:

```
journalctl -p warning..warning -n 20 --no-pager
```

This selects only warning-priority entries on journalctl implementations supporting priority ranges.

Compare it with:

```
journalctl -p warning -n 20 --no-pager
```

The second command includes warnings and more severe messages.

Understanding this distinction prevents inaccurate log summaries.

# Part 5 — Syslog Severity Levels

## 27. Learn the Eight Standard Severities

Syslog severity levels range from `0` to `7`.

| Number | Name          | Meaning                         |
| ------ | ------------- | ------------------------------- |
| 0      | Emergency     | System is unusable              |
| 1      | Alert         | Immediate action is required    |
| 2      | Critical      | Critical condition              |
| 3      | Error         | Error condition                 |
| 4      | Warning       | Warning condition               |
| 5      | Notice        | Normal but significant event    |
| 6      | Informational | Informational message           |
| 7      | Debug         | Detailed diagnostic information |

Lower numeric values represent higher severity.

This ordering is easy to confuse.

A priority of `3` is more severe than a priority of `6`.

## 28. Understand Log Levels in Applications

Applications often use names such as:

```
TRACE
DEBUG
INFO
WARN
ERROR
FATAL
```

These names are not identical to the syslog severity names.

An application must define how its own levels map to syslog priorities.

For this lab's structured application logs, you will use:

```
DEBUG
INFO
WARN
ERROR
CRITICAL
```

Your analysis script will define its own explicit ordering.

Do not assume that every logging framework uses exactly the same level names or semantics.

# Part 7 — Understand Journal Metadata

## 32. View Structured Journal Output

Run:

```
journalctl \
    -t veriqta-jun069 \
    --since '10 minutes ago' \
    -o verbose \
    -n 5 \
    --no-pager
```

You may see fields such as:

```
MESSAGE=
PRIORITY=
SYSLOG_IDENTIFIER=
_PID=
_UID=
_HOSTNAME=
_SYSTEMD_UNIT=
```

Not every entry contains every field.

Some fields are provided by the journal infrastructure; others may be supplied by the logging application.

## 33. View JSON Journal Output

Run:

```
journalctl \
    -t veriqta-jun069 \
    --since '10 minutes ago' \
    -o json \
    -n 3 \
    --no-pager
```

This produces JSON records.

Structured output is useful when another program needs to analyze journal data.

However, journal records may contain binary or unusual field values, and the JSON representation can vary in how such values are encoded.

Use a proper JSON parser rather than assuming every field is a simple string.

## 34. Understand Trusted Metadata

Some journal fields beginning with an underscore are populated or verified by journald rather than accepted as arbitrary application-supplied fields.

Examples may include:

```
_UID
_PID
_SYSTEMD_UNIT
```

These fields can help identify the process context associated with a message.

However, logging metadata is still not a substitute for a complete forensic chain of custody.

Processes can exit, PIDs can be reused, and logs may be incomplete or subject to retention.

## 38. Essential Log Inspection Commands

| Command                  | Purpose                              |
| ------------------------ | ------------------------------------ |
| `head -n 20 file`        | Show the first 20 lines              |
| `tail -n 20 file`        | Show the last 20 lines               |
| `tail -f file`           | Follow appended lines                |
| `grep 'ERROR' file`      | Find matching text                   |
| `grep -n 'ERROR' file`   | Include line numbers                 |
| `grep -i 'timeout' file` | Case-insensitive search              |
| `grep -F 'literal' file` | Fixed-string matching                |
| `awk '{print $1}' file`  | Extract a whitespace-delimited field |
| `sort file`              | Sort lines                           |
| `uniq -c`                | Count adjacent identical lines       |
| `wc -l file`             | Count newline characters             |

These commands are useful, but their behavior depends on the log format.

For example, whitespace-based `awk` parsing is fragile when a field can contain spaces.

# Part 11 — Understand Timestamps

## 43. UTC and Local Time

Run:

```

```

Then:

```

```

Then:

```

```

The final command produces an ISO 8601-style UTC timestamp.

Example:

```

```

The trailing `Z` indicates UTC.

## 44. Event Time Versus Ingestion Time

An application may record an event at:

```
09:13:05
```

But a centralized collector may receive it at:

```
09:13:08
```

These are different timestamps.

In distributed systems, network delay, buffering, clock drift, and retry behavior can affect when a record becomes visible.

When reconstructing an incident, identify which timestamp each system uses.

## 45. Clock Synchronization

On a systemd-based host, inspect:

```

```

```

NTP service:
```

These fields describe the local host's time configuration.

A synchronized clock improves cross-host correlation, but does not guarantee perfect timestamp ordering across all distributed components.

# Part 12 — Log Rotation and Retention

## 46. Why Logs Cannot Grow Forever

Logs consume storage.

If a busy application writes 1 GB of logs per day, retaining every file indefinitely can exhaust a filesystem.

Log retention requires an explicit policy.

Common controls include:

- Rotation.
- Compression.
- Age-based retention.
- Size-based retention.
- Centralized storage.
- Access restrictions.
- Integrity controls.
- Backup or archival requirements.

## 47. What Is logrotate?

`logrotate` is a utility commonly used to rotate, compress, and remove old text log files according to configuration.

Check availability:

```
command -v logrotate
```

Inspect the main configuration if readable:

```
if [[ -r /etc/logrotate.conf ]]; then
    sed -n '1,120p' /etc/logrotate.conf
fi
```

List configuration files:

```
ls -l /etc/logrotate.d 2>/dev/null
```

Do not modify system logrotate configuration in this lab.

## 48. Common logrotate Concepts

| Directive      | Typical purpose                                                   |
| -------------- | ----------------------------------------------------------------- |
| `daily`        | Rotate on a daily schedule                                        |
| `weekly`       | Rotate weekly                                                     |
| `monthly`      | Rotate monthly                                                    |
| `rotate N`     | Retain a specified number of rotated files                        |
| `compress`     | Compress rotated logs                                             |
| `missingok`    | Do not error if the log is absent                                 |
| `notifempty`   | Avoid rotating empty logs                                         |
| `create`       | Create a replacement log file with configured attributes          |
| `postrotate`   | Run commands after rotation                                       |
| `copytruncate` | Copy then truncate the active file, with potential data-loss race |

Rotation behavior depends on configuration and execution.

Do not assume a rotated file is automatically backed up.

## 49. Journal Retention Is Different

The systemd journal manages its own storage and retention behavior.


If available, you may see a summary of archived and active journal usage.

Do not run journal vacuum or deletion commands in this lab.

Your objective is to understand storage, not alter the host's retention policy.

# Part 13 — Design Structured Application Logs

## 50. Why Structured Logs Matter

Unstructured logs are written primarily for humans:

```
Something went wrong while connecting to the database.
```

Structured logs organize information into predictable fields:

```
timestamp=2026-10-17T09:13:05Z level=ERROR service=orders-api event=database_timeout request_id=req-1042
```

Structured fields make filtering and aggregation easier.

For larger systems, JSON Lines is also common:

```
{"timestamp":"2026-10-17T09:13:05Z","level":"ERROR","service":"orders-api","event":"database_timeout","request_id":"req-1042"}
```

For this lab, the final investigation tool will analyze a deliberately constrained, pipe-delimited format.

That lets you practice parsing, validation, filtering, and reporting with Bash and standard Linux utilities.

The format is educational. A production logging system should use an established structured logging format and an appropriate parser.

## 51. Define the Lab's Structured Log Format

Each record will contain exactly six fields:

```
TIMESTAMP|LEVEL|SERVICE|EVENT|REQUEST_ID|MESSAGE
```

Example:

```
2026-10-17T09:13:05Z|ERROR|orders-api|database_timeout|req-1042|Database request exceeded timeout
```

### Field contracts

| Field      | Required format                                                        |
| ---------- | ---------------------------------------------------------------------- |
| Timestamp  | UTC, `YYYY-MM-DDTHH:MM:SSZ`                                            |
| Level      | `DEBUG`, `INFO`, `WARN`, `ERROR`, `CRITICAL`                           |
| Service    | Lowercase letters, digits, hyphens; begins with a lowercase letter     |
| Event      | Lowercase letters, digits, underscores; begins with a lowercase letter |
| Request ID | Letters, digits, underscores, or hyphens                               |
| Message    | Printable text without pipe characters or control characters           |

The final tool will validate these fields.

It will also reject malformed records instead of silently treating them as valid.

# Part 15 — Build a Reusable Log Writer

## 59. Why Create a Logging Function?

Your earlier automation scripts used `printf` to report success and failure.

You can improve consistency by centralizing logging behavior.

A reusable logger should:

- Accept a severity.
- Accept an event name.
- Accept a request identifier.
- Accept a message.
- Produce a timestamp.
- Write a complete record.
- Reject malformed values.
- Preserve a meaningful exit code.

## 60. Create a Bash Logging Library

Run:

```
cat > lib/logging.sh <<'BASH'
#!/usr/bin/env bash

veriqta_log() {
    if (( $# != 5 )); then
        printf 'ERROR: Expected level, service, event, request ID, message\n' >&2
        return 2
    fi

    local level="$1"
    local service="$2"
    local event="$3"
    local request_id="$4"
    local message="$5"
    local timestamp=""

    case "$level" in
        DEBUG|INFO|WARN|ERROR|CRITICAL)
            ;;
        *)
            printf 'ERROR: Invalid log level\n' >&2
            return 2
            ;;
    esac

    if [[ ! "$service" =~ ^[a-z][a-z0-9-]*$ ||
          ! "$event" =~ ^[a-z][a-z0-9_]*$ ||
          ! "$request_id" =~ ^[A-Za-z0-9_-]+$ ]]; then
        printf 'ERROR: Invalid structured log identifier\n' >&2
        return 2
    fi

    if [[ -z "$message" ||
          "$message" == *'|'* ||
          "$message" == *$'\n'* ||
          "$message" == *$'\r'* ||
          "$message" == *$'\t'* ]]; then
        printf 'ERROR: Invalid log message\n' >&2
        return 2
    fi

    if [[ "$message" =~ [^[:print:]] ]]; then
        printf 'ERROR: Nonprintable log message\n' >&2
        return 2
    fi

    timestamp="$(date -u '+%Y-%m-%dT%H:%M:%SZ')" || return 3

    printf '%s|%s|%s|%s|%s|%s\n' \
        "$timestamp" \
        "$level" \
        "$service" \
        "$event" \
        "$request_id" \
        "$message"
}
BASH
```

This function writes to stdout, so the caller decides whether to display the record or append it to a file.

## 64. Create the Final Script

Run:

```
cat > scripts/veriqta-log-investigator.sh <<'BASH'

set -u
set -o pipefail

export LC_ALL=C

LAB_ROOT="$(

)" || exit 3

INPUT_ROOT="$LAB_ROOT/fixtures/structured"
REPORT_ROOT="$LAB_ROOT/reports"

COMMAND=""
INPUT=""
LEVEL=""
SERVICE=""
EVENT=""
REQUEST_ID=""
SINCE=""
UNTIL=""

usage() {
    cat <<'EOF'
VERIQTA Linux Log Investigator

Usage:
  veriqta-log-investigator.sh validate --input PATH

  YYYY-MM-DDTHH:MM:SSZ

  0  Success
  2  Invalid arguments
  3  Operational failure
  4  Malformed log records
  6  No matching records

}

error() {
    printf 'ERROR: %s\n' "$*" >&2
}

valid_timestamp() {
    local value="$1"
    local normalized=""

    if [[ ! "$value" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$ ]]; then
        return 1
    fi

    normalized="$(
        date -u -d "$value" '+%Y-%m-%dT%H:%M:%SZ' 2>/dev/null
    )" || return 1

    [[ "$normalized" == "$value" ]]
}

valid_level() {
    case "$1" in
        DEBUG|INFO|WARN|ERROR|CRITICAL)
            return 0
            ;;
        *)
            return 1
            ;;
    esac
}

parse_arguments() {
    if (( $# == 1 )) && [[ "$1" == "--help" ]]; then
        usage
        return 10
    fi

    if (( $# == 0 )); then
        usage >&2
        return 2
    fi

    COMMAND="$1"
    shift

    case "$COMMAND" in
        validate|summary|filter|timeline)
            ;;
        *)
            error "Unknown command: $COMMAND"
            return 2
            ;;
    esac

    while (( $# > 0 )); do
        case "$1" in
            --input|--level|--service|--event|--request-id|--since|--until)
                if (( $# < 2 )); then
                    error "Missing value for $1"
                    return 2
                fi

                case "$1" in
                    --input) INPUT="$2" ;;
                    --level) LEVEL="$2" ;;
                    --service) SERVICE="$2" ;;
                    --event) EVENT="$2" ;;
                    --request-id) REQUEST_ID="$2" ;;
                    --since) SINCE="$2" ;;
                    --until) UNTIL="$2" ;;
                esac

                shift 2
                ;;

            *)
                error "Unknown option: $1"
                return 2
                ;;
        esac
    done

    if [[ -z "$INPUT" ]]; then
        error "--input is required"
        return 2
    fi

    if [[ "$COMMAND" != "filter" ]] &&
       [[ -n "$LEVEL$SERVICE$EVENT$REQUEST_ID$SINCE$UNTIL" ]]; then
        error "Filter options require the filter command"
        return 2
    fi

    if [[ -n "$LEVEL" ]] && ! valid_level "$LEVEL"; then
        error "Invalid severity level"
        return 2
    fi

    if [[ -n "$SERVICE" &&
          ! "$SERVICE" =~ ^[a-z][a-z0-9-]*$ ]]; then
        error "Invalid service name"
        return 2
    fi

    if [[ -n "$EVENT" &&
          ! "$EVENT" =~ ^[a-z][a-z0-9_]*$ ]]; then
        error "Invalid event name"
        return 2
    fi

    if [[ -n "$REQUEST_ID" &&
          ! "$REQUEST_ID" =~ ^[A-Za-z0-9_-]+$ ]]; then
        error "Invalid request ID"
        return 2
    fi

    if [[ -n "$SINCE" ]] && ! valid_timestamp "$SINCE"; then
        error "Invalid --since timestamp"
        return 2
    fi

    if [[ -n "$UNTIL" ]] && ! valid_timestamp "$UNTIL"; then
        error "Invalid --until timestamp"
        return 2
    fi

    if [[ -n "$SINCE" && -n "$UNTIL" &&
          "$SINCE" > "$UNTIL" ]]; then
        error "--since must not be later than --until"
        return 2
    fi

    return 0
}

validate_input() {
    local canonical_root=""
    local canonical_input=""

    if [[ ! -d "$INPUT_ROOT" || -L "$INPUT_ROOT" ]]; then
        error "Structured fixture root is unavailable"
        return 3
    fi

    canonical_root="$(realpath -e -- "$INPUT_ROOT")" ||
        return 3

    if [[ -L "$INPUT" ]]; then
        error "Symbolic-link input rejected"
        return 3
    fi

    canonical_input="$(realpath -e -- "$INPUT")" || {
        error "Input path does not exist"
        return 3
    }

    case "$canonical_input" in
        "$canonical_root"|"$canonical_root"/*)
            ;;
        *)
            error "Input must be inside fixtures/structured"
            return 3
            ;;
    esac

    if [[ ! -f "$canonical_input" &&
          ! -d "$canonical_input" ]]; then
        error "Input must be a regular file or directory"
        return 3
    fi

    if [[ ! -r "$canonical_input" ]]; then
        error "Input is not readable"
        return 3
    fi

    INPUT="$canonical_input"

    return 0
}

make_input_manifest() {
    local manifest="$1"

    if [[ -f "$INPUT" ]]; then
        printf '%s\0' "$INPUT" > "$manifest" || return 3
        return 0
    fi

    if ! find "$INPUT" \
        -maxdepth 1 \
        \( -type f -o -type l \) \
        -name '*.log' \
        -print0 > "$manifest"; then
        error "Unable to discover log files"
        return 3
    fi

    return 0
}

run_analysis() {
    local manifest=""
    local output=""
    local file=""
    local status=0

    manifest="$(mktemp)" || return 3
    output="$(mktemp)" || {
        rm -f -- "$manifest"
        return 3
    }

    if ! make_input_manifest "$manifest"; then
        rm -f -- "$manifest" "$output"
        return 3
    fi

    while IFS= read -r -d '' file; do
        if [[ -L "$file" || ! -f "$file" || ! -r "$file" ]]; then
            error "Unsafe or unreadable log file: $file"
            rm -f -- "$manifest" "$output"
            return 3
        fi

        if ! cat -- "$file" >> "$output"; then
            error "Unable to read log file: $file"
            rm -f -- "$manifest" "$output"
            return 3
        fi
    done < "$manifest"

    rm -f -- "$manifest"

    if [[ ! -s "$output" ]]; then
        rm -f -- "$output"
        error "No log records found"
        return 6
    fi

    # The AWK program validates the complete dataset before
    # producing any selected records or summary.
    awk \
        -v command="$COMMAND" \
        -v selected_level="$LEVEL" \
        -v selected_service="$SERVICE" \
        -v selected_event="$EVENT" \
        -v selected_request="$REQUEST_ID" \
        -v since="$SINCE" \
        -v until="$UNTIL" '
    function valid_date(s, a, days, leap, maxday) {
        if (s !~ /^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$/)
            return 0

        split(substr(s, 1, 10), a, "-")

        if (a[2] < 1 || a[2] > 12)
            return 0

        leap = ((a[1] % 4 == 0 && a[1] % 100 != 0) ||
                (a[1] % 400 == 0))

        days[1] = 31
        days[2] = leap ? 29 : 28
        days[3] = 31
        days[4] = 30
        days[5] = 31
        days[6] = 30
        days[7] = 31
        days[8] = 31
        days[9] = 30
        days[10] = 31
        days[11] = 30
        days[12] = 31

        maxday = days[a[2] + 0]

        if (a[3] < 1 || a[3] > maxday)
            return 0

        if (substr(s, 12, 2) + 0 > 23)
            return 0

        if (substr(s, 15, 2) + 0 > 59)
            return 0

        if (substr(s, 18, 2) + 0 > 59)
            return 0

        return 1
    }

    function valid_level(level) {
        return level == "DEBUG" ||
               level == "INFO" ||
               level == "WARN" ||
               level == "ERROR" ||
               level == "CRITICAL"
    }

    function valid_record(    i) {
        if (NF != 6)
            return 0

        if (!valid_date($1) || !valid_level($2))
            return 0

        if ($3 !~ /^[a-z][a-z0-9-]*$/)
            return 0

        if ($4 !~ /^[a-z][a-z0-9_]*$/)
            return 0

        if ($5 !~ /^[A-Za-z0-9_-]+$/)
            return 0

        if ($6 == "" || $6 ~ /[[:cntrl:]]/)
            return 0

        return 1
    }

    BEGIN {
        FS = "|"
        malformed = 0
        matched = 0
        total = 0
    }

    {
        total++

        if (!valid_record()) {
            malformed++
            printf "Malformed record at combined line %d\n", NR > "/dev/stderr"
            next
        }

        count_level[$2]++
        count_service[$3]++

        if (selected_level != "" && $2 != selected_level)
            next

        if (selected_service != "" && $3 != selected_service)
            next

        if (selected_event != "" && $4 != selected_event)
            next

        if (selected_request != "" && $5 != selected_request)
            next

        if (since != "" && $1 < since)
            next

        if (until != "" && $1 > until)
            next

        matched++
        selected[matched] = $0
    }

    END {
        if (malformed > 0) {
            printf "Validation failed: %d malformed record(s)\n", malformed > "/dev/stderr"
            exit 4
        }

        if (command == "validate") {
            printf "VALID_RECORDS=%d\n", total
            printf "MALFORMED_RECORDS=0\n"
            exit 0
        }

        if (command == "summary") {
            printf "TOTAL_RECORDS=%d\n", total

            printf "LEVEL_DEBUG=%d\n", count_level["DEBUG"] + 0
            printf "LEVEL_INFO=%d\n", count_level["INFO"] + 0
            printf "LEVEL_WARN=%d\n", count_level["WARN"] + 0
            printf "LEVEL_ERROR=%d\n", count_level["ERROR"] + 0
            printf "LEVEL_CRITICAL=%d\n", count_level["CRITICAL"] + 0

            for (service in count_service)
                printf "SERVICE_%s=%d\n", service, count_service[service]

            exit 0
        }

        if (matched == 0)
            exit 6

        for (i = 1; i <= matched; i++)
            print selected[i]
    }
    ' "$output"

    status=$?

    rm -f -- "$output"

    return "$status"
}

main() {
    local status=0

    parse_arguments "$@"
    status=$?

    if (( status == 10 )); then
        return 0
    fi

    if (( status != 0 )); then
        return "$status"
    fi

    validate_input || return 3

    if [[ "$COMMAND" == "timeline" ]]; then
        local timeline_file=""

        timeline_file="$(mktemp)" || return 3

        # First validate all records before publishing the timeline.
        if ! run_analysis > "$timeline_file"; then
            status=$?
            rm -f -- "$timeline_file"
            return "$status"
        fi

        sort "$timeline_file"
        status=$?

        rm -f -- "$timeline_file"
        return "$status"
    fi

    run_analysis
}

main "$@"
```

# Part 17 — Essential Implementation Corrections

## 65. Correct the AWK Timestamp Pattern

Ubuntu 24.04 typically provides `mawk` as `/usr/bin/awk`.

Portable AWK implementations differ in support for interval quantifiers such as `{4}` and `{2}`.

To avoid relying on interval-expression support, change the AWK `valid_date` check to use an explicit fixed-width pattern.

Run:

```
python3 - <<'PY'
from pathlib import Path

path = Path("scripts/veriqta-log-investigator.sh")
text = path.read_text()

old = r'if (s !~ /^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$/)'
new = r'if (s !~ /^[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9]Z$/)'

if old not in text:
    raise SystemExit("Expected AWK timestamp pattern not found")

path.write_text(text.replace(old, new, 1))
PY
```

This correction applies only to the AWK program.

Bash's `[[ ... =~ ... ]]` regular expression support differs from the default AWK implementation.

## 66. Correct Timeline Error Propagation

The initial timeline branch contains this pattern:

```
if ! run_analysis > "$timeline_file"; then
    status=$?
```

That is incorrect for preserving the original failure status.

Inside the `then` branch, `$?` reflects the negated condition, not the original `run_analysis` failure code.

Replace the timeline branch with:

```
if run_analysis > "$timeline_file"; then
    status=0
else
    status=$?
fi

if (( status != 0 )); then
    rm -f -- "$timeline_file"
    return "$status"
fi
```

You can apply the replacement automatically:

```
python3 - <<'PY'
from pathlib import Path

path = Path("scripts/veriqta-log-investigator.sh")
text = path.read_text()

old = '''        if ! run_analysis > "$timeline_file"; then
            status=$?
            rm -f -- "$timeline_file"
            return "$status"
        fi'''

new = '''        if run_analysis > "$timeline_file"; then
            status=0
        else
            status=$?
        fi

        if (( status != 0 )); then
            rm -f -- "$timeline_file"
            return "$status"
        fi'''

if old not in text:
    raise SystemExit("Expected timeline branch not found")

path.write_text(text.replace(old, new, 1))
PY
```

This reinforces a critical lesson from JUN-064 and JUN-065: the exact placement of exit-status capture matters.

# Part 22 — Build the Regression Test Suite

## 84. Why Logging Tools Need Negative Tests

A log analysis utility must not silently accept malformed records.

Imagine a parser that accepts:

```
2026-99-99T99:99:99Z|ERROR|orders-api|database_timeout|req-1|Invalid timestamp
```

If it treats that as a valid event, time-based investigations can become misleading.

Your tests should verify both valid and invalid behavior.

The regression suite will check:

- Syntax.
- Help and usage errors.
- Valid records.
- Invalid severities.
- Invalid timestamps.
- Missing fields.
- Severity counts.
- Service filtering.
- Request-ID filtering.
- Time-window filtering.
- Empty matches.
- Timeline ordering.
- Input path restrictions.

```
cat > tests/run-tests.sh <<'BASH'

set -u
set -o pipefail

SCRIPT_DIR="$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P
)" || exit 1

LAB_ROOT="$(
    cd -- "$SCRIPT_DIR/.." && pwd -P
)" || exit 1

PASSED=0

pass() {
    PASSED=$((PASSED + 1))
    printf 'PASS: %s\n' "$1"
}

fail() {
    FAILED=$((FAILED + 1))

assert_status() {
    local description="$1"
    local expected="$2"

         2> "$TEST_ROOT/stderr" || actual=$?

    if (( actual == expected )); then

}

incomplete|ERROR|orders-api

}

}

    local valid=""

    else
```

## 95. Separate Facts from Hypotheses

### Observed facts

- A deployment was recorded before the timeouts.
- A configuration reload was recorded before the timeouts.
- Database timeout errors appeared afterward.
- A health-check failure was recorded.
- A restart request was recorded.
- Startup completion was recorded.
- Monitoring later recorded an availability alert.

### Plausible hypotheses

- The deployment introduced an invalid database setting.
- A connection pool was exhausted.
- A network interruption affected database traffic.
- The database experienced elevated latency.
- The application health check was too sensitive.
- The restart did not resolve the underlying issue.

### Not yet established

- That the deployment caused the outage.
- That the database server failed.
- That the restart restored normal availability.
- That the recorded application startup meant all dependencies were healthy.

## 96. Root Cause Analysis Template

For the fictional incident, write:

Symptom: Orders API requests experienced database timeouts and failed health checks.

Trigger under investigation: A deployment and configuration reload preceded the first recorded timeout.

Confirmed cause: Not established by the available synthetic logs.

Additional evidence required: Deployment configuration changes, database-side logs, network metrics, application connection-pool metrics, and service health measurements.

Immediate corrective actions: Validate deployment configuration, confirm database connectivity, review health-check behavior, and monitor request success rates.

Preventive controls: Structured logging, request correlation, deployment annotations, baseline monitoring, alerting, and automated configuration validation.

# Part 26 — Security and Production Hardening

## 98. Logging Security Principles

A professional logging design should address:

1. Least privilege: Only authorized users should access sensitive logs.
2. Confidentiality: Avoid recording passwords, tokens, private keys, or unnecessary personal information.
3. Integrity: Protect logs against unauthorized modification.
4. Availability: Prevent logging from exhausting storage or blocking critical services unexpectedly.
5. Retention: Keep logs for an appropriate, documented period.
6. Time accuracy: Synchronize clocks and use consistent timestamp formats.
7. Correlation: Include request IDs and other safe identifiers.
8. Access auditing: Record who can view or export sensitive logs where required.
9. Transport security: Protect logs sent to remote collectors.
10. Incident preservation: Preserve relevant evidence under an approved process.

## 99. Limitations of the Lab Investigator

The final script is designed for small, controlled fixtures.

It has several deliberate limitations:

- It reads the complete selected dataset into a temporary file.
- It is not a streaming, large-scale log processor.
- It does not provide cryptographic integrity protection.
- It does not authenticate log producers.

# Part 30 — Knowledge Assessment

## 112. Thirty Questions and Answers

1\. What is a Linux log? A record of events generated by a system component, service, or application.

2\. Why are logs important? They provide evidence for troubleshooting, incident reconstruction, operational monitoring, and auditing.

3\. What is systemd-journald? The systemd service that collects and stores journal records.

4\. What is journalctl? The command-line utility used to query the systemd journal.

5\. What is rsyslog? A logging daemon that can collect, process, store, and forward syslog-compatible messages.

6\. What is syslog? A family of logging conventions and standards for message representation and transport.

7\. What is a syslog facility? A category identifying the general source or purpose of a syslog message.

8\. What is a syslog severity? A numeric priority describing the importance of a log message.

9\. Which syslog severity number is most severe? `0`, emergency.

10\. What does `journalctl -b` do? Queries records from a selected boot, with no boot identifier normally meaning the current boot.

11\. What does `journalctl -u` do? Filters journal entries associated with a specified systemd unit.

12\. What does `journalctl -p err` do? Selects error-priority and more severe messages.

13\. What does `journalctl -f` do? Follows newly arriving journal entries.

14\. What does `logger` do? Submits a message through the system logging interface.

15\. Why might `/var/log/syslog` be absent? The host may not have rsyslog installed or configured to create it.

16\. What is a structured log? A log record organized into predictable fields.

17\. Why use UTC timestamps? To simplify correlation across hosts and timezones.

18\. What is a correlation ID? An identifier used to connect related events across operations or components.

19\. What is the difference between event time and ingestion time? Event time describes when an event occurred or was recorded by its producer; ingestion time describes when a collector received it.

20\. What is log rotation? The process of managing active and older log files to control storage and retention.

21\. What is logrotate? A utility commonly used to rotate, compress, and manage text log files.

22\. What is journal persistence? Storing journal records so they can survive a reboot, subject to configuration and retention.

23\. Why should logs not contain passwords? Logs may be copied, retained, or accessed by people and systems beyond the original application.

24\. What does a successful log write prove? Only that the logging operation succeeded according to its interface; it does not prove the underlying business operation succeeded.

25\. Why validate log records? To prevent malformed or misleading data from corrupting analysis.

26\. What does exit code `4` mean in the final project? One or more malformed log records were detected.

27\. What does exit code `6` mean? No matching records were available for the requested operation.

28\. Why is chronological correlation not enough to establish causation? Events occurring near each other in time may have different causes.

29\. What caused the fictional Orders API incident? The provided synthetic logs do not establish a confirmed root cause.

30\. What makes a logging investigation reliable? Correct scope, timestamp normalization, source identification, structured evidence, validation, independent corroboration, and careful conclusions.

# Part 31 — Interview Preparation

## 113. Twelve Interview Questions

1\. How do you investigate a failing Linux service?

I check the service state, query relevant journal entries using `journalctl -u`, examine application logs, establish a timeline, and correlate failures with deployment and infrastructure events.

2\. What is the difference between journald and rsyslog?

Journald collects and stores systemd journal records, while rsyslog processes syslog-compatible messages and can route them to files or remote destinations. They may operate together.

3\. How do you view logs from the current boot?

I use:

```
journalctl -b
```

4\. How do you filter journal logs by severity?

I use the `-p` option, for example:

```
journalctl -p err
```

5\. How do you inspect a specific service's logs?

I use:

```
journalctl -u service-name.service
```

and apply appropriate time filters.

6\. What would you do if `/var/log/syslog` did not exist?

I would inspect the logging architecture, check journald and rsyslog status, and determine where records are actually stored.

7\. Why are structured logs useful?

They make filtering, aggregation, correlation, and automated analysis more reliable.

8\. What is a correlation ID?

It is a value shared by related events, allowing an investigator to trace one operation across components.

9\. How do you investigate events across different timezones?

I normalize timestamps to UTC and account for clock synchronization and ingestion delays.

10\. How do you prevent logs from filling a filesystem?

I use an appropriate rotation, retention, compression, and storage-monitoring strategy.

11\. How do you protect sensitive logs?

I apply least-privilege access, avoid logging secrets, protect stored and transmitted data, and follow an approved retention policy.

12\. How do you determine the root cause from logs?

I use logs to establish observed events and hypotheses, then corroborate them with independent evidence before declaring a cause confirmed.

# 121. Lessons from the Trenches

1\. Logs are evidence, not conclusions. A recorded error tells you what the software reported. It does not automatically establish the underlying cause.

2\. Time normalization is essential. UTC timestamps and synchronized clocks make cross-system investigations more reliable.

3\. Structured logs reduce ambiguity. Consistent fields support filtering, aggregation, and correlation.

4\. Correlation IDs connect related events. They are often more reliable than guessing relationships based on timestamps alone.

5\. Severity levels must be interpreted consistently. Different logging systems may use different names and mappings.

6\. A missing log entry is not proof that an event did not happen. Logging may be disabled, delayed, filtered, inaccessible, or incomplete.

7\. Validate logs before analyzing them. Malformed records can produce incorrect counts and timelines.

8\. Protect log confidentiality and integrity. Logs often contain sensitive information and may be important incident evidence.

9\. Retention is an operational requirement. Without rotation and storage controls, logs can exhaust a filesystem.

10\. Good investigations separate facts, hypotheses, and confirmed causes. This discipline prevents premature conclusions and improves incident reports.
