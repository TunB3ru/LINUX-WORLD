# 1. Welcome to the Lab

Linux systems generate a continuous stream of operational information.

Services start and stop. Applications fail. Authentication attempts occur. Network interfaces change state. The kernel reports warnings. Scheduled jobs execute. Administrators perform maintenance.

On modern systemd-based Linux systems, much of this information is collected by **systemd-journald** and examined using **journalctl**.

For a Linux administrator, `journalctl` is one of the most important troubleshooting tools available.

It allows you to answer questions such as:

- Why did a service fail to start?
- What happened immediately before an application stopped responding?
- Did a service restart during an incident?
- Were there kernel errors during the current boot?
- What happened during the previous boot?
- Did an error occur before or after a deployment?
- Which process generated a particular message?
- Are warnings increasing?
- Are logs persistent across reboots?
- Can the evidence be exported for further analysis?

In JUN-069, you learned Linux logging fundamentals, including syslog concepts, log severities, traditional text logs, and the role of systemd-journald.

In this lab, you will go deeper.

You will learn to use `journalctl` as a systematic investigation tool rather than simply running commands and reading whatever appears on the screen.

You will practice interactive investigation, precise filtering, structured output, metadata inspection, boot analysis, controlled event generation, and automated evidence collection.

You will also build a reusable Bash utility that performs bounded journal queries and creates structured investigation reports.

**This is a follow-along lab.** Every major exercise includes commands to execute, expected behavior, verification steps, and an explanation of what the result means.

The lab is designed to be safe for a public GitHub repository. You will generate synthetic events rather than deliberately breaking real system services.

The journal may contain sensitive information.

- Usernames.
- Hostnames.
- IP addresses.
- Service names.
- Process identifiers.
- Authentication events.
- Filesystem paths.
- Application request details.
- Configuration information.
- Accidental secret exposure.

For this lab:

1. Use a non-root account for normal exercises.
2. Do not modify journald configuration.
3. Do not restart journald.
4. Do not restart or stop production services.
5. Do not clear or vacuum the journal.
6. Do not change journal access groups.
7. Do not publish unreviewed journal output.
8. Do not log credentials, tokens, or personal information.
9. Use unique, synthetic lab messages.
10. Keep raw host evidence out of the public repository.

Commands that inspect journal storage or configuration are read-only.

If a command requires additional privileges, record the access limitation rather than changing permissions just to complete the lab.

# Part 2 — Understand journalctl

## 11. What Is journalctl?

`journalctl` is the command-line utility used to query the systemd journal.

It can display records collected from:

- systemd services.
- Service stdout and stderr.
- Syslog-compatible applications.
- The kernel.
- Native journal logging APIs.
- Other supported journal sources.

Unlike reading a single traditional log file, `journalctl` can query a collection of structured records and filter by metadata.

---

## 12. Understand the Journal Architecture

A simplified architecture:

```text
                  Linux kernel
                       |
                       v
Applications ---> systemd-journald <--- systemd services
                       |
                       v
                Journal storage
                       |
                       v
                   journalctl
                       |
                       v
             Engineer investigation
```

The journal may store additional metadata beyond the visible message text.

That metadata is one reason `journalctl` is valuable for troubleshooting.

---

## 13. Journal Records Versus Text Log Lines

Traditional text log:

```text
Oct 17 14:15:00 server orders-api: database timeout
```

Journal record, conceptually:

```text
MESSAGE=database timeout
PRIORITY=3
SYSLOG_IDENTIFIER=orders-api
_PID=1234
_UID=1001
_HOSTNAME=server
```

The journal can expose fields that are not necessarily visible in its default display.

Not every entry contains every field.

Some metadata fields are populated by journald, while others are supplied by the message producer.

# Part 3 — Your First journalctl Queries

## 14. Display the Journal

Run:

```bash
journalctl
```

This may open an interactive pager.

Useful pager controls:

| Key | Action |
|---|---|
| `Space` | Next page |
| `b` | Previous page |
| `/pattern` | Search |
| `n` | Next search match |
| `N` | Previous search match |
| `g` | Beginning |
| `G` | End |
| `q` | Quit |

If you see a notice about insufficient permissions, your user may have access to only a subset of journal records.

Do not assume that a limited view represents the complete system journal.

---

## 15. Disable the Pager

Run:

```bash
journalctl --no-pager
```

This writes output directly to the terminal.

On a busy host, the output may be very large.

For operational work, prefer bounded queries.

---

## 16. Show the Most Recent Records

Run:

```bash
journalctl -n 20 --no-pager
```

Explanation:

- `-n 20` requests the last 20 matching entries.
- `--no-pager` prevents interactive paging.

This is often a useful first command during troubleshooting.

---

## 17. Show the Last Five Entries

Run:

```bash
journalctl -n 5 --no-pager
```

Count the displayed entries visually.

Remember that some journal output formats may include extra informational text or access notices.

---

## 18. Show Entries in Reverse Order

Run:

```bash
journalctl -r -n 20 --no-pager
```

The `-r` option displays entries in reverse chronological order.

This is useful when the most recent failure is your starting point.

Compare with:

```bash
journalctl -n 20 --no-pager
```

---

## 19. Follow Logs in Real Time

Run:

```bash
journalctl -f
```

This displays new entries as they arrive.

Stop with:

```text
Ctrl+C
```

### Bounded alternative

Run:

```bash
timeout 15s journalctl -f --no-pager
```

This limits the observation window.

A status of `124` from `timeout` generally means the time limit was reached. It does not necessarily indicate a journal failure.

# Part 4 — Filter by Time

## 20. Understand Time-Based Queries

During an incident, time filtering is essential.

You rarely need the entire journal.

Instead, you need records around the suspected failure.

`journalctl` supports:

```text
--since
--until
```

---

## 21. Query the Last Hour

Run:

```bash
journalctl \
    --since '1 hour ago' \
    --no-pager
```

This uses a relative time expression.

---

## 22. Query the Last Ten Minutes

Run:

```bash
journalctl \
    --since '10 minutes ago' \
    -n 50 \
    --no-pager
```

This combines time filtering with an output limit.

---

## 23. Query a Bounded Relative Window

Run:

```bash
journalctl \
    --since '30 minutes ago' \
    --until '10 minutes ago' \
    --no-pager
```

This selects records in a window ending ten minutes ago.

---

## 24. Query an Absolute Time Window

For a known incident date, use an explicit range.

Example:

```bash
journalctl \
    --since '2026-10-17 14:00:00' \
    --until '2026-10-17 15:00:00' \
    --no-pager
```

These timestamps are interpreted according to journalctl's date-parsing behavior and the relevant local timezone unless explicitly specified otherwise.

If the date is in the future or outside retained history, the query may return no entries.

For your own live investigation, substitute a window containing your generated test events.

---

## 25. Display UTC Timestamps

Run:

```bash
journalctl \
    --utc \
    --since '1 hour ago' \
    -n 20 \
    --no-pager
```

The `--utc` option changes how timestamps are displayed.

For formal incident timelines, document both the time filter's interpretation and the displayed timezone.

---

## 26. Use Precise Output Timestamps

Run:

```bash
journalctl \
    -o short-iso-precise \
    -n 20 \
    --no-pager
```

This output format includes more precise timestamp information than the default short display.

Try:

```bash
journalctl \
    --utc \
    -o short-iso-precise \
    -n 20 \
    --no-pager
```

This is useful when correlating closely spaced events.

# Part 5 — Filter by Service

## 27. Why Service Filtering Matters

A Linux host may run dozens or hundreds of services.

Reading every journal entry can bury the relevant evidence.

Use:

```text
-u
```

to filter by systemd unit.

---

## 28. Inspect journald's Own Unit

Run:

```bash
journalctl \
    -u systemd-journald.service \
    -n 30 \
    --no-pager
```

This is a useful service to inspect because it normally exists on systemd-based hosts.

---

## 29. Inspect SSH Service Logs

First check:

```bash
systemctl list-unit-files 'ssh.service' --no-pager
```

If available:

```bash
journalctl \
    -u ssh.service \
    -n 30 \
    --no-pager
```

If the SSH service is not installed, document that fact.

Do not install or start SSH just to generate log messages.

---

## 30. Combine Unit and Time Filters

Run:

```bash
journalctl \
    -u systemd-journald.service \
    --since '1 hour ago' \
    --no-pager
```

This narrows the investigation by both source and time.

---

## 31. Query Multiple Units

If the units exist, you can request more than one:

```bash
journalctl \
    -u systemd-journald.service \
    -u systemd-logind.service \
    -n 30 \
    --no-pager
```

This is useful when troubleshooting interactions between services.

# Part 6 — Filter by Priority

## 32. Review Syslog Priorities

The standard syslog severity scale:

| Number | Name | Meaning |
|---:|---|---|
| 0 | emerg | Emergency |
| 1 | alert | Immediate action required |
| 2 | crit | Critical |
| 3 | err | Error |
| 4 | warning | Warning |
| 5 | notice | Notice |
| 6 | info | Informational |
| 7 | debug | Debug |

Lower numbers indicate greater severity.

---

## 33. Show Errors and More Severe Messages

Run:

```bash
journalctl \
    -p err \
    -n 30 \
    --no-pager
```

This selects priorities `0` through `3`.

It does not mean that every selected message has exactly priority `3`.

---

## 34. Show Warnings and More Severe Messages

Run:

```bash
journalctl \
    -p warning \
    -n 30 \
    --no-pager
```

This includes warnings, errors, critical messages, alerts, and emergencies.

---

## 35. Select an Exact Priority

Run:

```bash
journalctl \
    -p warning..warning \
    -n 30 \
    --no-pager
```

This selects only warning-priority messages.

Compare:

```bash
journalctl -p warning -n 30 --no-pager
```

The two queries have different meanings.

---

## 36. Combine Priority and Unit Filters

Run:

```bash
journalctl \
    -u systemd-journald.service \
    -p warning \
    --since '24 hours ago' \
    --no-pager
```

This asks:

> Were warning-or-higher events recorded for this unit during the selected period?

If nothing appears, do not automatically conclude the service is healthy.

The absence of matching records is only one piece of evidence.

---

# Part 7 — Investigate System Boots

## 37. Why Boot Filtering Matters

A Linux system may have been restarted before an incident investigation begins.

The journal may contain records from multiple boots if persistent history is available.

Without boot filtering, you may accidentally combine events from different system lifetimes.

---

## 38. List Available Boots

Run:

```bash
journalctl --list-boots --no-pager
```

Typical output includes:

```text
-1 <boot-id> ...
 0 <boot-id> ...
```

The actual list depends on retained journal history.

If only the current boot is available, previous boot analysis may not be possible.

---

## 39. Inspect the Current Boot

Run:

```bash
journalctl -b -n 30 --no-pager
```

This selects the current boot.

---

## 40. Inspect the Previous Boot

Run:

```bash
journalctl -b -1 -n 30 --no-pager
```

This requests the previous boot.

Possible outcomes:

- Previous boot records appear.
- No previous boot is available.
- Journal access is restricted.

Do not change storage settings to force historical records to exist.

---

## 41. Inspect Early Boot Messages

Run:

```bash
journalctl -b -n 30 --no-pager
```

Then compare with:

```bash
journalctl -b --no-pager | head -n 30
```

For a large journal, the second command may cause the producer to receive a broken pipe after `head` exits. That is normal pipeline behavior and does not mean the journal itself is damaged.

For more controlled queries, prefer journalctl's native output options where possible.

---

## 42. Inspect Boot Errors

Run:

```bash
journalctl \
    -b \
    -p err \
    -n 30 \
    --no-pager
```

This helps identify recorded error-priority messages from the current boot.

Do not interpret every boot error as an ongoing fault.

Some messages may describe recovered or non-impacting conditions.

---

# Part 8 — Inspect Kernel Messages

## 43. Query Kernel Journal Records

Run:

```bash
journalctl -k -n 30 --no-pager
```

The `-k` option selects kernel messages and normally implies the current boot.

---

## 44. Query Kernel Warnings

Run:

```bash
journalctl \
    -k \
    -p warning \
    -n 30 \
    --no-pager
```

Kernel warnings may concern:

- Drivers.
- Storage.
- Filesystems.
- Networking.
- Memory.
- Hardware.
- Device initialization.

Not every kernel warning indicates a production incident.

---

## 45. Compare journalctl and dmesg

Run:

```bash
dmesg | tail -n 20
```

If access is denied, that may reflect kernel security restrictions.

Compare with:

```bash
journalctl -k -n 20 --no-pager
```

These interfaces are related but not identical.

`dmesg` normally reads the kernel ring buffer, while `journalctl -k` queries kernel messages collected into the journal.

Retention, permissions, and available history may differ.

# Part 10 — Investigate Journal Metadata

## 55. Understand the Syslog Identifier

The command:

```bash
logger -t veriqta-jun070 ...
```

sets a tag commonly represented as:

```text
SYSLOG_IDENTIFIER=veriqta-jun070
```

You can filter by that identifier using:

```bash
journalctl -t veriqta-jun070
```

---

## 56. Use Verbose Output

Run:

```bash
journalctl \
    -t veriqta-jun070 \
    --since '10 minutes ago' \
    -o verbose \
    -n 5 \
    --no-pager
```

Look for fields such as:

```text
MESSAGE=
PRIORITY=
SYSLOG_IDENTIFIER=
_PID=
_UID=
_HOSTNAME=
```

Not every entry includes every field.

---

## 57. Filter by an Exact Journal Field

Run:

```bash
journalctl \
    SYSLOG_IDENTIFIER=veriqta-jun070 \
    --since '10 minutes ago' \
    --no-pager
```

This demonstrates journal field matching.

Field queries are useful when you need more precise matching than searching visible text.

---

## 58. Understand Trusted Fields

Fields beginning with an underscore, such as:

```text
_PID
_UID
_SYSTEMD_UNIT
```

are commonly populated by journald based on available process or system context.

They are distinct from arbitrary fields supplied by an application.

However, trusted metadata is not a guarantee that every aspect of a log message is authentic or complete.

---

## 59. Query by Process ID

If you have identified a process ID in a journal entry, you can query it.

Example syntax:

```bash
journalctl _PID=1234 --no-pager
```

Replace `1234` with an actual observed PID.

Be careful: PIDs can be reused over time.

Combine PID filtering with boot and time constraints when investigating a specific process lifetime.

---

## 60. Query by User ID

Example:

```bash
journalctl _UID="$(id -u)" -n 20 --no-pager
```

This requests records associated with your numeric user ID.

The result depends on journal access and available metadata.

It is not equivalent to querying every action ever performed by that user.

## 79. Create the Investigator Script

Run:

```bash
cat > scripts/veriqta-journal-investigator.sh <<'BASH'
#!/usr/bin/env bash

set -u
set -o pipefail

export LC_ALL=C
export PATH="/usr/sbin:/usr/bin:/sbin:/bin"

umask 077

SCRIPT_DIR="$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P
)" || exit 3

LAB_ROOT="$(
    cd -- "$SCRIPT_DIR/.." && pwd -P
)" || exit 3

REPORT_ROOT="$LAB_ROOT/reports"

COMMAND=""
TAG=""
UNIT=""
SINCE="1 hour ago"
UNTIL=""
PRIORITY=""
LIMIT=100
OUTPUT=""

usage() {
    cat <<'EOF'
VERIQTA Journal Investigator

Usage:
  veriqta-journal-investigator.sh check
  veriqta-journal-investigator.sh query [OPTIONS]
  veriqta-journal-investigator.sh summary [OPTIONS]
  veriqta-journal-investigator.sh capture [OPTIONS] --output NAME

Options:
  --tag NAME          Exact syslog identifier
  --unit NAME         Exact systemd unit
  --since TIME        Start time (default: 1 hour ago)
  --until TIME        End time
  --priority LEVEL    emerg, alert, crit, err, warning,
                      notice, info, debug
  --limit NUMBER      Maximum records, 1-10000
  --output NAME       Capture basename, letters/digits/_/-
  --help              Show help

Exit codes:
  0  Success
  2  Invalid arguments
  3  Operational failure
  6  No matching entries
  7  Required command unavailable
EOF
}

error() {
    printf 'ERROR: %s\n' "$*" >&2
}

require_commands() {
    local command_name=""

    for command_name in journalctl date mktemp wc grep; do
        if ! command -v "$command_name" >/dev/null 2>&1; then
            error "Required command unavailable: $command_name"
            return 7
        fi
    done

    return 0
}

valid_priority() {
    case "$1" in
        emerg|alert|crit|err|warning|notice|info|debug)
            return 0
            ;;
        *)
            return 1
            ;;
    esac
}

parse_arguments() {
    if (( $# == 1 )) && [[ "$1" == "--help" ]]; then
        usage
        return 10
    fi

    if (( $# == 0 )); then
        usage >&2
        return 2
    fi

    COMMAND="$1"
    shift

    case "$COMMAND" in
        check|query|summary|capture)
            ;;
        *)
            error "Unknown command: $COMMAND"
            return 2
            ;;
    esac

    if [[ "$COMMAND" == "check" ]]; then
        if (( $# != 0 )); then
            error "check does not accept options"
            return 2
        fi

        return 0
    fi

    while (( $# > 0 )); do
        case "$1" in
            --tag|--unit|--since|--until|--priority|--limit|--output)
                if (( $# < 2 )); then
                    error "Missing value for $1"
                    return 2
                fi

                case "$1" in
                    --tag) TAG="$2" ;;
                    --unit) UNIT="$2" ;;
                    --since) SINCE="$2" ;;
                    --until) UNTIL="$2" ;;
                    --priority) PRIORITY="$2" ;;
                    --limit) LIMIT="$2" ;;
                    --output) OUTPUT="$2" ;;
                esac

                shift 2
                ;;

            *)
                error "Unknown option: $1"
                return 2
                ;;
        esac
    done

    if [[ -n "$TAG" &&
          ! "$TAG" =~ ^[A-Za-z][A-Za-z0-9_-]*$ ]]; then
        error "Invalid tag"
        return 2
    fi

    if [[ -n "$UNIT" &&
          ! "$UNIT" =~ ^[A-Za-z0-9_.@-]+$ ]]; then
        error "Invalid unit name"
        return 2
    fi

    if [[ -n "$PRIORITY" ]] && ! valid_priority "$PRIORITY"; then
        error "Invalid priority"
        return 2
    fi

    if [[ ! "$LIMIT" =~ ^[0-9]+$ ]]; then
        error "Limit must be numeric"
        return 2
    fi

    if (( ${#LIMIT} > 5 )); then
        error "Limit is out of range"
        return 2
    fi

    LIMIT=$((10#$LIMIT))

    if (( LIMIT < 1 || LIMIT > 10000 )); then
        error "Limit must be between 1 and 10000"
        return 2
    fi

    if [[ -z "$SINCE" ]]; then
        error "--since cannot be empty"
        return 2
    fi

    if [[ "$COMMAND" == "capture" ]]; then
        if [[ ! "$OUTPUT" =~ ^[A-Za-z][A-Za-z0-9_-]*$ ]]; then
            error "capture requires a safe --output name"
            return 2
        fi
    elif [[ -n "$OUTPUT" ]]; then
        error "--output is only valid with capture"
        return 2
    fi

    return 0
}

build_query_arguments() {
    QUERY_ARGS=(
        --no-pager
        --utc
        --since "$SINCE"
        -n "$LIMIT"
    )

    if [[ -n "$UNTIL" ]]; then
        QUERY_ARGS+=(--until "$UNTIL")
    fi

    if [[ -n "$PRIORITY" ]]; then
        QUERY_ARGS+=(-p "$PRIORITY")
    fi

    if [[ -n "$UNIT" ]]; then
        QUERY_ARGS+=(-u "$UNIT")
    fi

    if [[ -n "$TAG" ]]; then
        QUERY_ARGS+=(SYSLOG_IDENTIFIER="$TAG")
    fi
}

check_journal() {
    local probe=""

    probe="$(mktemp)" || return 3

    if ! journalctl -n 1 --no-pager > "$probe" 2>/dev/null; then
        rm -f -- "$probe"
        error "Unable to query the journal"
        return 3
    fi

    rm -f -- "$probe"

    printf 'JOURNALCTL_AVAILABLE=yes\n'
    printf 'JOURNAL_QUERY_SUCCEEDED=yes\n'

    return 0
}

collect_json() {
    local destination="$1"

    build_query_arguments

    if ! journalctl \
        "${QUERY_ARGS[@]}" \
        -o json \
        > "$destination"; then
        error "journalctl query failed"
        return 3
    fi

    if [[ ! -s "$destination" ]]; then
        return 6
    fi

    return 0
}

run_query() {
    local temp_file=""
    local status=0

    temp_file="$(mktemp)" || return 3

    collect_json "$temp_file"
    status=$?

    if (( status != 0 )); then
        rm -f -- "$temp_file"
        return "$status"
    fi

    cat -- "$temp_file"
    status=$?

    rm -f -- "$temp_file"

    if (( status != 0 )); then
        return 3
    fi

    return 0
}

run_summary() {
    local temp_file=""
    local status=0

    temp_file="$(mktemp)" || return 3

    collect_json "$temp_file"
    status=$?

    if (( status != 0 )); then
        rm -f -- "$temp_file"
        return "$status"
    fi

    python3 - "$temp_file" <<'PY'
import json
import sys
from collections import Counter

path = sys.argv[1]
counts = Counter()
total = 0

try:
    with open(path, encoding="utf-8") as stream:
        for line in stream:
            entry = json.loads(line)
            priority = str(entry.get("PRIORITY", "unknown"))
            counts[priority] += 1
            total += 1
except (OSError, UnicodeError, json.JSONDecodeError) as exc:
    print(f"ERROR: Unable to parse journal JSON: {exc}", file=sys.stderr)
    sys.exit(3)

print(f"TOTAL_RECORDS={total}")

for priority in range(8):
    print(f"PRIORITY_{priority}={counts[str(priority)]}")

print(f"PRIORITY_UNKNOWN={counts['unknown']}")
PY

    status=$?

    rm -f -- "$temp_file"

    return "$status"
}

run_capture() {
    local temp_file=""
    local target=""
    local metadata=""
    local status=0
    local count=0

    if [[ ! -d "$REPORT_ROOT" || -L "$REPORT_ROOT" ]]; then
        error "Report directory is unavailable or unsafe"
        return 3
    fi

    target="$REPORT_ROOT/$OUTPUT.jsonl"
    metadata="$REPORT_ROOT/$OUTPUT.metadata.txt"

    if [[ -e "$target" || -L "$target" ||
          -e "$metadata" || -L "$metadata" ]]; then
        error "Capture output already exists"
        return 3
    fi

    temp_file="$(mktemp "$REPORT_ROOT/.capture.XXXXXXXX")" ||
        return 3

    collect_json "$temp_file"
    status=$?

    if (( status != 0 )); then
        rm -f -- "$temp_file"
        return "$status"
    fi

    count="$(wc -l < "$temp_file")" || {
        rm -f -- "$temp_file"
        return 3
    }

    if ! mv -n -- "$temp_file" "$target"; then
        rm -f -- "$temp_file"
        error "Unable to publish capture"
        return 3
    fi

    if [[ -e "$temp_file" ]]; then
        rm -f -- "$temp_file"
        error "Capture destination collision"
        return 3
    fi

    if ! {
        printf 'LAB=JUN-070\n'
        printf 'CAPTURE_NAME=%s\n' "$OUTPUT"
        printf 'CAPTURED_AT_UTC=%s\n' \
            "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"
        printf 'TAG=%s\n' "$TAG"
        printf 'UNIT=%s\n' "$UNIT"
        printf 'SINCE=%s\n' "$SINCE"
        printf 'UNTIL=%s\n' "$UNTIL"
        printf 'PRIORITY=%s\n' "$PRIORITY"
        printf 'LIMIT=%s\n' "$LIMIT"
        printf 'RECORD_COUNT=%s\n' "$count"
    } > "$metadata"; then
        error "Unable to write capture metadata"
        return 3
    fi

    printf 'CAPTURE=%s\n' "$target"
    printf 'METADATA=%s\n' "$metadata"
    printf 'RECORD_COUNT=%s\n' "$count"

    return 0
}

main() {
    local status=0

    parse_arguments "$@"
    status=$?

    if (( status == 10 )); then
        return 0
    fi

    if (( status != 0 )); then
        return "$status"
    fi

    require_commands || return 7

    case "$COMMAND" in
        check)
            check_journal
            ;;
        query)
            run_query
            ;;
        summary)
            if ! command -v python3 >/dev/null 2>&1; then
                error "python3 is required for summary"
                return 7
            fi
            run_summary
            ;;
        capture)
            run_capture
            ;;
    esac
}

main "$@"
BASH
```

## 82. Important Limitations Before Testing

The first implementation is suitable for learning but has several production limitations.

### 82.1 Query time validation

The script passes `--since` and `--until` values to journalctl rather than implementing its own full date parser.

Invalid values should cause journalctl to fail, which the script reports as an operational failure.

A production CLI could classify invalid date syntax as usage error `2`.

### 82.2 No explicit query timeout

The script limits the number of returned records but does not impose a wall-clock execution timeout.

A production version should include a bounded execution policy.

### 82.3 Temporary-file cleanup

The script removes temporary files during normal control flow.

Unexpected termination may leave temporary files.

A production implementation should use carefully scoped cleanup traps.

### 82.4 Output publication

The capture mode uses a non-overwrite move and checks whether the temporary file remains.

This is not a complete transaction across the capture and metadata files.

A production implementation should use an atomic, collision-safe publication strategy and verify both artifacts.

### 82.5 Output confidentiality

JSON captures may contain sensitive host metadata.

They must remain private unless reviewed and sanitized.

## 97. Create the Regression Runner

Run:

```bash
cat > tests/run-tests.sh <<'BASH'
#!/usr/bin/env bash

set -u
set -o pipefail

SCRIPT_DIR="$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P
)" || exit 1

LAB_ROOT="$(
    cd -- "$SCRIPT_DIR/.." && pwd -P
)" || exit 1

TOOL="$LAB_ROOT/scripts/veriqta-journal-investigator.sh"

PASSED=0
FAILED=0
TEST_ROOT=""

pass() {
    PASSED=$((PASSED + 1))
    printf 'PASS: %s\n' "$1"
}

fail() {
    FAILED=$((FAILED + 1))
    printf 'FAIL: %s\n' "$1"
}

assert_status() {
    local description="$1"
    local expected="$2"
    shift 2

    local actual=0

    "$@" > "$TEST_ROOT/stdout" \
         2> "$TEST_ROOT/stderr" || actual=$?

    if (( actual == expected )); then
        pass "$description"
    else
        fail "$description (expected=$expected actual=$actual)"
        cat "$TEST_ROOT/stdout"
        cat "$TEST_ROOT/stderr" >&2
    fi
}

setup() {
    TEST_ROOT="$(mktemp -d)" || return 1
}

cleanup() {
    if [[ -n "$TEST_ROOT" &&
          -d "$TEST_ROOT" &&
          ! -L "$TEST_ROOT" ]]; then
        rm -rf -- "$TEST_ROOT"
    fi
}

main() {
    local unique_tag=""
    local status=0

    setup || return 1

    if bash -n "$TOOL"; then
        pass "Main script syntax"
    else
        fail "Main script syntax"
    fi

    assert_status "Help succeeds" 0 \
        bash "$TOOL" --help

    assert_status "Unknown command rejected" 2 \
        bash "$TOOL" unknown

    assert_status "Missing command rejected" 2 \
        bash "$TOOL"

    assert_status "Invalid priority rejected" 2 \
        bash "$TOOL" query --priority invalid

    assert_status "Invalid limit rejected" 2 \
        bash "$TOOL" query --limit abc

    assert_status "Zero limit rejected" 2 \
        bash "$TOOL" query --limit 0

    assert_status "Excessive limit rejected" 2 \
        bash "$TOOL" query --limit 10001

    assert_status "Unsafe output name rejected" 2 \
        bash "$TOOL" capture --output ../../outside

    assert_status "Missing capture output rejected" 2 \
        bash "$TOOL" capture

    assert_status "Output rejected for query" 2 \
        bash "$TOOL" query --output invalid

    assert_status "Invalid tag rejected" 2 \
        bash "$TOOL" query --tag 'bad tag'

    assert_status "Invalid unit rejected" 2 \
        bash "$TOOL" query --unit 'bad unit'

    assert_status "Unknown option rejected" 2 \
        bash "$TOOL" query --not-an-option

    assert_status "Missing option value rejected" 2 \
        bash "$TOOL" query --limit

    if ! command -v journalctl >/dev/null 2>&1; then
        printf 'SKIP: Journal integration tests (journalctl unavailable)\n'
    elif ! bash "$TOOL" check >/dev/null 2>&1; then
        printf 'SKIP: Journal integration tests (journal inaccessible)\n'
    elif ! command -v logger >/dev/null 2>&1; then
        printf 'SKIP: Journal integration tests (logger unavailable)\n'
    else
        unique_tag="veriqta-jun070-test-$$"

        logger \
            -t "$unique_tag" \
            -p user.notice \
            "event=regression_test run_id=$$"

        sleep 1

        bash "$TOOL" query \
            --tag "$unique_tag" \
            --since '5 minutes ago' \
            --limit 10 \
            > "$TEST_ROOT/integration.stdout" \
            2> "$TEST_ROOT/integration.stderr"

        status=$?

        if (( status == 0 )) &&
           grep -Fq "regression_test" \
               "$TEST_ROOT/integration.stdout"; then
            pass "Controlled journal integration"
        else
            printf 'SKIP: Controlled event not visible in journal\n'
        fi
    fi

    printf '\n'
    printf '%s\n' '========================================'
```

# Part 19 — Incident Investigation Workflow

## 100. A Disciplined journalctl Investigation

When responding to a real service incident, use a repeatable sequence.

### Step 1 — Confirm the host and time

```bash
hostname
date -u
timedatectl
```

Record the environment and timezone.

### Step 2 — Confirm the service

```bash
systemctl status example.service --no-pager
```

Replace `example.service` with the real service.

### Step 3 — Inspect recent service logs

```bash
journalctl \
    -u example.service \
    -n 50 \
    --no-pager
```

### Step 4 — Narrow the incident window

```bash
journalctl \
    -u example.service \
    --since '1 hour ago' \
    --no-pager
```

### Step 5 — Inspect warnings and errors

```bash
journalctl \
    -u example.service \
    -p warning \
    --since '1 hour ago' \
    --no-pager
```

### Step 6 — Check boot context

```bash
journalctl --list-boots --no-pager
```

### Step 7 — Check kernel events

```bash
journalctl \
    -k \
    -p warning \
    --since '1 hour ago' \
    --no-pager
```

### Step 8 — Correlate with deployment and infrastructure evidence

Compare:

- Deployment timestamps.
- Application request IDs.
- Database events.
- Network events.
- Service restart records.
- Monitoring alerts.

### Step 9 — Preserve bounded evidence

Export only the records needed for the investigation, under approved access controls.

### Step 10 — Document conclusions carefully

Separate:

- Observed facts.
- Possible explanations.
- Confirmed causes.
- Remaining unknowns.

# Part 21 — Troubleshooting Guide

## 103. Common journalctl Problems

| Symptom | Possible cause | Recommended investigation |
|---|---|---|
| No journal entries | No matching records or access restrictions | Check time, filters, and permissions |
| Previous boot unavailable | No retained history | Inspect storage and retention |
| Service logs missing | Wrong unit name | Inspect available units |
| Wrong timestamps | Timezone mismatch | Use `--utc` |
| Too much output | Broad query | Add time, unit, and priority filters |
| No logger event | Routing or visibility issue | Check tag, time, and journal access |
| JSON parsing fails | Unexpected or malformed output | Preserve stderr and inspect source |
| Disk usage high | Journal retention policy | Inspect `--disk-usage` and configuration |
| Access denied | Journal permission policy | Request approved access |
| Kernel records unavailable | Permission or collection limits | Compare supported interfaces |
| Capture already exists | Non-overwrite protection | Use a unique capture name |
| No matching records | Valid empty query | Review filter scope |
| Error count unexpected | Priority threshold semantics | Distinguish exact and range filters |
| Incident timeline unclear | Multiple clocks or missing context | Normalize timestamps and corroborate |
| Sensitive data in capture | Raw journal metadata | Redact before publication |

# Part 22 — Security and Operational Hardening

## 104. Least-Privilege Journal Access

Journal access may be restricted by filesystem permissions and group membership.

Some systems allow broader access to users in groups such as `systemd-journal` or administrative groups.

Do not add yourself to privileged groups solely for the lab.

Access should be granted according to the organization's operational policy.

---

## 105. Protect Captured Evidence

Journal captures should be treated as operational evidence.

Recommended practices:

- Restrict file permissions.
- Use dedicated storage.
- Avoid public sharing.
- Record capture timestamps.
- Record query parameters.
- Preserve original data when required.
- Create sanitized copies for reports.
- Document retention.
- Protect evidence from unauthorized modification.

---

## 106. Understand Missing Evidence

A journal query can return no entries because:

- The event never occurred.
- The event occurred but was not logged.
- The event was logged elsewhere.
- The record was removed by retention.
- The selected boot is incorrect.
- The selected time window is incorrect.
- The query filters are too restrictive.
- The current user lacks access.
- The logging pipeline was interrupted.

A reliable investigator does not confuse absence of visible records with proof of absence.

# Part 25 — Thirty Knowledge Questions and Answers

## 119. Knowledge Assessment

**1. What is journalctl?**  
A command-line tool used to query the systemd journal.

**2. What is systemd-journald?**  
The service that collects and stores journal records.

**3. What does `journalctl -n 20` do?**  
Displays the last 20 matching journal entries.

**4. What does `journalctl -f` do?**  
Follows new journal entries as they arrive.

**5. What does `--no-pager` do?**  
Disables interactive paging.

**6. What does `journalctl -u` do?**  
Filters records associated with a systemd unit.

**7. What does `journalctl -p err` select?**  
Error-priority and more severe messages.

**8. What is the most severe syslog priority?**  
Priority `0`, emergency.

**9. What does `--since` do?**  
Sets the beginning of a journal query's time window.

**10. What does `--until` do?**  
Sets the end of a journal query's time window.

**11. Why use UTC during incidents?**  
It simplifies correlation across hosts and timezones.

**12. What does `journalctl -b` do?**  
Selects records from a boot, normally the current boot.

**13. What does `journalctl -b -1` do?**  
Requests records from the previous boot.

**14. What does `--list-boots` show?**  
Boots represented in accessible retained journal history.

**15. What does `journalctl -k` do?**  
Queries kernel journal messages.

**16. What does `logger` do?**  
Submits messages to the system logging interface.

**17. What does `-t` mean in a journalctl query?**  
It filters by syslog identifier.

**18. What is `SYSLOG_IDENTIFIER`?**  
A journal field identifying the logging program or tag.

**19. What does `-o verbose` do?**  
Displays detailed journal fields.

**20. What does `-o json` do?**  
Outputs journal entries as JSON.

**21. What does `-o cat` do?**  
Displays message content without the usual journal prefix.

**22. What is journal persistence?**  
Retention of journal records across reboots when persistent storage is configured and records are retained.

**23. What does `journalctl --disk-usage` do?**  
Reports journal storage usage.

**24. What does `journalctl --verify` do?**  
Checks journal-file structure and supported integrity properties.

**25. What is a journal vacuum operation?**  
A retention operation that removes archived journal files according to specified constraints.

**26. Why should journal captures be protected?**  
They may contain sensitive operational information.

**27. What is a bounded query?**  
A query constrained by time, source, priority, or record count.

**28. Why are request IDs useful?**  
They help correlate related events across components.

**29. Does a journal error prove root cause?**  
No. It is evidence requiring interpretation and corroboration.

**30. What makes a journal investigation reliable?**  
Correct filters, accurate time context, metadata inspection, preserved evidence, independent corroboration, and careful conclusions.

# Part 26 — Twelve Interview Questions

## 120. Interview Preparation

**1. How do you troubleshoot a failing Linux service using journalctl?**

I inspect the service state, query recent unit records, narrow the time window, examine warning and error priorities, and correlate findings with related system events.

**2. How do you view logs for a specific service?**

```bash
journalctl -u example.service
```

**3. How do you view only recent errors?**

```bash
journalctl -p err --since '1 hour ago'
```

**4. How do you investigate a previous boot?**

```bash
journalctl -b -1
```

provided previous boot records are retained and accessible.

**5. What is the difference between journalctl and reading `/var/log/syslog`?**

`journalctl` queries structured journal records and metadata, while `/var/log/syslog`, where configured, is a traditional text log file.

**6. What does `journalctl -f` do?**

It follows newly arriving journal records.

**7. How do you inspect kernel errors?**

```bash
journalctl -k -p err
```

**8. Why might journalctl show no records?**

Possible causes include permissions, retention, incorrect filters, unavailable history, or no matching events.

**9. How do you export journal data for analysis?**

I use a suitable structured output format such as JSON or journal export, preserve query metadata, and protect sensitive records.

**10. How do you determine whether a service restarted?**

I correlate service unit records, lifecycle messages, timestamps, process metadata, and service state rather than relying on a single message.

**11. How do you protect journal evidence?**

I restrict access, preserve relevant metadata, avoid overwriting captures, use appropriate integrity checks, and sanitize material before public sharing.

**12. How do you establish root cause from journal logs?**

I reconstruct the recorded sequence, distinguish observations from hypotheses, and corroborate with application, infrastructure, deployment, and monitoring evidence.

# 127. Lessons from the Trenches

**1. Start with the correct time window.**  
A precise incident window reduces noise and makes correlation easier.

**2. Filter by service before reading everything.**  
Unit-level queries are often the fastest route to useful evidence.

**3. Understand priority semantics.**  
`-p err` selects errors and more severe messages, not just exact errors.

**4. Boot context matters.**  
A message from a previous boot may describe a different system state.

**5. Metadata is valuable.**  
Process, user, unit, and identifier fields provide context beyond message text.

**6. Use UTC for cross-system investigations.**  
Consistent timestamps reduce ambiguity.

**7. Generate controlled events when learning.**  
You do not need to break real services to practice journal investigation.

**8. Protect raw evidence.**  
Journal exports may contain sensitive operational information.

**9. A missing record is not proof that an event never happened.**  
Permissions, retention, collection failures, and query scope can hide evidence.

**10. Preserve meaningful exit codes.**  
Automation needs to distinguish success, invalid arguments, operational failures, and empty results.

**11. Validate generated reports.**  
A successful command does not automatically guarantee that every output artifact is complete.

**12. Separate observation from causation.**  
A restart following a deployment does not prove that the deployment caused the restart.
